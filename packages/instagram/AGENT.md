# Instagram direct-login protocol

- Own the direct Instagram Login single-image protocol, its native profile and the confidential login/account protocol. Application configuration, encrypted credentials, callback routes, connection persistence, inspected media, durable effects, the worker and Studio belong to their existing application boundaries.
- Pin the direct-login host `graph.instagram.com` and version `v26.0`. Never follow a provider redirect or a provider-supplied URL; requests use `redirect: 'error'`, `credentials: 'omit'`, a bearer token in the authorization header and a bounded timeout with an optional caller abort.
- Container creation is not a publication. Keep the container identity for the caller, read its status separately and publish only with the provider's own published media identity. A `PUBLISHED` container status is a status, not a media receipt, and a container identity is never a published identity.
- Expose the three operations separately. There is no internal polling, retry or republish: a lost write acknowledgement is ambiguous and requires reconciliation, not a second write. Only a structured 4xx rejection proves that no write occurred; a malformed body, a non-JSON body, a 5xx response, a network failure or a timeout stays ambiguous for a write and retryable for a read.
- Never return raw provider errors, caught exceptions, tokens or signed image URLs. Diagnostics stay sanitized and provider codes are mapped to local codes.
- Image inputs are public HTTPS URLs minted at execution from inspected Postdot-owned media, never arbitrary user content from a profile. Reject insecure, credentialed, fragmented, malformed and private or literal private-network URLs. Send a signed query string verbatim and never dereference the image from this package.
- The first format is exactly one JPEG with an optional caption and optional accessibility text. No text-only post, video, reel, carousel, story, poll, comment, moderation or analytics belongs to this package.
- The `8,000,000`-byte ceiling is a conservative application envelope below the documented 8 MB provider maximum, not a restatement of it. The 320-1440 pixel width band is provider rescaling and is not grounds to invent a rejection. Caption and accessibility text ceilings use the documented 2200 and 1000 character maxima; the caption hashtag and mention rules stay provider-enforced because they cannot be counted safely. Provider daily-limit prose is inconsistent, so no universal quota constant is encoded here.
- Synthetic tests establish local behavior only. Live acceptance requires an explicitly authorized Instagram professional account, a correctly configured application with eligible access and an operator-approved media URL. Development access does not establish App Review approval.

## Login protocol

- The login hosts are fixed: `www.instagram.com` authorizes, `api.instagram.com` exchanges the code, and `graph.instagram.com` serves the long-lived token, the refresh and the profile resource. Never accept a provider-supplied endpoint.
- The confidential code exchange posts the documented form to the fixed token endpoint. The selected documented flow does not document PKCE parameters, so this adapter disables them explicitly for that flow only. It does not claim that every Instagram flow rejects PKCE and it does not change the shared default.
- The documented code response carries the token, the user identifier and the granted permissions inside a one-item `data` envelope; some provider examples show the same fields at the top level. Accept those two shapes only. A mixed body, a body describing several accounts, an absent identifier or absent granted permissions is refused, because missing permission metadata never proves support.
- A body that carries a provider error beside a success shape is refused, and so is an error inside the envelope entry. An ambiguous body never yields an identity or a token.
- The app-scoped identifier and the professional publishing identifier are different identities. `account.id` is the professional `user_id` addressed by the media endpoints; `account.appScopedId` is the `/me` `id` and must match the user identifier reported by the code exchange. Only a business or media creator account with a usable username is eligible.
- The fixed token endpoints carry the client secret as a documented transport exception. Never log, return or attach those URLs, the secret, the code, the state or a token to an error, and never reuse an error cause.
- A durable Instagram credential needs a known lifetime. The long-lived token keeps the provider's actual lifetime, and an absent, null, zero, negative or malformed expiry is a failure on completion and on refresh. A 60-day lifetime is never guessed, an unknown lifetime never becomes a stored credential and the refreshed result therefore always carries a real expiry.
- Refreshing uses the long-lived token itself. An expired token cannot be refreshed and a token younger than 24 hours is refused before any request. Corrupt metadata is refused before any request too: a negative issuance or a lifetime that ends no later than it starts. The provider issues no refresh token, so none is invented.
- The callback accepts only the documented literal `#_` artifact and removes it before validation without rebuilding the address, so the rest of it, including any userinfo, stays visible to the checks below. Every other fragment, a foreign origin or path, userinfo, a duplicated state or code, an empty code and a refusal that does not carry the expected state are refused before any provider request.
