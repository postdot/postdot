# DESIGN-30 — Native-first motion policy

- Date: 2026-08-31
- Status: completed
- Scope: Motion accessibility, browser-native animation choices, and current UI
  transition usage
- Related issue: [ISSUE-005](../../../ISSUES.md)
- Related decision: [ADR-024](../../../decisions/ADR-024-adopt-a-native-first-motion-policy.md)

## What was done

- Reviewed the current web and shared UI motion usage. The product currently has
  small CSS transitions and no GSAP dependency or application animation runtime.
- Added ADR-024 with a native-first motion policy and explicit criteria for any
  future animation runtime.
- Added a shared `prefers-reduced-motion: reduce` fallback to the UI stylesheet.
- Replaced the existing broad `transition-all` and bare `transition` uses with
  targeted transition-property lists.
- Added motion guidance to the shared UI and web application agent instructions.
- Resolved ISSUE-005 and marked DESIGN-30 complete.

## Key decisions and why

- Do not add GSAP or another animation runtime without a concrete interaction
  that cannot be expressed clearly with CSS or native browser APIs. This keeps
  the initial browser dependency graph small while preserving a path for a
  justified future capability.
- Use CSS transitions for local feedback and restrict animated properties to
  color, opacity, shadow, border, and small transforms. Avoiding `transition-all`
  prevents unrelated layout or paint changes from becoming animated by default.
- Use the Web Animations API as the native escape hatch for finite sequences
  before evaluating a third-party runtime.
- Treat reduced motion as a shared foundation and preserve non-motion status
  communication so the workflow remains understandable without animation.

## Verification

- `bun run check` passes for all 11 workspaces.
- The production CSS contains the targeted transition properties and the shared
