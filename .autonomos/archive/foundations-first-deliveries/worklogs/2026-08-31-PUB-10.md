## Objective

Extend the validated LinkedIn member publisher from text-only posts to posts with
one Postbot-managed image, while preserving the existing project ownership,
immutable execution revision, provider-media delivery, and durable external-effect
boundaries.

This task adds one provider slice. It does not redefine the shared media model or
make videos, documents, multi-image posts, or provider-specific media features part
of the common domain contract.

## Accepted boundaries

- Use the existing `MediaStore`, verified media representations, and execution
  revision media references.
- Keep LinkedIn upload and post payload mapping inside `@postbot/linkedin`.
- Persist the provider image identifier through the existing
  `ProviderMediaDelivery` lifecycle before constructing the final post request.
- Treat upload processing, network failures, and missing provider identifiers as
  explicit outcomes; never retry an ambiguous final post blindly.
- Keep the default application authentication strategy and publisher credential
  ownership unchanged.
- Do not perform a new live LinkedIn image publication without separately approved
  content and an explicit disposable-test boundary.

## Provider evidence

LinkedIn's current documented image flow is multi-step: initialize an upload for an
owner, transfer the image to the returned upload URL, and reference the resulting
image URN from the Posts API. The current Marketing API version is `202608`.

The Images API documents asynchronous processing and does not support
`SYNCHRONOUS_UPLOAD`. A versioned `GET /rest/images` is unavailable with the
write-only `w_member_social` permission used by the member publisher. This slice
therefore treats the successful upload response and the final Posts API response as
the provider signals, without adding a read scope or a polling loop. The boundary
and follow-up option are recorded in [ADR-026](../../../decisions/ADR-026-linkedin-single-image-delivery.md).

Sources:

- [LinkedIn Images API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/images-api)
- [LinkedIn Posts API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/posts-api)
- [LinkedIn API versioning](https://learn.microsoft.com/en-us/linkedin/marketing/versioning)

## Acceptance criteria

- The LinkedIn package exposes typed image upload and image-post contracts without
  exposing access tokens in outcomes or errors.
- The worker can resolve one pinned image representation, upload it, persist its
  provider delivery state, and create an image post using the returned image URN.
- Provider media failures are classified into safe retry, permanent failure, or
  ambiguous outcome according to the external-effect boundary.
- A confirmed provider image upload is checkpointed before the final post, so a
  later final-post retry reuses the provider image and does not upload it again.
- An ambiguous provider upload retains its known image URN and remains blocked from
  blind re-upload until it is reconciled.
- Unit tests cover request mapping, upload URLs, provider status handling, redaction,
  and failure classification.
- SQLite-backed integration tests cover the worker path, durable upload checkpoints,
  and the interaction between provider media delivery and final post creation.
- `bun run check` and `bun run measure:footprint` remain green.
- The implementation and evidence are committed in focused conventional commits
  and published in a dedicated review branch.
