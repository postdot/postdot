# SECURITY-88 — Guard per-instance provider egress

## Objective

Define and enforce an operator-controlled outbound network policy for built-in
providers whose instance origin is selected by a project, starting with Mastodon.
The boundary must prevent private-network and metadata access without making a
second transport stack or weakening custom HTTP's existing guarantees.

## Decision

ADR-043 accepts the existing `@postbot/custom-http` egress authorizer and pinned
Node requester as the shared low-level network boundary. A provider-neutral
`createNetworkControlledFetcher` adapts that boundary to the Fetch API while the
application composition root remains responsible for supplying operator policy.

The policy is fail-closed by default:

- public HTTPS is allowed;
- public HTTP, restricted addresses, metadata endpoints, URL credentials, and
  redirects are rejected;
- an operator can explicitly allow an exact private hostname or CIDR with port
  and scheme through `POSTBOT_OUTBOUND_PRIVATE_DESTINATIONS`;
- the resolved address is pinned for the request and the original hostname is
  retained for Host/SNI behavior.

Mastodon receives the controlled fetcher in OAuth registration, callback account
verification, and worker publication execution. A policy denial is a permanent
failure before the external-effect boundary; resolution and post-dispatch
transport failures retain their existing retryable/ambiguous semantics.

## Implementation

- Added the Fetch API adapter and bounded request/response handling to
  `@postbot/custom-http`.
- Generalized the process configuration from the custom-channel-only
  `POSTBOT_CUSTOM_HTTP_PRIVATE_DESTINATIONS` name to
  `POSTBOT_OUTBOUND_PRIVATE_DESTINATIONS` and applied it to both custom HTTP and
  Mastodon.
- Injected one controlled Mastodon fetcher into the publisher runtime, OAuth
  routes, and built-in provider adapter composition.
- Added the `network_policy_denied` Mastodon permanent outcome and a stable API
  response for blocked connection attempts.
- Updated the custom HTTP package guidance and README to document its shared
  network boundary.

## Verification

- Custom HTTP egress, transport, and Fetch API adapter tests pass, including
  public/private policy, pinned address propagation, URL credential rejection,
  response limits, and a real local Node requester that proves redirects are not
  followed.
- Mastodon tests pass, including permanent classification of policy denial.
- API configuration, typecheck, lint, and format checks pass.
- The full `bun run check` gate passed: 13 packages, 112 database tests, 69 API
  tests, browser integration, build, format, lint, and typecheck.

## Follow-up

- Local or private Mastodon instances require an explicit operator rule; this is
  intentional and should be documented in deployment examples when a local
  provider test setup is added.
- If another runtime consumer needs network primitives that cannot remain
  coherent in `@postbot/custom-http`, reassess extracting the low-level boundary
  into a dedicated package instead of duplicating it.

## Protocol

No broader operating rule changed; the package-level network guidance was updated
because the shared boundary now serves code-owned per-instance providers.
