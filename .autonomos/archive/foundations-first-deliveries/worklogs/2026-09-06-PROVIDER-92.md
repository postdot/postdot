## Architectural decisions

- **Bot token, not OAuth.** Discord publishes through a project Bot token stored as
  the encrypted publisher credential accessToken (custom-http direct-secret
  precedent). No Better Auth involvement, no Discord OAuth flow, no deployment
  environment variables. The connection route verifies the token with
  GET /users/@me and the target with GET /channels/{id} before persisting.
- **Channel destination type.** Discord publishes into a channel snowflake, not a
  user account. Extended the shared destination union with `channel`
  (packages/db publisher-store type + parser, API publisherConnectionSchema),
  following the LinkedIn member/organization precedent. No database migration was
  needed: the storage CHECK constraint is type-agnostic. The adapter validates
  `channel` snowflakes (17-20 digits) and never requires destination == bot user.
- **Fixed origin, injectable fetcher.** Discord's API origin (https://discord.com)
  is provider-owned, not per-instance user input, so the adapter defaults to a
  timeout-bounded global fetch like LinkedIn. The controlled egress boundary is
  not routed because there is no operator-vs-user destination decision; the
  fetcher remains injectable and all tests use deterministic fakes.
- **Single-step media.** Discord attaches files inline with message creation
  (multipart payload_json + files[n]), so there is no reusable remote media ID.
  The adapter still reserves/starts each delivery, opens verified pinned media,
  sends one multipart POST, then completes each delivery with the returned
  attachment ID. A previously `uploaded` delivery can never be reused and fails
  closed as ambiguous (reconciliation required). Uncertain outcomes are never
  silently retried.
- **Reconnect semantics.** 401 authentication_required marks the credential for
  reconnect (new Bot token needed). 403 forbidden does not (channel permission
  problem, not credential problem).
- **Mentions disabled.** All messages send allowed_mentions {parse:[]} so automated
  publications cannot ping users/roles unexpectedly.
- **Profile.** discord-message-v1: text 1-2000 chars plus up to 10 JPEG/PNG images
  with required accessibility text (ported as attachment descriptions, max 1024).
  Guild text channels (types 0/5) only for v1; threads, forums, and DMs are
  rejected at connection time.

## Known limitations (deferred, for orchestrator review)

- Discord Create Message has no provider idempotency key: an ambiguous outcome
  (timeout/5xx after dispatch) can mean the message was created. The adapter
  surfaces this as ambiguous for manual reconciliation; automatic retry of
  ambiguous effects stays forbidden.
- Guild text/announcement channels only (types 0/5). Threads, forum posts, DMs,
  embeds, polls, and replies are out of scope for message-v1.
- 10 MiB per-image cap (documented default upload limit) and JPEG/PNG only,
  matching the portable Postbot media boundary.
- Bot tokens never expire; credential expiry is ignored and stored null.
- Pre-existing gap observed, not changed: Dockerfile COPY list lacks
  packages/mastodon (PROVIDER-87 follow-up, unrelated to this mission).

## Follow-up review fixes (same branch, before merge)

1. **Dockerfile mastodon manifest.** Added the missing
   `COPY packages/mastodon/package.json` line (the API depends on
   `@postbot/mastodon`, so a clean production install could miss the manifest).
   Validated with a full `docker build -t postbot-discord-review .`: production
   image builds end to end (frozen install, turbo build, migrations, dashboard).
2. **Pre-send media failure handling.** `prepareDiscordMedia` now fails
   already-started deliveries as non-ambiguous (retry-safe, no Discord request
   was sent) through a new `abortPreparedMedia` helper, instead of leaving them
   `uploading` where a later retry would misread them as ambiguous. Added a
   multi-media regression test asserting the first delivery lands in `failed`
   (ambiguous=false) with no dispatch.
3. **Connection route integration tests.** New
   `discord-routes.test.ts` threads an injectable `discordFetcher` through
   `PostbotAppOptions` → project module → publisher routes and covers: successful
   connection with token non-disclosure (response + publishers list, duplicate
   409), invalid token (400), unknown channel (400), unsupported channel type
   (400), malformed snowflake rejected before any Discord call (422), and
   session-auth requirement (401).
4. **Send Messages permission.** It cannot be derived from channel metadata, so
   the connection verifies token + channel existence/type only; the permission
   is enforced at publication time (Discord 403 → permanent failure, no
   reconnect). Clarified in the web dialog help text and in code comments on
   both the route and the adapter.
