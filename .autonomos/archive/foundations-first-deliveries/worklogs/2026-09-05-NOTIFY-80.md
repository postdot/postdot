# NOTIFY-80 — Persistent Project Notification Inbox

## Objective

Implement a durable, idempotent in-app notification projection for project human
actors without coupling publication workflows to presentation or future transports.

## Plan

1. Define the recipient, preference, notification lifecycle, and supported event
   contract.
2. Add migration-driven inbox, preference, and projection-cursor persistence with
   project isolation and idempotency tests.
3. Project an explicit allowlist of high-value publication outcome events and prove
   restart-safe cursor advancement.
4. Expose authenticated list, unread-count, read, archive, and preference operations
   through the typed API.
5. Run the complete repository gate and an independent read-only review before merge.

## Acceptance criteria

- Only project human actors are notification recipients; event actors remain
  attribution only.
- Reprocessing an event cannot duplicate an inbox item.
- Projection cursor advancement and inbox writes are atomic and restart-safe.
- Unknown event names or versions are skipped explicitly without blocking later facts.
- Preferences are project- and recipient-scoped and default safely when absent.
- Read and archive transitions are idempotent and project-isolated.
- No external provider call, web UI, or process-local event dependency is introduced.

## What was done

- Added a small notification domain contract and an explicit projection allowlist for
  successful, failed, ambiguous, and reconciled publication outcomes.
- Added project-scoped notification, preference, and projection-cursor tables through
  a committed Drizzle migration.
- Implemented atomic, restart-safe, idempotent journal projection for current project
  human actors, with unknown event versions skipped explicitly.
- Added default-on per-kind in-app preferences that affect future projection only.
- Added read and archive lifecycle operations, unread counts, complete keyset-paginated
  history, and authenticated TypeBox/Elysia routes.
- Added a bounded runtime that projects immediately and periodically, reports failure
  through readiness, and stops cleanly.
- Kept machine access tokens out of the human inbox surface and added OpenAPI coverage.

## Key decisions

- Event attribution never determines notification ownership. The current human actors
  of the event's project are resolved when the projection runs.
- Notifications are recipient-owned presentation state, not domain facts, so they have
  their own cursor, deduplication key, preferences, and acknowledgement lifecycle.
- Only durable terminal publication outcomes create inbox items. Transient claims and
  retries remain operational facts rather than user notifications.
- The runtime timer affects latency only; correctness resides in the SQLite journal,
  projection transaction, unique key, and durable cursor.
- External transports remain out of scope until they can consume a separate durable
  delivery outbox without coupling provider calls to publication workflows.
