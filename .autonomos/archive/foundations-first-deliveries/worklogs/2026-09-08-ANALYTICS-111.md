# ANALYTICS-111 — Harden large-project analytics reads and decide the projection boundary

## Objective

Reduce avoidable cost in the operational analytics reader, measure first-read
and repeated-refresh behavior at the existing benchmark scales, and decide
whether the SQLite-first projection boundary should move. Preserve the public
analytics contract, project isolation, truthful coverage, and the SQLite
source-of-truth posture.

## Branch and scope

- Branch: `analytics/111-harden-large-project-reads`
- Base: merged mainline `aa889111`
- Changed production scope: `packages/db/src/analytics-store.ts`
- Changed measurement scope: `scripts/benchmark-analytics.ts`
- No provider adapter, API schema, UI, migration, external service, or
  credential change.

## Changes

1. Removed three orderings from current aggregate-only snapshots. The builders
   calculate counts and minima, so ordering publications, jobs, or retryable
   IDs added sorting work without changing the response.
2. Reused one timezone formatter per process timezone and used the compact
   formatted date path for historical buckets instead of constructing a new
   formatter and parts map for every metric.
3. Replaced the per-attempt action `Set` with a nine-bit action mask. Duplicate
   action detection and the `duplicateAttemptFacts` coverage counter retain
   their previous semantics with fewer retained allocations.
4. Corrected benchmark memory attribution. The benchmark now reports first-read
   RSS/heap deltas separately from the post-warmup/post-sample measurements and
   forces garbage collection before memory snapshots. Latency is still measured
   without the explicit GC call in its timed region.

## Evidence

The deterministic benchmark fixture remains one project and one automatic
channel with four supported facts per publication, 20% legacy-style facts, and
unknown/unsupported coverage probes every 250 publications.

| Publications | Facts | First query | Warm median | Warm p95 | First RSS delta | Repeated RSS delta |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 4,008 | 38 ms | 24 ms | 25 ms | +21 MiB | +41 MiB |
| 5,000 | 20,040 | 149 ms | 130 ms | 132 ms | +37 MiB | +63 MiB |
| 20,000 | 80,160 | 558 ms | 565 ms | 580 ms | +115 MiB | +281 MiB |

At 20,000 publications, the result assertions remained complete: 20,000
current publications, 20,000 historical creations, 20,000 historical
publications, and 20,000 successful executions. Coverage remained explicit:
80 unknown-version facts, 80 unsupported facts, and 160 skipped facts. The
repeated RSS figure is a stress signal from the Bun/SQLite process after two
warmups and nine samples; it is not treated as proof of a leak.

## Decision

ADR-054 records the provisional interactive envelope of 5,000 publications and
20,000 historical facts per request for the query-time path. The public API is
not rejected outside this envelope yet. No projection or DuckDB engine is
introduced in this task. ANALYTICS-113 is reserved for a representative,
requirements-driven projection design when retention, refresh, concurrency, or
write-interference evidence justifies its lifecycle cost.

## Protocol

ANALYTICS-111 was started from the canonical main checkout by the orchestrator.
No shared development server, provider credential, real provider action, or
parallel worktree was used. The task remains compatible with ADR-053: SQLite
stays authoritative, and any future projection must be replayable and hidden
behind the storage-neutral analytics contract.
