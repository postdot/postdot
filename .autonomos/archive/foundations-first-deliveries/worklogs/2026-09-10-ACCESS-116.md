- Scope: self-hosted human accounts, instance roles, project membership, invitations,

## Evidence reviewed

- `packages/auth` configures Better Auth with email/password only and uses the Drizzle
  SQLite adapter. There is no current bootstrap gate, invitation flow, or social login.
- The API mounts Better Auth directly; authenticated routes expose only the session user
  ID/name and an optional project bearer-token principal.
- `projects` and `actors` are project-scoped. The current project store lists and loads
  projects by the presence of a human/agent/API-token actor with a matching subject ID.
  Project creation atomically creates the human actor and a system actor.
- ADR-030 explicitly deferred memberships/invitations and accepted the initial
  creator-actor model. It also makes project bearer tokens project-scoped and human-only
  for token management.
- ADR-038 says project human actors are the current notification recipients, while
  Better Auth users must not become the notification ownership model. The proposed
  membership layer supplies the missing active-recipient boundary.
- ADR-056 identifies runtime provider applications as instance-owned settings and the
  current routes accept any human session until an explicit instance-admin role exists.
- The web login currently exposes a signup toggle to every visitor. The dashboard
  supports a no-project state and global provider-application settings, but no account or
  membership administration surface.
- The existing recovery guidance requires preserving the Better Auth secret and
  publisher encryption key in addition to SQLite/media data; there is no current
  self-service password reset or offline admin-recovery contract.

## Policy decisions recorded

- First account on an empty database claims the instance and becomes the initial admin;
  public signup closes afterward.
- Email remains required as the account identifier, but SMTP/mail delivery is optional.
  Copyable one-use invitation links support installations without mail.
- Instance `admin` and `member` roles are separate from project `owner`, `editor`, and
  `viewer` roles. Instance admin does not imply project data access.
- Membership is Postbot domain state; actor rows remain attribution/history and are not
  authorization by themselves.
- Removal/disablement revokes human access and sessions but preserves project-owned
  publisher credentials, channel connections, machine tokens, actors, and audit history.
- Invitations are hashed, single-use, seven-day default expiry, revocable, and bound to a
  normalized target email. Project invitations cannot grant instance admin.
- Project machine-token management moves to project owners for new access while legacy
  human project access migrates to owner to preserve existing rights.
- Password/admin recovery is an explicit local/offline operator path when mail is absent;
  no permanent environment admin password or bypass token is introduced.
- Deployment secrets/configuration remain environment-owned; users, memberships,
  invitations, provider applications, publisher credentials, and project token metadata
  remain Postbot business data.

## Migration and implementation proposal

The ADR proposes additive instance/membership/invitation tables, deterministic legacy
backfill (oldest existing user becomes initial admin; existing human project actors
become project owners), explicit orphan-project reporting, instance-admin gating for
provider settings, active-membership notification resolution, and a five-phase rollout:
foundation/migration, bootstrap/invitation UX, authorization cutover, recovery/mail,
then hardening tests and browser flows.

## Open questions

The ADR leaves member-created project policy, verified-email timing, the exact ownership
of new-account invitations, the safe Better Auth recovery command, and future personal
data anonymization for governance/implementation review. These do not change the core
bootstrap and authorization boundary proposed here.
