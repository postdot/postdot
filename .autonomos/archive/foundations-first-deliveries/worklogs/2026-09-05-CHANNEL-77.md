## Objective

Make the already-integrated Bluesky backend usable through Postbot's supported
authenticated web client. The web surface must remain a thin client of the
existing API and provider contracts: it may collect the account handle and
present connection state, but it must not own OAuth, credentials, provider
identity, or publication rules.

## Scope

- Add Bluesky to the built-in channel creation choices.
- Add a handle-based Bluesky connection action and OAuth redirect handling.
- Present project-owned account destinations and disconnect state consistently.
- Expose `/oauth` through the development web proxy so the public client
  metadata document can be served from the same browser origin as the app.
- Validate the client route contract through the web typecheck, lint, unit suite,
  end-to-end suite, and production build.

## Implementation

- Added Bluesky to the built-in channel creation choices and profile labels.
- Added a handle-based connection dialog using the existing shadcn/Base UI
  primitives. The optional `@` prefix is normalized before the API request.
- Added the typed web client call and project dashboard action that redirects to
  the provider-owned OAuth authorization URL.
- Added project-owned Bluesky destination rendering and disconnect handling.
- Added the `/oauth` Vite development proxy alongside the existing `/api` proxy.
- Added an explicit opt-in Vite host allowlist for temporary HTTPS development
  tunnels; default local host checks remain unchanged.

## Validation

- `bun run --cwd apps/web typecheck`
- `bun run --cwd apps/web lint`
- `bun run check` (format, lint, typecheck, unit tests, end-to-end tests, build)
- Result: all checks passed; the real provider flow remains an explicit manual
  operator validation because it requires a public HTTPS origin.

## Integration and live validation

- The web implementation was integrated through PR #82. The explicit temporary
  HTTPS host allowlist and development proxy were integrated through PR #83.
- The PAR state compatibility fix was integrated separately through PR #84 before
  the live authorization attempt.
- On 2026-09-05, the operator connected the real Bluesky handle
  `the owner-authorized test handle` through a temporary Cloudflare HTTPS origin. Bluesky
  displayed the Postbot consent screen, the callback returned HTTP 200, and the
  Postbot dashboard displayed `Bluesky account — Connected`.
- An earlier attempt exposed a stale public tunnel URL and returned `503 Tunnel
  Unavailable`. The public-origin environment was replaced for the retry;
  the temporary tunnel was stopped afterward and the API was restored to its local
  development configuration.
- No real Bluesky publication was created or published. A publication smoke test
  remains a separate operator action requiring explicit authorization.

Out of scope:

- redesigning the web information architecture covered by `WEB-76`;
- app passwords or a second authentication strategy;
- automated real-provider actions or stored real credentials.

## Operator validation after implementation

The first real test remains a controlled manual flow. It requires a public HTTPS
origin serving the app, the metadata document, and the OAuth callback. The
operator will enter the handle `the owner-authorized test handle`, approve Postbot in the
already authenticated Bluesky browser session, publish a deliberately harmless
test post, and remove it manually afterward.
