## Objective

Add the first Bluesky built-in channel as a real vertical slice after the
provider connection boundary. The slice must exercise a provider-owned account
identity, provider-specific authorization and media semantics, project-owned
encrypted credentials, and the existing durable publication workflow without
turning the shared abstractions into a Bluesky-shaped framework.

## Delivered

- Added the private `@postbot/bluesky` package with the versioned Bluesky channel
  profile, capability limits, AT Protocol OAuth client bridge, and publisher
  contract.
- Used the official portable `@atproto/oauth-client` core with the official
  Web Crypto key implementation required by Bun. The Node-only OAuth wrapper
  remains unused because its runtime guard is incompatible with Bun.
- Added serializable OAuth state and session stores. DPoP private key material,
  token metadata, and provider session state are stored through Postbot's
  project-owned encrypted credential and authorization-attempt boundaries.
- Added a project-owned `account` destination for provider identities. The
  Bluesky DID is not inferred from the Better Auth user and Better Auth remains
  limited to Postbot's email/password application authentication.
- Added authenticated connect and callback routes plus a public client-metadata
  endpoint. Bluesky is intentionally disabled unless a configured HTTPS client
  metadata URL is available; local development must use a loopback-safe URL or
  an HTTPS development origin accepted by the AT Protocol client.
- Added the worker adapter for session restoration, refresh persistence, DID
  matching, text publication, JPEG/PNG image delivery, provider outcomes, and
  durable blob-upload checkpoints for safe retries.
- Kept LinkedIn, custom HTTP, `@postbot/oauth`, and the generic workflow lifecycle
  unchanged except for the explicit provider ports needed for composition.

## Verification

- Added package tests for OAuth client construction under Bun, serialized DPoP
  state, text publication, image publication, input limits, and reuse of a
  previously uploaded media blob.
- Added API, database, core, migration, worker, and configuration regression
  coverage for provider state, project-owned credentials, destination policy,
  capability limits, and the disabled-by-default Bluesky configuration.
- `bun run check` passed: format, lint, strict typecheck, unit/integration tests,
  browser E2E, and production builds for all 12 packages.
- No real Bluesky account, credential, or external provider action was used.

## Integration notes

The first real Bluesky authorization and publication must be performed as a
separate controlled operator validation once a public HTTPS client-metadata URL
and the corresponding callback origin are available. That validation is not a
reason to weaken the local default: without the required metadata URL, the
provider remains unavailable and no misleading OAuth link is exposed.
