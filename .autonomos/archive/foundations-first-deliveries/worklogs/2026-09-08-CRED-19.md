# CRED-19 — Runtime provider application configuration

- Status: implementation complete; branch ready for review
- Date: 2026-09-08
- Scope: provider application configuration versus publisher credentials and
  channel connections
- Related issue: ISSUE-059
- Related decision: ADR-056

## Evidence

The current model supports multiple channels and multiple project-owned provider
credentials. Publishers are unique per project/channel; credentials are unique
per project/provider/external account; publisher connections index credentials
without making a credential globally unique. The remaining runtime friction is
that LinkedIn, X, and Bluesky OAuth application configuration is currently
resolved from environment variables during API startup.

The local Bluesky smoke test exposed this boundary: the analytics route can use
public provider data without an OAuth token, but the web connection action
returned `503` when the instance lacked `BLUESKY_CLIENT_METADATA_URL`. A local
development connection was created through the existing encrypted stores only
to validate analytics; it is not evidence that the OAuth flow is configured.

## Implementation progress

The implementation branch adds migration-driven instance settings for LinkedIn,
Bluesky, and X provider applications. Client secrets use the existing encrypted
secret boundary and are never returned by the settings API. The settings routes
accept human sessions only; project bearer tokens cannot manage instance
configuration. Multiple applications per provider are supported with an active
default, explicit disable/promotion behavior, and provider-specific shape
validation.

OAuth attempts and publisher credentials retain the selected application identity
when a runtime-managed application is used. OAuth callbacks resolve that same
application, and LinkedIn/Bluesky/X worker refreshes do likewise.
Environment-backed configuration remains an explicit compatibility path for
existing development setups and is not silently selected for newly configured
providers.

Migration `0022_fresh_human_robot` adds the settings table and nullable composite
references from OAuth attempts and publisher credentials. Existing rows remain
valid with a null application identity. The public Bluesky client-metadata route
now resolves the active runtime application while retaining the environment
fallback.

## Decision captured for implementation

Keep deployment bootstrap variables and the encryption root key, but move
provider application settings into an encrypted, instance-owned runtime store.
Allow multiple application configurations per provider, associate the selected
configuration with OAuth attempts and credentials, and preserve unlimited
project-level accounts/channels subject only to provider-specific policy.

## Non-goals

This work does not remove provider-side app registration, callback registration,
scope approval, provider quotas, or the operator's responsibility for the
encryption root key. It does not add a universal provider abstraction or change
the project/channel ownership model.

## Validation result

The schema, authorization policy, runtime resolver, OAuth integration, and
settings API are implemented. The branch passed the repository check, including
format, lint, typecheck, package tests, the Playwright E2E test, and the full
build. Focused tests cover encrypted-secret redaction, provider-specific
validation, default promotion, project isolation, OAuth application selection,
and migration reproducibility.

The next boundary is review of the API/operator experience and, separately, a
web settings surface. No provider credentials or external provider calls were
added by this branch.

## Web settings surface (branch `feat/ui-provider-application-settings`)

The follow-up web boundary is implemented without changing the secret
contract. Authenticated operators can now manage instance-owned provider
applications at `/dashboard/settings/provider-applications`: list configured
applications, create or edit metadata, enable or disable an application, and
choose the active default for LinkedIn, Bluesky, or X. Client secrets are
write-only and are never returned to the browser; an edit with a blank secret
preserves the encrypted value already held by the API.

The page is available from the global settings navigation and supports the
English and French catalogs. It deliberately does not select an application
per channel yet; channel-level selection remains a separate follow-up after
the operator surface is reviewed. This branch passed the complete repository
check, including the Playwright E2E test and production build. The branch is
ready for review; CRED-19 remains open until the PR is integrated.
