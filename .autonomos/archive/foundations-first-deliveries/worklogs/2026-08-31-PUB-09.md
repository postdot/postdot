## Initial browser blocker

After restarting the IDE and ChatGPT, the official browser runtime still reported
that no browser connection was available. The supported browser surface cannot
complete the interactive LinkedIn authorization without a connected browser, and
no alternate automation path was used.

Local Chromium diagnostics confirmed that Google Chrome is running, but the
ChatGPT extension is not installed in the selected profile and the required
native-host manifest is missing. Opening Chrome or Chromium alone therefore
does not create a supported browser connection.

The documented recovery is to reinstall the Browser plugin from the ChatGPT
plugin UI. The native host and extension were not modified from this workspace.

## Current diagnosis

The operator has authenticated the intended LinkedIn member in the visible
browser. A fresh callback returned to `/dashboard?publisher=provider_unavailable`
after the OAuth attempt was consumed, but no `publisher_connection` or
`publisher_credential` was persisted. The current route catches the post-state
exception without recording a safe diagnostic, so the next step is to add
redacted provider-flow logging and reproduce the callback. The API is configured
on port `3001`; the web application remains on port `5173`.

The callback now records only the provider, project and channel identifiers,
flow stage, error name, and a bounded redacted error message when logging is
enabled. The diagnostic change passed the API format, lint, typecheck, and test
checks. A fresh authorization request reached LinkedIn's consent screen for
the authenticated member; no permission was approved during this attempt.

The operator then approved that consent screen. LinkedIn returned to Postbot,
but the authorization-code exchange failed with an OAuth response-body error
before any credential or connection was persisted. A second authorization
request is currently paused at the same consent screen so the provider error
details can be captured on a fresh callback; no publication request has been
sent.

The redacted diagnostic identified the exact provider response: the token
endpoint returned HTTP `401` with code `invalid_client` and description `Client
authentication failed`, during `exchange_authorization_code`. The configured
client identifier matches the application shown by LinkedIn, and the local
secret is present without dotenv truncation or the example placeholder; its
value was not read or recorded. LinkedIn's documented authorization-code flow
also requires sending `client_id` and `client_secret` in the form-encoded token
request, which is the behavior of the current OAuth adapter.

## Current blocker

The remaining dependency is external to Postbot's OAuth flow: the LinkedIn
application credentials must be verified or re-entered in the ignored
`apps/api/.env` file, without sharing the secret. The API must then be restarted
before a new authorization attempt can confirm the connection. No code change
is justified by the observed response, and no LinkedIn publication request has
been sent.

The LinkedIn Developer Portal was inspected without revealing the primary
secret. The application identity matches the configured public client
identifier, both local callback URLs are registered, and `w_member_social` is
available. After restarting the API from the current environment file, a new
consent flow produced the same HTTP `401 invalid_client` response. The remaining
unverified fact is therefore the provider's acceptance of the secret paired
with this client; the secret was not copied, displayed, or recorded by the
agent.

## Closure

The external dependency was resolved during the same session. The operator's
LinkedIn portal configuration matched the local client identifier and included
the API callback used by the running Postbot process. The client secret remained
local and was never displayed, copied, or written to a repository artifact.

The provider comparison and official documentation review showed that LinkedIn's
standard web authorization-code flow is distinct from its native PKCE flow. The
LinkedIn adapter now declares the standard web profile explicitly: client-secret
authentication, no PKCE parameters, and the existing transaction-bound state
validation. The shared OAuth implementation retains PKCE by default for flows
that support it. The issuer used for LinkedIn OpenID Connect metadata was also
corrected to `https://www.linkedin.com/oauth`.

The real flow then completed end to end:

- the callback persisted a project-owned LinkedIn connection;
- one approved text publication was scheduled and claimed by the running worker;
- LinkedIn accepted the post and returned a provider share identifier;
- Postbot persisted the external result, audit event, and successful job state;
- the exact external post was deleted through LinkedIn's Posts API, which
  returned HTTP `204`.

The follow-up read request was not used as a deletion proof because the current
LinkedIn permission set does not grant the Posts API read capability. The
successful `204` response from the provider's idempotent delete operation is the
recorded deletion evidence. Postbot intentionally keeps the local publication
record as `published`; it records the historical delivery result and does not
pretend that an external deletion occurred through an unimplemented Postbot
publication-deletion feature.

The live test also exposed and fixed a web routing defect: the nested publication
editor loader ran, but the dashboard parent did not render its outlet. The
dashboard now renders the editor route when it is active. The date-time helper
was corrected to display local time rather than UTC. The browser automation
surface could not commit a native `datetime-local` value reliably, so the final
near-term schedule was promoted through the same domain store used by the API;
the worker and LinkedIn request themselves ran through the real local runtime.
