# NOTIFY-81 — External Notification Delivery Outbox

## Objective

Build a transport-neutral, durable external notification delivery boundary that can
support Ntfy first and additional recipient transports later without coupling any
external effect to publication or in-app inbox state.

## Plan

1. Generalize the existing fenced external-effect executor without changing publication
   behavior.
2. Add project-recipient destination, subscription, projection cursor, and immutable
   delivery outbox persistence through a committed migration.
3. Implement atomic journal projection and prove that in-app preferences remain
   independent from external subscriptions.
4. Implement claim, effect-boundary, completion, retry, ambiguity, and lease-recovery
   persistence with deterministic concurrency tests.
5. Run the complete repository gate and an independent read-only review before merge.

## Acceptance criteria

- Only project human actors can own external notification destinations.
- Destination subscriptions are explicit per notification kind and independent from
  in-app preferences.
- Projection writes and cursor advancement are atomic, restart-safe, and idempotent.
- Concurrent workers cannot claim the same delivery.
- Expired claims requeue before the external-effect boundary and become ambiguous after
  it.
- Only an outcome that explicitly asserts no effect can be retried automatically.
- No real transport request, web UI, or provider credential is introduced.

## Implementation

- Added project-scoped external notification destinations owned by current human
  project actors, explicit destination/kind subscriptions, durable projection
  cursors, and immutable delivery snapshots.
- Added atomic event-journal projection and replay deduplication through a
  project/destination/source-event uniqueness constraint.
- Reused the fenced external-effect executor from `@postbot/core` for notification
  work without changing the publication wrapper contract.
- Added atomic claiming, lease recovery, an explicit pre-effect/post-effect
  boundary, bounded retries, terminal failures, and ambiguous outcomes.
- Kept NOTIFY-81 deliberately transport-neutral: there is no real provider request,
  notification UI, provider credential, or Ntfy dependency in this slice.
- Restricted destination deletion while delivery history exists so a running or
  ambiguous external effect cannot lose its destination reference. Disabling is
  the supported lifecycle operation.

## Independent review

A read-only review of the implementation found one correctness issue and one
data-lifecycle hardening opportunity:

- A retryable failure retained the previous `effect_started_at` value. A later
  lease expiry could therefore be classified as post-effect even though the new
  attempt had not started. Retry scheduling now clears that boundary, and a
  regression test covers a subsequent pre-effect lease expiry.
- A destination could be deleted through a cascading foreign key while delivery
  rows still existed. The delivery reference now restricts deletion, with a
  regression assertion; disabling remains the safe lifecycle operation.

The review also confirmed two deliberate follow-ups rather than implementation
defects:

- Public destination configuration is not a secret store. An encrypted secret
  boundary is recorded as `ISSUE-048` / `NOTIFY-82` and gates any real provider
  adapter.
- The first worker boundary is a central SQLite claim path. Actor validation is
  retained for executor compatibility, while worker identity and attribution are
  deferred until a concrete worker ownership requirement exists.

## Verification

- `bun run check` passed after the review fixes: formatting, lint, strict
  typecheck, unit/integration tests, browser E2E, and package builds.
- Database suite: 107 tests, 570 expectations.
- Core suite: 80 tests.
- API suite: 55 tests.
- Browser E2E: 1 test passed.
- The implementation was split across two focused commits so the behavioral
  change and review hardening remain independently auditable.

## Closure and follow-up

NOTIFY-81 is complete once its PR is integrated. `NOTIFY-82` remains the next
accepted task: define the deployment-owned encrypted secret boundary before any
Ntfy, Telegram, email, or webhook transport can be configured. The next adapter
must consume that boundary and must not copy plaintext credentials into public
destination metadata or immutable delivery history.
