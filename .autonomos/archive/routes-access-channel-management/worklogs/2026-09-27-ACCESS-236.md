# ACCESS-236 — Add action ceilings to user-owned API keys

- Status: complete
- Issue: [ISSUE-140](../ISSUES.md#issue-140-let-user-owned-api-keys-narrow-project-actions)
- Owner approval: The owner approved the action-ceiling plan and boundaries on 2026-09-27.
- Scope: Optional least-privilege action limits for generic, user-owned Postbot API keys.

## Accepted contract

- Effective project access is the intersection of the owner's current role, the key's project scope, and its optional action ceiling.
- A key with no action ceiling keeps dynamically inheriting the owner's current project actions, including existing keys with a null Better Auth permissions record.
- A key remains a generic external credential. Postbot does not infer whether its caller is a script, CLI, MCP client, or AI agent.
- Unknown routes and human-session operations fail closed for bearer keys. Workspace/project access administration, key management, publisher OAuth, notifications/realtime, audit events, and installation administration remain session-only.
- Permanent media deletion has its own capability, separate from regular media management.

## Implementation and verification

- Reused Better Auth's nullable `apikey.permissions` storage without a database migration. Added a centralized, explicit route-to-capability policy with exact method/path checks. After authenticating a bearer key, the API checks the route capability in addition to its existing project selection and role enforcement. Unknown routes are denied.
- Added capabilities for project reads, publication management, publication dispatch, channel management, media management, analytics refresh, and permanent media deletion. Limited capabilities serialize to Better Auth's native permission shape; null continues to mean no Postbot action ceiling.
- Updated session-only key create/update calls to use Better Auth's server API without request headers, since its client API does not allow permission writes. The API verifies a human session and passes the authenticated owner ID explicitly.
- Added localized create and edit controls, capability summaries, and the ability to restore the inherited-all setting. Existing key names, expiration, one-time token display, and project selection remain intact. Fixed the client serialization so “all actions” is sent as null, not as an invalid empty list.
- Declared authorization `403` responses for every action-mapped operation in OpenAPI and added an inventory test that checks those mappings. Expanded API tests for create/read/update, role revocation, project/action intersection, session-only routes, permanent-delete separation, and fail-closed unknown routes. Updated prior audit and OAuth tests to preserve session access while rejecting bearer-key access.
- Added an end-to-end browser test for creating a key, selecting projects/actions, editing its action ceiling, and verifying the rendered scope. Added [the user API-key guide](../../root-documentation-2026-10-25/source/docs/security/user-api-keys.md), updated the accepted decision record, and refreshed capability evidence.
- Validation: `bun run check` passed, including formatting, lint and spelling, typechecks, unit tests, all 36 standard Playwright scenarios, both password-recovery E2E scenarios, and all package builds. The API suite passed 226 tests. `git diff --check` passed.
- No `AGENT.md` update was needed: no lasting repository workflow rule changed.
