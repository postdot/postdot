# ACCESS-309 — Revoke project read access for API keys after owner removal

Scope: fix audit defect D1 only, following the existing contract that an
unrestricted key dynamically inherits its owner's current project actions
(ACCESS-236). No global key revocation, no role change, no UX redesign, and no
change to workspace-administrator visibility.

## Correction

`apps/api/src/plugins/auth.ts` now applies the caller's live project access to
API-key requests as well as sessions:

- The session-only option `authorizeProjectSessionAccess` was renamed to
  `authorizeProjectAccess` and is invoked in the key branch after the stored
  scope check and the action-ceiling check, keyed on the key's
  `ownerUserId`.
- `apps/api/src/modules/projects/index.ts` wires the same callback it already
  used for sessions, so there is exactly **one** authorization decision:
  `access.canAccessProject(projectId, userId)` first, then the documented
  workspace-manager reach limited to the project access surface.

Deliberately not done: the audit proposed a new `AccessStore` accessor for the
owner's accessible projects. Reusing the session callback achieves the same
result with no new access query and no second rule that could drift.

Preserved behavior:

- Hidden `404` masking, identical for sessions and keys.
- The stored key scope is still enforced first, so a `selected` key keeps its
  own narrowing, now intersected with live access.
- Action ceilings are unchanged: an insufficient ceiling while access is held
  still answers `403 insufficient_api_key_permissions`.
- Historical `actors` rows are untouched; audit attribution still resolves.
- Access to every other project the key owner still holds is unaffected.
- Mutations remain role-gated; nothing about scheduling, dispatch, retry, or
  ambiguity changed.

## Masking precedence change (one existing assertion)

`apps/api/src/modules/access/routes.test.ts` asserted that a revoked key
attempting `POST /channels` answers `403`. With live access enforced, the hidden
`404` now precedes the route role check, so the answer is `404`, matching what
the session path has always returned. The operation is still denied, and
revocation no longer reveals that the project exists. The assertion was updated
with that rationale; its intent (the key owner's role is rechecked) is unchanged.

## Non-regression coverage

`apps/api/src/modules/projects/access-revocation-regression.test.ts` now holds
three tests, all passing:

1. Reads before and after removal for both `all` and `selected` scope keys,
   covering channels, publications, due publications, analytics, provider
   analytics, tags, publishers, and **media library reads**; preserved access to
   a second project; session parity; masked `404` for revoked mutations; and
   project lists that omit the revoked project.
2. Team-grant inherited access: a `viewer` team grant lets the key read, the
   key still cannot mutate, and removing the user from the team revokes the
   inherited read immediately.
3. A key whose owner was never a member stays hidden on channels, analytics,
   and media.

The fixture explicitly demotes its members to an ordinary workspace member and
asserts `canManageWorkspace(...) === false`, which is what proved the D2
misreading.

## Remaining limits

- A key is still a valid credential after removal; it simply can no longer reach
  the revoked project. Automatic key revocation remains an owner decision.
- Workspace `owner`/`admin` keep their documented access-surface reach, which is
  unchanged by design.
- Read authorization inside the stores still resolves through the `actors` row;
  the boundary that now guarantees correctness is the shared macro callback, so
  any future route that bypasses `auth: true` would still rely on the store.
- Test gaps listed in the audit (notifications, audit events, analytics denial
  assertions, SSE over HTTP) remain open and are unrelated to this correction.
