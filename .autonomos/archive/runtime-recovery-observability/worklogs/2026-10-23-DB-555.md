# DB-555 — Explicit SQLite WAL policy and safe restoration

- Issue: ISSUE-187
- Status: complete
- Decision: [ADR-089](../../../decisions/ADR-089-explicit-sqlite-wal-policy.md), owner-approved configuration and restore scope

## Changes

Main file connections require WAL, use FULL synchronization, keep foreign keys
and wait up to five seconds per busy operation. Memory databases retain their
SQLite memory journal mode. Initialization fails explicitly if WAL cannot be
established and closes its connection.

Strict connection closure finalizes outstanding Drizzle prepared statements.
The old default close left prepared statements alive; a migration followed by
close and a journal-mode change reproduced a retained SQLite lock. The regression
test verifies statement finalization and immediate connection release. This is
not a claim to have isolated the historical shutdown observation in ISSUE-175.

Both restore paths ask SQLite to leave destination WAL mode before replacement,
under the existing runtime lock. SQLite checkpoints committed frames and retires
sidecars. Lock conflicts abort replacement, and orphaned sidecars are preserved
and rejected. Complete restore transitions before opening its destination media
fence, so that connection cannot retain an old WAL across the rename.
Database-only restore stages a SQLite snapshot rather than copying the source
main file without its outstanding WAL frames. Recovery holds remain intact.

Files: database client, backup implementation, two new test files, database
AGENT.md, deployment backup guide, ADR-089 and Autonomos issue/task records.
The AGENT.md addition is stable storage guidance, without session chronology.

## Evidence

- Initial disk probe: DELETE journal, synchronous 2, busy timeout 0.
- Active reader: rollback-mode writer immediately returned SQLITE_BUSY; WAL
  writer committed while the reader retained its old snapshot.
- Writer contention: independent process releases its transaction and the main
  connection completes; a persistent writer causes timeout after about five
  seconds without a partial write.
- Both restore modes recover over committed WAL left by a real SIGKILL, preserve
  only the snapshot rows and pass integrity checks and migrations.
- Online database and media snapshots include committed source WAL data while
  the source connection remains open. Direct database restore from an open WAL
  source was also checked with an isolated probe.
- Negative control: omitting destination WAL retirement makes all three initial
  restore regression scenarios fail, including corrupted schema/index checks.
- `bun run check:quick`: passed (format, lint, spelling, types).
- `bun run test:unit`: 1,550 passed, zero failed, including 253 database tests.
- `bun run test:e2e`: 133 main scenarios plus 4 SMTP/account recovery scenarios
  passed, zero failed, zero retries. The main matrix took about 25 minutes.
- `bun run test:container:recovery`: passed with a newly built production image
  using Bun 1.4.2 on x64. Startup termination, packaged media decoding, real
  authenticated HTTP, graceful stops, media backup/held restore and fail-closed
  restart after forced termination passed. Disposable image/resources cleaned up
  by the acceptance script.
- Host tests used Bun 1.4.3-canary.1. No real provider publication was performed.
