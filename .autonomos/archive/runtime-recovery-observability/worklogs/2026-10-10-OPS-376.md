# OPS-376 — Backup and restoration boundary

## Outcome

Reviewed `packages/db/src/backup.ts`, the maintenance command, startup wiring and
pending-job selection. Added an operational explanation distinguishing current
behavior from a proposed recovery hold. No runtime, schema, provider or backup
operation changed; no live database or credentials were used.

The owner accepted application-aware backup/restore tooling and administrator-owned
scheduling and retention. The OPS-371 daily automatic backup proposal is therefore
not the current direction. Its historical evaluation is retained with an explicit
replacement note.

## Findings

- The media bundle includes the SQLite snapshot and retained representation/avatar
  bytes, not deployment configuration or external secrets. Publisher decryption
  depends on separately preserved key material.
- Restore validates the bundle and requires matching store identity. Existing
  conflicting bytes are rejected. Missing objects are filled before database
  replacement; failure can leave copied objects. No cross-storage atomicity claim.
- Restore preserves jobs verbatim; startup starts publication, email and maintenance
  runtimes. Pending-job selection uses the restored state. No restore-specific hold
  was found. A provider effect completed after the snapshot can be absent from the
  restored database. This is code-path evidence, not a live duplicate-send experiment.
- Backup fence renewal occurs between streamed objects. Very long individual copies
  remain a boundary to evaluate before stronger guarantees.

## Recommendation

Define a durable recovery hold on restore and an explicit administrator review and
resume action. Include direct API effects, external email and background publication;
consider media cleanup and externally performed SQLite restores. Do not implement
provider-wide reconciliation, continuous replication or a backup scheduler as part
of this contract without a separate decision.
