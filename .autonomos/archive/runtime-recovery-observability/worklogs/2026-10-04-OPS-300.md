# OPS-300 — Graceful production container shutdown

Status: complete; root cause fixed and verified against a fresh production image.

## Problem

OPS-299 observed container exit code 137 during the existing recovery check:
`docker stop` waited out its grace period and Docker SIGKILLed the container.
Successful startup and restore therefore did not prove an orderly stop, and the
recovery script silently accepted the SIGKILL.

## Diagnosis

Bisected locally against the production bundle (`apps/api/dist/index.js`):

- Fresh server, `GET /ready` only, immediate SIGTERM → exit ~2s, lock released.
- Fresh server, 30× `GET /health` → clean exit. 70s idle uptime → clean exit.
  The 60s media-reconciliation interval is not involved.
- Fresh server, a single `GET /` (dashboard shell via `@elysia/static`) →
  SIGTERM runs the full drain and releases the runtime lock, but the process
  never exits: no sockets remain open, the listener is closed, yet the loop is
  retained until SIGKILL (exit 137).

Root cause: `@elysia/static` caches served files in an internal `LRUCache`
whose first `set()` starts a `setInterval` TTL sweep that is never cleared
(only an unused `[Symbol.dispose]` clears it). After the first static-file
response the Bun process cannot exit on its own. Every recovery-script
container serves the dashboard, so every `docker stop` ended in SIGKILL after
the grace period, with the lock already released — a confusing operator signal
that looks like a crash without the fail-closed stale-lock guard.

## Fix (bounded, drain semantics preserved)

- `apps/api/src/index.ts`: the SIGINT/SIGTERM/SIGHUP shutdown still awaits
  the worker and media-maintenance drains, stops the remaining runtimes,
  closes the listener and SQLite, and releases the quiescence lock — then
  exits explicitly with the drain outcome (0/1) and logs both phases via
  `[postbot-shutdown]` lines so `docker logs` distinguishes orderly shutdown
  from SIGKILL silence. A hanging drain still hangs (and stays observable);
  only post-drain dependency-owned handles are cut.
- `Dockerfile`: explicit `STOPSIGNAL SIGTERM`.
- `apps/api/AGENT.md`: records the explicit-exit rule and its cause.
- `.autonomos/archive/root-documentation-2026-10-25/source/docs/deployment/runtime-and-distribution.md`: records the verified
  contract (exit 0 + released lock vs exit 137 + retained lock).

No product behavior, scheduling, delivery, or recovery-exclusion rule changed.
The dev launcher already awaits child exit on SIGTERM and is unaffected.

## Acceptance hardening

`scripts/production-container-recovery.ts` now proves the distinction instead
of assuming it:

- After each `docker stop` (60s grace replaced by 30s plus the deprecated
  `--time` flag replaced by `--timeout`), the check requires exit code 0 with
  a 137-specific diagnostic, requires the runtime lock to be absent, and logs
  the stop duration.
- A new forced-termination probe `docker kill`s a serving container and
  requires exit 137, a retained runtime lock, and a refused fresh-server start
  (`already held`). No retained lock is ever deleted; probe data is disposable.

## Verification

- Fresh-image `bun run test:container:recovery`: source and restored
  containers each served the dashboard shell plus 25 assets and stopped
  gracefully (exit 0 in 0.2s, lock released; previously 60s wait + 137). The
  forced probe reported 137 with a retained lock and a refused restart.
- `bun run format`, `lint` (incl. spelling), `typecheck`, `test:unit`
  (17 turbo tasks + 17 script tests), `test:e2e` (Playwright suite + 2
  password-reset scenarios), and `bun run build` (17 tasks) all pass.
