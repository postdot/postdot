# OPS-306 — Reliable shutdown cleanup result

Base: 9e0de695f. Scope: shutdown cleanup signaling and its tests only.
DOCS-301 and AUDIT-307 were not started.

## Independent probe (ISSUE-151 confirmed)

A throwaway script outside the repo (removed afterwards) reproduced the OPS-305
probe on current source: acquire a lock in a temp directory, `chmod 0500` the
parent, call `release()`:

- `releaseThrew: false`, `markerRetained: true` (EACCES on unlink, intercepted
  by `removeLockIfOwned`).

The shutdown exception guard therefore cannot infer a successful release from
the absence of an exception, and exit 0 contradicted the documented cleanup
contract whenever removal failed silently.

## Consumer review

`RuntimeQuiescenceLock.release()` callers:

| Caller | Use | Change |
| --- | --- | --- |
| `apps/api/src/index.ts` startup failure | release-then-rethrow before serving | none (process never served; a retained marker stays fail-closed) |
| `apps/api/src/index.ts` shutdown | exit-code outcome | consumes the new boolean (exit 2 when retained) |
| `packages/db/src/backup.ts` restore paths (2) | `finally` release, result ignored | none: foreground operator commands; a retained marker already surfaces at next start, and changing their exit semantics is out of scope |
| `packages/db/src/local-account-recovery.ts` | `finally` release, result ignored | none, same rationale |
| tests (`runtime-quiescence`, `backup`, `local-account-recovery`, `scripts/dev-api`) | real module, result ignored | compatible without changes |

No mocks implement the interface.

## Choice: boolean result, not a throw

`release()` now returns true when no marker remains (removed, already absent,
or lost in an ENOENT race) and false when a marker is retained (removal
error, unreadable content, foreign token). Throwing was rejected: the restore
and recovery callers release inside `finally` blocks, where a new throw would
mask in-flight errors or change maintenance-command outcomes. A boolean is
backward compatible — existing callers compile and behave identically — while
the shutdown path maps `false` to exit 2. Token ownership checks, the
single-owner removal path, and the no-automatic-reclaim rule are unchanged;
`closeSync` still throws as before and is covered by the same guarded stage.

## Correction

- `packages/db/src/runtime-quiescence.ts`: `release(): boolean`,
  `removeLockIfOwned(): boolean`; the EACCES log line is preserved for
  operators alongside the machine-readable outcome.
- `apps/api/src/shutdown.ts`: new `createShutdownHandler` with injected
  dependencies; drain (fail-fast, exit 1), database close (exit 2), lock
  release (exit 2 on throw or retained marker) run as sequential guarded
  stages. Exit 0/1/2 contract unchanged in meaning, now truthful in all
  three branches.
- `apps/api/src/index.ts`: wires the real worker, runtimes, server,
  database, lock, and `process.exit`; orchestration stays thin.
- `packages/db/AGENT.md`, `apps/api/AGENT.md`,
  `.autonomos/archive/root-documentation-2026-10-25/source/docs/deployment/runtime-and-distribution.md`: record the boolean contract
  and the exit-2 meaning.

## Behavioral tests (outcomes, not messages)

`packages/db/src/runtime-quiescence.test.ts` (8 tests): success and
idempotent double release return true; externally removed marker returns
true; foreign token, corrupt content, and permission-denied removal return
false with the marker retained (the permission case skips when running as
root, which bypasses directory permissions).

`apps/api/src/shutdown.test.ts` (12 tests): orderly drain-before-cleanup
order with exit 0; in-flight operation gates all cleanup until it settles;
drain failure skips later drains yet still closes and releases with exit 1;
close failure still attempts release with exit 2; retained marker exits 2
with a single release attempt and no deletion by another path; throwing
release exits 2; a second signal during drain is ignored (single exit).

Deliberately not added: unit tests for the `process.exit` call itself and
fault injection for the live exit-2 branches — both signatures that matter
(exit 0, exit 137) remain covered end to end by the container acceptance.
