# REALTIME-96 — Evaluate the reactive client data layer

## Objective

Compare TanStack Query targeted invalidation with TanStack DB collections and
live queries for project publications, queue state, notifications, unread state,
and a derived attention view. Keep the experiment isolated and leave a clear
recommendation before introducing a real push transport or replacing the
dashboard data context.

## Initial evidence

- Postbot has a durable server event journal and notification projection, but the
  web client has no general push/reconnect data contract.
- The current API already exposes project-scoped publication and notification
  reads plus a notification-read mutation.
- Projection can lag the event that caused it, so a client refresh may observe
  the old read model even after receiving a valid signal.
- The required scope can be represented by two safe client DTOs and pure queue,
  unread, and attention selectors without exposing credentials or provider
  payloads.

## Implementation

- Created branch `spike/realtime-client-data-layer` from `main`.
- Added the web dependencies `@tanstack/react-query`, `@tanstack/react-db`, and
  `@tanstack/query-db-collection` using Bun and the existing lockfile.
- Added an isolated route at
  `/dashboard/projects/:projectId/realtime-prototype`; it is not linked from
  product navigation and uses only the local deterministic fixture.
- Added safe DTOs, typed event payloads, project guards, selectors, a local
  event source, authoritative/visible fixture maps, projection delay, duplicate
  delivery, reconnect, metrics, and failed-write controls.
- Added the Query prototype with explicit project query keys, exact resource
  refreshes, projection-aware retries, reconnect refresh, and normal read
  mutation handling.
- Added the DB prototype with typed `QueryCollection`s, live publication and
  notification queries, a publication/unread-notification join, and an
  optimistic notification-read transaction with rollback.
- Added 6 focused prototype tests covering selectors, all four event kinds,
  targeted Query refresh, projection delay, reconnect, deduplication, DB live
  join, optimistic rollback, and project isolation.
- Added proposed ADR-047; it recommends TanStack Query for the current product
  boundary and defers TanStack DB.

## Evaluation

| Observation                                           | Evidence                                                                                                             |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Targeted updates work in both options                 | Publication events only refresh the publication resource; notification events only refresh notifications             |
| Projection delay needs explicit handling              | The fixture delays visibility; both adapters retry until `eventIsApplied`                                            |
| Reconnect is a policy, not a library feature          | Both adapters use a bounded full refresh and expose reconnect/projection metrics                                     |
| DB live derivation works                              | A live query joins publication rows to unread notifications and updates from the two collections                     |
| DB optimistic reads work but add lifecycle complexity | `notifications.update` persists through `onUpdate`, and failed writes restore the prior unread row                   |
| Query is easier to follow against today's API         | It needs query keys, fetchers, and selectors; DB adds client/collection/live-query cleanup and refetch semantics     |
| The isolated bundle stays lazy                        | The main chunk is 252.29 kB raw / 81.84 kB gzip; the combined prototype route chunk is 351.58 kB raw / 97.47 kB gzip |

## Recommendation

Use TanStack Query as the initial reactive client layer with the small event
coordinator from the prototype. Do not integrate TanStack DB broadly yet. Keep
the DB adapter as a concrete reference for a later re-evaluation if queue,
calendar, inbox, and future screens begin duplicating normalized joins or
optimistic workflows.

## Proposed follow-up

- Define the real authenticated event stream, cursor/gap behavior, heartbeat,
  and post-projection ordering semantics.
- Integrate the Query coordinator behind a narrow production data boundary and
  validate it against the durable notification projection.
- Add browser-level coverage for reconnect, duplicate delivery, authorization,
  and the chosen data boundary before exposing it in the main navigation.
- Reconsider TanStack DB only when measured duplication or cross-screen joins
  justify its bundle and lifecycle cost.
