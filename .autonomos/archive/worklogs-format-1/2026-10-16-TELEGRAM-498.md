# TELEGRAM-498 — Telegram capability and contract discovery

## Outcome

Reviewed the official Telegram Bot API and FAQ against existing provider ownership, effect outcomes, connection policies and the accepted publication content boundary. Created draft SPEC-008 and linked ISSUE-165 to the research task and proposal. No provider implementation or public availability claim was added.

The proposal covers verified bot/channel connection without a send, encrypted project-owned credentials, raw URL/token redaction, native text versus caption limits, media inspection, one-result remote identity, ambiguous send handling, rate limiting, isolated acceptance tests and the package/runtime/Studio integration sequence. Polls and topics remain separate native format work.

## Decision boundary

A Telegram album returns several messages, whereas the current common executor outcome exposes one externalId. Both a single-media initial contract and album support are credible product directions. Recorded costs and responsibilities rather than silently choosing the smaller implementation or discarding remote identifiers. Asked the owner which belongs in the first integration; recommendation is text plus one image/video first, albums as separate complete work. The specification remains draft pending that choice. No dependent implementation has started.

The broader bot-based publishing work is authorized; this question concerns its concrete initial media scope under root AGENT.md Decision Discipline, not permission to research or routine code choices. The proposal also makes broadcast-channel scope explicit for review.
