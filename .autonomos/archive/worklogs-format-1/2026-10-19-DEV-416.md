# DEV-416 — Make the production image serve requests

## Plan

1. Reproduce the production image's behavior in a faithful local image and identify the cause.
2. Correct the cause with the smallest change that keeps the image's contract, and verify the whole API surface in the image.
3. Run the proportionate checks, record the evidence, and route the durable guidance.

## Problem

The image built by the repository `Dockerfile` cannot answer any route. Every request that reaches a compiled route fails with HTTP 500 and the container log carries:

```text
[Elysia] Failed to compile route GET /health: Cannot find module 'typebox/type'
```

The image's `HEALTHCHECK` therefore fails, `restart: unless-stopped` would restart the container in a loop, and the repository's own container acceptance, which waits for `/ready`, cannot pass.

## Cause

Elysia 2 compiles its routes at runtime and loads the TypeBox namespaces through a dynamic require it cannot bundle. The bundle therefore kept five external requires — `typebox/type`, `typebox/system`, `typebox/value`, `typebox/schema` and `typebox/compile` — and the final image carries only the bundle, the migrations and the dashboard assets, with no `node_modules`. The require failed at the first request, and every route that needs a compiled schema answered 500.

A checkout is not affected: the repository's `node_modules` resolves the require. That is why the defect only appears in the image, and why it survived every host-side test.

Elysia names its own two remedies in the error message: build with the AOT plugin, or register the namespaces manually with `setupTypebox`.

## Options considered

- Wire the namespaces statically with `setupTypebox`. No image change, no runtime dependency, and the namespaces are bundled. It touches the API composition, so the request-validation path has to stay correct.
- Precompile the routes with Elysia's AOT plugin. It removes the runtime compilation entirely, but it changes the build pipeline and the shape of the build output.
- Ship the `typebox` package in the image. It needs no code change and `typebox` has no dependencies of its own, but it leaves a runtime dependency in the image and would hide the next package that escapes the bundle.

The first was chosen: it is the documented answer to this exact failure, it keeps the image's contract of bundle plus migrations plus assets, and the request-validation risk is covered by the API's own schema tests and by the image probe below.

## Correction

`apps/api/src/app.ts` now registers the TypeBox namespaces statically, before the application is composed:

```ts
setupTypebox({
    typebox: {
        type: typeboxType,
        system: typeboxSystem,
        value: typeboxValue,
        schema: typeboxSchema,
        compile: typeboxCompile,
    },
})
```

The namespaces are static imports, so the bundler includes them. The rebuilt bundle keeps no external literal require at all.

## Evidence

Measured on two faithful local images, both built with bun 1.4.2, the version the `Dockerfile` pins, carrying the bundle at `/app/postbot.js`, the real migrations and the dashboard shell, with no `node_modules`:

| Route | Before | After |
| --- | --- | --- |
| `GET /health` | 500 | 200 |
| `GET /ready` | 500 | 200 |
| `GET /api/recovery/status` | 500 | 200 |
| `POST /api/projects` with an empty body | 500 | **422** |
| `GET /` (the dashboard shell) | 200 | 200 |

The 422 is the important one: it shows the value side of TypeBox is wired, so the request validation behaves as it does in a checkout, instead of failing to compile.

The bundle grew from 5.40 MB to 5.59 MB, which is the bundled TypeBox namespaces.

## Checks

- `apps/api`: 385 tests across 47 files, 3169 assertions, all pass. The schema validation suite is part of it.
- The container startup-termination check of DEV-415 passes against the fixed image and fails against the pre-correction image.
- `bun run check:quick`: format, lint, spelling and typechecks across the workspace pass without bypass.
- The repository's own container acceptance could not be run end to end here: the sandbox has no bridge networking for the published-port steps, and the packaged poster decoder needs the real image, whose build downloads and compiles ffmpeg. The CI image run remains the confirmation of the whole scenario.
