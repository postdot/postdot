# UX-295 — Failed draft application and server-state recovery

Status: complete; root integration gate passed.

## Findings

A promotion failure disabled the action without offering a server read outside the revision-conflict path. A lost response can hide a successful transaction; changing draft text must not make another application appear safe. The saved draft and the outcome of applying that draft are separate facts.

The existing server-version loader already preserves local work through the recovery comparison. This pass exposes that path without a new API, storage service, retry policy or lifecycle transition. Known revision conflicts retain their existing reconciliation path.

## Changes

- Place an actionable failure notice near application, using the existing status surface and shared button. It asks for a server check before another attempt.
- Keep a separate application-recovery flag across draft autosaves and reactive updates. It blocks application and conflicting lifecycle actions until an explicit server read succeeds.
- Read current publication state without repeating promotion or provider delivery. Do not infer transaction ownership from matching text.
- Protect a pending read against repeated activation and editing races; defer incoming reconciliation while the read is active.
- Reuse the existing local/server recovery decision when content or scheduling differs. Failed reads retain local content and the available check action.
- Preserve the saved-draft indicator when application or its verification fails; an actual autosave failure still reports a save failure.
- Stack notice and action at every width; an initial screenshot exposed side-by-side overflow and the corrected layout passes a viewport-width assertion.
- Make the selected target's scrollable technical payload keyboard accessible. A populated scheduled example exposed this pre-existing accessibility defect.

## Verification

Two isolated persisted browser scenarios passed: a rejected application and a successful server transaction whose response is deliberately dropped. Both start with a scheduled target and a locally cleared date.

They verify one application request, exact retained target state, continued draft editing without unlocking application, failed reads, local/server recovery of unsaved content and schedule, preservation of sibling selected targets, and accessibility/overflow at 1280, 820 and 390 pixels. Recovery never silently applies the restored draft. Screenshots were inspected; the mobile failure notice remains inside the content width.

Complete `bun run check` passed: formatting, lint/spelling, type checks, unit tests, 73 browser scenarios, two password-reset scenarios and all 17 build tasks. No real publisher was contacted.

## Readiness boundary and continuation

Scheduling retains a revision and may create an automatic job. It is not proof that an external platform is reachable or credentials remain valid when execution starts. Connection state and repair remain project-owned responsibilities; this pass does not add a provider preflight or change execution rules.

Recommended next task: UX-296, inspect missing/revoked automatic destination connections in publication detail using isolated data. Focus on a clear readiness state and repair path, without changing publisher credential ownership or retry semantics.
