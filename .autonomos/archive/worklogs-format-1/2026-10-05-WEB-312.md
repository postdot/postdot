# WEB-312 — Dashboard behavior when project access is lost mid-session

Diagnosis only. No product behavior was changed: the only non-test files touched
are this worklog and the Autonomos ledger.

## What was reproduced

Two isolated browser sessions against a real API, a real channel and a real
publication (no route mocking), plus deterministic API-level tests for the event
stream:

- `e2e/web-312-live-access-revocation.spec.ts`
  - an editor with Overview, Queue and an open editor, plus unsaved local text,
    loses direct project access while the tab stays connected;
  - an editor is downgraded to viewer while Overview stays open.
- `apps/api/src/modules/projects/access-revocation-stream.test.ts` pins the stream
  mechanism without a browser: access loss on an idle connected stream, silence
  on a role narrowing, and a fail-closed authorization lookup.

Caveat on the browser evidence: the dev proxy repeatedly tears the SSE connection
down (`vite http proxy error … socket hang up`), so the open tab re-read far
more often than production would. That changes only *when* the tab refetches.
Both paths end in the same refused refetch, so the end state asserted below is
the production one; the latency is not claimed as a product property.

Correction recorded by SSE-318 (2026-10-05), with the observation above left
intact: the proxy was the messenger, not the cause. The connection was being
closed upstream because Bun ends a connection idle for ten seconds while the
SSE heartbeat interval is fifteen, so every quiet stream was torn down before
its first heartbeat and the proxy reported the reset as `502`. The proxy flapping
recorded here, and the 502 recorded in WEB-314, were two views of that one
defect. See [SSE-318](2026-10-05-SSE-318.md).

## Findings

### 1. When the client discovers the loss

The project stream re-authorizes on **every pull**, twice around the journal read
(`realtime-routes.ts:409-421`, `:433`, `:447`), and an idle stream is pulled
again by the 15s heartbeat, so access loss is reported in-band as
`project.access-revoked` followed by a close, within one heartbeat. An
authorization lookup failure is treated as a revocation (fails closed,
`realtime-routes.ts:415-418`). Pinned by the first API test.

The client maps that signal to `refresh('project', true)`
(`project-realtime.tsx:517-521`), which invalidates `data`,
`calendarPublications`, `publicationQueues` and `publicationApprovals` — but
**not** `publicationEditors`, because `includePublicationEditors` is not passed,
unlike the `resync-required` branch at `:512-513`. There is no session re-check,
no global 403/404 handler, and no polling: `staleTime` is `Infinity` and
`refetchOnWindowFocus`/`refetchOnReconnect` are off
(`project-realtime.tsx:238-250`). The user stream only closes with
`user.access-revoked` when the user has **zero** remaining visible projects.

### 2. A role downgrade is invisible to the stream

The gate on the project stream is `canAccessProject`
(`realtime-routes.ts:207-213`), which tests access, not role. A viewer still
satisfies it, so a downgrade produces **no event at all** (second API test), and
no membership event exists in the journal vocabulary. The client learns the new
role only when the project data query happens to refetch *successfully* — that is,
opportunistically, through an unrelated journal event or a stream reconnect. In
the browser this happened within 20s and the create affordances withdrew
themselves, with no announcement. There is no gap in protection here, only a gap
in explanation and in timing.

### 3. What the server refuses (protection)

Immediate and independent of the open tab: `GET /membership` → 404,
`GET /publications` → 404, `GET /publications/:id/editor` → 404,
`POST /posts` → 403/404, `PATCH …/draft` → 403/404. A downgraded editor keeps
reading (200) and is refused on write (403).

### 4. What leaves the interface, and what does not

Refused refetches **do** empty the list surfaces: the calendar, Queue,
Performance and approval surfaces all swap their content for the generic
`QueryErrorState`. A later navigation re-runs the loaders, the project is no
longer among the user's projects, and the dashboard lands on the
`Create your first project` empty state, so the project disappears entirely.

What does **not** leave is the project identity and the role. The project data
query *errors* instead of returning new data, so its last successful bundle
survives: the project name stays in the selector and `projectRole: 'editor'`
keeps the sidebar `New publication` link armed. The editor instance is not
invalidated by the revocation signal and the route renders
`editorQuery.data?.editor ?? loaderEditor`, so the publication content stays on
screen and the body stays editable.

The only signals the user receives are the generic
`The requested resource could not be found.` alert and a `Save failed` status
from the refused autosave. No copy anywhere states that access was lost.

### 5. Local work survives

The editor recovery buffer (`postbot:publication-editor:v3:<project>:<publication>`)
is written on every local change and is only removed when there are no local
changes or after a successful save, so it is untouched by removal — pinned by
asserting the buffer count stays at one. The composer uses the analogous
`postbot:publication-composer:v1:<project>` key. Recovery after a failed save is
already implemented, and would work again if access were restored.

## Proposed bounded correction

Three separable pieces; only the first is unambiguous.

**A. Make the existing signal authoritative (mechanical, no new copy).** On
`project.access-revoked`, remove the project-scoped queries for that project —
`removeQueries` on the existing project key factories, never `queryClient.clear()`
— so no stale project data and no stale role survive, then let the dashboard land
on the empty project state that a navigation already produces today. Leave the
recovery buffers untouched, which preserves unsaved work. Cost: one branch in the
existing signal handler plus removing the four key families. No polling, no global
purge, no server change, no new translation.

**B. Explain the loss.** Requires new copy, because the current wording is a
missing-resource error the user cannot act on.

**C. Announce a role change.** Requires a new stream event subject and a server
emit on role change. Deliberately not recommended as part of the same correction:
it widens the surface for an event whose only effect would be an explanation.

### Product decisions left to the owner

1. **Silent drop or explicit explanation.** Should the removed project vanish
   (today's navigation outcome) or should the tab say that access to the named
   project was lost and offer a way back to the workspace?
2. **Disposition of unsaved local work.** The buffer keeps project content in the
   browser of a user who no longer has access. Keeping it preserves work and
   assumes the local browser is out of scope; offering copy-out and then purging
   it on acknowledgement protects the browser instead. These conflict and cannot
   both be the default.
3. **Whether to stay or go.** Should the tab navigate away automatically, or stay
   on a read-only shell of the last known state? Staying is friendlier to unsaved
   work, but it is also the state that currently shows an armed editor.
4. **Role downgrade announcement.** Accept the opportunistic refresh, or add the
   stream event from piece C purely to say "your role changed"?

## Deliberately not done

No periodic polling, no `queryClient.clear()` on revocation, no global 403/404
interceptor, no session invalidation, no server authorization change, and no new
translation.
