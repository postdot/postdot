## Destination-safety prerequisite implementation

The source now holds automatic publications when a known destination changes.
This is a prerequisite within SHARE-592, not delivery of channel sharing.

- Migration 0020 adds four columns without rebuilding tables or resetting data:
  monotonic channel generation, retained non-secret channel identity, publication
  confirmation generation and immutable execution destination snapshot.
- Connection replacement compares provider/account/destination identity and a
  SHA-256 endpoint fingerprint. The public endpoint origin is retained for
  intelligible identity; URL credentials, paths, fragments and query strings are
  excluded. Tokens are not captured.
  Same-account token renewal and display-name changes do not invalidate work.
  First connection preserves existing pre-connection scheduling semantics.
- Scheduler selection, claiming and external-effect admission check confirmation.
  A claim taken before reconnection returns to pending without changing its
  selected target or requested schedule. Execution resolution refuses a newly
  substituted account after pinning; a request already using the original
  connection can record its original outcome.
- Explicit confirmation checks the live generation and selected target, project
  authority, connection and lifecycle state. It preserves content, approval and
  scheduling. Replacing a pending retry creates a new job and preserves the old
  immutable execution; the confirmation fact links both jobs. Failed work still
  requires its normal explicit retry action. Historical rows without captured
  identity remain unrecorded, rather than being backfilled with today's account.
- API reads are project-scoped; confirmation requires editor authority and the
  publication:dispatch API capability. Stale generation/target returns 409.
  Client types derive request bodies from the API route contract.
- Studio shows the changed account and actual selected content, separately from
  newer unapplied draft edits. Confirmation explains that scheduled/overdue work
  may resume unchanged. History, translations, conflict recovery and realtime
  invalidation are included. Public channel guidance distinguishes source builds
  from the unchanged alpha.2 image.

## Credential renewal prerequisite implementation

Mechanical renewal now uses a database-connection-owned queue keyed by credential
ID. Independent accounts remain concurrent. Store facades on the server's one
SQLite connection share ownership; this is not a cross-process or duplicate-record
coordination promise. No schema migration or dependency change was needed.

- Preparation reloads active metadata and decrypts inside the queue, verifies its
  revision after decryption, and supplies a live injected clock. A caller cancelled
  while waiting releases only its own turn; failures release ownership as well.
  Queue entries are removed after completion and never cache plaintext tokens.
- A revision-fenced context persists renewal against the version read before the
  network request. OAuth replacement or revocation during that request prevents
  both stale token writes and stale reconnect-required marking. Existing explicit
  grant replacement remains available to authorized connection flows.
- X, LinkedIn, Mastodon and Instagram publication adapters use current expiration
  and application metadata; Mastodon reply and first-comment preparation shares the same queue.
  Instagram retains its known-expiration, minimum-age and granted-scope rules.
  Uploading and publishing do not hold the refresh queue. Late authentication
  failures in these adapters mark only the grant whose token they used, not a
  newer OAuth replacement.
- Bluesky's SDK can renew after initial restoration. The protocol package accepts
  optional durable-store and request-lock hooks, without depending on Postdot
  storage. The API bridge supplies the same credential queue for every SDK session
  operation and awaits encrypted session writes before releasing it. Both
  publications and outgoing replies/first comments use the bridge. A changed
  DPoP proof key requires a newly restored session rather than making an old SDK
  object adopt a new grant. Older caller APIs retain their memory-store defaults for independent protocol use.
- Publication effect admission, cancellation, project limits, selected content,
  destination generation and historical snapshots retain their existing contracts.
  Worker mutation wrappers continue checking active ownership. Cancellation does
  not mark an otherwise untouched queued credential as requiring reconnection.

### Migration preparation and next boundary

Inspection confirms the migration must replace project/channel/profile composite
foreign keys with attachment/workspace guarantees, not drop those guarantees.
Current profile and connection attribution references project actors, which cannot
remain deletable owners of surviving shared resources. Credentials authenticate
encryption using record ID, provider and secret field rather than project ID;
retaining credential IDs therefore permits ownership migration without inventing
new secrets. These are implementation constraints, not completed migration work.

Proceed with preserved ownership/attachment migration, workspace-scoped attribution,
management/use authorization and shared-resource retirement in one integrated lot.
Keep existing single-project creation intuitive. SHARE-592 remains in progress;
GitHub #12 and the accepted specification are not completed by these prerequisites.
