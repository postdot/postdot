# UX-329 — Profile Definition Validation Feedback

- Base: `2af412bb4`.
- Status: diagnostic complete; no product implementation.
- Owner approved the recommended diagnostic after UX-328.

## Operator outcome observed

A wrong text capability binding in the real profile dialog returns HTTP 400,
`invalid_content`. The dialog displays only **Profile action failed / The request
could not be completed.** It identifies neither the field nor the repair. The
operator's edited JSON remains intact, the original active profile is unchanged,
and no draft is created.

Deleting `capabilities` from the same JSON instead returns HTTP 500,
`internal_error`, rendered as **The server could not complete the action.**
Restoring the original editable definition then saves successfully (200), and
Preview impact becomes available. No activation or publication was performed.

These are separate defects: loss of actionable normalized diagnostics, and
missing structural validation before code accesses typed definition fields.
Detailed UI alone would leave the second defect unresolved.

## Isolated reproduction

A temporary Bun script used an in-memory migrated database, fake local account,
authenticated `createApp().handle()` requests, a custom manual profile, and a
separate core compiler for comparison. No live database, real credential, provider
or development-server configuration was used. Each invalid request left the
active/draft profile state byte-equivalent to the pre-request JSON snapshot.
A valid control saved afterwards with revision 1.

| Forbidden custom schema pattern | `schema.keyword_forbidden` | 400 `invalid_content` | `/contentSchema/properties/body/pattern` after normalization |
| Schema root changed to array | Eight normalized issues | 400 `invalid_content` | Schema root and dependent binding paths |
| Binding points to missing property | `binding.path_missing` | 400 `invalid_content` | `/fieldBindings/0/path` |

The unknown binding used a clearly fictitious sentinel. The API's existing joined
message echoed it; the UI did not. This demonstrates why parsing or directly
rendering the existing message is unsuitable. It is not evidence of a live
credential leak.

A disposable browser spec used the existing isolated harness and real API. It
asserted the 400 response, generic dialog feedback, retained JSON, unchanged active
profile and absent draft; then the malformed 500, recovery and successful save.
The final run passed in 9.2 seconds (scenario 6.8 seconds), one worker, no retry.
The screenshot was inspected. The first run reached the malformed case but failed
because the diagnostic expected the 400 fallback copy for a 500; that assertion
was corrected to the actual distinct internal-error copy. No product behavior was
changed to satisfy the probe.

The initial custom fixture omitted the required JSON Schema dialect; its creation
was refused before probing. Declaring the existing supported dialect fixed only
the fixture. The completed ten-case script took approximately half a second.
Both disposable source files were removed after measurement.

## Where information is lost

1. `saveChannelProfileDraftBody` in API project models accepts arbitrary record
   values; `resolveChannelProfile` casts the object to a typed definition.
2. The store normalizes metadata and calls the core profile compiler. Its JSON
   snapshot check cannot establish the shape of bindings, capabilities or execution.
3. `validateProfileDefinition`, `validateFieldBindings` and `validateCapabilities`
   dereference nested objects, call string methods and iterate arrays before any
   complete structural guard. The four malformed inputs above throw there.
4. For normalized failures, `invalidProfileError` in the store content codec
   discards path, code, severity and source and joins issue messages into one
   DomainInvariantError string.
5. The API error handler exposes only code/message through the declared error
   envelope. Unexpected errors remain safely generic; changing this globally is
   neither needed nor recommended.
6. Web `ApiError` preserves status/code/message/blockers, not profile issues.
   `formatApiError` uses a localized code mapping; `invalid_content` has no dedicated
   case and falls back to the generic request message. The profile dialog calls
   that formatter. It must not recover field information by parsing message text.

## Proposed bounded contract — not implemented

The next mission should address structural guards and profile-save feedback in
one coherent tranche, with one final validation obligation:

- Validate JSON definition structure before nested dereferences. Missing objects,
  wrong arrays and wrong primitive types become normalized profile issues rather
  than exceptions. Preserve the accepted schema policy, capability limits,
  binding checks and execution rules; do not add a migration or relaxed fallback.
- Preserve normalized issues across the draft-save boundary and project-specific
  API contract. Keep authentication, authorization, stale revisions, resource
  masking and unexpected internal failures on their existing paths.
- Return a bounded list of recognized issue codes and JSON Pointer paths, rooted
  consistently at the complete editable definition. Use fixed localized copy in
  the client. Do not return schema values, raw exception messages, stack traces,
  provider text or an arbitrary interpolated issue message as display copy.
- Normalize paths where they are produced. Custom schema-policy paths currently
  start at the schema, while domain/binding paths start at the definition; for
  example `/properties/body/pattern` needs `/contentSchema` prefixed. Do not
  blanket-prefix by `source`: compiler failures can already use `/contentSchema`
  while also carrying `schema_policy`.
- Keep an explicit safe fallback for unknown codes or unsupported detail, without
  dropping rejection or changing status into success. Do not introduce a global
  exception-to-detail renderer.
- Present one concise validation summary and field/correction list next to the
  JSON, replacing the generic failure for this known case. Keep the entered text,
  authoritative metadata and revision; disable preview of unsaved invalid work
  as today. Avoid nested cards or a second generic alert repeating the same fault.
- Keep the advanced JSON editor. A generated schema form, line navigation,
  automatic repair and automatic activation are outside this mission.

A typed profile-validation failure is a plausible preservation mechanism; the
implementation should choose the narrowest existing boundary that keeps issues
intact. This diagnostic does not prescribe a global error-envelope redesign or
convert its proposal into an accepted architecture decision.

## Limits and validation economy

Only the ten documented malformed definitions and the valid control were measured.
This is not an exhaustive schema, execution-tag or capability-variant audit. It
establishes actual failure sites, not a claim that every input error is unsafe or
that arbitrary stored profiles must be migrated. Creation/adoption/activation and
publication validation were not exercised beyond creating the isolated fixture.

Only documentation and task records remain in the change set. The selector must
classify those explicit paths as documentation; static gates apply. No full E2E
matrix, unit replay or build is justified for the recorded diagnostic alone.
The selector classified both retained paths as documentation. `check:quick` passed
with all 17 package tasks cached; repository spelling and diff checks passed.
`validated/full` remains on `2af412bb4`, the latest completely validated executable
state. The unrelated quoted cache directory is untouched.
