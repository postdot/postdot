# UX-405 — Simultaneous composer edits and explicit conflict resolution

Status: complete
Related contracts: DESIGN.md composer recovery and explicit destination-draft resolution; SPEC-010 JRN-02/COH-02

## Reproduced behaviour

Two real pages in one browser context shared cookies and localStorage. The server correctly refused the second tab's stale PUT with 409. A later successful save in the first tab replaced the shared recovery entry, however, so reloading the second tab offered the first tab's text instead of its own. The baseline failed on the absent second-tab excerpt. Conflict feedback was only a generic autosave status and tooltip, with no version comparison.

Inspection also found that deleting the actor-owned composer recovery point had no revision condition. Creating a post or clearing an old editor could remove another tab's newer recovery draft. The existing PUT revision alone also cannot distinguish a deleted draft from a new draft at the same revision.

## Changes and decisions

- Preserve a tab-local sessionStorage snapshot before the existing shared localStorage fallback. Both are best effort and tolerate an unavailable or corrupt counterpart. Recovery metadata records the known server draft identity/revision and unresolved-conflict state; it is stripped from the existing server content payload. Older recovery entries remain readable.
- Pause automatic writes after a real conflict, keep local editing available, explain why publication creation is unavailable, and offer explicit comparison. A reloaded tab keeps its own version even if the other tab saved again.
- Compare source text/title, target copy, media/tag counts and delivery timing in a responsive dialog. The complete local and saved payloads can be downloaded together. The operator explicitly chooses the saved version or replaces it with the local version; consequences appear before both actions. Nothing is merged automatically and there is still one server recovery point per actor/project.
- Both versions remain available until that explicit choice. Choosing replaces the active contents or stored draft; the optional download retains separate snapshots. This is not permanent version history, a media-byte backup or automatic import functionality. Tab-local recovery lasts for that tab's session; the shared fallback retains its existing best-effort role.
- The web client guards writes with the known draft identity and revision. PUT adds optional `expectedDraftId`; DELETE adds optional `expectedRevision`/`expectedDraftId` query parameters. The store checks them in its existing immediate transaction. No migration, permission change, new server object or transport replacement. Legacy unguarded DELETE remains compatible; the new web client always guards its known-draft cleanup.
- A refused replacement refreshes the comparison, preserving local content. A failed comparison read does not label the saved version as removed or allow a choice against unknown data; explicit refresh recovers it.
- Returning from channel setup must retain the known base while the initial read is pending. A targeted regression exposed an early metadata write that erased that base; corrected. Exact JSON-meaning comparison also recognizes a save already committed while the previous editor unmounted, without ignoring array order or changed content.

The Elysia OpenAPI generator marked an optional DELETE body required even though legacy runtime deletion passed. Conditional DELETE uses optional query guards instead, which preserves runtime compatibility and accurately generates optional parameters. The live schema and portable reference are verified; no exporter or dependency patch was added.

## Validation

Twenty distinct focused browser scenarios pass on the final application code. The combined invocation recorded 18 passes and two collector failures; both corrected collector cases then pass in a focused reprise (18.2 seconds). This is not a claim that the combined invocation exited successfully. The driver corrections use text assertions for the configured contenteditable editor reached through ordinary navigation, and await the explicitly held response before removing its interception. Content, inertness and conflict assertions remain.

Coverage includes:

- Genuine shared-context, same-account 409 conflicts; local edits remain available without repeated automatic PUTs; the second tab reloads its own version after the first saves again.
- Both explicit choices in English/dark and French/light, downloaded local/saved payload contents, another saved revision during comparison, and a refused replacement that refreshes the comparison before retry.
- Failed comparison reads, stale conditional DELETE, deletion/recreation at the same revision, legacy DELETE compatibility, and post creation without erasing newer recovery.
- Same-tab return from channel setup, including a server commit whose response arrives after navigation.
- Existing initialization/discard failures, local-only recovery, media/target formatting, title-only articles, interrupted composition and configured/legacy-editor transitions.

## Limits and next scope

No development publication is created or dispatched; browser mutations use isolated runtimes. No live-provider, physical-device, screen-reader or complete browser-matrix acceptance is claimed. Optional guards cannot retroactively protect requests from older clients that deliberately omit them.

The narrow apps/web/AGENT.md update preserves tab-copy, known-base and explicit-resolution constraints for future authoring changes. Recommended next task: verify recovery isolation across sign-out, sign-in and account changes in the same browser, including lost access. This is a focused follow-up investigation, not a claim of verified cross-account exposure.
