# UX-413 — Session refusal raised only by a media upload

Status: complete
Related: UX-409 (session pause), UX-412 (verification that left this case open)

## Reproduced behaviour

With the text already autosaved, a held upload was released after the current session was revoked. The upload failed with a 401, but the composer only showed the file's Retry action; the "Sign in again" pause appeared only after a later text edit or Create attempt triggered a refused draft write. The new journey failed on the missing sign-in action.

## Changes and decisions

- `MediaAttachmentPicker` gains an optional `onUploadError` callback, called for each failed file with its original cause. The picker does not interpret the error.
- The new-publication page passes `pauseForSessionError`, the same classifier used by autosave and creation (401 or `account_changed`). An upload refusal now pauses authoring and shows the sign-in continuation. The failed file and recovery bytes are untouched, so the existing resume path applies after sign-in.
- Other upload failures (network, size, verification) are not classified as session loss and keep the per-file Retry.

## Validation

- Three journeys in `composer-upload-session.spec.ts` pass; with the pending-media, upload-recovery and session-renewal specs, 24 journeys pass in the combined run.
- Web 299 unit tests and `bun run check:quick` pass.

## Limits and next scope

- The refusal is detected from the failed upload result; a refusal on the picker's library reads or deletions is not routed to the session pause.
- Revocation uses the real sign-out endpoint, not wall-clock expiry. No full matrix, physical-device or screen-reader acceptance claimed.

Recommended next task: route session refusals from the other media picker actions (library listing, deletion, URL import) through the same pause or a consistent sign-in message.
