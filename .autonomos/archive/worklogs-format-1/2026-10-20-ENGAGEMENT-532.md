# ENGAGEMENT-532 — Bluesky conversation replies

## Accepted scope

Owner accepted continuing with Bluesky replies and explicitly selected an outgoing reply history attached to the conversation, without creating Post/Publication/calendar entries. Work directly without delegation.

## Plan

1. Implement validated text-only Bluesky reply creation using root and parent strong references and a retained record key.
2. Persist conversation-owned requests, author attribution and claim/outcome history; apply existing ADR-009 fencing and ADR-037 journal semantics.
3. Use the existing singleton worker/scheduler and project connection; expose editor-only send and member read routes.
4. Extend the current comments disclosure and verify protocol, permissions, recovery and the focused browser journey.

## Boundaries

- Public plain-text replies only, no attachments, moderation, scheduled replies or automatic collection.
- Project editors send; all project members read outgoing history. API keys retain their existing action ceilings.
- Resolve root/parent CIDs immediately before sending; the parent must belong to the stored conversation and the connected DID must match the original publication's DID.
- Persist a request identity before execution, claim before processing and fence immediately before createRecord. Never automatically resend an uncertain outcome.
- Reuse one process and worker. No new service or permanent polling loop.
- No real provider send is authorized for acceptance; use synthetic protocol responses and isolated data.

## Implementation

- The Bluesky package owns live root/parent reference resolution against the fixed public AppView, plain-text validation (300 graphemes / 3000 UTF-16 units), an explicit retained record key, immutable request timestamp and createRecord outcome classification. Foreign-thread references and malformed inputs are rejected before writing. Missing or unexpected acknowledgements, network errors and key collisions remain uncertain. Diagnostics never include provider exception text.
- A generated additive migration, 0014_publication_comment_replies, stores the request identity, project/publication/actor, original connected account and credential identity, content, provider key, claims, lease, effect boundary and outcomes. The existing journal records request/start/completion/recovery in the same transactions. No plaintext credential is persisted in reply rows or exposed in history.
- Requests are bound to an available comment in the latest stored snapshot. Only editors enqueue replies; viewers read paginated history. Replaying a request ID with identical actor, publication, parent and text returns the same request; changing intent cannot reuse it. New endpoints retain the existing API-key action ceilings.
- The singleton publication worker also considers reply event times and processes one reply per round using the shared processNextExternalEffect contract. Stop remains the same awaited scheduler drain. No second worker, queue service, background provider collection or permanent polling loop was added.
- Before dispatch, the original publication DID, pinned connection and credential, original actor's live editor access and the session's actual granted create permission are checked. Refreshed session tokens are saved through the existing encrypted credential store. Live parent/root references are resolved again; connection/access/claim eligibility is checked after preparation and before the write.
- Each request retains a provider-generated TID. @atproto/common-web 0.5.13 was already locked and used by the SDK; it is now an explicit Bluesky dependency for key generation. The request's UUID remains the HTTP idempotency identity.
- First release uses one attempt per request. Confirmed no-effect failures become failed; users can compose a new request explicitly. Interrupted/uncertain effects become ambiguous and are never automatically retried. A 60-second deadline aborts dispatch; late preparation checks the abort/claim before writing. Expired pre-effect claims return to pending; expired claims past the durable boundary become ambiguous and stale completions are refused. The shared executor conservatively marks the boundary before provider preparation, so a crash there can produce a false ambiguous outcome rather than a duplicate.
- Studio adds a plain-text public reply composer to eligible Bluesky comments and an outgoing team history. It shows the connected account, length limit, pending/sending/sent/failed/uncertain states, sanitized optional delivery details, links and older history. A lost HTTP response can be retried with the same request identity. Viewers have no send control. While an open history contains an active request it rereads stored status every two seconds; it never collects provider comments. English/French catalogs cover all new controls and state explanations.
