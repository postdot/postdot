# DB-618 — Release publication claims after pre-effect transaction conflicts

## Scope and decision

Owner authorized the next optimization after merging PR #23. Work is isolated
on `fix/release-unstarted-claims`, based on `3529d5610`.

PERF-617 showed a long tail from running claims abandoned before the provider
call: scheduling recovered, but some jobs waited for the original five-minute
lease. The publication store now catches only recognized serialization/deadlock
failures from its pre-effect transaction. After that transaction has rolled back,
it attempts a separate transactional release, then rethrows the original error
so the existing scheduler backoff still applies.

Release requires the same running claim token, a null effect marker, a lease
later than the supplied operation timestamp, and a scheduled/ready publication.
The guarded update and recovery audit fact commit together. Run time and attempt
accounting are preserved; no delivery retry policy, requested schedule, channel
cadence or lease duration is changed. A new owner, a crossed effect boundary,
an expired claim or any cleanup failure keeps the existing lease-based recovery.
Unknown errors do not trigger early release. This is not permission to clear an
uncertain post-effect claim, nor a general database-outage retry mechanism.

The change is specific to publication claims, the path measured in PERF-617.
Reply, first-comment and notification stores retain their existing behavior.
No generic executor interface or new runtime dependency is introduced.

## Safety evidence

Real store tests inject the conflict at the scheduled-to-ready write, inside the
pre-effect transaction. PostgreSQL exhausts its eight real adapter attempts;
SQLite parity tests inject the same classified error at the store boundary.
The row becomes pending before lease expiry, the recovery fact commits once, and
the next executor pass calls the provider once and succeeds.

Guard cases simulate ownership transfer after rollback, expiry, a durable effect
marker followed by a synthetic acknowledgement error, failure inserting the
cleanup audit, and an unknown pre-effect error. None clears the claim. Audit
failure rolls back the release; the original conflict remains the reported error.
The committed-marker case still becomes ambiguous at lease recovery. Existing
DB-616 before/after-effect recovery tests remain unchanged and pass. A separate PostgreSQL connection also commits the effect marker after cleanup has read the unstarted claim; serialization retry observes that marker and refuses the release.

## Controlled timing probe

The opt-in benchmark gains `--conflict-boundary pre-effect`, injecting the same
scheduled-to-ready failure during seconds 30–35. The default boundary and all
other workload semantics remain unchanged. The parent implementation and the
new implementation use the same driver, disposable databases, default five-minute
lease, four projects, fixed 100 ms provider delay and 16 offered jobs/s for 60
seconds, followed by up to 360 seconds of durable drain. Provider job-ID duplicate
checks, admission checks, durable outcomes and final scheduler health remain
required. Workload runs are sequential on the same developer machine; this is not dedicated hardware isolation.

[Controlled timing results](2026-11-07-DB-618-timing.json):

| Metric | Parent | Early release |
| --- | --- | --- |
| Durable succeeded jobs | 960 | 960 |
| Full drain from arrival start | 348.2 s | 66.0 s |
| Longest intended-offer-to-provider wait | 309.3 s | 7.7 s |
| Wait p95 | 19.0 s | 7.4 s |
| Duplicate provider calls | 0 | 0 |
| Admission violations | 0 | 0 |
| Final scheduler | started | started |

Both runs used the same seconds 30–35 fault window. Dynamic retries produced 45
injected statement failures in the parent run and 48 with early release. The
parent also encountered one natural serialization failure; the new run reported
only the three injected recovery episodes. These are single runs, not a fixed
error-count replay or a statistical throughput comparison. The intended change
is removal of the pre-effect lease-wait tail when owner cleanup can commit.
All four projects received exactly 240 provider calls in each run; no pending,
running or ambiguous job remained. Producer lag p95 stayed below 8 ms.

Reproduce against each implementation using the same driver:

```sh
POSTDOT_TEST_POSTGRES_URL=postgres://... bun scripts/benchmark-worker-admission.ts --engine postgres --seconds 60 --rate 16 --effect-ms 100 --conflict-seconds 5 --conflict-boundary pre-effect --drain-seconds 360
```

The parent control imports the pre-change runtime from the PR #23 worktree,
whose runtime source matches the merged base. The new driver changes only fault
placement/report metadata, not the actual worker or synthetic provider behavior.
No shorter lease, different concurrency limit or provider retry is responsible
for the result. Cleanup remains best effort; these timings are not a publication
deadline guarantee or a higher production capacity ceiling.

- PostgreSQL workflow-store suite: **31 passed, 2 skipped**, including the real
  competing-connection marker race. SQLite workflow-store tests pass as well.
- API workflow suites: **146 passed / 1 PostgreSQL-only skip** on SQLite;
  **147 passed** on PostgreSQL.
- `bun run check:quick` passes. The runtime change is confined to the publication
  store; no UI, migration, provider transport or generic executor change.
- Both controlled workload commands succeeded and ended with healthy schedulers.
- Owned temporary PostgreSQL container stopped and removed after qualification.

The next useful qualification is a longer natural-contention run of this release
path. Reply, first-comment and notification claim cleanup can be evaluated
separately against their own state and attribution contracts; they are not
silently opted into this publication-specific optimization.
