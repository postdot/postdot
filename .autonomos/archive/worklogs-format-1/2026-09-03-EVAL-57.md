# EVAL-57 — Validate one controlled automatic LinkedIn image publication loop

- Scope: one operator-approved automatic LinkedIn organization publication with text and one image
- Branch: `eval/eval-57-image-outcome`

## Objective

Exercise the provider path that combines Postbot's verified media lifecycle,
immutable execution revision, automatic worker delivery, and the LinkedIn
organization destination. Confirm the durable Postbot outcome after the real
provider response without turning this recurring validation into a release gate.

## Safety boundary

- Use only the existing operator-selected project and connected LinkedIn
  organization channel.
- Use a disposable, clearly identified smoke-test publication and one
  non-sensitive Postbot brand image.
- Do not publish to a member profile, perform a bulk action, retry an ambiguous
  provider result, or delete external content automatically.
- Do not record provider identifiers, credentials, session details, external
  publication identifiers, or the exact test content in repository artifacts.
- Obtain action-time approval immediately before the worker causes the external
  publication effect.

## Plan

1. Verify the clean `main` baseline and Autonomos task state.
2. Prepare one local automatic publication through the dashboard with one
   verified image and a future due time.
3. Obtain action-time approval naming the selected destination and the exact
   disposable content before triggering delivery.
4. Verify the provider acknowledgement, worker state, durable publication
   outcome, media delivery checkpoint, audit trail, and dashboard state.
5. Record the result, run the quality gate, and integrate through a focused
   remote pull request.

## Preparation and execution

The local dashboard draft was created through the normal compose flow with one
generated PNG derived from the tracked Postbot mark. The draft was queued for
automatic delivery to the existing connected organization channel. The worker
later attempted the due job before this session resumed because the local API
runtime remained active while the draft was waiting.

The first attempt failed while starting the provider media delivery: the delivery
store used its wall clock for `created_at`, while the worker used the logical
workflow processing timestamp for `last_attempt_at`. A millisecond skew violated
the SQLite timestamp invariant before the media representation was opened or a
provider upload request was invoked. The durable row remained `pending` without
a remote media identifier, so this attempt provided no evidence of an external
provider media effect. The publication was conservatively classified as
ambiguous by the external-effect boundary and was not retried blindly.

FIX-58 aligned provider media reservation timestamps with the workflow
processing clock and added a skewed-clock regression test. The focused tests and
the repository quality gate passed. After action-time approval, the same
disposable image workflow was executed through the real worker. The provider
acknowledged the upload and publication; Postbot persisted the job as succeeded,
the publication as published, and the provider media delivery as uploaded. The
dashboard queue displayed the target as published.

The scheduled time was advanced only in the local database for this approved
smoke test so the worker could be exercised immediately. No external content was
deleted automatically.

## Outcome

- First attempt: safely retained as an ambiguous local record; no provider media
  request was reached.
- Fixed attempt: provider acknowledged the image publication and all durable
  Postbot checkpoints reached their successful terminal states.
- Dashboard verification: the target was displayed as `Published`.
- Safety boundary: no provider identifiers, credentials, session details,
  external publication identifiers, or exact test content are recorded here.

## Handoff

The controlled image loop is complete. Repeat this validation periodically with
a fresh disposable publication when provider or workflow changes warrant it.
Keep all external identifiers and exact test content out of the worklog.
