# UX-294 — Draft application and scheduling consequences

Status: complete; root integration gate passed.

## Findings and accepted boundaries

The existing promotion contract selects an immutable target revision. With no scheduled time the publication remains a draft; with a time it becomes scheduled. Clearing the time returns it to draft. Scheduled automatic delivery queues the selected revision; manual delivery remains human work. This pass changes no API, target ownership, approval requirement or delivery contract.

Two concrete defects were identified:

- Application had no pending guard or progress state, allowing repeat clicks and edits while the selected target request was in flight.
- A content-only application parsed the minute-resolution date widget again and silently removed seconds/milliseconds from an existing schedule. A persisted browser test exposed this difference.

## Changes

- Guard in-flight promotion synchronously and expose its pending state on the action.
- Temporarily disable source/destination editing, scheduling, channel changes and conflicting lifecycle actions during that request.
- Defer incoming editor reconciliation until the promotion request settles, preserving existing reactive refresh behavior.
- Preserve the exact stored timestamp when the schedule was not edited.
- Name the existing result: use a version, schedule, update a scheduled publication, or return to draft. Success messages use the same result rather than target-revision jargon.
- Keep plain progress text and existing iconography; no new dependency or bespoke loading widget.

## Verification

- Existing detail lifecycle browser baseline passed before changes.
- Two real persisted promotion journeys passed: draft and scheduled manual publication.
- Double-click sends one promotion request and creates one target revision; target editor becomes non-editable while the request is held.
- Applying destination content preserves the shared source and sibling publication; a scheduled timestamp is retained exactly.
- Clearing the date exposes Return to draft and produces a persisted draft with no date, preserving selected content.
- Initial root gate passed 70 browser scenarios; one Discord spoiler contrast check failed just after hiding formatted content. Its unchanged isolated replay passed. The test now waits for hidden/visible content before running accessibility analysis; the complete rerun passed.

Browser scenarios use isolated runtime data and do not contact a real publisher. Automatic job creation was traced through the accepted specification and store transaction; no live automatic publication was attempted.

- Final `bun run check` passed: formatting, lint/spelling, type checks, unit tests, 71 browser scenarios, two password-reset scenarios and all 17 build tasks.
- Pending-state screenshots were reviewed against the existing detail layout.

## Recommended continuation

Review failed application requests and connection readiness. The generic failure path leaves the editor in an error state; inspect whether the operator has a clear reconciliation path that preserves local work before considering retry behavior. Treat a lost response as an unknown result until server state is read; do not silently retry promotion or delivery.

No new design or ownership decision is required: labels now describe the existing accepted transitions. No AGENT.md update is proposed.
