# UX-296 — Automatic destination readiness in publication detail

Status: complete; full integration gate passed.

## Findings and boundaries

Publication detail showed lifecycle and delivery errors but had no current connection state or direct channel repair path. A scheduled or failed publication can still require connection repair. Scheduling success is not proof of destination readiness.

Connection state already belongs to the project dashboard query and its reactive refresh. This pass consumes that existing state, adds no network polling, performs no credential check against an external platform and changes no API or delivery semantics.

## Changes

- Integrate missing, revoked and reconnect-required connection information into the existing lifecycle surface for upcoming automatic work.
- Link directly to the affected channel's connection row; preserve project routing and use the existing connection dialog there.
- Make connection repair primary while a connection problem is known; retain explicit retry as a secondary action rather than removing it or changing its contract.
- Retain consultation access for viewers, without presenting them as able to reconnect.
- Keep active connections, manual delivery and completed/historical publications quiet. An omitted connection input is unknown rather than a known missing connection.
- Add stable channel row anchors and sticky-header scroll spacing, including manual-profile rows.
- Preserve existing scheduling, cancellation and explicit retry behavior. Opening repair does not perform any of these actions and does not claim to resume delivery.

## Verification

The focused browser journey passed. It uses persisted article content with browser-only automatic lifecycle/connection fixtures; it does not claim to execute a real automatic publication. Missing, revoked and reconnect-required cases were reviewed in dark and light themes at 1280, 820 and 390 pixels, with accessibility and overflow assertions and inspected captures.

The targeted link places the correct row in the viewport and its action opens the existing DEV.to credential dialog. Viewer presentation stays consultative; active/manual/published cases hide the connection notice. The browser sent no project mutation request, and actual stored source content, draft, publication and selected target remained unchanged.

The first root gate was interrupted for a screenshot-driven hierarchy correction: repair must visually precede retry when the connection requires repair. The final `bun run check` passed after that change: 74 browser journeys, two password-reset journeys and 17 build tasks. The final mobile capture confirms connection repair is primary and retry secondary. No real publisher was contacted.
