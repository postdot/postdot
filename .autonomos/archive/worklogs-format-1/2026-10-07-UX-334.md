# UX-334 — Discord Editor, Preview and Payload Parity

- Base: `df7249ca6`.
- Status: diagnostic complete; no product changes.

## Findings

Two source-preservation defects were reproduced through a native edit in the
installed `ConfiguredPublicationEditor`, hosted by `/editor-lab`:

| Input before editing | Serialized output after adding an exclamation mark |
| --- | --- |
| `>>> Quote` followed by a newline and `next` | `> > > Quote` followed by two spaces, a newline and `> > > next!` |
| `<@123456789012345678>` | `&lt;@123456789012345678&gt;!` |

Neither input activates `requiresSourceMode`. Initial loading alone preserves the
original string; the conversion happens on an editor update, which serializes the
parsed document. Thus an unrelated edit can change native destination syntax.
The control `**bold** __underline__` retains both formatting marks after editing.
Equivalent delimiter normalization is not treated as a defect.

The preview also interprets `>>> Quote` as three nested CommonMark block quotes.
Discord documents this marker as a multiline quote. Subtext `-# Small text` stays
literal in the preview and round-trips unchanged: this is a rendering gap, not
source loss. Mentions are displayed as literal identifiers rather than resolved
identities; no remote identity resolution was attempted.

## Existing boundaries that work

Discord enables emphasis, underline, strikethrough, spoilers, inline code, code
blocks and block quotes. Existing renderer tests cover these combinations, escaped
syntax and security boundaries. Headings, lists and masked links trigger the
existing source-mode safeguard rather than silently going through unsupported
rich-editor nodes. These source-mode inputs must not be judged from a raw codec
round-trip that the application never performs.

The Discord publisher sends the input string unchanged. An isolated simulated
fetcher captured this body without a network request:

```json
{"content":">>> Quote\nnext <@123456789012345678>","allowed_mentions":{"parse":[]}}
```

Notification suppression is intentional and separate from text preservation.
The adapter does not repair editor conversions; altered bytes can reach its
payload. No real Discord publication was performed.

## Evidence and reproduction

A temporary Playwright scenario switched `/editor-lab` to Discord, entered each
input through Source, checked the unchanged serialized text, switched back to the
rich editor and typed an exclamation mark at the end. The observed output above
came from the production editor component, not a replacement implementation.
One scenario passed in 2.5 seconds (4.7 seconds including the isolated harness),
with one worker and no retry. The temporary scenario was removed after diagnosis.

A separate Bun probe exercised `createMarkdownCodec`, `requiresSourceMode` and
`renderToStaticMarkup(PublicationDiscordBody)`, confirming source-mode decisions,
serialization and nested quote/subtext rendering. The publisher probe used
`createDiscordPublisher` with an injected fetcher and fictitious credentials.

These are direct component and adapter observations, not an authenticated
composer-to-provider journey. No claim is made about native client appearance,
custom emoji resolution, embed generation or every Discord syntax combination.

## Reference

The [official Discord formatting guide](https://support.discord.com/hc/en-us/articles/210298617-Markdown-Text-101-Chat-Formatting-Bold-Italic-Underline),
consulted on 2026-10-07, documents multiline quotes with `>>>`, subtext with `-#`,
and the supported emphasis, heading, list and link forms. It supports the syntax
comparison, not a claim of pixel-level preview fidelity.

## Recommendation

UX-337 should first preserve native syntax through unrelated rich-editor edits.
Evaluate the existing source-mode safeguard against dedicated extensions; avoid
expanding capabilities or changing mention notification policy in this repair.
After source preservation, a separate preview pass can address multiline quotes
and subtext. This diagnostic does not choose an implementation or claim that a
literal mention preview is equivalent to Discord's resolved rendering.
