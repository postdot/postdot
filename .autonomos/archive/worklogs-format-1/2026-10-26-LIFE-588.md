# LIFE-588 — Project and workspace lifecycle

Implemented GitHub #10 under accepted ADR-094. Owners can archive, restore or
permanently delete active or archived projects/workspaces after reviewing impact.
Deletion with existing history is supported; remote publications remain untouched.

## Delivery

- Versioned SQLite migration adds lifecycle state, non-cascading minimal receipts
  and durable object cleanup ownership. SQL guards prevent new content/effect
  admission without preventing already-started effects from recording outcomes.
- API previews include counts, publication states, pending/uncertain/active work,
  workspace projects and a fingerprint checked inside the mutation transaction.
  Cancellation is explicit; OAuth attempts expire. Pre-effect claims are cancelled;
  effects already sent finish before physical removal. Restoration never requeues.
- Workspace retirement aggregates projects and memberships. A manageable active
  replacement is required for the default workspace; restoring a workspace leaves
  its projects archived. Human accounts and unrelated workspaces remain intact.
- User-owned keys inherit live roles and scope, with project:manage and explicit
  project:permanently_delete action ceilings. Former initiators gain no continuing
  permission on live resources; only the initiating user can read the minimal
  receipt after cascading deletion. Instance admin status alone grants no content.
- Studio provides impact/confirmation dialogs and an archived-resources screen,
  read-only archived project pages, and pending cleanup progress. Navigation stays
  usable. English/French copy and narrow-screen behavior are covered.
- CLI project/workspace impact, archive, restore and delete commands use typed
  transport and require the preview fingerprint for writes; they do not silently
  repeat destructive requests. Authored guidance is in apps/docs only.
- Storage cleanup survives a database reopen, storage outages and configured-store
  mismatch, respects complete-backup fences, and retries idempotently.

## Corrections found during validation

The exact OpenAPI route inventory now includes release identity and lifecycle
routes. A worker fairness assertion assumed a fixed completion order for two
concurrent projects; it now requires both projects in the first two slots.
The reply SQL guard initially also blocked an already-sent reply's outcome and
lease renewal. It now allows the existing running owner to finish; a regression
case proves this while refusing new admission.

The first broad browser invocation incorrectly used production mode for tests
that intentionally activate the development-only legacy editor and editor lab.
It was interrupted rather than changing those assertions or exposing development
features in production. The normal matrix and focused production checks are
recorded below. The normal matrix finished with 141 passes and two failures:
initial tag-catalog retry visibility and the WEB-314 observed-refetch assertion.
Both passed in the immediate focused reproduction without changing assertions.
The access-refetch case also passes in the final development rerun; no assertion
was changed. Its initial timeout remains intermittent evidence, not proof that
all 143 passed in one invocation. Investigate if it recurs rather than widening
waits or treating a targeted pass as proof of a product fix.

The tag case reproduced again in the final development group. Constant 503
responses combined with automatic backoff/restarts kept its initial catalog in
Loading instead of reliably presenting explicit Retry. Catalog reads now surface
failure without automatic retries, retaining the existing explicit retry control
and last-known catalog behavior. All four tag scenarios pass after the correction,
and its error/retry case also passes against production assets. No wait or
assertion was weakened. One workspace test locator was scoped to its Members
panel because transient group controls shared the same accessible button name;
its invitation, access, keyboard and accessibility assertions remain intact.
