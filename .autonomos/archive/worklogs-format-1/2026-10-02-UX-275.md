# UX-275 — Notification follow-up and touch targets

## Scope and evidence

Reviewed NotificationInbox, the publication detail loader, notification persistence,
ADR-038 and ADR-058. Recipient ownership is distinct from current project access:
the global inbox query filters by recipient user and optional project, not current
publication visibility. A notification reference is therefore not proof that its
subject can still be opened. The detail loader currently delegates errors to the
root boundary; adding raw links would not resolve unavailable subjects gracefully.

## Bounded correction

Read and archive remain separate explicit operations. Increased their targets
from 24 pixels to 44 pixels on narrow layouts and 32 pixels on desktop, preserving
the existing row composition, localized names and four-pixel separation. No automatic read mutation or permission change was introduced.

Extended the existing isolated localized notification journey with measured
hit-area/separation assertions and screenshots at 1280 and 390 pixels. Existing
populated fixtures cover delivered, failed, ambiguous and custom messages; the
suite also exercises loading/error/retry and unread badge behavior.

Full `bun run check` passed: formatting, spelling/lint, typing, unit tests,
49 browser scenarios, two password recovery scenarios and 17 build tasks.

## Navigation behavior — approved and implemented

The operator job is to reach the affected publication, not manage notification
metadata. The owner explicitly selected opening without marking read. The subject title
is the explicit navigation target; read and
archive visibly separate. Avoid another whole-row click target or a repeated
Open button beside a clickable title. Keep an unread notification unread when
opened: this preserves current explicit read semantics and avoids coupling a
failed navigation to an acknowledgement.

| Situation                                | Behavior                                                                                                                                              |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Existing publication, access allowed     | Close the inbox and open the publication in its own project context. Preserve explicit read/archive state.                                            |
| Project removed or access revoked        | Keep the inbox open with a compact item-local unavailable message. Do not disclose new subject details. Keep recipient-owned read/archive operations. |
| Publication removed                      | Same unavailable result; do not remove or automatically archive the historical notification.                                                          |
| Temporary network/server error           | Item-local retry; retain the notification and its read state.                                                                                         |
| Unknown or projectless subject           | Plain notification text until an explicit supported route exists.                                                                                     |
| Subject disappears after an access check | Publication route needs a deliberate unavailable state with a return path; a preflight alone cannot guarantee continuity.                             |

Do not infer access solely from the client project list. Fresh server authorization
remains authoritative. Resolving navigation must cover both preflight and route
failure, including the race after a successful lookup. Prefer reusing the existing
publication read endpoint before considering any new domain endpoint.

The alternative of marking read after a successful open was presented and not
selected. Existing read/archive mutations remain authoritative. Opening first
checks the existing publication editor read endpoint, then navigates; 403/404
produce the same generic item-local unavailable message. Other lookup failures
remain local and the title can be retried. The detail route has its own unavailable
state and an Overview link for a subject that disappears after the check.

## Files and next steps

Changed the notification component, publication detail error boundary, English
and French catalogs, browser tests and Autonomos tracking. The two focused
journeys passed: all supported outcome titles open by keyboard; unsupported
subjects remain plain text; simulated 404, 403 and 503 responses stay local; a
simulated deletion race reaches the route-specific return state. Opening never
produces read/archive requests. Reviewed isolated desktop and mobile captures,
including light/dark unavailable states. Tests use isolated data and simulated
errors, not the owner's live project or real permission changes.
