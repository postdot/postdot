# UX-340 — Execution-Based Channel Readiness

- Base: `9fa243926` (implementation); proposal began at `c56537586`.
- Status: complete; full validation passed. The owner approved the enriched list on 2026-10-07.

## Operator contract

A manual channel is usable without a publisher connection, whatever its profile
identity. A declarative HTTP profile offers the existing HTTP connection action.
A built-in execution uses its declared contract identifier to choose the existing
provider connection flow, rather than inferring that flow from profile identity.
Unknown provider contracts must not be silently offered an HTTP connection.
Archived and viewer behavior, publisher compatibility and credentials remain
unchanged.

## Existing reads and alternatives

The channel list joins the active profile version but returns only its identity.
The profile-state endpoint exposes active and draft profile definitions. It could
be fetched separately for each row without changing the public contract, but
would add one request per channel, extra loading and failure states, and redundant
profile definitions just to select a connection action.

Recommended: add a small execution summary to the channel list read model,
derived from the version joined by `channels.profile_version_id`. Expose the kind
and, for built-in execution, the contract identifier only. Do not expose the
whole declarative HTTP definition, authentication bindings, or a draft contract.
Do not add a database column or migration. Keep profile identity for labels,
avatars and management; it is not a connection capability.

An explicit enriched list response was selected instead of changing unrelated
mutation responses or the domain Channel entity for a presentation read. Browser
cache updates retain enriched metadata on lifecycle updates; activation refreshes
the list from the active version.

## Implementation plan (executed)

1. Derive the summary from the existing active-version list read and expose it
   through the API schema and client types.
2. Resolve manual, HTTP and known built-in provider actions from that summary;
   preserve read-only and archive controls and reject unsupported action guesses.
3. Retain deterministic list/readiness tests and one browser regression using
   supplied manual and webhook profiles, with active-version changes if the
   existing activation fixture permits them without altering publication rules.
4. Run the ADR-077 selector on actual modified paths and choose validation once:
   a DB/API read-model change may require the complete control.

## Implementation

The list joins the same active profile version as before and projects an execution
summary from its stored definition: `{kind: "manual"}`, `{kind:
"declarative_http"}`, or `{kind: "built_in", contractId}`. The explicit list item
read model and API schema are additive; Channel creation, lifecycle and editor
entity responses remain unchanged. No migration, new service or per-row HTTP
request was added. The summary does not expose execution revision, HTTP mode,
authentication bindings, schema or the full profile JSON.

The connection panel resolves its actions and provider-application requirements
from this summary. Manual rows use the existing Manual badge; declarative HTTP
uses its existing setup dialogue; custom identities with a known built-in
contract use that provider's dialogue. An unknown built-in contract gets a
localized explanation without an HTTP fallback. Labels and avatars continue to
use profile identity. Read-only and archived controls are still hidden as before.

Creation reloads the channel list before adding a new destination to the composer;
rename, archive and restore cache updates retain execution metadata which is
absent from their entity response. Profile activation follows the existing
project refresh path. No publisher compatibility, authorization, notification,
publication or profile activation policy changed.

## Retained proofs

- Store regression: custom manual summary; an HTTP draft not yet activated leaves that
  summary unchanged; activation changes both the active version and summary;
  HTTP configuration is omitted; a custom native identity reports its contract;
  an outsider cannot read the list. Four tests in the existing creation file pass.
- Existing API creation regression now reads the actual list response and asserts
  its manual summary and absence of profile JSON/schema. The focused test passes.
- The retained connection-recovery spec adds one journey. It reads both starter
  definitions from the real creation dialogue, creates the manual channel there,
  and asserts its immediate Manual state. HTTP and custom native controls open
  the appropriate dialogues, while an unknown contract offers no connection.
  Rename/archive/restore retain readiness. The manual row is inspected at 1280,
  820 and 390 pixels with no page overflow; narrow screenshot is readable.

The final focused browser journey passes in 8.9 seconds (11.4 with harness). No
provider connection was submitted and no real credential was used. One earlier
run failed on my new locator (`Rename` instead of `Rename channel`); only the
locator was corrected. Importing the web starter module into the root E2E scope
also failed type checking because its alias belongs to the web project; reading
the actual dialogue removed this dependency and strengthened creation coverage.
A new API assertion initially lacked its response type annotation; corrected
before the full browser matrix ran.

## Validation decision

The selector reports the full 39-file matrix for the changed read model, client
and shared dashboard context. A first gate stopped during root type checking,
before browser tests. The final control was launched on the final executable
state, with the installed Playwright browser path explicitly provided. No

The code supports execution-based connection setup for all declared execution
kinds. This does not claim provider-native publishing for arbitrary custom
schemas, pixel fidelity, or exhaustive layout coverage of every provider.
