# DB-612 — Instance topology and multi-instance coordination

Owner decisions (2026-11-07): plan approved; background runtimes run on one elected
leader instead of distributing job claims with `SKIP LOCKED` (ADR-097 §7 amended).

## Inventory of in-process coordination (before)

Realtime wakeup hub (SSE), draft-change signals, work-scheduled replans, video preview
queue, email settings cache, OAuth credential-refresh queue, lifecycle in-flight
request/write counters, media preview/purge exclusion, notification projection and
email runtimes, worker, media maintenance. Each assumed a single process.

## Delivered

- Topology by construction, reported by startup logs and `/ready` (`topology`):
  SQLite → one server (runtime lock file); PostgreSQL + local media → one server
  (session advisory lock with heartbeat; a lost lock drains and exits 1);
  PostgreSQL + S3 → several servers.
- `InstanceCoordination` (`@postdot/db`): local (single) or PostgreSQL. Signals travel by
  `LISTEN/NOTIFY` (`postdot_signals`; project lists chunked under the payload limit);
  a reconnect triggers `resync` (streams reread the journal, the leader replans).
  Leadership is a session advisory lock on a reserved connection with a `pg_locks`
  heartbeat; a lost leadership drains and exits 1 so the orchestrator restarts the
  server as a follower. Followers serve HTTP and are ready when the database answers.
- Signals: `projects` (commit observer → every instance's realtime hub; projection and
  email on the leader), `work`, `media` (previews requested on followers), `email-settings`
  (every instance reloads, leader replans), `draft` (draft viewers on any instance).
- `SqlDatabase.exclusive(key, op)`: cross-process exclusive section outside
  transactions (SQLite: in-process queue; PostgreSQL: advisory lock on a reserved
  connection). Used by OAuth credential refresh and by media preview writes versus
  physical purge (replaces in-memory maps).
- Lifecycle cleanup waits `cleanupGraceMs` (the upload lifetime) with several servers,
  covering object writes in flight on another server.
- Expand/contract migration policy: older servers keep running on a newer schema;
  `runMigrations` reports `newer` migrations and the API logs them.
- PostgreSQL runbook (`apps/docs/.../postgresql.mdx`): topology table, multi-server
  requirements, rolling releases, `pg_dump`/`pg_restore`, password recovery, collation.
  Collation decision: any collation works; ordering of names follows it (documented).
- Offline password recovery on PostgreSQL: `account recover-password --database-url`,
  one transaction (hash, sessions, reset links); confirmation by database name before
  connecting.

## Verification

- Contract tests on both engines for `exclusive`; on PostgreSQL across two independent
  pools; instance-lock and leadership loss detected after `pg_terminate_backend`.
- `scripts/multi-instance.test.ts`: two real API processes on PostgreSQL + an S3
  stand-in. One leader, one follower; a stream on the follower wakes for a change made
  through the leader within 5 s (the stream otherwise waits 15 s); after SIGKILL of the
  leader the follower takes over; SIGTERM exits 0. Negative control: with project
  signals disabled the stream test fails (a first version passed falsely because a
  dangling read swallowed the event; fixed by reusing the pending read).
- check:quick; db 356 SQLite / 368 PostgreSQL; auth 20/20; API 567/567; scripts 117 (+2 PG).
- CI: the PostgreSQL job also runs the multi-instance test.

## Limits

- The lifecycle impact preview's "active requests" count is per server.
- Throughput does not scale with servers: background work runs on the leader.
- Local test cluster: the environment stops background processes between turns; the
  PostgreSQL test server is restarted when needed.
