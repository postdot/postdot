# PROV-569 — Provider integration boundaries

## Authorization and scope

Owner approved static typed provider modules across all nine existing integrations, with separate protocol/server/browser ownership, provider-owned configuration and engagement rules, extension proof and grouped validation. This is one coherent migration, not repeated per-provider approvals. No new provider capability, real provider call, public release or remote push is authorized.

## Plan

1. Define static provider contracts and composition points.
2. Migrate connection, authoring, constraints and preview knowledge in the web client.
3. Consolidate server configuration and persistence policies while preserving invariant enforcement.
4. Prove a synthetic extension, run affected and milestone checks, crystallize and integrate locally.

## Validation sequencing

Finish all unit/pretest, type-generation, build and container operations before starting browser validation. Freeze web files and avoid Docker start/stop during browser runs. Inspect failure totals across complete logs, not only the last successful cases.

## Ownership and extension evidence

The comparable audit scans TS/TSX files in API, web, DB and core, excluding tests,
stories and provider directories, for equality/inequality against the nine literal
provider identities. HEAD had **34** matching files; the final tree has **one**,
`editor-experiment-page.tsx`, which labels a development-only demo dialect. This
is a bounded source audit, not a claim that every provider string disappeared.

The synthetic module is test-only, not a shipped tenth integration. It enters the
ordinary browser and versioned worker registries and supplies a persistence policy
with visibly different normalization. Tests cover unknown/manual refusal,
duplicate identities, access, receipt arming and revoked-credential claim refusal.
No production shared feature or store gains a synthetic-name branch.

For a basic additional publishing integration, the required application edits
outside its provider directory are two server composition files
(`providers/registry.ts` and `providers/routes.ts`) and two browser composition
files (`providers/registry.ts` and `providers/api.ts`). Optional rich dialects or
engagement add their corresponding capability registration. Provider application
persistence still requires an explicit schema migration for a new application
identity; new workspaces retain the existing manifest/Docker obligations. These
are deliberate boundaries, not omitted extension work.

## Changed areas

- `apps/api/src/providers/<provider>`: nine server integrations, policies, runtime,
  typed routes, worker revisions, analytics and engagement ownership.
- `apps/web/src/providers/<provider>`: nine browser definitions, dialogs, forms,
  typed API methods, authoring controls, previews and the Discord dialect.
- Shared API project services, web features and API transport consume the new
  contracts. `packages/core/src/provider-*-policy.ts` describes injected policies;
  DB application/comment/reply stores retain their invariant enforcement.
- Existing tests follow relocated modules; extension tests cover new boundaries.
  ADR-091 records the accepted architecture. API/web AGENT guidance records only
  reusable ownership rules. Task and issue tracking close this coherent slice.
