# UX-327 — Profile authoring identity and fingerprint ownership

- Base: `24a70dc2f`.
- Status: diagnosis complete; no product implementation.
- Committed scope: task tracking and this diagnostic/proposal only.

## Reproduction, not just a code hypothesis

A temporary Playwright probe used the existing isolated API/web harness, created
its own account, project and manual channel, and exercised the actual Edit profile
JSON field and Save draft button. It was removed after diagnosis. No user project,
provider, shared database or production configuration was modified.

| Step | Observed result |
| --- | --- |
| Change body limit to 900, retain both original fingerprints, save | 200; new draft version 2, revision 1 |
| Change the saved draft's limit to 800, retain its schema fingerprint, save | 400 `invalid_content`; immutable schema identity collision |
| Read saved state after refusal | Identical to the previous saved draft |
| Set schema fingerprint to an arbitrary `operator-chosen-…` string, retain original complete profile fingerprint, request version 999, save | 200; same draft ID, version 2, revision 2 |
| Change profile identity | 400; identity change explicitly prohibited |
| Change origin from `built_in` to `custom` | 400; origin change explicitly prohibited |
| Create another manual channel, edit its first draft to limit 899 with original fingerprints | 400; same shared compiler collision |
| Read original active profile after these operations | Unchanged |

The actual UI displays only `Profile action failed` / `The request could not be
completed.` for the schema collision. The temporary probe initially expected the
specific cause in the alert and failed; its corrected assertion recorded the
actual generic message. The final full probe passed in 8.5 seconds including the
harness. This is diagnostic evidence, not a retained regression suite.

A separate isolated compiler experiment confirmed the dependence on cache state:
compiling schema A succeeds; compiling schema B under the same identity/version/
fingerprint in the same compiler fails with `profile.schema_hash_conflict`;
compiling B in a fresh compiler succeeds. This does not prove a live server restart
path, and a restart is not a proposed remedy. It proves that the collision guard
cannot independently establish fingerprint correctness.

## Ownership and mechanism

`channel-profile-store.ts` normalizes the draft to the active profile's identity,
origin and next version. The caller cannot change identity or origin; the supplied
version is replaced. The store creates the version record ID and maintains its
optimistic revision. An existing draft is updated without advancing its profile
version. These are distinct concepts and should not be presented as editable JSON
metadata.

Both fingerprints are currently caller-supplied nonblank strings, stored verbatim.
Built-in definitions themselves use symbolic `sha256:…` values rather than actual
hexadecimal digests. Therefore it would be incorrect to claim existing values are
cryptographically verified content hashes or retroactively reject them.

The compiler cache key is profile identity, version, schema fingerprint and
execution contract ID. Its canonical schema comparison catches different schemas
reusing that key. The key is not channel-scoped, explaining the second channel's
refusal. This guard is useful and must not be removed to make editing work.

Complete profile fingerprints also survive in target and approval snapshots;
promotion checks both fingerprints along with the selected profile version and
content. Stored profile mapping checks JSON metadata against record columns.
Changing historical fingerprints would therefore cross persistence, approval and
execution boundaries; it is outside this proposal.

Relevant implementation locations:

- `packages/db/src/manual-store/channel-profile-store.ts`: draft normalization,
  compilation and optimistic revision checks.
- `packages/core/src/channel-profile.ts`: nonblank fingerprint validation,
  canonical schema comparison and compiler cache.
- `packages/core/src/profile-presets.ts`: symbolic built-in fingerprint values.
- `packages/db/src/manual-store/mappers.ts`: stored metadata consistency.
- `packages/db/src/manual-store/publication-promotion-store.ts`: approval snapshot
  consistency checks.
- `apps/web/src/components/channel-profile-editor-dialog.tsx`: exposes the whole
  definition and requires manual fingerprint management.
- `apps/web/src/lib/api.ts`: generic localized error formatting, not the remote
  validation message.

## Recommendation requiring approval: UX-328

Let Postbot own technical metadata for newly edited drafts. The server is the
preferred boundary because API clients and the web must follow the same rules.
Keep content schema, declared bindings, capabilities and optional execution
configuration operator-authored; show identity, origin, version and fingerprints
as read-only metadata. Initially keep the advanced definition JSON editor rather
than introducing a broad form builder.

Before implementation, specify the canonical representation and exact inputs:
normalize server-owned metadata first, derive a schema fingerprint from the
canonical content schema, and derive a complete definition fingerprint excluding
its own fingerprint field. Specify treatment of derived schema metadata, version,
execution configuration, ordering and no-op saves. Retain compiler validation,
collision detection and expected revision guards. Hash implementation belongs in
shared domain tooling compatible with Bun, not duplicated inside React.

Apply this only at the authorized draft-save boundary for newly saved definitions.
Do not rewrite existing active, superseded, historical or selected definitions,
change built-in packaged values, automatically migrate publication drafts, or
change activation/approval semantics. Explicitly decide whether the existing API
continues accepting old fingerprint fields while overriding them, or needs a
separate authoring input shape; that compatibility decision is not made here.

Credible alternatives:

1. Keep caller-owned fingerprints and explain the manual procedure. Smallest
   change, but requires operators to manage global identity conventions and does
   not establish correctness; not recommended.
2. Compute fingerprints only in the web editor. Improves one client while API
   callers still face the same hidden ownership problem; not recommended.
3. Compute fingerprints at the server's draft-save boundary and make metadata
   read-only. Recommended, but changes the save contract and requires explicit
   owner acceptance before implementation.

This proposal is not an accepted ADR and no implementation is started.
