# DEV-414 — Production entrypoint under a startup termination

<!-- cspell:ignore opencode xhigh tini -->

## Plan

1. Establish the parent ground truth on the production path: the built bundle as a plain process, and the same bundle as PID 1 in a container.
2. Register a bounded delegated mission for a committed regression that exercises the production bundle, and review it against the acceptance criteria.
3. Integrate, clean up, and record the evidence and the durable guidance.

## Context

DEV-412 corrected the API so that a termination received during the startup window runs the same drain as a running server and releases the runtime marker. DEV-413 proved the development launcher path. The production path is different in one decisive way: the container runs the API as PID 1, and the kernel does not apply the default action of SIGTERM to PID 1. An API that has not installed a handler therefore IGNORES the stop signal entirely.

## Parent ground truth, established before the mission

Production bundle, built with `bun build ./src/index.ts --outdir ./dist --target bun --minify` (3226 modules, about 170 ms), run as a plain process with the production environment, temporary database, media and web-assets directories, and synthetic secrets:

- The runtime marker appears at the first statement of the startup.
- A SIGTERM in that window ends the bundle with exit code 0 in about 105 ms, logging `[postbot-shutdown] SIGTERM received; draining worker and runtimes` and `shutdown complete with exit code 0`.
- The API never served, the marker was released, and the next start of the same bundle served the health endpoint and released the marker again.

Same bundle as PID 1 in a container (`oven/bun:1`, `--network none`, an isolated `/data` directory):

| Deployment shape | Bundle | `docker stop` duration | Container exit | Runtime marker |
| --- | --- | --- | --- | --- |
| API as PID 1 | before DEV-412 | 3097 ms, the full grace period, then SIGKILL | 137 | **retained** |
| API as PID 1 | after DEV-412 | 110-138 ms | 0 | released |
| `init: true`, tini as PID 1 | before DEV-412 | 60 ms | 143 | **retained** |
| `init: true`, tini as PID 1 | after DEV-412 | 122 ms | 0 | released |

In the defective run without an init process the container logs are empty: the API never saw the signal, because PID 1 ignored it. With an init process the API is an ordinary child, so the default disposition killed it with 143. In both shapes the marker stayed in the persistent `/data` volume, so the next deployment of that volume would have been refused by the fail-closed exclusion until an operator removed the marker by hand.

## Delegation decision

The standing owner direction in the root `AGENT.md` requires a bounded delegation to MiniMax M3.1 Flash Free through OpenCode for each subsequent task, with the highest advertised reasoning variant: `opencode/minimax-m3.1-flash-free` with `variant=max`.

The orchestrator keeps the container validation, the review, the integration and the cleanup. The delegated mission receives the verified production-path facts and implements the committed regression that exercises the production bundle without Docker, so the guarantee stays covered by the ordinary test suite.

## Implementation mission

- Owner: parent orchestrator. Worker: delegated MiniMax M3.1 Flash Free mission in a dedicated worktree.
- Allowed writes: one new test file under `scripts/`, and a temporary, byte-for-byte restored replacement of `apps/api/src/index.ts` for the negative control only.
- Forbidden: every other file, product behavior, configuration, dependencies, lockfiles, governance, commits, merges, `main` writes, Docker, the network, the owner's `.env`, real database, real media root, default ports, real credentials, and further delegation.
- Acceptance: the production bundle is built by the test itself; a termination during its startup releases the runtime marker and the bundle exits 0; the API never served; the next start of the same bundle serves the health endpoint and releases the marker again; every wait is bounded and the temporary directories are removed only after the owned child exited.
- Stop: the scoped uncommitted diff, the exact check results, the negative-control evidence, and the limitations. The parent reviews and executes the final test in the canonical checkout.

## Round 1 and round 2

The worker delivered a new test file, `scripts/production-startup-shutdown.test.ts`, that builds the real production bundle with `Bun.build` into a temporary directory and exercises it. The parent reviewed the whole file and copied it into the canonical checkout: 1 pass, 0 fail.

Parent negative control with the REAL pre-correction `apps/api/src/index.ts`: the test fails at `expect(exitCode).toBe(0)` with `Expected: 0, Received: 143`, the platform default disposition. The candidate is load-bearing against the real defect.

The parent accepted the isolation, the explicit environment, the in-test bundle build, the marker trigger, the drain-log assertions and the bounded cleanup, and requested two revisions: the pid recorded in the marker had to be tied to the bundle child the test started, and the child's `signalCode` had to be asserted null so the test states that the process ended on its own drain path. The worker implemented both in round 2.

The worker also measured its own flakiness: 36 consecutive passes of the focused test, including 5 passes under 8 busy CPU loops on a 16-core machine.

## Final acceptance

Parent verification in the canonical checkout, with the revised candidate:

- `bun test scripts/production-startup-shutdown.test.ts`: 1 pass, 0 fail, 18 assertions.
- Negative control with the real pre-correction source: the test fails with `Expected: 0, Received: 143`.
- `bun test scripts`: 79 tests, 78 pass. The single failure is the pre-existing, unrelated `scripts/postbot.test.ts` expectation that omits the `facebook` entry of `oauthReadiness`; it fails identically on a clean tree.
- `bun run check:quick`: format, lint, spelling and typechecks across the workspace pass without bypass.
- No whole E2E matrix was run. The affected behavior is the production process lifecycle, covered by the new real-process regression, the API-level and launcher-level regressions, and the container measurements above.

## Evidence

- The production artifact now has a committed regression: the bundle is built by the test, so the guarantee never depends on a stale `apps/api/dist`, and CI exercises it because the root `test` step runs before `build`.
- The container measurements remain the orchestrator's evidence: the fail-closed marker policy is unchanged by this task, and the marker is still released only through the token-checked release of the lock that created it.
- The worktree and its branch were removed after the parent confirmed that the canonical file matches the accepted candidate. The parent-owned container script, the temporary old bundle and the temporary old source copy were removed as well. No normal database, media root, owner credential, owner `.env` or existing service was touched at any point.

## Next steps

The container-level startup termination is proven by measurement but is not a committed regression: `scripts/production-container-recovery.ts` is the CI entrypoint for the production image and does not stop a container during its startup.

Recommended next task: add that container-level check to `scripts/production-container-recovery.ts`, so the PID 1 guarantee is proved by the CI image rather than only by an orchestrator measurement, and confirm the check against a locally built image through `POSTBOT_CONTAINER_TEST_IMAGE`.
