# PROVIDER-357 — Native Mastodon video

Base: `0e59c14d3`. Status: complete. Owner accepted the Mastodon follow-up.

## Plan and boundary

1. Check official upload, processing and instance-limit contracts.
2. Add a new immutable video-capable profile, preserving image-only status-v1.
3. Upload one ready MP4, record its provider identifier, defer processing durably,
   then publish with the existing idempotency key. Keep uncertain uploads ambiguous.
4. Verify provider behavior, durable worker execution and existing browser authoring.

Use the existing H.264/AAC-LC inspection, private byte-range playback and storage
policy. Video is exclusive of images, with required accessibility text, three
seconds to thirty minutes and a 100,000,000-byte portable ceiling (installation
storage can be smaller). Honor the instance's advertised MIME, size and pixel
limits before any upload. Frame-rate metadata is not persisted: the provider
remains authoritative for its advertised frame-rate limit. No conversion or extra
service. Old image execution remains registered unchanged.

Official references checked 2026-10-08:
- https://docs.joinmastodon.org/methods/media/ — multipart POST v2/media returns
  200 or asynchronous 202; GET v1/media returns 206 while processing. Both use
  write:media, already requested by Postbot.
- https://docs.joinmastodon.org/entities/Instance/ — configuration advertises
  supported MIME types, video_size_limit and video_matrix_limit per instance.

No provider credential or live external publication will be used. Preserve the
pre-existing quoted cache directory. Final validation is selected according to
ADR-077; API composition requires the full gate once the executable tree is final.

## Implementation and bounded evidence

The Mastodon package exports the original image-only profile and a new version 2
profile. Both execution revisions are registered. Video uploads use streaming
multipart bodies, with a remote identifier recorded before processing checks.
A 206 processing response defers the durable job for one minute without consuming
its retry budget; processing is bounded to thirty minutes. No status is submitted
before readiness. Unknown upload outcomes stay ambiguous.

Two provider tests exercise instance limits, exact multipart bytes and description,
202/206/200 processing, mismatched identifiers and secret-safe errors. Five worker
scenarios use real SQLite checkpoints and the inspected MP4 fixture: readiness
following five deferrals, instance rejection before transfer, processing rejection,
uncertain upload and processing timeout. The initial combined run passed 31 tests.

The existing native-video browser journey now also covers Mastodon. Both platform
cases passed (14.5 seconds including the harness). The Mastodon media asset carries
its accessibility description through selection and draft creation. Playback,
seeking and 1280/390-pixel layouts are checked; screenshots were inspected. No new
web component was needed. The initial test incorrectly searched for an accessibility
field outside its editing surface; the fixture now uses the existing library
accessibility default, so this journey does not claim to test editing that field.

Limitations: all provider requests are simulated. Frame rate remains enforced by
Mastodon because Postbot does not persist it. Existing image upload processing is
unchanged. Existing channels retain their immutable profile until explicitly
upgraded; new Mastodon channels receive version 2. There is no transcoding.
