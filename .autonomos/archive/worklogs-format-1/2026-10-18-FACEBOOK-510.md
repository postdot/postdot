# FACEBOOK-510 — Encrypted Meta configuration and Studio Page selection

## Outcome

Added Facebook to the existing instance-admin OAuth application settings and connected Studio to the authenticated Facebook Page-selection routes. A successful authorization opens a Page picker; no Page is selected automatically. Pages without publishing access are disabled. Pagination retains each choice's discovery cursor. Closing or completing the picker removes its temporary selection reference from the current URL.

Facebook remains absent from channel-creation presets and the publication worker. This pass does not advertise a usable publishing integration or claim live Meta acceptance. The picker can be inspected independently in Storybook using synthetic Pages and the production component.

## Configuration and authorization

Application IDs and secrets use the existing encrypted provider-application store. Facebook requires a numeric application ID. The form uses App ID/App secret labels, exposes its exact callback URL and shows the HTTPS requirement only when relevant. Header and actions remain outside the scrolling body in both the settings form and Page picker.

Runtime resolution respects stored defaults and disabled applications. Callback and pending selection resolve the exact stored application that started authorization, rather than the current default. Tests cover default changes, disabling an application, a declined authorization, and a foreign callback session. A foreign session receives no project-specific return path and cannot consume the owner's authorization attempt. Provider failures continue to expose no raw errors or tokens.

The two temporary phases now share provider ID `facebook` and carry explicit `authorization` or `page-selection` context. The previous stage-specific provider ID could not satisfy the existing composite provider/application foreign key once an actual stored application was used. Both phases bind the stored application ID and client ID; callbacks and Page requests reject the wrong phase. Old experimental pending attempts require starting authorization again; no compatibility alias or persistent data rewrite was introduced.

## Migration

The existing provider-application table enforced the provider list and configuration shape through CHECK constraints. Generated migration 0012 widens those constraints to include Facebook, copying all existing rows and recreating the existing indexes. No existing migration was rewritten.

A dedicated test migrates an isolated database through the previous journal, creates an encrypted LinkedIn configuration and a referencing encrypted pending attempt, then upgrades it. It verifies byte-for-byte configuration preservation, successful decryption, retained attempt/application binding, no foreign-key violations, Facebook configuration creation and repeat migration behavior. No manual migration, reset or fixture data was applied to the shared development database.
