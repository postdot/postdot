# WEB-564 — User API-key contracts

## Outcome and decisions

Derived UserApiKey and UserApiKeyCapability from Eden responses and replaced the
web's handwritten declarations with re-exports. Migrated list/create/update/revoke
wrappers to Eden with inferred results and existing ApiError normalization.
Preserved readonly input arrays by copying them at the request boundary. Update
separates array fields before spreading the other fields so the compiler can
verify their mutable request representation without a conversion. Optional fields
remain omitted and explicit null values remain present. No authentication,
server, SDK dependency or shared client factory changes.

Eleven compile-time assertions cover four response shapes, token absence from
key metadata, project/action scopes, nullable expiration, the seven capabilities
and unchanged creation/update input contracts.

## Validation and investigation

- Static gates passed: formatting, lint, spelling and typecheck.
- Production web build passed.
- 285 web tests plus 17 client/access API tests passed: 302 total, zero failures.
  API coverage includes project subsets, independent action ceilings, permanent
  deletion capability, owner-role rechecks and session-only administration.
- Three permanent browser scenarios passed in the initial focused run:
  access-137-user-api-keys and both access-132-instance-access cases.
- A temporary browser acceptance called the actual web module against the
  isolated API, covering all four wrappers. It verified creation-only token
  visibility, selected-project access, preserved action/project/expiration values
  after renaming, explicit null update bodies, invalid-project/time errors,
  forbidden key administration by bearer token, absent revoked keys and a 401
  when authenticating with a revoked token. No key tokens were logged.
- The first temporary run incorrectly expected null expiration to remove the
  deadline. Investigation found the configured 180-day default in auth plugins;
  the API maps null expiration to undefined expiresIn, which preserves the stored
  deadline on update. A raw-fetch baseline reproduced the previous wrapper's
  creation/update payloads and confirmed that behavior. The revised acceptance
  asserts the existing default and exact expiration preservation for both old
  transport and Eden, while continuing to assert explicit null request fields.
  No product behavior or permanent assertion was changed to accommodate this.
- The isolated acceptance rerun passed in 4.2 seconds, giving four distinct
  passing browser scenarios overall. Removed the temporary file afterward;
  existing browser scenarios and configuration remain unchanged.
- Focused validation is proportionate to these four known wrappers. No full
  matrix/container replay: shared transport factory, dependencies and server
  runtime remain unchanged.
