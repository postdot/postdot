## Operator outcome

The saved profile preview now lists affected publications instead of reporting only
aggregate counts. One publication appears once, with separate consequences for
its working draft and its selected target awaiting delivery. Publications needing
review appear first; normalized validation paths and messages remain attached to
the affected content. Each row has an explicit inspection link to the existing
publication editor. Adaptation remains available only after a different profile
is active; this preview neither adopts a draft nor activates a profile.

Profile JSON is a disclosure, initially open for editing and closed after a
successful preview. Its height is bounded rather than growing with the entire
JSON document. The dialog now has an effective desktop width override and explicit
mobile margins. Technical profile changes remain available behind a separate
compact disclosure, without enclosing every publication in a card.

## State and data boundaries

- Identity labels come from the existing paginated publication summaries. The
  lookup stops when all affected IDs are found or pagination ends. No endpoint,
  stored record, timer or polling mechanism was added.
- The assessment owns row identity and compatibility. A missing or failed name
  lookup cannot hide affected work: IDs and inspection links stay available,
  with an explicit retry for metadata failure.
- Editing the JSON invalidates the displayed assessment and requires saving
  before a new preview. Activation still requires the existing successful,
  compatible assessment. This prevents displaying one profile while assessing
  a different saved document.
- Session generations discard results from a previously closed or switched
  dialog. A failed initial load cannot leave the previous channel's draft ID
  available for preview.
- Existing activation, approval, delivery, adoption and migration policies remain
  unchanged. Inspection closes the dialog and navigates explicitly.

## Follow-up: activation entry point

The existing web activation button rejects `assessment.hasReviewRequired`, while
ADR-020 and the server support activation that preserves incompatible content and
marks it for review. This is an existing mismatch, not corrected here. The UI path
cannot currently activate an incompatible proposed profile, so adaptation to that
new version cannot begin through this dialog. UX-326 should trace this gap and
present an explicit activation interaction with the actual consequences before
changing the button gate. No automatic migration or old-contract consent follows
from resolving it.
