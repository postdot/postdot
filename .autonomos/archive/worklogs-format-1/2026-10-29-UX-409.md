# UX-409 — Renew sessions without transferring composition between accounts

Status: complete
Related: UX-406/407/408; SPEC-010 COH-02; DESIGN.md recovery and failure states

## Reproduced behaviour

- Revoking the current browser session through the real sign-out endpoint while leaving the composer mounted caused its next autosave or Create draft to receive 401. The page kept its text but offered no direct sign-in continuation. Both focused baselines failed on the missing Sign in again action.
- Explicitly changing the dashboard's project search context through browser history revalidated the authenticated route without leaving the project. After signing in as a second account through the same cookie jar, the header changed to that account while the first author's composition survived in the project-lifetime provider. Returning from Channels exposed that text in the second account's mounted composer. The focused baseline failed on the blocked form; its capture contained the first author's text. The same-author control passed before the fix.
- Ordinary child navigation did not itself refresh the parent session identity in this fixture. The regression deliberately changes a loader dependency to exercise revalidation. It does not claim automatic detection on window focus.

## Changes

- The dashboard's stateful subtree is keyed by authenticated user ID. A different author recreates dashboard state, feature QueryClient providers and project composition; a new session for the same author retains them. The presented-route shell selection remains unchanged.
- Composer reads, saves, discards, conflict rereads and creation failures share the session-refusal transition. A 401 pauses authoring and automatic writes, preserves the original-author browser recovery, closes obsolete choices, and offers Sign in again. The continuation retains the current composer pathname and query, including the selected editor. Existing login validation still limits continuation destinations.
- Creation reports failures to the invoking composer even when its action wrapper consumes the exception for normal feedback. This also makes an account-change refusal pause immediately after Create draft, rather than waiting for another autosave. A refused action preserves its existing error handling and returns no created publications.
- Submission prevents the browser default immediately and checks the pause/conflict state again after draining queued saves. A save that discovers an invalid session cannot be followed by a creation attempt from that queue.
- The account/session notice owns its feedback, avoiding a duplicate generic action error. A terminal session refusal is not presented as ongoing initial loading.
- Browser account setup is extracted into a shared fixture; the isolation assertions remain. The affected selector includes the fixture and renewal journeys. The narrow web guidance records the author-keyed state lifetime and recovery continuation.

No Better Auth configuration, backend authorization, session duration, API contract, storage ownership or polling mechanism changes.

## Limits and next scope

Session refusal is reactive to a request, and identity changes are handled when the authenticated route revalidates. This pass adds no polling, cross-tab authentication broadcast, automatic focus redirect or background-session protocol. Browser cases revoke a real current session rather than waiting for its configured lifetime; they exercise the same server refusal, not wall-clock expiration mechanics. No full default matrix, physical-device or screen-reader acceptance is claimed. Development data is not used for browser mutations.

Recommended next task: inspect interrupted media uploads and their retry/cancel recovery across composer navigation, using isolated storage and without sending publications to a live provider.
