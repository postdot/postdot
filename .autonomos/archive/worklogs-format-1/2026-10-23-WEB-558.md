# WEB-558 — Preserve Eden response types through the web wrapper

- Issue: ISSUE-188 (partial implementation; issue remains open)
- Status: complete
- Scope: typed response extraction, five project-tag methods and compiler-discovered prerequisites

## Implementation and compatibility findings

`unwrap` accepts data tied to its generic result type and returns that value
without a type assertion. Existing explicitly annotated callers must now match
the actual server response. List/create/rename/archive/restore project-tag
methods infer their complete responses from Eden. Common ApiError conversion and
empty-response handling remain unchanged.

The first compiler pass exposed an upstream prerequisite. The installed
@elysiajs/eden 1.4.9 response type imports ELYSIA_FORM_DATA from Elysia, but
installed Elysia 2.0.0-exp.64 does not export it. With dependency declaration
checking skipped by the existing configuration, success payloads become unknown.
This affects Eden responses before the web wrapper sees them.

Validated @elysia/eden 2.0.0-beta.2 with the same server version in a private
temporary installation, including an expected error for an invented response
field. Its declared Elysia peer range starts at 2.0.0-exp.23. Newer beta.6
requires an Elysia beta upgrade and was not selected. Replaced only the SDK
package/import and its lockfile entry; the server version is unchanged.

References: [official v2 Eden setup](https://next.elysiajs.com/eden/installation/),
[exact candidate metadata](https://registry.npmjs.org/@elysia/eden/2.0.0-beta.2).
The installed v1 declaration and installed server exports provided the concrete
symbol-mismatch evidence; no dependency files were patched.

With compatible Eden types, only two response mismatches remained: composer
GET/PUT return an opaque record, while the browser declared fully typed composer
content. Reused the existing recovery shape checks as an exported content guard.
Both API boundaries validate that content before producing the browser model and
raise invalid_response for malformed content. Local recovery still requires its
version, timestamp and recoverable content. The complete server draft is retained;
this change does not rewrite stored drafts or remove unknown content fields.

The SDK's shipped MIT notice exactly matches the retained upstream text. Updated
its package/version headings in the existing license bundle and direct dependency
inventory, preserving the full copyright and license text.

## Validation

- Five compile-time tag-response contracts are part of the web typecheck.
  Negative control restoring the old unchecked helper fails all five contracts;
  restored typed implementation passes. No new unchecked conversion or compiler
  option weakening was introduced.
- Two new content-guard tests cover complete, title-only/empty and optional-scope
  content, plus opaque and malformed records, media, targets and tag IDs.
- Focused client transport and recovery tests: 8 passed, zero failed.
- `bun run check:quick`: format, lint, spelling and types passed.
- `bun run test:unit`: 1,552 passed, zero failed, including 285 web tests.
- `bun run test:e2e`: 133 main scenarios in 24.9 minutes plus 4 SMTP/account
  recovery scenarios passed, zero failed, zero retries. This includes the four
  tag lifecycle/error/permission scenarios and real autosave/recovery paths.
- `bun run test:container:recovery`: freshly built Bun 1.4.2 x64 image passed
  authenticated HTTP, packaged media decoding, startup termination, graceful
  shutdown, media backup/held restore and fail-closed forced termination.
- After updating notice metadata, rebuilt the normal production image and checked
  inside it that both the inventory and full license bundle name the new SDK.
  No runtime source changed between these two image builds.
- Host checks used Bun 1.4.3-canary.1. No live provider action was performed.
