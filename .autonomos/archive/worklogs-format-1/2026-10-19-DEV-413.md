## Plan

1. Register a bounded delegated mission for a launcher-level regression of the DEV-412 correction, on a dedicated worktree with offline dependencies.
2. Review the candidate against the mission acceptance criteria, run the isolated launcher test in the canonical checkout, and request revisions until the result holds.
3. Integrate, clean up the worktree and branch, and record the evidence.

## Context

DEV-412 established and corrected the API-level behavior: a termination received during the startup window now runs the same drain as a running server, releases the runtime marker through the token-checked release, and exits 0. The API-level regression lives in `scripts/dev-api.test.ts` and proves the API process alone.

What is still unverified is the developer-facing path: the development launcher (`scripts/dev-api.ts`) owns the API child, forwards the operator signal to it, and restarts it after a watched change. The SITE-410 symptom was a development watcher restart that left the API without a listener while retaining a database handle, so the launcher path deserves its own evidence.

## Parent ground truth, established independently of the candidate

Before reviewing any candidate, the parent wrote its own external reproduction of the same scenario, with the same isolation rules: a temporary fixture root, a synthetic `.env`, a symlink to the real API entry point, an OS-allocated loopback port and a temporary database and media directory.

With the DEV-412 correction in place: the marker appears, the operator stop reaches the child inside its startup window, the child logs `[postbot-shutdown] SIGINT received; draining worker and runtimes` and `shutdown complete with exit code 0`, the marker is released 126 ms after the signal, the API never served, and the second launcher run answers the health endpoint.

With the pre-correction source restored: the launcher reports `API stopped (pid N, code 130)`, the marker is retained, and the second launcher run does not serve — the owner-facing failure.

The parent ground truth is therefore established independently of the delegated candidate.

## Round 1 review

The worker delivered a purely additive test in `scripts/dev-api.test.ts` (247 lines, no existing test or assertion modified). The parent reviewed the whole diff, copied it into the canonical checkout and ran it there: `bun test scripts/dev-api.test.ts` gave 8 pass, 0 fail.

The parent negative control used the REAL pre-correction `apps/api/src/index.ts`, not a stub: the new test fails at the drain-log assertion, with the launcher reporting `API stopped (pid 483270, code 143)`. The candidate is load-bearing against the real defect.

The parent accepted the structure, the isolation and the bounded cleanup, and requested three revisions: the launcher's report of the child's exit code must be asserted explicitly (`code 0`) instead of only the `[postbot-dev] API stopped` prefix, which also holds for the defective run; the pid recorded in the marker must be tied to the pid the launcher reported for its own child; and the "never served" flag must be named for what it measures, since it counts any response and not only a successful one.

Scope note: the worker wrote one line into the canonical worklog, outside its allowed scope. The canonical product files were verified untouched, and the parent owns the record.

## Round 2 and final acceptance

The worker implemented the three requested revisions in `scripts/dev-api.test.ts` only: the launcher's report of the child's exit code is now asserted explicitly with `/\[postbot-dev\] API stopped \(pid \d+, code 0\)/` for both launchers, so the assertion is no longer satisfied by the defective `code 143`; the pid recorded in the marker is tied to the pid the launcher reported for its own child, through a bounded helper that parses the launcher's first `API started (pid N)` line; and the "never served" flag is renamed `responded`, with a comment stating that any response counts as the API having served.

Parent verification in the canonical checkout, with the candidate copied in:

- `bun test scripts/dev-api.test.ts`: 8 pass, 0 fail, 66 assertions.
- Negative control with the REAL pre-correction `apps/api/src/index.ts`: the new test fails at the drain-log assertion, with the launcher reporting `API stopped (pid 488688, code 143)`. The candidate is load-bearing against the real defect.
- `bun test scripts`: 78 tests, 77 pass. The single failure is the pre-existing, unrelated `scripts/postbot.test.ts` expectation that omits the `facebook` entry of `oauthReadiness`, added by the Facebook work stream; it fails identically on a clean tree.
- `bun run check:quick`: format, lint, spelling and typechecks across the workspace pass without bypass.
- No whole E2E matrix was run. The affected behavior is the development launcher process lifecycle, covered by the new real-process regression and the existing launcher tests.

The worktree and its branch were removed after the parent confirmed that the canonical file matches the accepted candidate byte for byte. The parent-owned external reproduction script and the temporary old-source copy were removed as well. No normal database, media root, owner credential, owner `.env` or existing service was touched at any point.
