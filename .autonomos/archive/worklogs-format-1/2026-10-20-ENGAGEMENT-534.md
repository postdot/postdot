# ENGAGEMENT-534 — Mastodon conversation replies

## Scope and plan

Owner accepted extending the conversation-owned reply workflow to Mastodon. Work directly without delegation.

1. Verify native status replies, identity and public conversation boundaries.
2. Extend stored request identity to explicitly identify the provider, account and original instance, preserving Bluesky history.
3. Prepare live Mastodon context and send through the existing durable executor; expose the existing Studio reply form for Mastodon.
4. Verify the protocol, authorization, account/instance isolation, recovery and focused browser workflow; integrate locally.

## Boundaries

Text-only replies to available comments in the retained public snapshot. Editors send; members read. Preserve the more restrictive public/unlisted visibility of root and parent. No private/direct conversations, attachments, moderation, scheduling, automatic retries or live external publication. Reuse the singleton worker and conversation history without creating Posts or Publications.

## Verification and outcome

- The reply store now identifies the provider, account and original Mastodon instance explicitly. Generated migration `0015_conversation_reply_providers` renames `account_did` to `account_id`, labels retained rows as Bluesky and preserves request IDs, text, provider keys, claims, outcomes and audit attribution. The upgrade regression starts from actual migrations 0–14 with retained pending, running, sent and uncertain rows; foreign keys remain valid and reapplying the migration runner is safe.
- Mastodon replies use the original publishing instance's local status IDs, not remote permalinks. Preparation verifies the live token account, ownership of the delivered source status, public/unlisted root and parent, and live ancestry. Only account verification receives credentials; context reads remain anonymous and use the existing network-controlled transport. A public/unlisted reply preserves the more restrictive visibility. Text is bounded to 500 UTF-16 units, matching the current built-in authoring envelope; stricter instance rejection remains a known no-effect failure.
- Enqueueing requires an available comment in the retained snapshot and live editor access. Execution pins the provider, connection, encrypted credential, account, source and instance. The claim, project access and instance are checked again after preparation. The original runtime transport also refreshes expired tokens, with rotated tokens saved through encrypted storage. Session parsing and refresh metadata helpers were extracted unchanged from the publication adapter to avoid divergent behavior.
- Replies retain the request UUID as the provider key, send `in_reply_to_id` and require acknowledgement of the parent, account and chosen visibility. Missing or mismatched acknowledgement is uncertain. Caller cancellation is combined with the publisher timeout. The shared durable executor retains its conservative boundary and one-attempt policy: an interrupted or uncertain write is never automatically resent.
- Studio uses the existing comments disclosure, text composer and team history for both providers. The API supplies provider, text limit and instance metadata; the interface shows the matching counter and safe destination links. Connection and uncertain-result help now names the correct platform in both EN and FR. A lost HTTP response retries the same request identity. Viewers read history without send controls. No Post, Publication, calendar entry, new worker, collector or external dependency was added.
- Static gate passed: formatting, lint, spelling, workspace types and complete EN/FR catalogs (1953/1953 each).
- Final focused command passed: `bun test packages/mastodon/src packages/db/src/publication-reply-migration.test.ts apps/api/src/modules/projects/publication-replies.test.ts apps/api/src/modules/workflow/providers/conformance.test.ts apps/api/src/modules/workflow/worker.test.ts scripts/production-bundle-dependency.test.ts` — 96 tests, 928 assertions, 4.62 seconds. Includes native context isolation, protocol payload/acknowledgement, caller cancellation, encrypted token rotation, shared worker delivery/recovery, permissions, unchanged Mastodon poll/video contracts and the production bundle guard.
- Final isolated browser command passed: `bunx playwright test e2e/publication-replies.spec.ts` — 2 scenarios, 19.7 seconds. Both providers cover composition, lost-response replay with the same request identity, sent and uncertain history, links, French mobile display and viewer read-only access. Transport states are simulated; application/worker integration is exercised separately by the focused API suite.
- The first parameterized Mastodon browser fixture incorrectly used the snapshot API URL as the publication's native external ID. Corrected it to the native numeric ID plus retained permalink; both provider workflows then passed. Visual review caught and corrected the inherited Bluesky-only recovery wording. Product assertions were retained.
- No live provider request or publication was performed. Real Mastodon acceptance remains unverified.
