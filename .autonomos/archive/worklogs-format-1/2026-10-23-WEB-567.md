# WEB-567 — Feature-owned project data and actions

## Outcome and ownership

Refactored the complete project dashboard data boundary in one implementation
batch. The shared dashboard context shrank from 876 to 134 lines. It retains
project identity, membership/role, channels and publisher connections used by
navigation. The parent loader now loads those three resource groups instead of
also fetching publication lists, due publications and tags on every project page.
Global workspace/account navigation remains in its existing context.

- project-resources owns shared Query option factories and feature publication
  reads/pagination. Overview and Queue subscribe to their publication resources;
  Media, Channels and project-access surfaces do not load those resources.
- project-channel-actions owns channel lifecycle and publisher connection actions,
  preserving form-owned connection errors and creation validation details.
- project-publication-actions owns publication mutations and their feedback.
- project-tags owns catalog mutations, shared by tag management and authoring.
- publication-composer-context owns composition state and submission. Its dedicated
  session deliberately lasts for the project navigation lifetime so composition,
  channel setup and resume preserve the draft. It does not fetch publication lists,
  due work or tags on unrelated routes, and its changes do not broadcast through
  the navigation context.
- project-query-keys and project-query-invalidation own resource identity and
  refresh selection. Publication writes preserve navigation/membership data;
  channel changes refresh channel/connection data and publication projections;
  tag events refresh the catalog and publication projections.

All reads use the existing project-scoped QueryClient. Inactive project queries
are invalidated without fetching; their next observer receives fresh data.
Realtime refresh coalescing, projection-delay retries, editor-specific draft
signals, visibility recovery and access verification remain in place. No server,
authentication, dependency or database contract changed.

## Lifecycle verification and corrections

The first focused browser pass exposed initial suspension recreating the
uncommitted QueryClient. Requests succeeded but the overview never committed and
repeated the same reads. A feature Suspense boundary inside the mounted dashboard
frame fixes that lifecycle; navigation and the cache stay mounted while feature
data loads. No timeout or existing assertion was relaxed.

Preserved creation targeting: the first empty destination receives the newly
created channel, not an arbitrary existing channel. Channel-list synchronization
keeps valid targets, clears archived targets and preserves the existing fallback
when a selected channel is removed. Connection forms still receive rejected
requests directly, keeping credentials/handles and retry feedback local.

The complete focused rerun passed all eight scenarios without retries: all five
channel-authoring-identity cases, the new feature-loading acceptance and both
web-312-live-access-revocation cases. That includes creating the first destination,
composition resume through channel setup/OAuth callback, and role downgrade.

  them after the local transition corrections; the commit hook repeats them.
- All 1,555 unit/script tests passed, including 287 web tests. The final web
  selection was rerun after the feature-entry correction: 287 passed.
- The full 134-case browser suite ran in 24.7 minutes: 132 passed and two exposed
  transition regressions. Initial loading lacked a main landmark/heading; returning
  to Queue after a write briefly rendered an invalidated empty snapshot, exposing
  two creation actions. No selector or accessibility assertion was relaxed.
- Feature entry now resolves invalidated publication/due data before rendering;
  already committed views retain their snapshot on refresh/refusal. The fallback

- The first correction rerun passed all six non-accessibility cases: the feature
  loading budget, all three publication-media journeys and both live-revocation

  had missed the rendered block; applied and inspected the actual fallback.
- The final accessibility/loading-budget rerun passed both cases in 20.8 seconds,
  including all five project surfaces in the accessibility smoke. All 134 distinct
  main cases therefore have passing evidence, with focused revalidation after
  the two local corrections rather than a second complete matrix replay.
- All four separate SMTP/account-recovery browser cases passed.
- The final root production build passed all 21 tasks, including the web build.
- Application files stayed frozen during each browser run. No production-container
  replay: API/dependencies/runtime packaging are unchanged.

Two permanent cache regression tests verify that publication writes refetch only
observed publication data, mark inactive same-project data stale, retain foreign
project/navigation data and fetch the inactive resource on its next read. Channel
invalidation preserves membership and the tag catalog while invalidating channel
and publication projections.

The permanent project-feature-data browser scenario verifies zero publication,
due or tag reads on Media and Channels, no publication reads on Tags, and real
publication/due reads on Queue. This distinguishes feature ownership from merely
moving the old aggregate loader to a different file.
