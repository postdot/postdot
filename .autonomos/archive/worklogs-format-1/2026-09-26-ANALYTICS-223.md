# ANALYTICS-223 — Decide whether operational analytics needs a web surface

- Status: decision brief delivered; owner decision pending
- Date: 2026-09-26
- Issue: ISSUE-131
- Scope: compare a project web surface with the existing project-authorized API; no UI, metrics, or API changes

## Evidence

- `GET /api/projects/:projectId/analytics` is authenticated and project-scoped. It returns current publication and execution/workload snapshots, historical publication and execution outcomes, retry/recovery counts, latency summaries, daily buckets, and explicit data-coverage quality.
- This is Postbot operational analytics, not social engagement analytics. It does not report likes, reach, impressions, or clicks. Provider engagement is a separate read model; the current implemented collection slice is Bluesky-specific.
- The authenticated web dashboard has no analytics route, and the current CLI has no analytics command. The existing project overview is a publication calendar; the queue and sidebar expose current publication/action workload, not historical execution aggregates.
- The API defaults to a 30-day range and accepts up to 366 days. The provisional query-time planning envelope is 5,000 publications and 20,000 historical facts per request; it is not an enforced limit. At 20,000 publications, the hardened local synthetic benchmark measured roughly 558 ms first-read latency and +115 MiB first-read RSS, with repeated-read RSS requiring care. These measurements are not production guarantees.
- ADR-051 explicitly kept a dashboard out of the analytics foundation. ADR-054 retained query-time reads within a provisional envelope rather than adding a projection speculatively.

## Options

1. Add a concise project web page using the current API only. It could summarize delivery outcomes, retries, delays, and coverage gaps without new collection. This would make the data discoverable to web users, but introduces a new navigation destination and ongoing UI/testing work; the page would need to be clearly named and must not imply provider engagement statistics.
2. Keep the endpoint available without a web page. This avoids presenting internal delivery diagnostics as a user-facing analytics product. The tradeoff is that ordinary web and CLI users cannot discover these values without an API client.
3. Defer the UI decision until a concrete user workflow is identified. Keep the API and current overview/queue intact, then revisit when users need a specific historical answer or provider engagement coverage supports a coherent product surface. This is not a permanent rejection of analytics UI.

## Recommendation and owner decision

Recommend option 3 for now: preserve the project-authorized API, add no charts or new metrics, and do not add an “Analytics” page until Postbot has a demonstrated question that the calendar and queue cannot answer. The current endpoint is chiefly operational and can be useful for troubleshooting, but a generic project analytics page risks being mistaken for social-performance analytics. Revisit when actual use establishes the question, audience, and useful time range.

Owner decision requested: agree to defer the web page while keeping the API, or prioritize a concise operational analytics page now? This choice is needed before any UI implementation; it does not block independent work.
