# UX-410 — Recover interrupted composer uploads

Status: complete
Related: UX-409 author-keyed dashboard lifetime; DESIGN.md recovery and failure feedback

## Reproduction and changes

A real browser upload cut at its raw PUT produced an error but removed the file from Uppy immediately. There was no retry action and no retained file on return. The regression failed on the absent Retry upload control. Inspection also found that picker cleanup called Uppy destroy while persistence was still attached: destroy cancels every file and that cancellation cleared the recovery snapshot.

- Keep failed blobs queued with explicit Retry and Cancel controls, named for their file. Apply and remove successful files only; a failed recovery attempt remains available for another choice. Existing addition ordering and attachment deduplication remain.
- Record the acknowledged upload intent in file metadata and an author/picker/file-scoped synchronous checkpoint. A raw retry or a lost finalization response uses that same intent rather than reserving another asset. Only a server `upload_expired` response retires a known intent and starts a fresh reservation with the retained bytes.
- Carry an AbortSignal through reservation, raw transport, finalization and inspection reads. Removing a file aborts its client request and prevents later finalization or success events. Cancelling does not delete project media: an already-created pending reservation remains subject to existing maintenance expiry.
- A successful completion or explicit cancellation leaves a short-lived dismissal marker so a slightly older asynchronous recovery snapshot cannot resurrect the file. Checkpoints and markers expire after 24 hours; stale entries are pruned for the current picker.
- Install the controller and persistence in an effect, so discarded React renders do not install orphan listeners. Navigation detaches persistence before cancelling the in-memory queue. Picker callbacks ignore results after unmount. Return offers an explicit recovery choice rather than attaching a late result to the old screen.
- Browser recovery IDs include the authenticated author. Standalone previews without an author do not install persistent recovery. Legacy unscoped browser entries are not adopted or deleted; they retain their previous expiry. The dashboard exposes only the optional user ID needed for this browser scope, without changing access control.

The backend contracts and asset ownership are unchanged. Media remains project-owned; the author scopes browser-selected bytes and their recovery, not the resulting shared asset.

## Validation

- Focused baseline reproduces the lost failed-file retry. The first browser reprise then reached successful attachment; its list assertion was corrected from `assets` to the actual `media` response property.
- Three focused upload cases pass before the final pass: raw retry, lost-finalization retry and navigation/account isolation. The cancellation scenario confirmed the existing reserved-asset lifecycle; its final assertions require one stored but unverified asset, zero finalizations and no recovered or attached file. The browser driver waits for the raw server write before cancelling its held response, rather than assuming cancellation can retract bytes already received.
- Web unit tests: 299 pass, including one reservation across a lost-finalization retry, abort without finalization/late attachment, and server-authorized renewal of an expired intent. Script tests: 117 pass, including the affected media selector.
- Quick gate: all 21 tasks pass. Production web build passes.
- The first grouped pass exercised all 13 targeted journeys: 11 passed. The cancellation assertion assumed an undelivered request, while the server had already stored its bytes; the revised driver deliberately holds a successful raw response and still requires no finalization or attachment. A legacy media scenario double-clicked Add channel after an immediate DOM count raced its route-driven dialog; the second click is removed and the visible form is still required.
- Final media reprise: all six interruption/recovery journeys pass, including both locales with mobile Axe/overflow checks. The legacy dashboard/media journey then passes after replacing its hidden empty-calendar link with the visible day Create publication control; its date/schedule assertions remain. Across the grouped pass and reprises, all 13 distinct targeted journeys pass, including mixed/media-only publications, library bulk actions and four narrow composer/navigation cases.
- French/light mobile failure capture was visually inspected. Recovery controls also respect the parent picker disabled state.
- Final quick gate and production web build pass; API and development web respond successfully on ports 3002 and 5173.

## Limits and next scope

Browser blob recovery remains best effort. The installed Golden Retriever uses browser storage, retains small files by default, and can return missing-file placeholders when bytes are unavailable; the existing Select again action remains. See [upstream recovery documentation](https://uppy.io/docs/golden-retriever/). A lost reservation response has no acknowledged intent ID to reuse; this pass does not add backend reservation idempotency. Explicit file reselection is a new selection, not an automatic retry guarantee. Retry re-sends the raw body using its known intent; byte-range upload resumption is outside scope. Concurrent picker tabs, exhausted browser storage, physical devices and screen readers are not accepted by this pass.

All browser mutations use isolated API, database and media directories. No live publication delivery or development-file upload is performed.

Recommended next task: verify publication creation while files are still uploading, including which pending state should block creation and how that state is communicated.
