# META-62 — Prove visible control for app-managed worktree missions

- Status: blocked by the current harness control surface
- Started: 2026-09-04
- Base commit: `45454d85d366fe4a6598f4381aceb915995e402f`
- Scope: orchestration evidence and operating-method validation only; no Herald product code

## Objective

Determine whether the Codex app-managed worktree task path provides the durable
identity and operator controls required for Herald's orchestrator model:

- durable task identity;
- observable progress and final status;
- interruption or cancellation;
- attribution of the worker and its changes;
- operator visibility in the Codex app;
- deterministic cleanup without shared-resource ownership.

The experiment must not start Herald servers, access provider credentials, use
the browser, mutate the database or media roots, merge branches, or change
product code.

## Mission contract

The orchestrator owns the canonical checkout, Autonomos artifacts, task-board
state, evidence, and final interpretation. Any independent reviewer is
read-only and may inspect only the operating-policy files named in its prompt.
The reviewer may not edit files, start processes, use secrets, call external
providers, or make repository changes.

## Control experiment

An independent read-only reviewer was dispatched through `multi_agent_v1` with
no forked conversation context and an explicit no-write mission. The control
plane returned agent ID `01a06c6a-4182-7c23-97d4-ffc61f6fd99d`. A first
`wait_agent` call timed out after 30 seconds without a terminal status. The
orchestrator then sent an explicit interruption request, which returned a
submission ID. The subsequent wait returned a final result whose report was
labelled `INTERRUPTED`, while the tool status classified the agent result as
`completed`; the agent was then closed after the terminal result was available.

In parallel, the Codex app task listing was inspected. It exposed existing
Codex conversations, including Herald tasks, but did not expose the dispatched
multi-agent reviewer or its agent ID. No Herald server, browser session,
provider credential, database, media root, branch, or product file was touched.

## Interim assessment

The available control plane is useful for bounded sub-agent work because it
provides an orchestrator-side identity, wait, interruption request, terminal
result, and close operation. It is not yet sufficient to claim an
operator-visible app-managed worktree lifecycle: visibility is absent from the
task list, and interruption semantics are not unambiguous when a report says
interrupted but the technical status says completed.

The explicit-worktree fallback therefore remains the default for any mission
that changes Herald. The app-managed path remains gated by ISSUE-029 until a
separate acceptance run proves all required controls with a durable
operator-facing handle. This task is blocked rather than complete: the missing
visibility and unambiguous cancellation are properties of the current harness
control surface, not a Herald repository change that can be completed safely
from this worktree.

The independent reviewer also identified three useful documentation gaps: a
per-phase acceptance checklist is missing, interruption acknowledgement and
terminal-state semantics are not defined, and the operator-visible handle and
cleanup proof are not specified. These are addressed in the root operating
policy; the app-managed path itself is not declared solved.
