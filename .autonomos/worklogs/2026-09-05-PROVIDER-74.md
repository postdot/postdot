# Worklog — PROVIDER-74

## Objective

Generalize the built-in provider connection boundary before adding a second automatic
provider. The immediate target is not a universal provider framework: it is a small,
explicit seam that keeps provider truth in provider modules while preserving Herald's
project ownership, encrypted credentials, OAuth-attempt lifecycle, and workflow
contracts.

## Starting evidence

- The execution registry already resolves versioned built-in adapters and fails closed
  for unknown contract identities or provider mismatches.
- Publisher runtime construction and routes are still LinkedIn-shaped, including the
  callback path, OAuth scopes, destination selection, profile lookup, and credential
  completion.
- Channel profile resolution and publisher-store connection normalization still contain
  LinkedIn-specific assumptions.
- Better Auth remains unrelated to publisher connections; application authentication is
  email/password only.

## Mission boundary

In scope:

- provider-owned connection descriptors and application ports;
- provider-agnostic route/runtime composition;
- provider-specific destination and credential validation through explicit injected
  policies;
- regression coverage proving LinkedIn behavior remains unchanged and a provider-shaped
  test double can cross the boundary without central LinkedIn branches;
- Autonomos tracking and a complete deterministic quality gate.

Out of scope:

- Bluesky implementation or a decision between AT Protocol OAuth and app passwords;
- changes to the publication state machine, project ownership, or custom HTTP DSL;
- real provider calls or credentials;
- web UX work.

## Decision constraints

1. Do not replace provider modules with a universal payload or authentication DSL.
2. Do not make `packages/db` import provider packages. Inject narrow policies where
   persistence needs provider-specific validation.
3. Do not make Better Auth responsible for publisher accounts or tokens.
4. Preserve the existing LinkedIn API behavior until a deliberate versioned route
   change is justified.
5. Stop and record an open decision rather than guessing a provider authentication
   model needed only by Bluesky.

## Acceptance criteria

- Provider-specific connection behavior is represented by an explicit typed boundary.
- Generic routes and runtime composition no longer need a new LinkedIn-shaped branch for
  every future built-in provider operation.
- Database validation receives provider policy through an application-owned port and
  remains independent of provider package imports.
- LinkedIn text, image, refresh, reconnect, destination, and OAuth regression tests
  remain meaningful and pass.
- A provider-shaped test double demonstrates registration, connection policy, and
  execution identity without a live network call.
- Full format, lint, strict typecheck, unit/integration, browser E2E, and build gates
  pass before the branch is proposed for integration.

## Stop condition

If the boundary requires choosing Bluesky's authentication mechanism, media semantics,
or account identity model, stop that part of the implementation and leave the choice in
ISSUE-041 for an explicit evidence-backed decision.

## Progress after the route extraction

The LinkedIn connection flow now lives in a provider-owned route module. The database
publisher store no longer contains a LinkedIn branch for destination defaults or
validation: built-in providers inject a narrow connection policy, while custom HTTP
continues to use its own endpoint and authentication rules. Unknown built-in providers
now fail closed when no policy is registered.

The task remains in progress because provider runtime composition and the Bluesky
authentication profile still need their own evidence and implementation boundary.
