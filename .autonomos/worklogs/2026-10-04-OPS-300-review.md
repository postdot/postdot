# OPS-300 review — shutdown and acceptance robustness follow-up

Scope: robustness of the OPS-300 shutdown path and its container acceptance
only. DOCS-301 was not started. All three review leads were confirmed as real
gaps and corrected; no lead was dismissed as invalid.

## Lead 1 — finally-path exceptions (confirmed, fixed)

The OPS-300 shutdown caught drain failures but not exceptions from the
`finally` block (`closeDatabase`, `runtimeLock.release()`). A throw there
skipped the completion log and `process.exit`, so the 0/1 exit was not
guaranteed: with the static-asset interval present the process would have hung
to SIGKILL (137) with the lock already released.

Fix in `apps/api/src/index.ts`: the drain, the database close, and the lock
release are now three sequential guarded stages with an explicit contract —
exit 0 orderly, exit 1 drain failure (cleanup still attempted), exit 2
incomplete final cleanup. The lock release is attempted exactly once through
the single token-checked owner path; a release failure keeps the marker
(fail-closed) and only escalates the exit code, never retries deletion.

## Lead 2 — unbounded refused-restart probe (confirmed, fixed)

The probe used a foreground `docker run --rm` with no bound: a regression that
let the server start would hang the gate indefinitely, and the runaway
container (random name, not the tracked one) would leak past the script
`finally` cleanup while holding the data directory.

Fix in `scripts/production-container-recovery.ts`: the probe now runs detached
under an identifiable name (`<container>-refused-restart`), is polled up to
20s for a prompt non-zero exit, must cite the held lock (read from both log
streams — the refusal surfaces on container stderr), and is always removed
with `rm --force`, which also terminates a regressed running container.

## Lead 3 — raw exception logging (confirmed, fixed)

`console.error(..., error)` printed raw exception text, against the API
rule that raw exception messages stay out of logs.

Fix: new `apps/api/src/shutdown.ts` with `describeShutdownError(step, error)`
returning the convention-shaped `{step, name, message}` — name sanitized,
message redacted (bearer/secret patterns), whitespace collapsed, 500 chars
max, mirroring the provider-route `redactErrorMessage` convention and the
`error-handler.ts` name rule. Shutdown lines stay on `console.error` (sync,
safe before `process.exit`) like the other `[herald-*]` lifecycle logs.
Covered by `apps/api/src/shutdown.test.ts` (5 tests: naming, redaction,
truncation, non-Error input, subclass names).

## Considered and deliberately not done

- Best-effort drain continuation (attempt remaining stops after one fails):
  rejected. Fail-fast remains safe because the explicit `process.exit` cuts
  any skipped stage, and best-effort would add branching without changing the
  exit guarantee.
- Unit tests for the `process.exit` paths: rejected. They would require
  exporting shutdown internals for marginal value; both live signatures
  (exit 0, exit 137) are covered end to end by the container acceptance.
- Deduplicating the two local `redactErrorMessage` copies in the LinkedIn/X
  provider routes into the new helper: observed but out of scope; no behavior
  changes there in this pass.
- Replacing `@elysia/static` or passing `app.stop(true)`: reaffirmed out of
  scope. The hang was the cache TTL interval, not connections; force-closing
  transports would additionally abort in-flight client requests.

## Verification

- New unit tests pass (`apps/api`: 236 pass, 0 fail, 28 files, incl. the 5 new
  shutdown-diagnostic tests).
- Full `bun run check` passes: format, lint (incl. spelling), typecheck, unit,
  browser e2e plus password-reset scenarios, and build (17 tasks).
- Fresh-image `bun run test:container:recovery` passes: source and restored
  containers each served the dashboard shell plus 25 assets and stopped
  gracefully (exit 0 in 0.2s, lock released); the bounded probe confirmed
  forced termination stays visible (exit 137, retained lock, refused restart
  citing the held lock) with guaranteed probe cleanup.

## Remaining limits

- The exit-2 branches have no fault-injection coverage; they are verified by
  structure plus the exit-0/137 acceptance, not by a live close/release
  failure.
- The 20s probe bound is heuristic (refusal normally exits in ~2s); a very
  slow daemon could in theory exceed it and fail the gate loudly rather than
  hang it — the preferred failure mode.
- The upstream `@elysia/static` immortal interval remains; re-verify shutdown
  when that dependency is upgraded (the acceptance test fails loudly on a
  return to 137).
- Shutdown diagnostics intentionally carry step/type only, not full context;
  deep diagnosis still uses the worklog bisection method.
