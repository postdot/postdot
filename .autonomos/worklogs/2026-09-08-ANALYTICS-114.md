# ANALYTICS-114 — Implement the first real Bluesky provider-owned engagement collection

## Objective and scope

Turn the existing Bluesky provider-owned observation slice into an explicit,
bounded public collection path. The slice collects the connected account's
followersCount, followsCount, and postsCount, plus likeCount, replyCount,
repostCount, quoteCount, and bookmarkCount for Bluesky publications already
known by Postbot. Operational analytics, discovery, feed crawling, scheduling,
UI, cross-provider scoring, content mutation, and real provider validation
remain out of scope.

## What changed

- Added explicit `partial_response` availability semantics across the core
  provider-observation contract, API schema, SQLite schema, and migration
  0021_thankful_jack_power. The migration rebuilds the observation table while
  preserving existing rows and indexes.
- Hardened the Bluesky public AppView reader with an injectable fetcher, no
  Authorization header, a default 10-second timeout capped at 60 seconds,
  abort coverage for fetch and JSON parsing, explicit provider error mapping,
  and validation of DID, handle, AT URI, CID, counters, and source timestamps.
- Kept collection strictly bounded to one profile read and one
  `app.bsky.feed.getPosts` hydration request for at most 25 known publication
  AT-URIs. There is no feed, search, firehose, or account-content discovery.
- Preserved measured zeroes, missing optional counters, blocked/not-found
  posts, rate limits, temporary failures, malformed responses, unsupported
  metrics, and omitted requested posts as distinct normalized observation
  states. No raw provider payload, error text, token, or credential is stored
  or returned.
- Added a sanitized per-invocation coverage envelope with complete, partial,
  and unavailable states, requested/returned/measured counts, and explicit
  metric gaps. `observedAt` preserves valid Bluesky `indexedAt` source times;
  `fetchedAt` remains Postbot's snapshot/idempotency boundary and freshness is
  `unknown`.
- Kept the project-authenticated GET route provider-free and made collection
  available only through the existing explicit POST route. Project isolation,
  known-publication selection, immutable snapshot history, and same-fetch
  idempotence remain owned by the existing database/service boundaries.
- Added focused reader, API, store, and migration compatibility tests. The
  operational analytics route and ANALYTICS-111 projection work were not
  changed.

## Decisions and durable limits

- The public AppView endpoints are the official provider surface for this
  slice: `app.bsky.actor.getProfile` and `app.bsky.feed.getPosts`. The latter
  has a 25-URI limit and no cursor, so the implementation treats it as one
  bounded known-content hydration page rather than inventing pagination.
- A missing optional counter is `not_reported` with a null value; a provider
  zero is `measured` with value 0. An omitted requested URI is
  `partial_response`, not `not_found`, because omission does not prove
  deletion. Provider timestamps are source index timestamps, not a freshness
  guarantee.
- Re-executing with the same `fetchedAt` is deduplicated by the existing
  project/provider/subject/metric/fetch-time key. A later fetch time creates a
  new immutable snapshot, so history is not silently overwritten. Repeated
  provider URIs in one collection keep the first Postbot publication
  association.
- The publication's existing `external_id` is the Bluesky AT-URI used for
  known-content hydration. The returned CID is recorded as the provider
  content revision identifier; a future revision-history relation is a
  separate decision.
