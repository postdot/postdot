# CRED-20 — Explicit provider application selection at channel OAuth start

- Status: implementation complete; branch ready for review
- Date: 2026-09-08
- Scope: make the runtime provider application choice explicit for OAuth
  channel connections without changing credential ownership
- Related issue: ISSUE-060
- Related decisions: ADR-056

## Implementation

The LinkedIn, Bluesky, and X channel OAuth start routes now accept an optional
`providerApplicationId`. The runtime resolver validates the id against the
requested provider and requires the application to be active. A missing id
continues to resolve the active provider default, preserving existing clients.
The selected id is already persisted on the authorization attempt and copied
to the resulting project-owned publisher credential by the existing runtime
boundary.

The typed web API client exposes the optional parameter for LinkedIn and
Bluesky and adds the X OAuth start method. The web settings surface remains
the place to manage applications; a channel-level selector can be added as a
separate UI pass without changing this API contract.

## Safety and validation

Invalid, disabled, or cross-provider application ids resolve to the existing
fail-closed provider-unavailable response and never fall back to another
application. No secret is returned or moved to the client.

The API regression coverage verifies that a non-default LinkedIn application
is selected and pinned to the authorization attempt. Targeted API/web
format, lint, typecheck, and tests pass; the complete repository gate remains
required before integration.
