# DOMAIN-39 — Define the multi-destination authoring and source-conflict recovery contract

- Date: 2026-09-02
- Status: complete
- Scope: shared source authoring, multi-publication creation, sibling draft recovery
- Task: DOMAIN-39
- Issues: ISSUE-009, ISSUE-010

## Objective

Turn the accepted `Post` to independent `Publication` model into a complete,
user-visible authoring contract without weakening zero-loss editing, target
revision immutability, or channel-owned validation.

## Working plan

1. [x] Trace the current API, persistence, and web composer behavior against the
   accepted source and target-revision decisions.
2. [x] Identify the smallest reusable domain operations needed to create and edit
   several publications from one source post.
3. [x] Compare credible recovery semantics for sibling drafts after a shared source
   revision changes, including preservation of target-specific work.
4. [x] Record the accepted recovery contract before implementing a migration or UI
   flow that would make the behavior difficult to change.

## Current evidence

- The domain and persistence boundaries already accept several publication inputs
  for one source post.
- The main web composer now renders a repeatable list of destination drafts and
  submits all of them in one atomic post creation request.
- A stale sibling draft is rejected when its source revision no longer matches the
  shared post. Existing tests prove the fail-closed invariant and preserve the
  sibling's old target work.
- `ADR-002`, `ADR-014`, and `ADR-015` require independent target content and
  explicit promotion; they do not yet define how a human reconciles a stale
  sibling draft.

## Implementation map

- `apps/api/src/modules/projects/post-routes.ts` already exposes one atomic
  `createPost` operation whose request contains a source plus an array of
  publication inputs.
- `packages/db/src/manual-store.ts` validates every channel profile and target in
  the same transaction before inserting the post, working drafts, target revisions,
  media references, audit events, and automatic jobs. A failure rolls back the
  complete creation rather than leaving a partial fan-out.
- `apps/api/src/app.test.ts` already exercises two publications created from one
  source, including different target content and independent draft/scheduled
  states. The server boundary is therefore not the missing first step.
- `apps/web/src/routes/dashboard.tsx` keeps one source draft and a list of
  independently editable target drafts. `PublicationTargetList` owns the
  repeat/remove interaction and each card keeps its channel, target copy, delivery
  mode, and schedule together.
- `savePublicationDraft` accepts source and target edits together. A source edit
  increments the shared post revision and updates only the editing draft's source
  revision; sibling drafts become stale by design. The current API exposes the
  conflict as HTTP 409 and has no recovery operation.

## Recovery options under consideration

### Option A — Explicit per-publication rebase

Keep the current fail-closed behavior. A stale draft shows the current source and
the draft's source revision, then offers a three-way review. The user may apply the
new source to that target, keep or edit its target-specific adaptation, and save a
new draft revision. No target is changed until the user confirms the result.

This preserves independent target work and makes the conflict visible, but it
requires a source-diff/review surface and a server operation with explicit expected
revisions.

### Option B — Explicit regeneration for untouched adaptations, review otherwise

Track whether a target draft still equals the adaptation generated from its previous
source revision. An explicit source-update action may regenerate only those
untouched drafts; manually edited targets remain in review with their content
preserved.

This reduces repetitive work while protecting deliberate target edits, but adds a
derived-state comparison and clearer semantics for target overrides.

### Option C — Silent sibling propagation

Advance the source revision and rewrite sibling drafts automatically from the new
source.

This is the least code, but it can destroy channel-specific edits and contradicts
the zero-loss and explicit-promotion boundaries. It is not recommended.

## Accepted direction

Use Option A as the first explicit contract. It is the smallest behavior that
preserves every existing invariant without inventing heuristics about whether a
target edit was intentional. Option B can be added later if real authoring data
shows that repeated manual rebases are materially costly. This recommendation is
accepted by the owner on 2026-09-02. The durable contract is recorded in
[ADR-027](../decisions/ADR-027-use-explicit-publication-draft-rebase.md).

## Non-decisions

This task does not introduce a generic workflow engine, a new `Rendition`
aggregate, automatic text truncation, silent target mutation, or a replacement
for the accepted small semantic source vocabulary.

## Accepted recovery contract

Each working draft stores the source snapshot it was based on. A stale draft can
be explicitly rebased to the current shared source through a project-scoped API
operation. The operation advances the draft's source base and revision while
preserving its target content, selected target revision, schedule, and delivery
state. It does not promote or merge browser-local edits. The editor remains
responsible for reviewing the base/current/local values and for an explicit save
and promotion afterward.

## Current boundary

The source-conflict recovery slice is implemented. Working drafts persist their
source base, the migration backfills only unambiguous legacy rows and fails closed
when a stale legacy draft has no recoverable snapshot, and the store/API/editor
now expose the accepted explicit rebase flow. `ISSUE-010` is resolved after merge.

`ISSUE-009` is resolved after the multi-destination authoring pass. The main
composer now creates one source post with several target inputs while preserving
independent target content, schedules, and delivery modes. The existing queue and
per-publication editor expose the persisted validation and outcome for each target.
This pass intentionally does not add a generic schema editor to the compose form;
arbitrary custom profile payloads remain governed by the existing channel profile
and publication-editor contracts.

## Implemented recovery slice

- Added a validated `base_source_content` snapshot to every publication working
  draft and included the schema migration in the committed Drizzle history.
- Added a fail-closed migration guard. Current legacy drafts are backfilled from
  their source post; a legacy draft whose source revision is already stale aborts
  migration instead of receiving a fabricated base snapshot.
- Added the atomic `POST .../draft/rebase` operation with expected-draft-revision
  compare-and-swap semantics and an attributable `publication.draft.rebased`
  audit event.
- Added editor recovery controls that preserve browser-local edits, show the
  draft/current source snapshots, and block save/promotion until a stale draft is
  explicitly rebased.
- Added database, API, migration, and type/schema coverage for the new contract.

## Implemented multi-destination authoring slice

- Replaced the single-target dashboard composer state with a reusable target-draft
  model and a repeatable `PublicationTargetList` component.
- Kept channel, target-specific copy, delivery mode, and schedule together for
  every destination; target updates use functional React state updates so rapid
  interactions cannot overwrite a sibling card.
- Preserved the shared source media selection and mapped it independently into
  each target payload, including LinkedIn commentary adaptation.
- Added browser coverage for two destinations with different target payloads,
  schedules, delivery modes, shared media, and repeat/remove interactions.

The UI remains intentionally bounded to the common authoring vocabulary. It does
not guess or rewrite arbitrary custom profile payloads; the server still validates
each target atomically and the dedicated publication editor remains the place for
profile-specific JSON when that workflow is available.
