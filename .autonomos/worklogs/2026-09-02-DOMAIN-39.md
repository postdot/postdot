# DOMAIN-39 — Define the multi-destination authoring and source-conflict recovery contract

- Date: 2026-09-02
- Status: in progress
- Scope: shared source authoring, multi-publication creation, sibling draft recovery
- Task: DOMAIN-39
- Issues: ISSUE-009, ISSUE-010

## Objective

Turn the accepted `Post` to independent `Publication` model into a complete,
user-visible authoring contract without weakening zero-loss editing, target
revision immutability, or channel-owned validation.

## Working plan

1. Trace the current API, persistence, and web composer behavior against the
   accepted source and target-revision decisions.
2. Identify the smallest reusable domain operations needed to create and edit
   several publications from one source post.
3. Compare credible recovery semantics for sibling drafts after a shared source
   revision changes, including preservation of target-specific work.
4. Record the unresolved owner decision before implementing a migration or UI
   flow that would make the behavior difficult to change.

## Current evidence

- The domain and persistence boundaries already accept several publication inputs
  for one source post.
- The main web composer currently submits one publication input, so the central
  multi-destination workflow is not reachable from the primary authoring surface.
- A stale sibling draft is rejected when its source revision no longer matches the
  shared post. Existing tests prove the fail-closed invariant and preserve the
  sibling's old target work.
- `ADR-002`, `ADR-014`, and `ADR-015` require independent target content and
  explicit promotion; they do not yet define how a human reconciles a stale
  sibling draft.

## Implementation map

- `apps/api/src/modules/projects/post-routes.ts` already exposes one atomic
  `createPost` operation whose request contains a source plus an array of
  publication inputs.
- `packages/db/src/manual-store.ts` validates every channel profile and target in
  the same transaction before inserting the post, working drafts, target revisions,
  media references, audit events, and automatic jobs. A failure rolls back the
  complete creation rather than leaving a partial fan-out.
- `apps/api/src/app.test.ts` already exercises two publications created from one
  source, including different target content and independent draft/scheduled
  states. The server boundary is therefore not the missing first step.
- `apps/web/src/routes/dashboard.tsx` keeps one channel id, one target-content
  string, one delivery mode, and one schedule in local state, then sends a single
  publication input. The missing product slice is the authoring model and UI state
  for several independently editable targets.
- `savePublicationDraft` accepts source and target edits together. A source edit
  increments the shared post revision and updates only the editing draft's source
  revision; sibling drafts become stale by design. The current API exposes the
  conflict as HTTP 409 and has no recovery operation.

## Recovery options under consideration

### Option A — Explicit per-publication rebase

Keep the current fail-closed behavior. A stale draft shows the current source and
the draft's source revision, then offers a three-way review. The user may apply the
new source to that target, keep or edit its target-specific adaptation, and save a
new draft revision. No target is changed until the user confirms the result.

This preserves independent target work and makes the conflict visible, but it
requires a source-diff/review surface and a server operation with explicit expected
revisions.

### Option B — Explicit regeneration for untouched adaptations, review otherwise

Track whether a target draft still equals the adaptation generated from its previous
source revision. An explicit source-update action may regenerate only those
untouched drafts; manually edited targets remain in review with their content
preserved.

This reduces repetitive work while protecting deliberate target edits, but adds a
derived-state comparison and clearer semantics for target overrides.

### Option C — Silent sibling propagation

Advance the source revision and rewrite sibling drafts automatically from the new
source.

This is the least code, but it can destroy channel-specific edits and contradicts
the zero-loss and explicit-promotion boundaries. It is not recommended.

## Provisional recommendation

Use Option A as the first explicit contract. It is the smallest behavior that
preserves every existing invariant without inventing heuristics about whether a
target edit was intentional. Option B can be added later if real authoring data
shows that repeated manual rebases are materially costly. This recommendation is
not an accepted decision until the owner confirms the recovery behavior.

## Non-decisions

This task does not introduce a generic workflow engine, a new `Rendition`
aggregate, automatic text truncation, silent target mutation, or a replacement
for the accepted small semantic source vocabulary.

## Pending owner decision

When a shared source edit advances the source revision while sibling target work
still exists, should Herald use Option A (explicit per-publication three-way
rebase, preserving the target until confirmation) as the first recovery contract?
The answer determines the server operation and the web authoring state; no policy
is inferred from the current fail-closed error.
