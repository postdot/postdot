# WORK-11 — Make automatic execution history append-only and attributable

- Date: 2026-09-03
- Status: completed
- Scope: `packages/db` workflow execution history
- Task: WORK-11
- Related issue: ISSUE-011
- Decision: [ADR-028](../decisions/ADR-028-use-audit-events-as-execution-journal.md)

## Objective

Make every automatic publication attempt and outcome reconstructible without
replacing the current job and publication state projections. The existing
project-scoped `audit_events` table will be reused as the append-only journal.

## Accepted boundary

- Automatic execution actions use a stable `publication.execution.*` vocabulary.
- Events identify the publication and carry the job ID and attempt number in
  structured, non-secret metadata.
- Claims, effect-boundary transitions, outcomes, cancellation, and expired-claim
  recovery write their event in the same transaction as their state changes.
- The claim token and publisher credential material never enter audit metadata.
- No execution-history table, generic repository, or retention subsystem is
  introduced without evidence that the existing audit record is insufficient.

## Implementation plan

1. Add the workflow audit insert path and event metadata helpers.
2. Make claim persistence transactional with its `claimed` event.
3. Record effect-boundary, outcome, cancellation, and lease-recovery events in
   their existing transactions.
4. Add failure-injection and timeline assertions for all execution paths.

## Invariants

- A failed audit insert rolls back the associated lifecycle transition.
- A retry keeps the job attempt counter while its previous outcome remains in
  the audit timeline.
- Expiry before the external-effect boundary is recoverable; expiry after it is
  ambiguous and is never silently retried.
- Stale claims and duplicate completions remain no-ops and create no events.
- Existing current-state and public workflow behavior remains unchanged.

## Implementation

Added `packages/db/src/execution-audit.ts` for the stable automatic-execution
action vocabulary and JSON metadata serialization. The workflow store now wraps
job claims in an immediate transaction and records the claim event together with
the attempt increment. Existing effect-boundary, completion, cancellation, and
expired-claim recovery transactions now append their corresponding events after
the state changes succeed.

The journal identifies the publication as its entity and records the job ID,
attempt, transition details, timestamps, retry information, external result
identifiers, and normalized operational errors. Claim tokens and publisher
credentials are not persisted in the metadata.

## Verification

The focused workflow suite passed 14 tests with 105 expectations. It covers
successful publication, scheduled retry and exhaustion, terminal failure,
ambiguous provider outcomes, pre- and post-boundary lease recovery, cancellation,
stale fences, duplicate completion, and audit-trigger rollback for both claim and
completion transitions.

The full repository gate passed formatting, lint, strict typechecking, all unit
and integration tests (including 73 database tests and 36 API tests), the browser
E2E test, and all package builds. No whitespace errors were reported.

An independent read-only review of the resulting workflow boundary and event
semantics approved the implementation with no blocking findings.
