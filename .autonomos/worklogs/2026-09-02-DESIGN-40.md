# DESIGN-40 — Design and implement the project calendar planning surface

- Date: 2026-09-02
- Status: completed
- Scope: authenticated project calendar route and planning composition
- Task: DESIGN-40

## Objective

Give Herald a dedicated calendar surface for scanning scheduled publications
by time and moving into the existing publication editor without changing the
publication, scheduler, or persistence contracts.

## Owner-approved boundary

- The calendar is a project-scoped route beside Overview, Compose, Queue,
  Channels, and Media.
- It is a planning and orientation surface, not a second scheduler or a
  replacement for Queue.
- Existing publication states, target content, channel ownership, and editor
  semantics remain authoritative.
- The route must remain useful for manual and automatic destinations and must
  preserve the source-to-destination relationship when a user opens a day or
  publication.

## Selected provisional contract

- Show one project month at a time with Monday-first weeks and a stable
  six-week grid on desktop and tablet.
- Provide previous month, next month, and today controls without changing
  publication scheduling state.
- Group every scheduled publication by its local calendar date. Each item
  exposes its source title, destination channel, time, delivery state, and a
  direct link to the existing publication editor.
- Keep unscheduled publications explicit rather than placing them in an
  artificial date. Due manual work keeps its attention state in the same
  calendar surface.
- Replace the compressed month grid with a day-grouped agenda on narrow
  screens so the task remains readable without horizontal scrolling.

This is a provisional visual and interaction contract pending the owner's
rendered review; the underlying data and route boundary are implementation
decisions for this task.

## Alternatives considered

- A dense month grid for every viewport would preserve one composition but
  make destination, state, and time unreadable on a narrow screen.
- A chronological agenda for every viewport would be efficient for mobile
  but would lose the month-level planning signal that makes a calendar useful
  beside Queue.
- A calendar with drag-and-drop rescheduling or an inline scheduler would
  introduce new mutation semantics and conflict handling that are not part of
  the existing publication contract. The current surface links to the
  editor, where scheduling already has explicit promotion semantics.

## Initial evidence

- The current API exposes project publication summaries with state, channel,
  delivery mode, source title, and an optional scheduled timestamp.
- The current project route owns the loaded publication collection, so a first
  calendar candidate can be derived without a new backend endpoint.
- The Queue remains the denser comparison surface; the calendar should make
  time, destination, and next action legible at a glance.

## Implementation

- Added a project-scoped Calendar route and workspace navigation entry.
- Added pure local-date grouping and month-grid derivation with unit tests.
- Added desktop/tablet month and mobile agenda compositions, plus explicit
  empty and unscheduled states.
- Added route-level browser coverage for the empty state, scheduled event,
  month navigation, and editor handoff.
- Added a shared-shell scroll reset so route changes do not preserve a stale
  vertical offset underneath the sticky header.

## Validation

- The live authenticated workspace rendered the empty and populated calendar
  states with representative project data.
- The mobile render used the agenda rather than a horizontally compressed
  month grid; no horizontal overflow was observed.
- Calendar navigation moved to the following month and returned to the
  current month; a scheduled event opened the existing publication editor.
- `bun run --cwd apps/web test` passed with 9 tests.
- The focused E2E flow passed after covering the empty calendar, month
  navigation, scheduled entries, mobile agenda overflow, and editor handoff.
- The full repository gate passed: `bun run check`.

## Next steps

  composition, density, and state emphasis.
- Keep drag-and-drop, multi-week planning, filtering, and calendar-specific
  scheduling semantics out of this task until their interaction and domain
  contracts are separately designed.
- Revisit calendar density and additional planning affordances after the
  owner visual checkpoint, without weakening the Queue/editor boundaries.
