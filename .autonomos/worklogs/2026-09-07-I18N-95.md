# I18N-95 — Web localization foundation

## Objective

Evaluate the principal localization approaches for Herald's Vite/React SPA and
establish a small, testable foundation without coupling interface language to
publication content or API credential/provider behavior.

## Initial evidence

- Interface copy was mostly embedded directly in web components.
- There was no locale preference, translation catalog, fallback contract, or
  language switcher.
- Date and number formatting was scattered across components.
- The API already exposed stable error codes and parameters, making client-side
  translation preferable to translating server prose.
- TanStack Router is used for the SPA and can support locale-aware public routes,
  but the authenticated workspace does not currently need locale-prefixed URLs.

## Evaluation

The following official documentation was reviewed:

- TanStack Router's i18n guidance: https://tanstack.com/router/latest/docs/guide/internationalization-i18n
- Paraglide Vite integration: https://paraglidejs.com/vite
- Paraglide TanStack Router integration: https://paraglidejs.com/tanstack-router
- Paraglide strategies and client-only switching: https://paraglidejs.com/strategy
- inlang project/tooling documentation: https://inlang.com/documentation
- i18next TypeScript and translation loading: https://www.i18next.com/overview/typescript
- FormatJS React Intl: https://formatjs.github.io/docs/react-intl/
- Elysia plugin overview: https://elysiajs.com/plugins/overview

Decision comparison:

| Approach | Strengths | Costs for Herald now | Result |
| --- | --- | --- | --- |
| Paraglide JS/inlang | Vite and TanStack examples, typed message functions, build-time generation, tree-shaking | Compiler/toolchain input; full catalog migration still required | Recommended foundation |
| React i18next | Mature runtime ecosystem, lazy backends, broad integrations | Runtime instance/string-key model and less direct tree-shaking guidance | Keep as credible alternative |
| FormatJS/React Intl | Strong ICU and `Intl` formatting primitives | Runtime provider/formatter integration before product conventions exist | Keep for future formatting-heavy needs |
| Hand-written dictionaries | Minimal dependency footprint | Recreates validation, extraction, formatting, fallback, and tooling work | Rejected for the long-lived product |
| Elysia/API translation | Useful for server-owned messages and request negotiation | Duplicates the UI catalog and destabilizes API/CLI semantics | Deferred |

## Implementation

- Added the governance record `ADR-046`, later accepted by the project owner.
- Added the accepted issues and tasks for localization, live project updates,
  contextual notifications, and information density in the Autonomos artifacts.
- Added `@inlang/paraglide-js@2.25.0` to the web toolchain.
- Added the inlang settings, pinned message-format module, and `en`/`fr`
  catalogs under `apps/web/project.inlang` and `apps/web/messages`.
- Added compile lifecycle hooks for build, typecheck, and tests. Generated
  `apps/web/src/paraglide` output is ignored and recreated by those commands.
- Added `LanguageProvider` at the root route. It owns locale state, calls the
  generated Paraglide runtime, and synchronizes `document.lang`/`document.dir`.
- Added a small accessible language menu to the dashboard header using the
  shared UI primitives and Solar Icons.
- Added direct tests for English/French message functions.

## Browser issue found and fixed

The first real browser run crashed immediately with:

> Base UI: MenuGroupContext is missing. Menu group parts must be used within
> `<Menu.Group>` or `<Menu.RadioGroup>`.

The existing dropdown wrapper exposed `GroupLabel`, which requires a Base UI
group context. The new language menu initially composed that primitive in an
invalid structure. The menu was simplified to a plain visual label plus regular
menu items, avoiding an unnecessary radio-group context for two locale actions.
The account menu received the same safe label treatment. After restarting Vite,
the browser showed the menu, exposed English and French as menu items, and
switched from English to French without a reload or error boundary.

## Verification

- `apps/web`: `bun run i18n:compile` passed.
- `apps/web`: format, lint, typecheck, and tests passed after the initial test
  global import correction; the web test suite passed 31 tests.
- `apps/web`: production build passed. The current main bundle is approximately
  251.61 kB (81.63 kB gzip); the previous recorded build was approximately
  246.92 kB (79.87 kB gzip). This is an early directional comparison, not a
  final budget decision, because the branch also adds the menu surface.
- Browser: dashboard loaded on the isolated Vite port, language menu opened,
  and English → French switch completed through the real accessibility tree.
- No API, provider, publication, credential, or database behavior was changed.

## Remaining work

- I18N-99 should migrate production UI copy incrementally and introduce shared
  date/number/plural formatting helpers.
- Re-evaluate catalog splitting/lazy loading when the locale count and bundle
  measurements justify it.
- Decide later whether a user account preference should override browser
  preference and whether public/documentation routes need localized URLs.
- REALTIME-96 remains the separate workstream for live notification and queue
  updates; this foundation does not pretend that notifications are pushed yet.

## Result

The localization foundation is implemented and browser-verified on
`feat/i18n-foundation`. The project owner accepted ADR-046: Paraglide is now the
selected localization foundation. The full product is not yet translated; that
is an explicit follow-up rather than an implicit unfinished runtime mechanism.
