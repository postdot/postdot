## Objective

Review two independent architecture audits supplied by the project owner against
the current repository, accepted specifications, decision records, tests, and
runtime behavior. Separate confirmed structural gaps from intentional sequencing,
partially implemented boundaries, and observations that do not require action.

This pass is investigative. It must not turn an external recommendation into an
accepted architectural decision or implementation without project-owner review.

## Reconciliation findings

### Confirmed product and workflow gaps

| Finding | Evidence | Classification and consequence |
| --- | --- | --- |
| The web composer creates only one publication for a post. | `apps/web/src/routes/dashboard.tsx` sends one item in `publications`; `apps/api/src/modules/projects/post-routes.ts` and `packages/db/src/manual-store.ts` already accept and persist an array. | Confirmed critical product gap. The distinctive `Post` to multiple independent `Publication` workflow exists in the server boundary but is not usable from the main web authoring path. |
| Shared source edits have no user-facing recovery path for stale sibling drafts. | `packages/db/src/manual-store.ts` rejects a draft whose `sourceRevision` is stale. `packages/db/src/manual-store.test.ts` proves the first sibling can advance the source while the second remains stale and blocked. | Confirmed recovery gap, not a defect in the concurrency invariant. `ADR-014` and `ADR-021` explicitly require fail-closed compare-and-swap behavior. A follow-up must define rebase, propagation, or explicit review semantics before changing the invariant. |
| The target editor exposes raw JSON. | `apps/web/src/components/publication-editor.tsx` renders the `target-json` textarea. | Confirmed UX gap. Generated field editing is a valid proposal, but it must preserve runtime-defined custom schemas, provider-owned bindings, manual channels, and server-side validation. It is not grounds for removing the accepted JSON Schema profile boundary. |
| Execution transitions are not appended to the audit trail. | `packages/db/src/workflow-store.ts` updates publication and job rows on completion and recovery without inserting an `audit_events` row. The audit table and route already exist. | Confirmed auditability gap. Current publication and job state remains useful, but success, retry, failure, ambiguity, and recovery cannot be reconstructed as an append-only execution history. |
| The job stores an attempt counter and current error, not an attempt journal. | `packages/db/src/domain-schema.ts` defines `jobs.attempts` and one `error_message`; retry clears current claim and error fields. | Confirmed observability gap. The next design must decide the minimum durable attempt record and retention semantics without confusing job state with publication state. |
| Runtime health does not expose scheduler failure. | `apps/api/src/modules/health/routes.ts` always returns `status: ok`; `packages/core/src/scheduler.ts` has a terminal `failed` state; `apps/api/src/index.ts` starts the worker separately from the HTTP app. | Confirmed operational gap, with one unresolved contract question: `/health` may remain liveness while a readiness endpoint reports scheduler, database, and maintenance state. This boundary requires an explicit decision before implementation. |
| Project access is currently limited to the creating human actor. | `apps/api/src/modules/projects/routes.ts` lists projects through `manualStore.listProjects(user.id)` and creates the actor during project creation. No membership, invitation, or project-token route/model is present. The CLI uses `HERALD_SESSION_COOKIE`. | Confirmed sequencing gap. The absence is already acknowledged by the M5 milestone and does not imply a need for Better Auth publisher accounts. Before network exposure, bootstrap, membership, and machine access must be deliberately completed. |
| Direct publication-editor navigation can load a different shell project. | The `/dashboard` loader loads `projects[0]`, while the child editor route receives its own `$projectId`. | Confirmed route-state gap. The shell and child route need one URL-authoritative project context; this is separate from the visual design slice. |
| Shell navigation uses local anchors that do not exist in the editor child. | `apps/web/src/components/dashboard-shell.tsx` uses `#overview`, `#compose`, `#publications`, `#channels`, and `#media`; those IDs are rendered by `DashboardWorkspace`, not `PublicationEditor`. | Confirmed navigation gap on nested editor routes. The eventual route composition should preserve useful back-navigation rather than merely changing link syntax. |
| `manual-store.ts` has grown to 3,742 lines. | `packages/db/src/manual-store.ts` contains project, channel/profile, post/draft, publication, media resolution, reconciliation, and audit persistence. | Confirmed maintainability risk, not an immediate correctness failure. A future split should follow use cases and transaction boundaries; it must not introduce a generic repository layer merely to reduce line count. |
| The documented coverage command fails. | `bun run test:coverage` ran 222 passing tests but failed while Bun loaded `e2e/publication-media.spec.ts` through the Playwright test runner, which is not valid under `bun test`. | Confirmed tooling/documentation defect. Coverage must either target unit/integration files explicitly or use a dedicated Bun test configuration; the command and its documentation must agree. |
| Backup recovery does not carry the publisher encryption key. | `ADR-012` deliberately keeps the deployment key outside SQLite and says recovery must cover it separately. The README documents database/media bundle commands but not the separate key recovery procedure. | Confirmed operational documentation gap. Keeping the key outside the archive is correct; a complete recovery runbook must state how the operator preserves and restores the key without putting it in the bundle. |

### Intentional sequencing or non-defects

- One automatic provider, limited browser scenarios, and the absence of Redis or
  other services are consistent with the accepted single-process, evidence-first
  direction. They do not justify broadening the stack now.
- A calendar/timeline and an MCP server are useful future surfaces, not evidence
  that the current architecture is incorrect. They remain compatible with the
  existing API and product direction but need their own scope and contract work.
- The accepted continuous-development policy in `SPEC-005` is not a release
  shortcut. The reports correctly identify the risk of building foundations ahead
  of a usable loop, but reintroducing an MVP/V1 cut would contradict the accepted
  product direction. The practical response is to prioritize complete evidence
  around the central publication loop, not to discard durable boundaries.
- The dynamic JSON Schema profile, provider-owned capability contract, local/S3
  storage seam, `Post`/`Publication` distinction, and `Channel`/`Publisher`
  distinction are aligned with accepted decisions. Their presence is not itself
  proof of over-engineering; the missing editor and recovery surfaces are the
  actionable concerns.

### Prioritized follow-up proposal

This ordering is a proposal, not an accepted implementation plan:

1. **Publication fan-out and source-edit recovery.** Define the user-visible
   behavior for creating multiple targets and for revalidating or rebasing sibling
   drafts after a shared source revision changes. Keep target and execution
   snapshots immutable once promoted or started.
2. **Execution history and runtime readiness.** Define an append-only attempt
   record, audit-event semantics for every worker outcome, and separate liveness
   from readiness if both are needed. Add failure-injection evidence before
   changing the worker state machine.
3. **Project and machine access.** Decide the initial bootstrap policy, whether
   project membership is needed before public exposure, and the project-scoped
   credential contract for CLI and agents. Keep publisher credentials outside this
   boundary.
4. **Web route and editor composition.** Make the project URL-authoritative,
   remove shell state duplication where the router can own it, and replace raw
   target JSON with a schema-aware editor only after the profile-to-field UI
   contract is defined.
5. **Maintainability and operational hygiene.** Split the persistence store by
   coherent transaction/use-case boundaries, fix the coverage command, and expand
   the backup runbook and recovery test to include the separately managed key.

## Required owner decisions before implementation

The audit does not require an immediate answer on every observation. The next
design pass should nevertheless settle these boundaries before code changes:

1. When a post has several publication drafts and one editor changes the shared
   source, should Herald offer an explicit sibling rebase, mark siblings for
   review while preserving their target edits, or use another owner-approved
   reconciliation flow?
2. Should `/health` remain a liveness endpoint with a separate readiness endpoint,
   or should its current public contract become readiness-aware?
3. What is the first intended machine-access contract: project-scoped tokens,
   another credential type, or a deliberately human-only CLI until that boundary
   is designed?
