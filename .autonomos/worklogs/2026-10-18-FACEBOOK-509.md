# FACEBOOK-509 — Session-bound Facebook Page connection lifecycle

## Outcome

Implemented the application service and authenticated HTTP routes for Facebook authorization, callback completion, sanitized Page discovery and explicit Page selection. Selection persists an encrypted project-owned Page credential and publisher connection. Runtime configuration is opt-in through PublisherRuntimeOptions; the default installation has no Facebook application configured and returns 503. No Studio control, environment configuration, provider-application settings, content-profile registration or worker activation was added.

## Boundaries and implementation

The service requires a human session, current project editor access, an active channel with the built-in Facebook contract, and the connecting actor. Attempts bind project, channel, actor, provider, callback and application client ID. The OAuth callback consumes its attempt before exchanging a one-use code. It checks actual permissions and creates a separate short-lived, encrypted pending-selection phase. The browser receives only an opaque selection reference and sanitized Page metadata, never user or Page tokens. Pending choices are reusable for discovery and consumed once before connection persistence.

Page selection rechecks permissions and the exact chosen Page's publishing task. It never chooses a fallback. Authorization is checked again after provider reads. Concurrent selections have one consumption winner and create one connection. New credentials are revoked if connection persistence fails; existing credentials follow the established reconnect token-replacement path and are not revoked as unrelated cleanup. Page-token expiry is stored as unknown because Page discovery does not provide it; this is not a claim of permanent validity.

HTTP routes preserve the shared authentication macro and hidden project 404 boundary. API keys cannot execute the service. Responses containing authorization URLs or Page choices are not cached. The callback returns a 303 to the validated local return path, uses no-referrer, and reports failures without callback details or provider errors. Error transport uses Elysia's typed status wrapper; success responses retain TypeBox validation. The browser selection UI is still pending, so the callback target query is not presented as a completed human flow.
