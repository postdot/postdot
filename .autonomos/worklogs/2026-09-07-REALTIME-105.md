# REALTIME-105 — Establish the post-commit project signal boundary

## Objective

Replace SQLite polling as the normal realtime trigger with an action-reaction
boundary that dispatches only after a transaction containing an audit fact has
committed.

## Implemented

- Added `createDatabaseTransaction` and a transaction-local project-id frame to
  the DB package.
- Added `recordDatabaseCommitProject` and instrumented every production audit
  event writer.
- Added post-commit observer registration with isolated error handling.
- Replaced the process-level 250 ms journal watcher with a project-scoped
  in-memory wakeup hub exposing `publish(projectIds)`.
- Wired the API database observer to the realtime hub and notification
  projection.
- Made the notification projection interval opt-in; production startup runs a
  durable recovery pass and normal commits run projection immediately.
- Removed the now-unused global journal scan API.
- Superseded ADR-049 with ADR-050.

## Correctness coverage

- A successful transaction publishes only after its state and audit fact are
  visible.
- A rolled-back transaction publishes nothing.
- An observer failure does not turn a committed transaction into a failed
  transaction.
- Nested transaction frames do not leak project ids from a rolled-back
  savepoint.
- Project waiters are isolated and wake without a database timer.

## Limits

The boundary is process-local and covers Herald's supported single-process
write paths. A future multi-process deployment will need a durable
cross-process signal. The SQLite journal remains the replay source after a
crash or reconnect; the in-memory signal is not treated as durable state.
