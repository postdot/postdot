# MAINT-43 — Extract publication authoring persistence

- Date: 2026-09-03
- Status: completed
- Scope: `packages/db` publication authoring persistence and composition
- Task: MAINT-43
- Related issues: ISSUE-016, ISSUE-020

## Objective

Reduce the remaining responsibility concentration in
`packages/db/src/manual-store.ts` by extracting the publication authoring
lifecycle behind the existing `createManualStore` facade. The extracted unit
will own editor reads, working-draft saves, source rebases, and target
promotion while preserving the existing domain and transaction behavior.

## Starting point

- MAINT-41 extracted project and channel persistence.
- MAINT-42 extracted channel-profile state, draft, impact, and activation
  persistence while keeping profile impact atomic.
- `packages/db/src/manual-store.ts` still combines post creation, publication
  authoring, media resolution, manual execution, ambiguous reconciliation, and
  audit/listing concerns.
- The publication authoring lifecycle is concentrated in the editor-state
  reads and the `savePublicationDraft`, `rebasePublicationDraft`, and
  `promotePublicationDraft` transactions.

## Boundary and invariants to preserve

- Keep `createManualStore(database, options)` and all exported manual-store
  types stable for API, web, CLI, and test consumers.
- Keep the authoring lifecycle together because its operations share optimistic
  draft revisions, source-revision conflict detection, profile validation,
  media resolution, immutable target revisions, scheduling state, and audit
  attribution.
- Preserve one SQLite transaction for each draft save, rebase, or promotion.
  Promotion must continue to create the target revision and reconcile the
  pending automatic job atomically.
- Keep post creation, manual publication execution, and ambiguous-outcome
  reconciliation outside this boundary; they have distinct transaction
  semantics and will be reviewed separately.
- Do not introduce a generic repository abstraction, duplicate ownership of
  shared job/audit statements, or change domain/schema/migration behavior.

## Alternatives considered

- Move only the three transaction callbacks: insufficient because the editor
  reads and the shared target/draft persistence statements belong to the same
  authoring boundary.
- Extract all publication behavior, including manual execution and ambiguous
  reconciliation: rejected because execution and reconciliation have different
  external-effect semantics and would make the new module a second catch-all.
- Move every shared SQL statement into the new module: rejected because post
  creation and channel-profile activation still depend on selected statements;
  shared ownership would become unclear or require duplication.
- Introduce a generic persistence/repository interface: rejected because it
  would hide Bun SQLite transaction behavior without a second backend or a
  concrete test seam.

## Implementation

- Added `packages/db/src/manual-store/publication-authoring-store.ts` as the
  owner of publication editor reads, working-draft saves, source rebases, and
  target promotion.
- Kept the existing `createManualStore(database, options)` facade and all
  public authoring methods stable by composing the extracted store into it.
- Kept one SQLite transaction for each draft save, rebase, and promotion.
  Promotion still creates the immutable target revision, snapshots revision
  media, updates publication state, and reconciles the pending automatic job
  atomically.
- Kept shared actor, publication, channel/profile, media, job, and audit
  operations explicit in the injected persistence context. This avoids
  duplicate SQL ownership and preserves the transaction behavior used by
  profile activation and post creation.
- Moved persisted JSON parsing, canonical content hashing, validation-error
  construction, and row-to-domain mapping into focused `content-codec.ts` and
  `mappers.ts` modules shared by the remaining store and authoring boundary.
- Moved the publication column fragment into `sql-fragments.ts` so publication
  queries share one definition.
- No schema, migration, API route, or public store contract changed.
