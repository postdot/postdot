# UX-267 — Configuration review and context continuity

## Scope and evidence

Reviewed the owner's captures and the General, API keys, installation overview,
instance access, provider applications and workspace administration compositions.
This pass uses source inspection and isolated browser journeys; it does not claim
an exhaustive visual review of the live installation or change real accounts.

## Changes

- The account Settings entry carries workspace and project context. Preferences
  now resolve that project instead of always rendering an empty selector.
- Sidebar settings links and workspace-selector administration retain the same
  context. Explicit no-project context remains `none`; no arbitrary project is
  assigned when entering preferences directly.
- Empty selector identity uses the same full-height segment as resource avatars
  in the compact header, preserving menu-row geometry separately.
- Calendar inspection uses one raised sheet material across header, body and
  footer, with inset content blocks; the general overlay token remains unchanged.
- The navigation matrix asserts project continuity through preferences and
  workspace administration. Existing administration-scope assertions remain.

## Review findings and proposed sequence

1. **Personal account (UX-268).** General exposes appearance/language and API keys
   have their own page. No authenticated profile/name/avatar/password editor is
   wired in the web app. Email password-reset APIs exist. Add a deliberate Account
   destination with profile and security sections; specify avatar storage and
   validation, current-password requirements, session consequences and recovery
   before implementation. Do not confuse publisher OAuth with person login.
2. **Scope and navigation (UX-269, continuation of UX-244).** Keep personal,
   installation and workspace settings distinct. General is a preference page,
   not a generic landing page to pad with explanatory cards. Administration
   Overview currently repeats the sidebar's two destinations; assess removing
   the redundant landing or replacing it only with useful installation state.
   Keep permissions visible in navigation and readable on copied/direct URLs.
   Remaining return controls resolve a workspace landing rather than necessarily
   the originating project's exact route; review return behavior and switching a
   selector while inside Configuration before changing that contract.
3. **Administration forms (UX-270).** Workspace groups use multiple nested raised
   and translucent inset sections. Review populated groups, members, invitations,
   permission details and mobile actions together. Provider applications have a
   separate form/list composition and retain explanatory OAuth text that can be
   necessary: review which material belongs at setup time rather than deleting
   capability/security guidance. API-key secret reveal, action ceilings and
   revocation must stay explicit. Compare light/dark, loading/error and narrow
   states rather than applying a mechanical reskin.

## Decisions

Project selection is navigation context on global settings, not an authorization
scope. It belongs in existing search parameters for shareable and reload-safe
navigation, not hidden local storage. Global settings keep project realtime
subscriptions disabled and do not acquire project operational navigation.

The drawer issue is adjacent-material composition, not evidence that every
popover should become darker. Avoid another global palette change to fix one
patchwork surface.
