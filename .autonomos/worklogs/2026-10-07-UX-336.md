# UX-336 — Apply Upload Results in File-Addition Order

- Base: `ad8c7e67b`.
- Status: complete; targeted and full checks passed.
- Owner accepted the UX-335 recommendation to preserve addition order without
  serializing uploads.

## Outcome and boundaries

The existing uploader still processes a single batch sequentially and independent
batches may overlap. Their selection effects are now applied in batch-addition
order. A completed later batch waits for earlier batches to settle, not for a new
upload to start. Failed or undefined results release their position; successful
files from partially failed batches retain Uppy result order. No placeholders,
new recovery policy, new provider call, dependency or server contract is added.

Application reads `currentValueRef` at the moment the batch is applied. It appends
new assets without restoring an old selection, preserving existing accessibility
metadata, library choices, deletions and explicit reordering of existing assets.
The existing interaction lock and recovery-completion path remain unchanged.
Removing files from Uppy after their upload settles does not remove the media
references retained by the controller for buffered results.

## Implementation

`createOrderedUploadResults` lives beside the existing upload orchestration in
`apps/web/src/lib/herald-media-upload.ts`. Reserving a slot is synchronous in the
picker's `files-added` callback, before the upload starts. Completion settles a
slot exactly once; ready leading slots apply in order. The picker catches rejected
uploads and settles their slot with the existing error presentation.

Two unit tests prove reverse completion is buffered, duplicate settlement is
ignored, a failed batch releases successors and application uses the current
selection rather than its earlier snapshot.

The retained destination-preview browser scenario now holds the first finalize,
adds a second file and requires its successful finalize response to finish before
releasing the first. Three distinct colored numbered assets must render in
red/green/blue order at both widths. The saved composer draft fetched from the
server must contain exactly the preview asset identifiers in the same order.
This replaces the temporary diagnostic expectation of green/red/blue with the
accepted regression contract.

## Limits and next recommendation

Later successful attachments are not selected until an earlier batch settles;
this preserves order without serializing network work. An earlier indefinitely
pending request still delays later selection, as it previously delayed its own
selection. There is no new timeout or cancellation policy.

Recovery completion bypasses the ordinary file-add sequence as before; no new
ordering guarantee for recovered mixed batches is claimed. No real provider
delivery was exercised. Deletion/reordering safety is established by current-state
application and existing interaction guards, not by a new end-to-end concurrent
reorder journey.
