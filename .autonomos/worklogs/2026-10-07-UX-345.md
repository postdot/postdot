# UX-345 — Project composer adaptations through active bindings

Base: `fe622cfc8`. Follow the measured mismatch in UX-344.

## Correction

Explicit composer adaptations no longer guess `body`, `text`, `commentary`,
`body_markdown` or `media` from a platform identity. Immediately before creation,
read each adapted destination's active profile through the existing profile API
and use `adaptSourceContentToProfile` from core. Profile reads run concurrently,
once per adapted channel in a submission; no persistent profile cache is added.
The common source object is still submitted independently and remains unchanged.

Unmodified destinations retain server-owned source projection. The existing
DEV.to override decision remains to preserve title-only article drafts and their
empty body field; its field names now also come from declared bindings. This
tranche does not redesign when the composer offers article controls.

All profile reads finish before the single create-post request. A failed read
uses the existing action error path, without clearing work or sending a partial
creation. There is no guessed-field fallback. No API shape, channel-list metadata,
provider call, migration or promotion rule changes.

## Profile changes and concurrency boundary

Reading at submission avoids reusing an old cached profile. It does not lock an
active profile between read and POST. The server still validates the submitted
content against the profile it resolves at creation: an intervening incompatible
activation produces the existing review-required draft or scheduling rejection.
No claim of atomic profile pinning is made, and no new expected-version contract
is introduced. Existing source-fallback and empty-adaptation semantics stay intact.

## Retained browser proof

One new scenario in the existing composer pilot file creates root manual,
nested manual, nested HTTP and unmodified nested destinations from shipped
starter data. Two distinct real image assets are created through reserve,
upload and finalize. They are selected in reverse creation order through the UI.

The scenario refuses one active-profile read with a deterministic 503. It proves
zero post requests, retained source and attachments, then permits the read and
proves exactly one successful create request. Persisted drafts are compatible
with no validation issues; customized text uses the declared path, unmodified
text comes from the common source, and all destination media keep selection order.
The unmodified input contains no explicit target override. No publisher is called.

The focused scenario passed in 10.3 seconds (14.1 seconds with harness).
UX-344 supplies the pre-correction diagnosis and exact wrong-field examples.
Native destination and title-only behavior are covered by the existing pilot and
neighboring journeys in the final control, rather than duplicated here.

## Validation decision

The shared dashboard context is transversal, so the selector retains the complete
matrix. Static checks precede the complete matrix. The first attempt was interrupted on
the native regression described below; the final executable code passed a complete
control after the scoped correction.
No container behavior changes; container recovery is not required.

## Remaining scope

Custom article-control visibility, profile activation races, remote transmission,
and arbitrary provider-specific fields are not newly proved. Core projection
handles only Herald-owned semantics; it does not invent provider-specific values.
Next proposed diagnosis: determine whether composer formatting, title and length
controls for custom identities follow declared capabilities or platform names.

## Native article compatibility correction

The first complete control was stopped after the existing composer pilot
scenario failed on the required-title field diagnostic. The projection initially
omitted a blank headline, whereas the existing DEV.to override explicitly wrote
an empty title. A missing-field issue has a different path from an empty-field
issue, so the inline error disappeared. The native override now preserves its
empty headline as well as its empty body, using declared binding paths. The test
assertion was not weakened. The existing title-only article scenario passed even
in that interrupted run. The full pilot file is checked before the final control.

## Final validation and closure

The corrected pilot file passed all six scenarios in 1.6 minutes. Final
`bun run check` passed: 93 browser scenarios in 19.4 minutes, two password-reset
scenarios in 9.5 seconds, all unit suites, static checks and 17 builds. One worker,
no retries, no weakened assertions. The interrupted first control is recorded
above rather than counted as a successful run. Final documentation is checked
with `check:quick`; no second complete matrix is required for that documentation.

UX-345 is closed. UX-346 is registered as a diagnosis of custom-profile composer
controls against declared capabilities, without a presumed product correction.
