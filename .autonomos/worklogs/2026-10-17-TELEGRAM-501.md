# TELEGRAM-501 — Telegram execution and durable media

## Outcome

Registered the message-v1 Telegram adapter in the production worker registry. It resolves project credential secrets, validates the execution shape and snapshot media count, and forwards only common publication identity to the executor. Only an explicit authentication rejection marks credentials for reconnection; permission failures do not mislabel a valid token.

For a single pinned media, enforce format/byte/geometry bounds, reserve/start the existing delivery ledger, verify storage metadata and checksum, and hash the actual buffered bytes again before upload. The second hash prevents a same-size change between the initial verified read and the upload. Media are buffered as Blob inputs, bounded to the provider's 10/50 MB policy; this is not a streaming or zero-copy claim.

The protocol now requires the returned media file identity for media success. It remains an opaque provider value and cannot contain the credential. Complete the ledger with that file identity; persist the chat/message identity as the publication result. Missing identity or incomplete ledger completion remains ambiguous. Uploaded, uploading, remote-identified and ambiguous deliveries are never blindly replayed. Definite rejection marks the delivery failed so an allowed later retry can start again. Rate-limit deferral is preserved.
