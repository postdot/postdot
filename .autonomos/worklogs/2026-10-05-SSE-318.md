# SSE-318 — Quiet event streams survive the runtime idle ceiling

Fix and evidence for the defect prepared in
[SSE-318 preparation](2026-10-05-SSE-318-preparation.md). This pass touches
shared transport, so the full control is reserved for the final state.

No retry was added, no wait was lengthened, no timeout was widened beyond the two
SSE requests, and no product behaviour changed.

## The constraint, demonstrated before choosing an approach

The direction asked for Bun's `server.timeout(request, 0)` on the two SSE routes
only, and for a demonstrated constraint if that could not be done cleanly.

Access from Elysia is partially available:

- Bun's `serve` options are documented to receive the server handle as the second
  argument of `fetch`, and Elysia's Bun adapter passes it through
  (`live = serve.fetch = withOrigin(built.fetch)`).
- Elysia publishes the handle as `app.server`, and `listen()` assigns it
  synchronously before returning.
- **But the handle is only published on the instance that called `listen()`.**
  `createAuthenticatedElysia` builds a separate `new Elysia()` which is mounted
  with `use()`, so the instance that reaches `registerRealtimeRoutes` has
  `app.server === undefined`. Proven at runtime with a temporary probe:
  `[probe] app.server is undefined` on every stream request.

The direct approach therefore does not work, and it fails *silently*: the call
becomes an optional-chained no-op, so the fix appears applied while the stream
still dies. Confirmed by measurement, not by inspection alone — with the direct
`app.server?.timeout(request, 0)` in place the probe still showed `ECONNRESET` at
12002 ms.

The resolution keeps the direction intact: one explicit module-level bridge,
`apps/api/src/serving.ts`, published from `index.ts` right after `listen()`, read
by the two SSE routes. Only those two routes call it, and it only ever passes `0`.

## What changed

- `apps/api/src/serving.ts` (new): holds the serving handle and exposes
  `keepResponseAliveBeyondIdleTimeout(request)`, which disables the idle ceiling
  for one request. No-op when no server publishes a handle, which is the case for
  in-process tests.
- `apps/api/src/index.ts`: `registerServingHandle(app.server)` after `listen`.
- `apps/api/src/modules/projects/realtime-routes.ts`:
  - both SSE routes call the bridge *after* authorization, cursor parsing, and the
    cursor-ahead check, so rejected requests keep the default timeout;
  - both streams enqueue `: connected\n\n` from `start()`.

The `: connected` frame is an SSE comment: no event name, no data, no cursor. It
flushes the response so the client sees the stream immediately instead of after
the first heartbeat, and it fixes the notification stream specifically, which
previously wrote nothing until it had something to send and therefore never
flushed its status line.

Deliberately unchanged: the 15 s heartbeat interval, the re-authorization check
on every pull, the resync and access-revoked frames, disconnect handling, and
draft-change subscription cleanup. The diff to the stream logic is one constant,
two calls, and two `start()` hooks.

## Evidence

Every number below comes from the isolated probes or from tests. No browser suite
was rerun to produce them.

### Silent connection beyond several heartbeats

`bash scripts/sse-proxy-repro.sh chunks 75`, direct and through the proxy in the
same run:

```
direct:  5ms, 7ms, 15010ms, 30013ms, 45015ms, 60017ms  → still open at 75002ms
proxied: 8ms, 9ms, 15011ms, 30016ms, 45018ms, 60019ms  → still open at 75001ms
```

Four heartbeats, identical arrival sequences on both paths. Before the fix the
same probe showed one frame and then `ECONNRESET` at 12003 ms.

### Event received after silence, direct and through the proxy

`bash scripts/sse-proxy-repro.sh late-event 20` holds the stream quiet across a
heartbeat, then creates a channel on the same project:

```
direct:  event project.update (channel.created) 13ms after the mutation
proxied: event project.update (channel.created)  5ms after the mutation
```

No `502`, no `socket hang up` in the Vite log.

### User stream opens with no history

`bash scripts/sse-proxy-repro.sh user-stream`:

```
direct:  200 at 4ms, text/event-stream, frame ": connected"
proxied: 200 at 7ms, text/event-stream, frame ": connected"
verdict: opened with no business event
```

Before the fix this request never returned a `200` at all: the response headers
were never sent before the runtime closed the connection, so the proxy
answered `502`.

### Other routes keep their timeouts

- The runtime's default is untouched: `bun scripts/sse-runtime-idle-probe.ts`
  still shows a bare `Bun.serve` response torn down at 12003 ms with Bun's own
  `Bun.serve() timed out a request after 10 seconds` warning.
- No `idleTimeout` and no server-wide `server.timeout` appears in the diff; the
  only timeout call added is `keepResponseAliveBeyondIdleTimeout`, on the two
  authorized stream requests.
- A feasibility probe run before the change showed the same Elysia app serving an
  exempt stream that stayed open at 20 s while an untouched route on the same
  server was reset at 12003 ms.

### Revocation still effective, cleanup still runs

- `access-revocation-stream.test.ts`: 3 passing, covering revocation on the next
  idle pull, revocation on lookup failure, and byte-identical frames for refusal
  and failure.
- `realtime-validation.test.ts`: the burst test asserts 24 idle subscribers each
  hold one pending waiter and that the count returns to 0 after cancellation.
  It now also consumes each stream's opening comment, because a stream writes it
  before it starts waiting on the hub.
- Full API package: 256 passing, 0 failing.

### New regression coverage

- `serving.test.ts`: the bridge passes exactly `(the same request, 0)`, is a
  no-op without a handle, and can be withdrawn.
- `realtime-routes.test.ts`: both streams open with exactly `: connected\n\n`
  and no `event:`, `data:`, or `id:`; heartbeats still follow; a resuming client
  still asks the journal for everything after its own cursor, so the opening
  frame cannot skip an entry.

### Browser proof against the real mechanism

`bunx playwright test e2e/realtime-validation.spec.ts
e2e/web-312-live-access-revocation.spec.ts
e2e/web-314-editor-access-state.spec.ts` — 15 passed in 3.4 min, one worker, no
retry. These cover live revocation, the editor access machine, and the
notification inbox over a real browser stream.

- `2026-10-05-AUDIT-317.md` finding 5 keeps its measurements and gains the same
  correction of cause.

## Left deliberately undone

- **Removing the compensating waits.** Four specs hold 14 fixed sleeps and
  ceilings up to 300 s. Those are now candidates for removal, but shortening a
  wait and removing the defect that justified it are separate changes, and the
  second needs its own evidence.
- **Raising or removing the 15 s heartbeat.** The idle ceiling is now disabled for
  these two requests, so the heartbeat no longer races a runtime limit. Lowering
  the heartbeat anyway would trade permanent write traffic for nothing.
- **The governance change** proposed in the AUDIT-317 worklog is still unapplied.
