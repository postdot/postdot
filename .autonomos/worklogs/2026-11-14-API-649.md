# API-649 Implement admin API-key capabilities, anti-escalation, and `POST /api/access/members`

- Outcome: Added the 5 administrative API-key capabilities (`project:access_manage`, `publication:approve`, `workspace:manage`, `api_key:manage`, `instance:admin`), unrestricted `'all'` capability inheritance gated by live instance/workspace/project roles, strict anti-escalation enforcement on key creation/updates, server-authoritative Better Auth organization sync so `Bearer` API keys work identically to browser sessions, `POST /api/access/members` direct user/service-account provisioning with optional initial API key issuance, `GET`/`DELETE /api/access/members/{userId}/api-keys`, `project:read` expansion, and non-OAuth `channel:manage` credential routes (`devto`, `discord`, `telegram`, `bluesky`).
- Decisions:
  - Kept `publication:approve` distinct from `publication:manage` so content/draft-authoring agent keys cannot self-approve scheduled or review-gated posts unless explicitly granted `publication:approve` or `'all'` by a role holder.
  - Added server-side organization member/team/invitation sync helpers in `packages/auth/src/server-actions.ts` instead of forwarding request `headers` to Better Auth's cookie-only `auth.api.*` methods, keeping workspace and instance authorization enforced in Postdot handlers.
  - Corrected `toWorkspaceInvitation` in `apps/api/src/modules/access/workspace-routes.ts` to treat `null` `teamId` from Better Auth as omitted so TypeBox response validation does not return `422` on non-team workspace invitation acceptances.
  - Enforced strict anti-escalation in `api-key-routes.ts` when an API key with `api_key:manage` creates or updates another key (no widening `projectIds`, `actionAccess`, or capabilities beyond the calling key's own grants, while respecting Better Auth's 32-character API key name bound).
