# MAINT-42 — Extract channel-profile lifecycle persistence

- Date: 2026-09-03
- Status: completed
- Scope: `packages/db` channel-profile persistence and composition
- Task: MAINT-42
- Related issues: ISSUE-016, ISSUE-020

## Objective

Reduce the remaining responsibility concentration in
`packages/db/src/manual-store.ts` by extracting channel-profile state reads,
draft writes, impact previews, and activation behind the existing
`createManualStore` facade. Preserve the atomic relationship between profile
activation, publication draft/target assessment, media validation, and pending
job updates.

## Starting point

- MAINT-41 already extracted project and channel creation/listing while keeping
  the public manual-store facade unchanged.
- `packages/db/src/manual-store.ts` was 3,461 lines and still owned channel
  profile evolution alongside posts, publication drafts, target revisions,
  media resolution, reconciliation, and audit reads/writes.
- The profile lifecycle currently consists of `getChannelProfileState`,
  `createChannelProfileDraft`, `previewChannelProfileActivation`, and
  `activateChannelProfile`.
- Profile activation read persisted working drafts, pending target revisions,
  and pinned target media; it can update assessment state, cancel or reschedule
  pending jobs, and create new jobs for compatible automatic publications.

## Boundary and invariants to preserve

- Keep `createManualStore(database, options)` and all exported manual-store
  types stable for API and test consumers.
- Keep profile-specific SQL and transactions in the extracted module, while
  making every cross-use-case dependency explicit.
- Keep one SQLite transaction responsible for a profile activation and all of
  its assessment, publication, media, job, and audit effects.
- Preserve project/actor authorization, active/draft profile state rules,
  optimistic revisions, immutable profile versions, media capability checks,
  automatic-job reconciliation, and audit attribution.
- Do not introduce a generic repository interface, split an atomic operation
  across stores, or change domain/schema/migration behavior.

## Alternatives considered

- Move only the four public methods: insufficient because the activation
  transaction depends on profile-impact queries, publication updates, media
  resolution, and job statements that would remain hidden in the old module.
- Duplicate all dependent SQL in a new module: gives a quick split but creates
  competing ownership of shared publication/job statements and makes drift
  likely.
- Introduce a universal persistence/repository abstraction: rejected because
  it would hide Bun SQLite behavior without a second backend or a concrete test
  seam.
- Extract a profile-specific transaction module with an explicit persistence
  context: selected for review because it keeps transaction ownership visible,
  allows shared publication/media operations to be injected deliberately, and
  preserves the stable facade.

## Implementation

- Added `packages/db/src/manual-store/channel-profile-store.ts` as the owner of
  profile-specific SQL, impact assessment, draft persistence, preview, and
  activation transaction orchestration.
- Kept `createManualStore(database, options)` and its public profile methods
  stable by composing the extracted store into the existing facade.
- Kept shared actor, channel, profile, publication, media, job, and audit
  statements in their existing owner and exposed their use through an explicit
  typed persistence context. This avoids both a generic repository and
  duplicate ownership of publication/job SQL.
- Preserved one SQLite transaction for activation. Profile activation still
  updates profile state, publication assessments, working drafts, pending jobs,
  and audit attribution atomically.
- Reused the manual store's `ChannelProfileCompiler` instance so profile and
  publication workflows retain one validator cache.
