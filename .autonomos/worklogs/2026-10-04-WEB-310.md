# WEB-310 — Withhold viewer-forbidden actions in Overview and the calendar

Scope: UI gating only, following the AUDIT-309 finding. No new role policy, no
server change, no redesign, and the post-revocation state stays a separate
mission.

## Correction

Reused the existing editor predicate and the Queue gating pattern; no new
permission concept was introduced.

- `apps/web/src/components/publication-calendar-page.tsx`: the header
  `New publication` action now requires `canEditProject` (previously only
  `noChannels`), the bulk action bar renders only for editors, selection
  changes are ignored for viewers, and `readOnly` is passed to the calendar.
  The empty-state channel action was already gated and is unchanged.
- `apps/web/src/components/publication-calendar.tsx`: a `readOnly` prop hides
  the month day-add button, withholds week/day slot creation (slot clicks fall
  back to the existing day-expansion inspection behavior), and hides the
  selection-mode entry point that drives bulk mutations.

Consultation is untouched: event clicks still open the contextual preview, the
summary bar, due/scheduled reading, navigation, and the Queue link all behave
exactly as before for every role.

Distinction the mission asked for:

- **Forbidden** (role): create and bulk mutation entry points are not rendered
  at all for viewers, so no forbidden control and no raw 403 error.
- **Temporarily unavailable** (state): the existing `disabled` plus
  `disabledReason` behavior is kept, so an editor whose selection is not all
  `scheduled` still sees a disabled Reschedule/Cancel with its reason.

## Server controls verified

The server was already correct, confirmed both in the browser scenario and in a
throwaway API probe (since removed):

| Operation as viewer | Answer |
| --- | --- |
| `PATCH /publications/schedule` | 403 `forbidden` |
| `PATCH /publications/cancel` | 403 `forbidden` |
| `POST /channels` | 403 `forbidden` |

## Browser evidence

`e2e/web-310-overview-viewer-actions.spec.ts` (one journey, both roles, real
invitations and sessions, only the publications list is route-mocked):

- Owner: `New publication` and `Select` visible; Reschedule/Cancel absent
  until something is selected.
- Viewer: no `New publication`, no `Select`, no `Create publication`
  (month day-add), no Reschedule and no Cancel anywhere on Overview, while the
  scheduled publication is still visible and opens its preview sheet with
  channel, schedule, and status.
- Editor: `New publication` visible, `Select` visible, and selecting the
  publication reveals an enabled Reschedule/Cancel toolbar.

Non-vacuity was proved by reverting each gate layer separately: with the page
gating removed the viewer sees `New publication` (1) and the run fails; with
the calendar gating removed the viewer sees `Select` (1) and the run fails.

One test-design flaw was found and fixed while proving this: absence
assertions (`toHaveCount(0)`) initially passed against a page that had not
finished rendering. The scenario now waits for the rendered calendar
(`[data-calendar="reui"]`) before asserting absence.

## Observation left out of scope

The preview sheet's footer label follows the publication lifecycle
(`canEditPublication`), not the role, so a viewer opening a `scheduled`
publication sees "Edit publication" and lands on the read-only editor. That is
the existing preview contract and the destination is genuinely read-only, so
this mission did not change it.

## Remaining limits

- Week/day slot clicks for a viewer now expand nothing and create nothing; the
  time grid has no separate read affordance beyond event clicks.
- The `readOnly` prop is per component; the Queue, Media, and Channels pages
  keep their own equivalent gates.
- Post-revocation presentation is unchanged and remains its own mission.
