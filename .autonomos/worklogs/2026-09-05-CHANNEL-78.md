## Objective

Make the Bluesky OAuth connection flow work with authorization servers that use
Pushed Authorization Requests (PAR), while preserving the encrypted provider-state
and callback checks already owned by Herald.

## Evidence

- A live Bluesky authorization request returned an authorization URL containing only
  `client_id` and `request_uri`; the generated OAuth `state` was stored internally by
  `@atproto/oauth-client`.
- The previous route read `state` from the returned URL, returned `provider_unavailable`,
  and never created an authorization attempt.
- After the fix, the same real request returned HTTP 200, created a pending Herald
  authorization attempt, and opened `bsky.social`'s authorization page.

## Implementation

- Added a Bluesky state-store wrapper that captures the exact internal state key when
  the OAuth client writes it, while preserving the existing serializable state format.
- Updated the connection route to use the captured state key and retain a direct-URL
  fallback for authorization servers that do not use PAR.
- Added a Bun Web Crypto digest compatibility mapping for the lower-case algorithm
  names used by the AT Protocol client.
- Added focused regression tests for state-key capture and digest mapping.
