# PUB-237 — Specify the approval-request lifecycle and executable scheduling boundary

- Status: complete
- Issue: [ISSUE-139](../ISSUES.md#issue-139-separate-publication-preparation-from-approval-and-dispatch)
- Owner direction: The owner confirmed that a constrained external client must be able to prepare content without being able to publish or schedule it, and that an unapproved requested time must not trigger delivery.

## Current implementation evidence

- `packages/core/src/model.ts` defines publication states for drafts, scheduled work, execution, outcomes, and cancellation. It has no editorial-approval state. Its `reviewState` is limited to content/profile compatibility and must not be reused for editorial approval.
- `apps/api/src/modules/projects/api-key-permissions.ts` maps draft creation and editing to `publication:manage`, while scheduling, cancellation, publishing, retry, and reconciliation require `publication:dispatch`. This already provides the least-privilege boundary needed for an external client that may prepare but not dispatch.
- `packages/db/src/manual-store/publication-creation-store.ts` creates an actual scheduled publication when a real `scheduledAt` is supplied. The promotion path in `packages/db/src/manual-store/publication-promotion-store.ts` creates or updates the worker job for automatic publications. A proposed time therefore must be stored separately from the executable schedule and must not pass through these paths before approval.
- The existing project publication routes check editor authority for schedule and publish operations. The approval action can build on this human-session boundary; API keys must not gain approval authority.

## Accepted workflow contract

1. A limited API key may author or edit draft content and submit a review request with an optional proposed delivery time. It still cannot call dispatch operations.
2. A pending request is not scheduled work. Its proposed time is separate from `scheduledAt`; it creates no worker job and causes no provider side effect.
3. An authenticated human session with project editing authority reviews and approves or rejects the exact immutable target revision. Approval may schedule the publication, but only through an explicit human action.
4. If the proposed time passes first, the request remains pending and inert. Approval after that time must require an explicit choice to select a new time or publish now; there is no automatic late dispatch.
5. A rejection returns the item to an editable draft. Any content change after submission invalidates the request/approval and requires a new review of the changed revision.
6. Existing direct human scheduling remains unchanged unless the publication is explicitly submitted for approval. The workflow is about generic external access and does not identify an API caller as an AI agent.
7. No CLI/MCP client work is included.

## Implementation boundary

`PUB-238` is the authorized implementation task. It must prove that overdue or edited requests cannot create executable work, that bearer keys cannot approve, and that only approval of the reviewed revision can promote the requested time to a real schedule. It also owns the concise web review surface and localized, deterministic browser coverage.

No application code, migration, or runtime behavior changed in PUB-237.
