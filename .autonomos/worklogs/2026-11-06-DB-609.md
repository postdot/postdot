# DB-609 — Asynchronous persistence port (phase 0 of ISSUE-194)

Status: in progress (2026-11-06), branch `feat/postgres-storage-profiles`.
Owner direction: offer PostgreSQL alongside SQLite, preferably in one image. Single
instance by construction for SQLite or local media. Planned, documented transfers
SQLite ↔ PostgreSQL and local ↔ S3. Alpha with no users: compatibility with existing
databases and the migration chain is not required, and migrations may be regenerated.
Decision record: [ADR-097](../decisions/ADR-097-selectable-storage-profiles.md) (proposed).

Plan: register the issue, ADR and phased tasks; inventory phase 0; build the async port
with ambient transactions and an SQLite writer gate; convert one store end to end as a
proof; check in with the owner before converting the rest.

## Findings that shaped the design

- Stores use about 470 **raw `bun:sqlite` prepared statements** with `?N` parameters.
  The Drizzle query builder is used 4 times; Drizzle mainly holds the schema and
  migrations. Portable SQL plus a small dialect module is therefore cheaper than an
  ORM rewrite.
- Bun 1.4.4 `Bun.SQL` provides one async API for SQLite and PostgreSQL. A scratch test
  showed that under SQLite an outside read during an open `begin()` sees uncommitted
  rows, and an outside insert becomes part of the transaction (shared connection, no
  isolation). The SQLite profile keeps `bun:sqlite` behind a writer gate; `Bun.SQL` is
  kept for PostgreSQL.
- Triggers (79) and views (11) are written by hand in migrations 0019/0021/0023/0025.
  A regenerated baseline (DB-610) needs an explicit extras file per engine.

## Delivered so far

- `packages/db/src/sql/port.ts`: engine-neutral `SqlDatabase` / `SqlStatement` port
  (`get` → `null` when empty, `all`, `run` → `{changes}`, `values`, `exec`, `transaction`,
  `inTransaction`, `transactionScope`, `afterCommit`).
- `packages/db/src/sql/sqlite-adapter.ts`:
  - a FIFO writer gate admits one transaction or autocommit statement at a time;
  - `AsyncLocalStorage` frames bind statements to the open transaction;
  - nested transactions run as savepoints, and concurrent sibling savepoints are refused;
  - after-commit callbacks are dropped on rollback, and a context that escapes its
    transaction falls back to the gate.
- `client.ts`:
  - `createDatabase` attaches `database.sql`;
  - `defineTransaction(database, async cb)` returns `{(), deferred, immediate, exclusive}`;
  - `recordDatabaseCommitProject` publishes once per async transaction after the
    outermost commit;
  - legacy synchronous transactions throw while the async writer is busy (transitional
    guard, to be removed when the conversion is complete).
- `taxonomy-store` was converted end to end: statements, 10 transactions, async public
  methods, and multi-read listings inside one deferred transaction snapshot. Its callers
  were converted too: 13 API route handlers and two db test files.
- The conversion tooling is temporary, lives outside the repository (session scratchpad)
  and is guided by `tsc`:
  - `await_statements.py` converts statements and transactions;
  - `await_callers.py` awaits callers;
  - `make_async.py` makes enclosing functions async from TS1308 locations.
  It is ASI-safe for the repository's no-semicolon style.

## Transitional constraint

Until every store is converted, synchronous and async transactions coexist on one
connection; the guard turns any overlap into an error instead of corrupting isolation.
The branch must not be released before DB-609 completes.

## Continuation: full asynchronous conversion

The continuation converted the runtime stores, their API/provider callers, the
executor and scheduler, Better Auth hooks, fixtures, CLI qualification and analytics
benchmark. Store statements now use `database.sql`; the remaining Drizzle query
builders in reply/first-comment persistence run synchronously inside `runSync`,
which acquires the same gate. Startup migrations, offline recovery, backup and
fixture setup retain native SQLite access under their quiescence boundary.
The transitional synchronous transaction API and its obsolete guard test were
removed. The active persistence port is the single runtime transaction boundary.

### Isolation and ordering

- Public operations with several SQL steps now use explicit transactions: deferred
  snapshots for composite reads and immediate transactions for mutations. This
  includes authorization plus grant/actor writes, publication editor/list reads,
  notification mutations, shared-channel discovery, media usage/list reads and
  provider configuration/delivery checkpoints. Existing write transactions remain
  nested savepoints where these operations compose.
- Promise-returning array predicates and mappers became sequential awaited
  operations. This preserves ordering and prevents concurrent sibling savepoints.
- A refused concurrent savepoint must drain its already-running siblings before
  rollback. Otherwise a late sibling could write after rollback in autocommit.
  Both root transactions and savepoints now drain their descendants; regression
  tests check outer rollback and preservation of the parent scope.
- Better Auth uses the shared gate for individual adapter operations as well as
  transactions. Its native synchronous Drizzle transaction cannot keep an async
  callback atomic. The invitation lookup also uses the async port. A regression
  test proves that an auth read cannot see a pending Postdot write that rolls back.
- OAuth consumption remains committed before decrypting its erased envelope. A
  wrong deployment key must not make a callback reusable. Its binding check and
  state transition share a transaction, followed by decryption outside it.
- Runtime notification projection drains pending work before shutdown. Scheduler
  shutdown drains pending planning reads, ignores superseded plans and never arms
  a timer after stopping. An in-flight lease heartbeat drains without rearming
  after its external effect finishes. Focused tests hold these operations open to
  verify their ordering.
- API publication services and readiness probes no longer read the native client.
  Async access checks and remote-reader test hooks are awaited, including access
  revocation during a provider response.
- Type-aware promise rules now cover `db`, `api`, `auth` and `core`; auth/core lint
  scripts enable them. Compiler-guided audits cover the runtime and its scripts.

### Preparation for DB-610 (scratch only)

Generated a fresh SQLite baseline from the current Drizzle schema and compared it
with a database built by the existing migration chain. Current live objects are
**70 application tables, 160 explicit indexes, 48 triggers and 6 views**. The
larger initial trigger/view counts counted replaced objects across the full chain.
Column types, defaults, nullability and primary-key positions match after ignoring
physical column order.

The generator emits invalid SQL for `publications_channel_planning_at_idx`: it
splits the `coalesce` expression into quoted column names. DB-610 must keep that
expression index in reviewed extras. The generated schema also omits
`projects_workspace_id_id_uidx`, the 48 live triggers and the 6 live views. These
objects must be preserved explicitly and tested against the generated baseline.
No migration chain or existing database was replaced by this investigation.

Additional continuation checks:

- Realtime shutdown now closes streams immediately and drains pending user lookups
  before releasing database resources. Commit observers are removed before stopping
  projections, preventing late wakeups from reopening work during shutdown.
- Scheduler wakeup rechecks its stopped state after the asynchronous durable read,
  and server startup rechecks shutdown after asynchronous runtime initialization.
- Focused realtime/shutdown suites: 59 passed. Core/auth/scripts after the added
  scheduler cancellation regression: 239 passed.
- Baseline foreign keys also expose one existing declaration/history difference:
  `instance_state.default_workspace_id` uses `NO ACTION` in the historical schema
  and `RESTRICT` in the Drizzle declaration. DB-610 must make this choice explicit;
  all other foreign-key rows and CHECK-constraint counts match in the scratch
  comparison. Generation must also preserve the initial singleton state row.
- The full browser matrix exposed a timeout waiting for the mocked X reconnect
  success alert; its failure snapshot already shows the successful connection and
  alert. A focused rerun is running; no assertion or timeout was weakened.
- The focused trace reproduced the timeout on the denial callback instead of
  reconnect. Mocked OAuth performs a full document navigation with routing/cache
  disabled; development module loading took about 4.6 seconds, while subsequent
  API reads completed in 5–30 ms. The test now waits for the callback document's
  `load` boundary before checking the same alert with the unchanged assertion
  timeout. This is a navigation synchronization correction, not a product change.
