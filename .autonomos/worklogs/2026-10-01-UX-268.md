# UX-268 — Personal account contract

Status: complete; accepted contract implemented and full repository gate passed. The owner
accepted independent imported avatars and password changes that revoke other
sessions while preserving the current browser.

## Existing boundary

Herald mounts Better Auth's native handler. The installed implementation already
provides session-only `update-user` (name/image) and `change-password` endpoints.
The web API wrapper currently exposes neither. The native password mutation
verifies the current password and applies Herald's configured password policy.
With `revokeOtherSessions: true`, the installed version deletes prior sessions
and issues a replacement cookie for the current browser. A mounted integration
regression must verify this behavior rather than relying only on documentation.

Sources:
- `packages/auth/src/index.ts`
- `packages/auth/node_modules/better-auth/dist/api/routes/update-user.mjs`
- https://better-auth.com/docs/concepts/users-accounts

## Accepted first frame

Add Account to the personal Configuration group alongside General and API keys.
Use a centered Account title and existing left return. Two compact task sections:

- Profile: avatar beside the editable name, email as identity metadata rather
  than an editable field. Save appears as a normal explicit action for changed
  profile values, with errors beside the affected control.
- Security: password change is an explicit disclosure/dialog with current,
  new and repeated password. Use existing password-field semantics and policy.
  Do not show three permanently empty password inputs on the initial page.
  The dialog states the other-session consequence once, next to confirmation.

No account deletion, email-change flow, provider login or unrelated session
manager is implied by this proposal. These have separate lifecycle consequences.

## Avatar alternatives

1. Recommended: personal image upload, independent of workspace/project media.
   Stored through the existing media storage adapter but with separate ownership,
   object namespace and lifecycle. The avatar persists across workspace switches
   and cannot be deleted through a project's media trash.
2. Bounded first slice: editable name and password; keep the current generated
   avatar until the personal-media contract is accepted and implemented.

A remote image URL would avoid implementing upload but creates an external
image dependency and an awkward settings control. Project-media selection would
misrepresent ownership. Neither is the recommended photo-editing experience.

## Acceptance before implementation is complete

- Profile mutation updates header identity without losing current settings URL,
  project/workspace selection or unsaved unrelated controls.
- Server validation, invalid current password, policy errors and interrupted
  requests remain actionable. Password values never enter logs/local storage.
- Other isolated sessions stop authenticating after the password change; the
  current browser remains usable with its replacement cookie.
- Saving profile data cannot change email, membership or authorization roles.
- If upload is chosen: server-authoritative type/size validation, avatar access
  and replacement/deletion cleanup are tested under local and supported object
  storage contracts. Do not introduce a second file-storage implementation.
- Verify narrow/wide, keyboard, both locales/themes and pending/error states.

## Implementation and evidence

- Added the Account route to personal Configuration, with a compact identity form,
  camera action, editable name, read-only email and disclosed password dialog.
  Saving or uploading refreshes header identity without navigating elsewhere.
- Password changes use native Better Auth validation and hashing. The mounted
  HTTP regression verifies incorrect current passwords, replacement cookies and
  revocation of a second session. Name validation trims and bounds the value;
  native image updates are blocked to preserve the personal storage lifecycle.
- Session-only avatar routes reject foreign origins, oversized streams, SVG and
  unsupported/animated images. Inspection detects the actual image type and
  limits dimensions. Images remain authenticated, private and non-cacheable.
- The migration and DB-owned avatar ledger use the existing local/S3 storage port.
  Replacement/deletion have retryable cleanup, independent person ownership and
  the existing complete-backup deletion fence. Version 2 bundles include avatars;
  version 1 recovery remains supported. No project media ownership changed.
- Focused API/storage tests passed, including local and fake-S3 adapters, cleanup
  retries, backup fencing and verified backup/restore. The isolated browser journey
  passed name/photo/password updates and errors, both locales/themes and 1280,
  820 and 390 px, with zero automated accessibility violations. Inspected wide
  light and narrow dark screenshots, including the password disclosure.
- Development API restored after verifying the stopped process held a stale
  runtime marker and no process had the database open. Both development services
  are available. Source-watch reload reproduced the stale-lock failure; the API
  currently runs in development without automatic reload to remain available.
  OPS-271 tracks a graceful development restart boundary without weakening
  runtime-lock safety. No real account credentials or profile data were changed.
