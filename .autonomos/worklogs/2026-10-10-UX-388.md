# UX-388 — media loading and transfer review

## Changes

Replaced initial loading text in the media page, attachment dialog and inline
picker with one shared skeleton. It follows the actual grid/compact/list column
rules, preview sizes and filename/context regions. Six placeholders reserve a
recognizable content area, without visible explanatory text. The status remains
named for assistive technology; animation respects reduced motion. Existing
assets remain visible during background refreshes.

## Transfer findings (code, not traffic measurements)

MediaPreview uses the authenticated original content route. Images are lazy
loaded, but the rendered dimensions do not resize the transmitted image. Video
uses preload=metadata and the server implements byte ranges. This is not proof
that a browser only transfers a small amount; MP4 structure matters. Content
responses use private, no-store: there is no HTTP cache reuse for these bytes.
The library paginates at 24 assets; this is not an unlimited whole-library load.

Do not relax cache rules as a cosmetic shortcut: requests enforce live access.
Recommend bounded image derivatives stored alongside originals, served through
an authorized preview endpoint and reused by library/search. Originals remain
for viewing/download/publication. Derivatives are disposable, not an additional
source of truth. No new service required. Sharp is a candidate, not installed or
selected yet: https://sharp.pixelplumbing.com/api-resize/ . Check Bun/container
compatibility before adoption. Video posters are a separate step; the previously
accepted no-FFmpeg production constraint remains in force.

## Verification

Static checks and one existing media-library browser scenario, holding the list
request to prove a visible skeleton, no loading text and removal after response,
then completing existing viewing/information/bulk actions. No full suite.
Final result: 1 passed in 14.4s (19.0s with harness); loading screenshot inspected. Thumbnail pipeline not implemented here.
