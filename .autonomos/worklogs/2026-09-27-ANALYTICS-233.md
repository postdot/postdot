# ANALYTICS-233 — Define the first useful publication-performance analytics workflow

- Status: complete research; product recommendation not yet adopted as an implementation decision
- Issue: [ISSUE-137](../ISSUES.md#issue-137-define-a-useful-publication-performance-analytics-workflow)
- Research date: 2026-09-27
- Repository: Postbot, local `main`
- Scope: publication outcomes visible to Postbot users, not Postbot runtime telemetry

## Objective

Recommend a concrete user workflow and an implementation boundary for the
publication-performance analytics the owner described (for example, views and
comments). This work is discovery only: no provider calls, collector changes,
database changes, schedules, credentials, or user interface were added.

## Existing Postbot behavior verified

- Postbot has two distinct data surfaces. `/api/projects/:projectId/analytics`
  reports Postbot-owned publication and execution facts. The separate
  provider-observation contract is for network-reported metrics. These must not
  be merged or presented under an ambiguous operational-telemetry screen.
- The only provider collector is Bluesky. It explicitly collects public profile
  and known-post counters, at most 25 known posts per request. It stores
  normalized observations and exposes an authenticated API read route; the
  collection route is explicit, and reading stored observations does not call
  Bluesky. There is no collector schedule and no project-dashboard analytics
  route today.
- A full Bluesky collection can produce up to 128 rows: three account metrics
  and five metrics for each of 25 known posts. The store's default read page is
  100 rows, with pagination up to 500, so a consumer must request a sufficient
  page or follow `hasMore` to read a complete snapshot.
- Each observation records the provider metric name, value/unit, subject,
  reporting period, observed/fetched timestamps, availability, freshness, and
  provenance. Raw provider response bodies are not retained.
- Observations are immutable per fetch instant. The table has no TTL or
  deletion method; project deletion cascades to them. Consequently, enabling
  recurring collection would retain every recorded snapshot unless a separate
  lifecycle policy is designed.
- A once-daily full Bluesky collection at the current 25-post bound would write
  at most 46,720 observations per channel-year (128 × 365), before indexes.
  This is a row-count scenario, not a measured SQLite size or a prediction of
  typical use. Ten such channels would be about 467,200 rows/year. The practical
  growth driver is frequency × known content × metrics, so opening a page must
  not itself trigger upstream collection.

## Current provider capability and fit

The earlier six-provider matrix in [ANALYTICS-109](2026-09-07-ANALYTICS-109.md)
remains a useful detailed baseline. Its material findings were checked against
current official documentation on 2026-09-27. “Available” means the provider
documents the capability; it does not mean Postbot implements it.

| Provider | Relevant post-level data | Access and product fit for Postbot |
| --- | --- | --- |
| DEV.to / Forem | Lifetime views, reactions, comments; also historical date-range and hourly past-day analytics. | Best documented fit for the owner's examples. Uses an API key, matching the existing connection style. Exact rate, retention, and freshness guarantees were not established in the current docs; confirm those before automatic collection. |
| Bluesky | Likes, replies, reposts, quotes, bookmarks; public profile follower/following/post counts. | Postbot already has the only implemented collector. Public reads need no provider credential, but the standard counters do not include views or impressions and do not provide provider history. Strong second provider and useful example of honest “not supported” metrics. |
| X | Public likes, replies, reposts, quotes, bookmarks, and impressions; additional non-public engagement/click values require user-context authentication. | Technically rich, but current X API pricing is pay-per-resource (currently $0.005 per Post read and $0.010 per User read; separate owned-read rules and monthly caps apply). Do not silently poll it or assume the discounted owned-read tier applies to a Postbot user's account. |
| LinkedIn | Impressions, members reached, reshares, reactions, comments, and additional metrics for eligible member posts. | Requires `r_member_postAnalytics` and access to LinkedIn's Community Management API. Postbot's current member scopes do not include that permission. Product approval, roles, versioning, and aggregation restrictions make it a gated follow-up, not a safe default. |
| Mastodon | Favourites, boosts, quotes, replies, and account follower/following/status counts. | Useful provider-native interaction counts, but the standard status/account objects do not supply a common views/impressions metric. Instance-specific visibility, policy, and identity need preserving. |
| Discord | Per-message reaction counts, including normal and burst reactions. | Postbot already uses a bot token and stores the returned Discord message ID, so a read path is technically plausible. It would require the bot to have message-read/history permissions in the channel and remains community/message interaction, not audience exposure analytics. Do not claim views or reach parity here. |

The providers do not define the same “view,” “impression,” or “reach.” Metrics
must remain named and attributed to their provider. Do not add a combined
cross-network view/reach number, engagement rate, or universal score. Even when
labels sound similar, aggregation and reporting periods must be verified before
combining them.

## User-workflow options

| Option | Value | Main limitation |
| --- | --- | --- |
| Add counters only to each publication's detail page | Keeps each value beside its post and is a small surface. | Does not answer “which of my recent publications performed best?” without opening posts one by one. |
| Add a project-level **Performances** page, one entry per published destination, with a provider-specific detail view | Gives the intended analytics overview while preserving channel attribution and filtering/sorting by date or provider. | Requires a web read model that handles partial provider coverage and clear freshness/availability states. |
| Put operational and provider analytics together on the existing operational report | Reuses the word “analytics” and some existing routes. | Mixes Postbot delivery facts with network-reported audience response—the exact conceptual confusion the owner ruled out. |

## Recommendation

Create a project-level **Performances** experience in the normal work/navigation
space, distinct from configuration and from operational telemetry. The useful
unit is a published destination (a Postbot publication on one provider), not a
single source post detached from its network outcomes.

The first screen should list published destinations and show only the metrics
that destination's provider actually reports, alongside a last-updated time and
an explicit unavailable/not-supported state. Selecting an entry can reveal its
provider-native details. Account follower trends, comment inboxes, discovery of
posts created outside Postbot, and “best time to post” are adjacent capabilities,
not prerequisites for this workflow.

For the first provider-backed implementation slice, prioritize DEV.to/Forem to
prove the views/reactions/comments use case, then surface the existing Bluesky
observations to validate partial coverage and a provider with no view metric.
This pair tests both the desired view-shaped data and the truthful absence case.
It is a delivery order, not a permanent provider limit. Keep X behind a visible
cost/access policy and LinkedIn behind its actual permission approval; do not
hold the whole user experience hostage to them. Add Mastodon and Discord only
with their own supported semantics and access paths.

Do not make dashboard reads call providers. For the initial experience, show
stored observations and let the user explicitly refresh a supported connection;
refresh must update the cache without delaying normal page reads. Prefer a
provider's own historical analytics endpoint where it exists (Forem); use
Postbot-collected snapshots only when the provider exposes current counters and
the product has chosen a refresh policy. Before recurring collection, accept a
provider-aware cadence, X spend guard, bounded post selection, and retention
policy. The current indefinite snapshot store is not sufficient authority to
silently enable scheduled growth.

Do not introduce a cross-provider aggregate score or translate “views” and
“impressions” into one number. Aggregate only within the same provider and
verified metric/period semantics; otherwise display per-destination rows.
Keep every missing or inaccessible value distinct from a measured zero.

## Proposed implementation sequence

1. Build the project **Performances** read experience and contract over stored,
   provider-owned observations; request all pages and render timestamps,
   partial coverage, and unavailable states. Keep it separate from the
   operational analytics API and do not fetch external data during page reads.
2. Add Forem article analytics using the documented totals/history endpoints
   and existing connection credential, with fixtures for metrics, empty
   responses, authorization, and rate-limit/error states. Verify endpoint
   quota/freshness behavior and ensure the content id maps to a Postbot
   publication before writing observations.
3. Surface the existing Bluesky observations in the same workflow and expose
   “views not provided” as an honest capability, not a zero. Keep the explicit
   collection action until an automatic cadence and retention boundary are
   separately accepted.
4. Reassess user value and data growth with the working page before adding
   automatic sync or more providers. X requires an explicit cost policy;
   LinkedIn requires provider program/scope access; other providers remain
   provider-specific rather than parity obligations.

This sequence gives Postbot an actual user-facing publication-performance path
without introducing a cloud dependency, a new analytics service, recurring
unbounded snapshots, or a false promise that all six networks expose views.
It does not establish a V1 or a permanent feature ceiling.
