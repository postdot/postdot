# UX-407 — Guard publication creation against account changes in a stale tab

Status: complete
Related: UX-406 (recovery isolation and draft guards)

## Reproduced behaviour

UX-406 guarded the composer draft endpoints but left `createPost` unguarded. A tab left on the original author, with another account signed in elsewhere in the same browser, still held its own content and could submit it; the request would carry the signed-in account's cookie and create the post under that account. The new browser scenario asserts the refusal; the API test asserts the contract directly.

## Changes and decisions

- `createPost` body gains optional `expectedUserId`. A mismatch returns 409 `account_changed` after the role check and before any store access. Omitting it stays compatible for API keys, CLI and older clients, like the draft guards.
- The Studio composer sends the author it rendered for. The refusal reuses the localized `account_changed` message ("Reload this page to continue"); the form keeps its text and the local copy stays under its author's key. The subsequent autosave refusal raises the UX-406 reload alert.
- Scope is deliberately limited to the one mutation that carries composer content. Channel setup and other project actions started from the composer carry no authored content and were not changed.

## Validation

- New browser scenario: a stale tab clicks Create draft after another tab signed in as a second author; the POST returns 409, the URL and typed text remain, and the second author has no publication. The five scenarios of `composer-account-isolation.spec.ts` pass.
- Adjacent post-creation journeys still pass (older-tab creation, composition recovery, title-only article, repeated-channel destination, tag-assignment feedback).
- API guard assertion added to the taxonomy post test; API 558 and web 296 unit tests pass; `bun run check:quick` passes.

## Limits and next scope

- The conflict comparison dialog can still read the saved draft as the current account if the account changes while it is open (carried over from UX-406, not reproduced).
- No proactive detection on focus: the stale tab learns of the change on its next write.
- Full browser matrix and physical-device acceptance not claimed.

Recommended next task: reproduce and close the comparison-dialog read under an account change, then decide whether a focus-time session check is worth its cost.
