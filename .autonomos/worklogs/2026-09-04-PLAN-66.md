# PLAN-66 — Next product sprint and isolated missions

Date: 2026-09-04
Status: completed

## Objective

Turn the selected open issues into an explicit next sprint and prepare bounded
implementation missions that can be dispatched safely through the established
orchestrator and explicit-worktree fallback.

## Integration gate

The current canonical `main` is `2c549ef2`. The verified audit-boundary work is
on local commit `11408cbb` on branch `qual/65-audit-boundary-regressions` and
must be integrated through a pull request before any sprint mission is
dispatched. Missions must use the resulting canonical head as their base and
must not start from an unmerged local branch.

No worker may start shared development servers, use real provider credentials,
modify `main`, merge, push, or edit shared governance files. The orchestrator
owns integration, browser and E2E validation, external effects, and cleanup.

## Sprint scope

The sprint is intentionally organized around project-owned custom channels and
supported machine access, with provider and scheduling guardrails before the
next expansion:

- `CHANNEL-67` maps to `ISSUE-033`: complete web onboarding and lifecycle for
  runtime-defined channels.
- `ACCESS-68` maps to `ISSUE-032`: expose project machine access through the
  supported web client and CLI.
- `PROVIDER-69` maps to `ISSUE-027`: establish a small explicit built-in
  provider execution contract before adding another built-in provider.
- `TIME-70` maps to `ISSUE-035`: define scheduling timezone semantics before
  expanding calendar behavior.

The recurring real-use validation in `ISSUE-021` remains a checkpoint at the
end of relevant work, not a parallel implementation task. `ISSUE-025`,
`ISSUE-026`, `ISSUE-031`, `ISSUE-034`, `ISSUE-036`, and `ISSUE-037` remain
outside this sprint because they do not currently block the selected product
objective.

## Mission contracts

The following contracts are dispatch-ready templates. The exact Codex-managed
worktree path and base hash must be recorded at dispatch time after the
integration gate is satisfied.

### CHANNEL-67 — Web channel onboarding and lifecycle

- Branch: `channel/67-web-runtime-channel-lifecycle`
- Semantic owner: the authenticated web channel-management experience and its
  client-facing state handling.
- Allowed paths: `apps/web/src/**`, relevant web tests, and generated route
  output owned by the TanStack Router tooling. `packages/client/src/**` may be
  added only if a typed route surface is genuinely missing.
- Forbidden paths: `.autonomos/**`, root configuration and lockfiles,
  `packages/db/**`, `packages/core/**`, provider packages, credentials,
  migrations, shared development resources, and real provider calls.
- Acceptance: a project owner can create and manage built-in and
  runtime-defined channels through the existing versioned profile and impact-
  assessment contract; lifecycle actions are explicit; existing publication
  references and credentials remain valid; the UI exposes validation and
  destructive-action consequences without inventing a second domain model.
- Checks: package-local format, lint, typecheck, and unit/integration tests
  only. Browser and E2E validation belongs to the orchestrator.
- Stop condition: any missing API or persistence invariant, new data ownership
  decision, migration requirement, or need to change the shared profile
  contract. Report the gap instead of expanding the mission.
- Report: changed paths, lifecycle matrix, tests, unresolved product decisions,
  and any browser scenarios the orchestrator must verify.

### ACCESS-68 — Machine access in operator clients

- Branch: `access/68-project-machine-clients`
- Semantic owner: project-token management and bearer-auth usage in the
  supported client and CLI surfaces; the existing API and persistence boundary
  remain the source of truth.
- Allowed paths: `packages/client/src/**`, `packages/client` tests,
  `scripts/herald.ts`, CLI tests, and the minimal authenticated web surface
  required to manage tokens. This mission must run separately from CHANNEL-67
  if both touch `apps/web/src/**`.
- Forbidden paths: token schema or migration changes, `.autonomos/**`,
  publisher credentials, logs containing token material, shared servers,
  default database/media paths, and external network side effects.
- Acceptance: a human-authenticated operator can create, display once, list,
  and revoke project tokens; ordinary project operations can use a bearer token;
  plaintext token values never enter persistent state, logs, or normal API
  responses after creation.
- Checks: package-local format, lint, typecheck, and unit/integration tests.
  The orchestrator performs any browser verification with isolated runtime
  resources.
- Stop condition: the existing API contract cannot support the client behavior,
  or authorization semantics require a new governance decision. Do not alter
  application authentication or publisher credential ownership.
- Report: command matrix, redaction evidence, authentication-path tests, and
  any required orchestrator-only checks.

### PROVIDER-69 — Built-in provider execution contract

- Branch: `provider/69-execution-contract`
- Semantic owner: the boundary between the workflow worker and built-in
  provider modules, without adding a new provider.
- Allowed paths: `apps/api/src/modules/workflow/**`, the publisher runtime
  composition under `apps/api/src/modules/publishers/**`, provider contract and
  test files in `packages/core/src/**`, `packages/linkedin/src/**`, and their
  package-local tests.
- Forbidden paths: database schema and migrations, custom-channel DSLs,
  Better Auth, shared governance files, real provider credentials, and
  unrelated UI or storage changes.
- Acceptance: provider credential resolution, capability checks, dispatch, and
  outcome mapping have a small explicit boundary; current LinkedIn text and
  image behavior remains unchanged; tests prove permanent, retryable, and
  ambiguous outcomes; no universal provider abstraction is introduced without
  evidence.
- Checks: package-local format, lint, typecheck, and unit/integration tests.
  The orchestrator owns provider smoke tests and the full repository gate.
- Stop condition: the proposed boundary requires changing publication
  semantics, database ownership, or a generic configuration language. Return a
  design report instead of forcing the abstraction.
- Report: before/after responsibility map, rejected alternatives, tests, and
  whether the next built-in provider can be added without enlarging the worker
  hotspot.

### TIME-70 — Scheduling timezone decision

- Branch: `time/70-scheduling-timezone-semantics` (only if implementation is
  later authorized)
- Semantic owner: the project scheduling-time interpretation across storage,
  authoring, calendar display, device changes, and existing data.
- Initial mode: read-only analysis; no code or Autonomos artifact edits by a
  worker. The orchestrator records the accepted decision after owner review.
- Allowed inspection: `packages/core/src/**`, `packages/db/src/**`,
  `apps/web/src/**`, relevant specifications, decisions, and tests.
- Forbidden actions: schema changes, migrations, date conversion changes,
  browser/server startup, and silently selecting a timezone policy.
- Acceptance: a decision report compares credible policies, identifies the
  meaning of existing timestamps, describes device and project behavior, and
  states migration and test consequences. Implementation starts only after an
  explicit accepted decision.
- Stop condition: the report cannot establish a safe interpretation of current
  data or more than one credible policy remains.
- Report: policy alternatives, invariant table, migration impact, test matrix,
  and a proposed ADR outline.
