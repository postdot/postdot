# ACCESS-14 — Add project-scoped bearer tokens and attributable machine principals

- Date: 2026-09-03
- Status: completed
- Task: ACCESS-14
- Issue: ISSUE-013
- Decision: [ADR-030](../decisions/ADR-030-project-scoped-machine-access.md)

## Objective

Give trusted scripts, CI, agents, and a future CLI a project-scoped authentication
boundary while keeping Better Auth limited to human email/password sessions and
preserving project-owned actor attribution.

## Accepted boundary

- Human sessions remain the application authentication mechanism.
- The initial human project policy remains creator-only; memberships and invitations
  are not introduced without a concrete collaborative requirement.
- Authenticated humans can manage tokens for projects they can access.
- A token is a revocable or optionally expiring bearer credential for exactly one
  project, with no fine-grained scopes in this slice.
- Token-authenticated operations use an `api_token` actor and cannot create projects
  or manage access tokens.
- Interactive publisher OAuth flows remain session-only; token-authenticated
  clients may use existing publisher connections but cannot start or complete a
  browser redirect flow.
- Plaintext token material is returned only at creation and is never persisted,
  logged, or exposed in metadata responses.

## Evidence

The repository already has `api_token` in the actor vocabulary and accepted
specifications require project-scoped machine access. Current gaps are the token
storage/rotation boundary, bearer authentication, and the actor lookup paths that
still restrict access to human subjects.

## Implementation and verification

- Added the project access-token table and migration with project/actor composite
  foreign keys, token metadata, expiry, revocation, and audit attribution.
- Added typed API routes for human token creation, metadata listing, and revocation;
  token plaintext is returned only by creation and is never stored or audited.
- Added authoritative Bearer authentication with project-token actors while
  preserving cookie sessions and rejecting malformed or invalid bearer headers
  without session fallback.
- Extended project-owned stores to authorize `api_token` actors and kept project
  creation, token management, and interactive LinkedIn OAuth session-only.
- Added OpenAPI Bearer/session schemes, public-route opt-outs, human-only security
  metadata, and explicit authentication/validation error responses.
- Targeted DB/API tests pass; the full repository gate passes with 76 DB tests,
  42 API tests, one browser E2E test, and all package builds.
- An independent review found no blocking issue after the OAuth, OpenAPI, response,
  and one-time-secret corrections were applied.
