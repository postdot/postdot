# UX-347 — Active-profile composer headline and length feedback

Base: `8aaf7cd85`. Approved follow-up to UX-346.

## Read and failure contract

The active destination profile is read through the existing authenticated API.
React Query keys include project, channel and active profile version. Infinite
stale time avoids typing-driven reads; activating another version updates the
channel list through existing realtime handling and selects a new key. No polling,
focus refetch or connection refetch is introduced. Failed reads are not retried
automatically: a quiet inline notice provides an explicit retry. Source text and
media remain editable; the existing title value is preserved, even when its custom
control cannot be established without the profile. Pending reads announce loading;
failed reads do not claim confirmed custom constraints. Existing native DEV.to
title and X weighted feedback remain available without a successful read.

Submission still uses UX-345's fresh reads. Preparation feedback does not pin a
profile atomically across creation, change server validation or authorize delivery.

## Controls and ownership

Use existing schema-aware target field resolution and declared headline/primary
text semantics, including nested bindings. A required headline exposes the
existing shared source title control; optional
manual metadata remains hidden to preserve the established workspace layout.
The native DEV.to control remains available. No destination title model is
introduced. Character counts
use Unicode code points, as JSON schema string length does. Declared grapheme
limits use Intl.Segmenter. Feedback does not pass maxLength into the editor or
input, truncate text, or block invalid draft persistence. Native X retains its
existing weighted parser and counter. Rich-editor dialects remain unchanged;
Markdown source acceptance is not treated as permission for article/Discord UI.

## Evidence plan

Unit cases cover nested semantics and an emoji sequence that has three code
points but one grapheme. A retained scenario in the existing composer pilot
covers root/nested short profiles, an unavailable read followed by retry,
retained source and headline, no reads per keystroke, narrow layout and persisted
invalid drafts with correctly projected headline and body. Existing native pilot
and X journeys supply adjacent controls.

## Validation decision

The selector falls back to the full matrix because the new helper is not mapped.
Do not bypass that conservative decision. Run focused proof first, then one
complete final control; no container behavior changes.

## Focused results and corrections

The retained scenario passed in 7.5 seconds (10.0 with harness), including a real
profile-draft save and activation from eight to ten characters. The new version
updates feedback without replacing text or headline. A narrow screenshot was
inspected; no page overflow. Both root and nested destinations persist complete
over-limit text as review_required drafts, with no missing-headline issue.

Two initial test assumptions were corrected: profile-draft save returns 200, not
201; initial development requests occur as a simultaneous pair under StrictMode
and provider cleanup. The network trace established that timing. The test samples
the initial read count, proves no increment from typing, then exactly one extra
read for explicit retry. refetchOnMount is disabled as well as focus/reconnect
refetching and retries; no assertion depends on an imagined single dev mount.
A TypeScript schema union in the unit fixture needed an explicit record view.
No production rule or server response was changed to satisfy these assertions.

## Limits

Custom weighted algorithms are not implemented here; native X keeps its existing
parser and display. Required fields and arbitrary schema constraints remain
server-authoritative. The title is still shared source state. No article or
Discord dialect is inferred for custom destinations. Profile activation races
between preparation/submission are not made atomic. Narrow English/dark rendering
is exercised; native/localization coverage comes from neighboring journeys.

## Neighboring layout regression

The first complete control exposed two failures: generic manual profiles gained
an optional title, and switching from X to Common moved the editor vertically.
The same optional-headline condition caused both. That attempt was stopped.
Headline visibility is now limited to declared required headlines and the existing
native DEV.to control; optional manual metadata remains hidden. Existing assertions
are unchanged. Focused neighbors are checked before the final complete control.

## Final control and closure

The two affected layout neighbors plus the new custom scenario passed together:
3/3 in 32.6 seconds. Final `bun run check` passed: 94 browser scenarios in
18.6 minutes, two password-reset scenarios in 9.0 seconds, all unit suites
(including 151 web tests), static checks and 17 builds. One worker, no retries,
no weakened assertions. The earlier interrupted control was not a successful
validation; the complete final run is the validation reference. Documentation is
finalized with static gates only; no third complete matrix for documentation.

UX-347 is closed. UX-348 records a bounded diagnosis of remaining platform-name
assumptions in composer controls, editor dialects and previews. No correction or
new formatting contract is presumed before that diagnosis.
