# OPS-217 — Evaluate crash-safe runtime exclusion

- Status: complete
- Date: 2026-09-26
- Base: `feat/offline-account-recovery` at `9fc5a9fe3`
- Issue: ISSUE-127
- Scope: Evaluate crash release and restore exclusion without changing the lock contract or promoting ADR-068

## Findings

- The current runtime lock uses exclusive creation of a database-specific
  `.runtime.lock` marker. Restore acquires it before validating the source or
  touching the destination. Graceful shutdown removes the marker; process death
  cannot run that cleanup, so automatic reclamation is intentionally absent.
- A child Bun process acquired the current server lock on a temporary database
  path under `/tmp`. A real `restoreDatabase` call from the parent was rejected
  at lock acquisition before it inspected a deliberately missing backup. After
  SIGKILL, the marker remained and restore continued to fail closed. This
  reproduces both the safety property and the operator-recovery cost.
- A separate `flock(2)` prototype used a persistent temporary lock file on the
  repository's local ext4 filesystem. A second process could not acquire the
  exclusive lock while the holder was alive; after SIGKILL, the second process
  acquired it. This demonstrates the kernel primitive's process-lifetime
  behavior on this Linux host only; it is not a Bun integration or a test of
  macOS, Windows, network filesystems, or production container volumes.
- The production Dockerfile uses the official Bun Linux image. The development
  guide requires Bun but does not declare native Windows or macOS API deployment
  support. The repository therefore has a confirmed Linux container target but
  no explicit host-platform support matrix.

## Options and trade-offs

1. **Keep the current fail-closed marker.** It remains dependency-free, easy to
   inspect, and verified to exclude restore while present. A hard stop requires
   an operator to confirm that no Postbot process remains and remove the exact
   marker. This is the only option already integrated and regression-tested
   through the complete server, restore, and recovery lifecycle.
2. **Use a process-lifetime OS file lock.** Linux `flock(2)` releases ownership
   when the final descriptor closes, including after process death. Windows
   `LockFileEx` also releases locks after process termination, though the OS may
   take time to do so. This meets the desired crash behavior when every Postbot
   participant uses the same lock. The lock file must be a stable inode and must
   never be unlinked or replaced while participants may hold it; a separate
   database-specific lock file is appropriate because restore atomically
   replaces the database file. Advisory-lock semantics, file-descriptor
   inheritance (including close-on-exec handling), filesystem behavior, and
   migration from existing stale marker files must be covered explicitly.
   An additional ext4 experiment confirmed that unlinking and recreating the
   lock path while its original inode is locked lets a second process lock the
   replacement inode. The lock file therefore cannot be removed on release.
3. **Use a heartbeat/stale-timeout lockfile.** A mature JavaScript option such
   as `proper-lockfile` avoids native bindings, but reclaim is based on an
   `mtime` threshold. A long pause or delayed filesystem update can make a live
   holder appear stale; its own documentation also notes that SIGKILL and VM
   fatal errors do not run cleanup. It therefore cannot establish the requested
   strict active-restore exclusion without relying on timing assumptions.
4. **Reclaim based on PID or marker age.** This is rejected by ISSUE-127 and
   ADR-068: PID reuse, host identity, process namespaces, and long pauses prevent
   either signal from proving that the database is unused.

## Recommendation

Do not replace the lock as part of this evaluation. The Linux experiment proves
that a kernel-owned lock can remove stale-marker cleanup on a local filesystem,
but it does not establish a supported cross-platform implementation. The
available cross-platform lock package advertises Unix and Windows primitives,
but its upstream currently reports version `0.0.1`, one repository star, and no
release history; that is insufficient evidence for a core database-safety dependency.
`proper-lockfile` is more established but uses staleness timeouts and does not
meet the issue's no-false-reclamation requirement.

Before implementation, the owner should choose whether direct native Windows
and macOS deployments are supported in addition to the Linux container. If the
answer is Linux-only for the server runtime, a separate implementation task can
evaluate a maintained Bun-compatible binding around whole-file `flock`, with a
stable never-deleted lock inode and cross-process tests for server startup,
restore, account recovery, SIGKILL release, and filesystem failure. If native
Windows/macOS are supported, first select a dependency with proven Bun support
and CI coverage on every supported OS; retain the existing fail-closed contract
until that evidence exists. Do not use a stale timeout as an automatic fallback.

ISSUE-127 remains accepted because the current behavior is unchanged. ADR-068
remains proposed; this evaluation does not promote it or alter its contract.

## Verification

- Cross-process sidecar experiment: active restore blocked before source
  validation; after SIGKILL the marker remained and restore failed closed.
- Cross-process Linux `flock` experiment on ext4: active holder excluded a
  second process; after SIGKILL a second process acquired the lock.
- Unlink/recreate experiment on ext4: a second process acquired a replacement
  lock inode while the original inode remained locked.
- No application source, lock behavior, or ADR status was changed.
