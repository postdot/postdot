# FACEBOOK-507 — Content profile and permission-gated Page selection

## Outcome

Defined the isolated page-post-v1 Facebook profile, compiled with the actual core compiler and native validation adapter. Text, link or one JPEG/PNG photo can provide content; a title is not invented. Cross-field errors identify text/link fields. Source adaptation maps body/media and preserves an explicit destination link rather than scraping URLs from prose. Photo-only source content needs no dummy text. Schema rejects extra fields, malformed references and multiple media. The shared protocol and profile treat an empty optional link as absent; meaningful link plus photo is rejected.

The native endpoint reference does not establish a text maximum. The draft profile intentionally leaves text capabilities unset rather than inventing one or changing the shared capability contract. This is not an unlimited-text claim; the profile and adapter are not registered in the API, channel catalog, worker or Studio. Resolve this before enabling creation.

Added actual granted-permission reading and explicit Page selection to the server-side protocol. Selection checks the three publishing permissions through /me/permissions before obtaining a Page-token batch, then requires the selected canonical Page ID and CREATE_CONTENT task. Missing, declined or expired grants stop before Page-token discovery. Contradictory, unknown, malformed and paginated/incomplete permission replies fail closed. No fallback to another Page. Existing pagination uses only an explicit cursor and fixed Graph endpoint.

The returned selection contains a Page token for later encrypted persistence; it remains server-only. Narrow package guidance states that token provenance and project/actor binding must be established by the validated OAuth callback, not inferred from this metadata helper.

## OAuth boundary and remaining scope

The initial intention included connection wiring. Reading the current official manual-login guide exposed a concrete compatibility checkpoint: its code exchange uses GET with code/client-secret parameters, while the existing oauth4webapi wrapper uses standard POST and PKCE by default. The web guide does not establish PKCE enforcement. This pass does not interpret that absence as evidence that PKCE is unsupported, disable it, or introduce an active callback based only on mocks. Recorded the checkpoint in the existing discovery document. Connection persistence and full OAuth remain unfinished; no secure connection is claimed.
