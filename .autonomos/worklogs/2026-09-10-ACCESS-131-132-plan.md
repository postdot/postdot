# ACCESS-131 / ACCESS-132 — Implementation plan

- Date: 2026-09-10
- Status: in progress
- Related policy: ACCESS-116, ISSUE-062, ADR-061
- Dependency: the accepted instance/project access policy is normative; this
  plan does not reopen its core decisions.

## Split

### ACCESS-131 — backend foundation

- Additive instance-state, instance-membership, project-membership, and
  invitation persistence with deterministic legacy backfill.
- Make first-account bootstrap race-safe and close anonymous signup after the
  instance is claimed, while keeping the local single-operator path frictionless.
- Add centralized instance/project role checks and replace the temporary
  session-only boundaries for provider applications and shared categories.
- Preserve project-owned publisher credentials, machine-token attribution, and
  historical actors while changing authorization to active memberships.
- Expose typed invitation/member/category authority routes and stable error
  semantics for the web slice.

The first slice does not invent SMTP, hosted identity, or an environment admin
password. Offline recovery/mail delivery remain explicit follow-up work.

### ACCESS-132 — web and browser validation

- Add concise bootstrap, instance-member, project-member, and invitation
  surfaces using the existing Base UI/shadcn primitives.
- Keep instance settings visibly instance-scoped and preserve the selected
  project as navigation context without granting project access implicitly.
- Support copyable invitation links and invitation acceptance without claiming
  that mail was sent.
- Add localized access-denied, empty, loading, and conflict states plus
  deterministic browser coverage for bootstrap, invitation, membership, role
  boundaries, and provider-application administration.

## Coordination contract

ACCESS-131 owns schema, migration, domain stores, authorization helpers, and
API response/error contracts. ACCESS-132 may build against those typed contracts
in its own worktree but must not duplicate authorization or persistence logic.
The lead agent reviews both slices, integrates them only after cross-project and
last-admin invariants are covered, and runs the full repository gate before a
PR.

## Current slice result

- The additive migrations now persist instance state, instance/project
  memberships, and hashed invitations. A legacy database with projects but no
  user is marked `bootstrapBlocked` and cannot be claimed by the first signup.
- The first email signup claims the instance atomically; later public signups are
  rejected while existing sign-in and account-link flows remain available.
- Instance-scoped provider applications, categories, access summaries, and
  invitation operations now require an enabled instance-admin session. Project
  bearer tokens are rejected on those routes.
- The UI scope clarification from DESIGN-120 is integrated. The new instance
  access screen preserves the selected project as navigation context, shows the
  signed-in user's membership, lets an instance admin create/copy/revoke an
  invitation, and lets an already-authenticated invited user accept it. The
  screen does not claim to send email.
- Project creation now requires an enabled instance membership and persists the
  creator as an owner membership. Session access to project routes is checked
  centrally once durable memberships exist; projects with no membership rows
  retain the actor-backed compatibility path until legacy backfill is available.
  Project settings remain editor-only, and project bearer tokens cannot mutate
  those settings.
- Deliberate follow-ups remain: a typed member-list/role-management surface,
  complete last-admin/member lifecycle invariants, invitation acceptance that
  creates a new account, and the eventual legacy project-membership backfill.
  These are not hidden behind the current UI.
- Verification completed: 136 DB tests, 143 API tests, 47 web tests, 14/14
  browser E2E tests, 100% EN/FR message coverage, package format/lint/typecheck,
  and a production build across all 16 packages.

## Parallel follow-up result

- The member API is now complete for the current policy: admins can list
  instance memberships and update another member's role or enabled state;
  bearer tokens and non-admin sessions are rejected; the last enabled admin
  and the current admin cannot be removed through this surface.
- The web access screen consumes that contract. It shows the member list only
  to admins, keeps the current membership read-only, and renders concise
  localized errors for the server invariants.
- Migration `0029_durable_project_memberships` and the migration-runner
  backfill are both deterministic and idempotent. They create only recoverable
  owner memberships and fail closed with an explicit project/user reason when
  a legacy project cannot be mapped safely.
