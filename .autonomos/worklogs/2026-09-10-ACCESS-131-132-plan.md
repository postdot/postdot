# ACCESS-131 / ACCESS-132 — Implementation plan

- Date: 2026-09-10
- Status: planned
- Related policy: ACCESS-116, ISSUE-062, ADR-061
- Dependency: the accepted instance/project access policy is normative; this
  plan does not reopen its core decisions.

## Split

### ACCESS-131 — backend foundation

- Additive instance-state, instance-membership, project-membership, and
  invitation persistence with deterministic legacy backfill.
- Make first-account bootstrap race-safe and close anonymous signup after the
  instance is claimed, while keeping the local single-operator path frictionless.
- Add centralized instance/project role checks and replace the temporary
  session-only boundaries for provider applications and shared categories.
- Preserve project-owned publisher credentials, machine-token attribution, and
  historical actors while changing authorization to active memberships.
- Expose typed invitation/member/category authority routes and stable error
  semantics for the web slice.

The first slice does not invent SMTP, hosted identity, or an environment admin
password. Offline recovery/mail delivery remain explicit follow-up work.

### ACCESS-132 — web and browser validation

- Add concise bootstrap, instance-member, project-member, and invitation
  surfaces using the existing Base UI/shadcn primitives.
- Keep instance settings visibly instance-scoped and preserve the selected
  project as navigation context without granting project access implicitly.
- Support copyable invitation links and invitation acceptance without claiming
  that mail was sent.
- Add localized access-denied, empty, loading, and conflict states plus
  deterministic browser coverage for bootstrap, invitation, membership, role
  boundaries, and provider-application administration.

## Coordination contract

ACCESS-131 owns schema, migration, domain stores, authorization helpers, and
API response/error contracts. ACCESS-132 may build against those typed contracts
in its own worktree but must not duplicate authorization or persistence logic.
The lead agent reviews both slices, integrates them only after cross-project and
last-admin invariants are covered, and runs the full repository gate before a
PR.
