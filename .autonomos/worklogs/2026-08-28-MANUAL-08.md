# MANUAL-08 — Manual-channel vertical slice

## What Was Done

- Added migration-driven `audit_events` persistence with project-scoped actor
  attribution and indexes for project timelines and entity history.
- Added a transactional manual workflow store in `packages/db` for projects,
  channels, posts, publications, due manual work, manual completion, and audit
  inspection. It reuses the framework-independent constructors and publication
  transitions from `packages/core`.
- Added authenticated Elysia 2 beta REST resources for projects, channels, posts,
  due manual publications, manual publication completion, and audit events.
- Connected Better Auth session resolution through an Elysia v2 `derive` macro and
  kept `/health` and the Better Auth handler public.
- Added a client-first TanStack Router dashboard with a login/sign-up screen,
  project and manual-channel creation, scheduled publication creation, due-work
  inspection, and manual completion.
- Added a small HTTP CLI with human-readable and `--json` output for the same
  project, channel, publication, and audit resources. Authenticated CLI requests
  use an explicit session cookie through `HERALD_SESSION_COOKIE` or `--cookie`.
- Regenerated TanStack Router's route tree and aligned Vite's runtime `@/` alias
  with the TypeScript path alias.
- Made the API apply the committed migrations before constructing the manual store,
  and passed the workspace migration directory explicitly for the bundled API
  footprint process.

## Key Decisions and Why

- Manual channels remain channels without publishers. Manual publications do not
  create fake publishers or execution jobs; a due scheduled publication is promoted
  to `ready` and then `published` atomically, with the human actor recorded.
- Audit events are a small durable table and explicit store operations, not a
  speculative event bus or generic repository abstraction. This satisfies the
  accepted M3 attribution requirement while preserving the SQLite-first boundary.
- Project access is resolved through a human actor whose `subjectId` is the Better
  Auth user ID. Every project-scoped query checks that actor before returning data.
- The initial API surface is intentionally narrow: project and channel CRUD needed
  for the slice, post creation with channel-specific publications, due manual work,
  completion, and audit inspection. Automatic publisher configuration remains in
  `PUB-09`.
- The dashboard and CLI are API clients. They contain no publication state machine
  or database logic.
- The Elysia 2 beta API uses a `derive` macro for authenticated route context. The
  implementation is isolated in `apps/api`; transport errors are mapped there while
  domain transitions remain in core/store code.

## Limitations and Next Steps

1. The API process does not yet serve the built SPA assets; static serving and the
   single-process package layout belong to `OPS-10`.
2. CLI authentication currently requires a session cookie. Project-scoped API token
   issuance and agent credentials remain part of the later V1 authentication work.
3. The slice does not configure automatic publishers or create execution jobs for
   automatic channels. That behavior remains deliberately owned by `PUB-09`.
4. Complete the review and merge workflow, then proceed to the first publisher
   feasibility spike without expanding MANUAL-08's scope.
