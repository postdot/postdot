# DEV-414 — Production entrypoint under a startup termination

<!-- cspell:ignore opencode xhigh -->

## Plan

1. Establish the parent ground truth on the production path: the built bundle as a plain process, and the same bundle as PID 1 in a container.
2. Register a bounded delegated mission for a committed regression that exercises the production bundle, and review it against the acceptance criteria.
3. Integrate, clean up, and record the evidence and the durable guidance.

## Context

DEV-412 corrected the API so that a termination received during the startup window runs the same drain as a running server and releases the runtime marker. DEV-413 proved the development launcher path. The production path is different in one decisive way: the container runs the API as PID 1, and the kernel does not apply the default action of SIGTERM to PID 1. An API that has not installed a handler therefore IGNORES the stop signal entirely.

## Parent ground truth, established before the mission

Production bundle, built with `bun build ./src/index.ts --outdir ./dist --target bun --minify` (3226 modules, about 170 ms), run as a plain process with the production environment, temporary database, media and web-assets directories, and synthetic secrets:

- The runtime marker appears at the first statement of the startup.
- A SIGTERM in that window ends the bundle with exit code 0 in about 105 ms, logging `[postbot-shutdown] SIGTERM received; draining worker and runtimes` and `shutdown complete with exit code 0`.
- The API never served, the marker was released, and the next start of the same bundle served the health endpoint and released the marker again.

Same bundle as PID 1 in a container (`oven/bun:1`, `--network none`, an isolated `/data` directory):

| Bundle | `docker stop` duration | Container exit | Runtime marker |
| --- | --- | --- | --- |
| before DEV-412 | 3097 ms, the full grace period, then SIGKILL | 137 | **retained** |
| after DEV-412 | 110-138 ms | 0 | released |

In the defective run the container logs are empty: the API never saw the signal, because PID 1 ignored it. The marker stayed in the persistent `/data` volume, so the next deployment of that volume would have been refused by the fail-closed exclusion until an operator removed the marker by hand.

## Delegation decision

The standing owner direction in the root `AGENT.md` requires a bounded delegation to MiniMax M3.1 Flash Free through OpenCode for each subsequent task, with the highest advertised reasoning variant: `opencode/minimax-m3.1-flash-free` with `variant=max`.

The orchestrator keeps the container validation, the review, the integration and the cleanup. The delegated mission receives the verified production-path facts and implements the committed regression that exercises the production bundle without Docker, so the guarantee stays covered by the ordinary test suite.

## Implementation mission

- Owner: parent orchestrator. Worker: delegated MiniMax M3.1 Flash Free mission in a dedicated worktree.
- Allowed writes: one new test file under `scripts/`, and a temporary, byte-for-byte restored replacement of `apps/api/src/index.ts` for the negative control only.
- Forbidden: every other file, product behavior, configuration, dependencies, lockfiles, governance, commits, merges, `main` writes, Docker, the network, the owner's `.env`, real database, real media root, default ports, real credentials, and further delegation.
- Acceptance: the production bundle is built by the test itself; a termination during its startup releases the runtime marker and the bundle exits 0; the API never served; the next start of the same bundle serves the health endpoint and releases the marker again; every wait is bounded and the temporary directories are removed only after the owned child exited.
- Stop: the scoped uncommitted diff, the exact check results, the negative-control evidence, and the limitations. The parent reviews and executes the final test in the canonical checkout.
