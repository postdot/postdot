# PERF-620 — Early release under prolonged natural contention

## Scope and method

Owner authorized the next local qualification under the restored local-integration
cadence. The runtime is local main at `5d99cdb53`, including DB-618's publication
claim release. This pass changes only the opt-in benchmark's observations and
error reporting; no application behavior, dependency, lease or concurrency policy
is changed. No remote push, new PR or CI wait is part of this intermediate pass.

One fresh disposable PostgreSQL database receives 300 seconds of arrivals at
24 publications/s across four projects. Synthetic effects wait 100 ms and return
success without network I/O. There is no injected failure window. Two physical
effect slots, one per project, remain in force. Normal PostgreSQL durability,
automatic maintenance and the default five-minute claim lease remain enabled.
The producer stops after its fixed schedule; durable drain is observed for up to
600 further seconds, giving a finite maximum observation window of 15 minutes.

```sh
POSTDOT_TEST_POSTGRES_URL=postgres://... bun scripts/benchmark-worker-admission.ts --engine postgres --seconds 300 --rate 24 --effect-ms 100 --drain-seconds 600
```

The observer retains admission errors without automatically retrying mutations.
Such errors still make the command unsuccessful, but accepted work can drain and
its durable outcome remains available for analysis. `created` means admissions
acknowledged to the producer; final durable counts and provider IDs also expose
any mismatch. Reported worker errors do not alone stop observation, but a terminal
scheduler, unfinished work, non-successful durable outcomes, duplicate effects
or admission violations still fail qualification.

After shutdown, read-only queries count recovery facts by their reason, final
publication states and claim attempts. This distinguishes owner release from
lease expiry and keeps safe ambiguity visible. One-second samples retain process
RSS, scheduler state, acknowledged creation and provider-return counters. They
are observations, not extra scheduler hints. The drain polls pending/running
rows once per second. Provider returns alone are not treated as durable success.

## Results

[Aggregated results](2026-11-08-PERF-620-results.json):

- **7,200 offered, acknowledged and durably successful publications**; all four
  projects completed exactly 1,800 provider calls.
- Zero producer errors, reported worker errors, duplicate provider calls,
  admission violations, ambiguous outcomes or unfinished jobs.
- Maximum physical concurrency: two. Final scheduler: `started`.
- Arrivals lasted 300 seconds; 4,914 provider calls returned during that window,
  leaving 2,286 calls outstanding. Full durable drain finished at **441.1 s**
  from the start, approximately 141 seconds after arrivals stopped.
- Intended-offer-to-provider wait: p50 **66.1 s**, p95 **134.1 s**, maximum
  **140.5 s**. Producer lag p95 stayed below 6 ms, so insertion backpressure did
  not hide the offered rate.
- The observed workload backend logs contain **1,775 serialization failures**
  and no deadlock. No failure escaped transaction handling to the scheduler.
  These are server-side transaction failures, including successful adapter
  replays, not failed publications. The backend set was observed during the run;
  the count is not a claim about disconnected sessions or other databases.
- Persisted claim attempts: maximum one, total 7,200. No claim-recovery fact was
  recorded. Neither early owner release nor lease-expiry recovery was needed.
- Client RSS peaked at approximately **117.1 MiB**, including the benchmark's
  retained per-call samples. PostgreSQL server memory is not included.

The workload grows a queue while offered work exceeds service capacity, then
drains successfully once arrivals stop. It supports normal-path stability and
transaction replay under this natural contention. It does **not** independently
re-exercise DB-618's early-release branch: no transaction exhausted its retry
handling at that boundary. The controlled fault tests remain the evidence for
that behavior. This single run does not establish a safe rate or publication
deadline under other workloads.

## Limits

This is a local finite synthetic workload, not a production capacity ceiling,
full HTTP admission benchmark or long-term memory-leak proof. The PostgreSQL
server is local, media and provider rate limits are absent, and the run exercises
publication jobs only. Natural contention is stochastic; a successful run cannot
prove that cleanup never fails or that post-effect ambiguity is impossible.
The machine is a shared development host, not dedicated benchmark hardware.

## Validation and cleanup

Initial five-second PostgreSQL smoke: 40 offered and acknowledged jobs, all
published, no producer errors, one claim per job and no duplicate provider calls.
The final report retains admission errors and recovery reasons explicitly;
static type/format/lint checks cover these observation-only changes. The normal
local commit hook runs the static gate. No browser or full behavioral matrix is
warranted for this observer/evidence checkpoint. The owned PostgreSQL container
was stopped and removed after collecting the workload backend error counts.
No remote push, new PR or CI run is triggered.

No further runtime correction is justified by this run. The next integration
step can be a grouped milestone when other work is ready, rather than another
blind test cycle aimed at obtaining a natural failure.
