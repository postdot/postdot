# WEB-314 — Bounded unverified-access state machine for the publication editor

## Pre-implementation verifications

### Membership contract for workspace managers without content access

`GET /api/projects/:projectId/membership` returns the caller’s direct grant or
404 when there is none (`apps/api/src/modules/projects/member-routes.ts:224-240`).
It never consults workspace management: unlike the project list
(`apps/api/src/modules/projects/routes.ts:46-65`) and the access-surface
fallback (`apps/api/src/modules/projects/index.ts:108-113`), the membership
route has no `canManageWorkspace` branch. A workspace owner or admin without a
direct project grant therefore receives 404.

For this editor-bounded tranche that 404 means “editor capability cannot be
established,” which matches the existing loader contract: `loadProjectData`
already requires the same membership read
(`apps/web/src/lib/dashboard-context.tsx:53-80`). No business rule is changed,
but the result must not be generalized as a global access statement for every
project surface. The same 404 shape also covers a deleted project; the denied
surface therefore speaks of removed access, consistent with the existing masked
404 behavior, without claiming to distinguish deletion from revocation.

### Expired session and 401 handling

Authentication runs before any route handler: a missing session returns 401
`unauthorized` (`apps/api/src/plugins/auth.ts:178-186`). A 401 from the
verification read therefore signals an unusable session or transport, never a
project revocation. The classifier maps 401 to technical error, 403/404 to
denied access, and every other failure to technical error. The open editor only
redirects to login on navigation-time loader checks; the in-place machine must
not invent a revocation from a 401.

### Business-rule conflicts found

None blocking. Additive UI states, additive translations, additive client
guards; server authorization, revision protocol, recovery retention, and loader
semantics are unchanged. One deliberate client-ordering choice, explicitly
requested: under a divergent local draft, confirmation adopts no new reference
revision and leaves the existing write-conflict path to fire on the next save.

## Acceptance criteria (recorded before implementation)

### Ambiguous signal

- On `project.access-revoked`, the editor page suspends new server writes,
  preserves local changes immediately, and issues exactly one
  `GET /membership` read. No polling, no focus/reconnect/visibility trigger,
  no duplicate read for a repeated signal while verifying.

### Technical error

- A compact state is shown with the existing Retry action
  (`common_retry`). The draft stays mounted and preserved. No automatic retry
  and no automatic write resume. An explicit retry issues exactly one new
  verification read.

### Confirmed refusal

- The editor and its server data are replaced by an “Access removed” surface
  with a return to the available projects. The local recovery buffer is
  preserved separately and never purged automatically. Late responses neither
  erase the buffer nor re-enable actions. No persistent response envelope is
  kept: only a later authorized read may establish the server result.

### Confirmed editor or owner

- The server editor is reread once, then reconciled with existing
  conflict/rebase semantics: clean working copy adopts the server snapshot;
  divergent working copy keeps local content, keeps the current reference
  revision, and surfaces a conflict. Autosave resumes only after
  reconciliation.

### Confirmed viewer

- Read-only consultation, no writes, unsaved local modifications preserved
  separately in the existing buffer.

### Late responses

- Any editor-owned async continuation whose access epoch changed must apply
  nothing: no state overwrite, no dirty clearing, no buffer deletion, no cache
  invalidation, no navigation, no success message. Outstanding HTTP cannot be
  recalled; only dispatch and application are fenced.

### Epoch scope for the first tranche

- A shared per-project access epoch lives in the editor page’s control state
  and is consumed only by editor-owned flows: draft autosave, explicit server
  reload, restore-against-server, rebase, promotion, tag replacement,
  outcome reconciliation, and post-action editor reloads. Queue, calendar,
  channels, media, approvals, notifications, composer, and proactive
  role-change announcement stay out of scope. Parent-level cache effects of
  editor-initiated lifecycle actions are a documented residual for tranche two.

### Required proof

- Unit: reducer transitions, error classifier mapping, reconcile decisions
  including the concurrent-conflict matrix, and byte-identical
  `access-revoked` frames for refusal versus lookup failure.
- Browser: suspension with exactly one verification read, late-response
  quarantine with buffer preservation, technical-error retry issuing exactly
  one new read, and confirmation into a concurrent conflict with reference
  revision unchanged.

## Implementation (completed, awaiting validation of this proposal)

### What was built, bounded to the publication editor page

- `apps/web/src/lib/project-access-verification.ts`: `ProjectAccessStatus`
  (`confirmed | verifying | denied | technical-error`), a pure reducer with a
  per-project epoch, the membership-error classifier (401 always technical,
  403/404 denied for this page, everything else technical), and the
  post-confirmation reconcile decision (never advance the reference revision
  under a divergent draft).
- `apps/web/src/lib/project-realtime.tsx`: a local subscriber registry for the
  project `access-revoked` signal. The stream itself is unchanged; subscribers
  only observe the same ambiguous signal the bridge already handles.
- `apps/web/src/routes/dashboard/projects/$projectId/publications/$publicationId.tsx`:
  owns the machine, issues exactly one `api.getProjectMembership` per entry
  into verification, renders the verifying notice, the compact technical-error
  state with Retry, and the denied surface with a return to project selection.
  A membership role override stands only until ordinary project data refreshes,
  which are strictly fresher.
- `apps/web/src/components/publication-editor.tsx`: freezes new writes while
  unverified, guards every editor-owned async continuation with the access
  epoch, reconciles on confirmation without advancing the reference under
  divergence, and preserves local state plus the recovery buffer throughout.
- Translations: two additive keys only (`editor_access_checking`,
  `editor_access_denied_title`); Retry, project selection, and technical-error
  copy reuse existing strings.

### Amendment to the recorded criteria: refused writes also trigger verification

The criteria recorded before implementation said an isolated mutation failure
must not start verification. Browser evidence forced a correction: in this
environment the event stream dies at the proxy (502), nothing ever refetches
the editor query, and the in-band signal cannot arrive — the only honest,
authoritative discovery left is a refused editor-owned write (403/404 from the
real server, unlike a silent transport). The trigger set is therefore the
in-band signal, a refused editor refetch, or a refused editor-owned write,
all feeding the same one-shot verification guarded by status. This is an
extension of the trigger, not a policy change: no polling, no new endpoint,
no new event. Parent-level lifecycle callbacks (`onPublish`/`onRetry`/
`onCancel` internals and their project-cache refreshes) stay out of the first
tranche as a documented residual; only their editor follow-up reads are
epoch-guarded.

### Residuals explicitly deferred to tranche two

- Parent cache effects of editor-initiated lifecycle actions.
- Queue, calendar, channels, media, approvals, notifications, composer.
- Proactive role-change announcement (no new event proposed).
- Long-term buffer retention after permanent denial.

### Proof results

- Unit (`project-access-verification.test.ts`): 6 tests covering reducer
  transitions, duplicate-signal suppression, the 401 rule, and the reconcile
  matrix including concurrent conflict.
- Stream (`access-revocation-stream.test.ts`): byte-identical frames for
  refusal versus lookup failure.
- Browser (`e2e/web-314-editor-access-state.spec.ts`): suspension with frozen
  editor and held verification, late-success quarantine with buffer intact,
  technical-error retry into confirmation and concurrent conflict with local
  work preserved. Exact-once dispatch is pinned by reducer tests; the browser
  asserts absence of repeat behavior, because background project-data refetches
  share the membership endpoint under proxy flapping.
- Full gate (`bun run check`): 80 passed with one load-related flake in
  `publication-concurrent-editing` (8/8 standalone, unrelated to access
  handling), plus 14/14 on the affected perimeter on re-run. The updated
  WEB-312 characterization now expects the denied surface instead of the
  armed editor the correction removes.
- Three implementation defects were found and fixed during proof: conditional
  hooks after the denied early return (twice), and swallowing the reconcile
  error that the outcome panel renders itself (now rethrown after reporting).
