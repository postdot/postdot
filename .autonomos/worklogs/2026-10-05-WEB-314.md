# WEB-314 — Bounded unverified-access state machine for the editor

Proposal only. No product behavior, transport, translation, polling, purge,
retention policy, authorization rule, or test was changed in this pass.

## Scope

This is a bounded correction proposal for the publication editor only. It does
not generalize request epochs to Queue, calendar, channels, media, approvals,
notifications, or the composer. Those areas keep their current behavior until
a later tranche is validated.

The proposal answers three gaps left by WEB-313:

1. `removeQueries` cannot serve as an access fence.
2. `project.access-revoked` conflates genuine revocation with an unavailable
   authorization check.
3. The editor has no explicit state for work that is unsent, already sent, or
   confirmed.

## Proposed states

Use four explicit states per project:

- `ACCESS_CONFIRMED`
- `ACCESS_VERIFYING`
- `ACCESS_DENIED`
- `ACCESS_TECHNICAL_ERROR`

The initial state is `ACCESS_CONFIRMED` after the project and editor loaders
succeed. The state must live outside TanStack Query so that cache removal,
query errors, and stale fallbacks cannot erase the fence. It should reset on
project change, route remount, or navigation, because a new route match has its
own loader result.

A downgraded viewer is not a fifth access state. A successful membership read
returns `viewer`; the machine returns to `ACCESS_CONFIRMED`, while the existing
role predicate makes the editor read-only.

## Transitions

| Event | From | Result |
|---|---|---|
| Project and editor loaders succeed | Entry | `ACCESS_CONFIRMED`, with the server-supplied role. |
| `project.access-revoked` | `ACCESS_CONFIRMED` | Enter `ACCESS_VERIFYING`, increment the project access epoch, freeze new editor writes, preserve snapshots and buffers, and send exactly one membership read. |
| Duplicate `access-revoked` for the same project | `ACCESS_VERIFYING` | Ignore the duplicate; do not send another verification read. |
| Membership read returns owner or editor | `ACCESS_VERIFYING` | Update the effective role, reconcile the editor, then return to `ACCESS_CONFIRMED`. |
| Membership read returns viewer | `ACCESS_VERIFYING` | Update the effective role to viewer, keep the editor readable, force read-only mode, then return to `ACCESS_CONFIRMED`. |
| Membership read returns 403 or 404 | `ACCESS_VERIFYING` | Enter `ACCESS_DENIED`; preserve content and buffer; force read-only mode; do not navigate or purge. |
| Verification fails technically | `ACCESS_VERIFYING` | Enter `ACCESS_TECHNICAL_ERROR`; preserve content and buffer; offer one explicit retry. |
| Stale verification response | Any | Ignore a response whose epoch no longer matches the current epoch. |
| Explicit retry | `ACCESS_DENIED` or `ACCESS_TECHNICAL_ERROR` | Increment the epoch and send exactly one new membership read. |
| Ordinary successful project-data refresh | `ACCESS_CONFIRMED` | Update the role only; no state transition and no announcement. |
| Direct mutation returns 403 or 404 | `ACCESS_CONFIRMED` | Keep the existing per-action error; do not start verification from an isolated action failure. |
| Navigation or remount | Any | Let the new loaders determine the next entry state through existing routing behavior. |
| Stream reconnect or resync without corroboration | `ACCESS_VERIFYING` | No transition; connectivity alone does not resolve authorization ambiguity. |

No interval, focus, reconnect, or visibility handler may start verification.
Only the ambiguous signal and an explicit user retry may do so.

## Existing server read used for disambiguation

The proposal uses the existing membership endpoint:

```text
GET /api/projects/:projectId/membership
```

through the existing client method:

```ts
api.getProjectMembership(projectId)
```

(`apps/web/src/lib/api.ts:733-737`).

This read is preferable to a full project reload because:

- it is small and role-carrying;
- it does not overwrite editor text, tags, schedule, or media;
- its response directly supplies the updated permission;
- it can be issued once per ambiguous signal.

Map its result as follows:

- `200 owner/editor/viewer`: authorization is confirmed; update the role.
- `403/404`: the current session cannot establish project membership; enter
  `ACCESS_DENIED`.
- Network failure, timeout, abort, HTTP 5xx, unexpected status, or session-level
  authentication failure: enter `ACCESS_TECHNICAL_ERROR`.

A workspace manager without a direct project grant can receive membership 404
while retaining a different workspace-level project surface. The first editor
tranche should therefore treat this result as “editor capability denied,” not
as a global statement about every workspace route. That edge remains an owner
decision.

## Recovery and updated permissions

Recovery has two separate stages: confirm access, then reconcile content.

### Confirmed owner or editor

1. Apply the membership role.
2. Fetch one authoritative editor snapshot with the existing editor-read API.
3. Compare the server snapshot against the preserved local draft and recovery
   buffer.
4. Adopt the server revision and metadata.
5. Retain local source, target, schedule, dirty state, and buffer when they
   differ.
6. Clear dirty state only when the local working copy matches the server.
7. Allow autosave to resume only after reconciliation, so it does not send a
   stale expected revision first.

This avoids both destructive outcomes: the server is not overwritten blindly,
and local work is not discarded silently.

### Confirmed viewer

Apply the viewer role and keep the publication readable. Existing read-only
predicates remove creation and mutation entry points. No announcement event is
required for enforcement because the updated permission itself changes the UI.

### Denied access

Force read-only mode, preserve the last confirmed editor snapshot, preserve the
working copy, and preserve the recovery buffer. Do not replace content with an
error page, navigate away automatically, invalidate loaders, or purge caches
as part of this first tranche. Those behaviors remain product decisions.

### Technical error

Freeze writes, preserve everything, and expose an explicit retry. Do not infer
denial from a timeout, failed lookup, server error, or expired session.

## Separating server data from unsaved local work

Maintain three distinct layers:

1. **Last confirmed server snapshot:** loader data, query data, editor object,
   expected revision, publication lifecycle fields, and server draft metadata.
2. **Local working copy:** source content, target text, schedule value, dirty
   flags, save status, tag selection, and operation indicators.
3. **Durable local buffer:** the existing editor recovery entry.

During `ACCESS_VERIFYING`, `ACCESS_DENIED`, or `ACCESS_TECHNICAL_ERROR`:

- never replace the working copy with an ambiguous server response;
- never clear dirty state because a request failed;
- never delete or overwrite the recovery buffer automatically;
- never treat a late successful response as proof that access was restored;
- never treat a late failed response as proof that access was revoked.

Autosave, server reload, restore-against-server, rebase, promotion, tag
replacement, outcome reconciliation, and post-action editor reload all need the
shared access epoch because each can otherwise apply a stale response after the
boundary. Pure reads used for display, navigation, preview, and copying do not
need an epoch; they need the access status.

## Already-sent operations

An already-sent HTTP request cannot be recalled: the current web API does not
use `AbortController` for these editor operations. The proposal therefore
controls dispatch and application, not the network itself.

For a response arriving after the access epoch changed:

- do not set the editor to saved;
- do not clear dirty state;
- do not delete recovery data;
- do not invalidate project queries on the basis of that response;
- do not navigate;
- do not display success;
- do not infer revocation from failure alone.

A late successful autosave stays represented as local-only work rather than
confirmed saved work. A late failure stays represented as an unresolved
operation rather than proof of revocation. If the server actually applied the
write, the next authorized reconciliation observes it. If it did not, the
preserved buffer and working copy retain the user’s intent.

For `write_conflict`, preserve local changes and defer resolution. The conflict
proves that newer server data exists; it does not prove that the current tab
may fetch or overwrite it while access is unverified.

The proposal does not yet decide whether the full late-response envelope
should be retained in memory or discarded after observing its arrival. Either
choice needs owner validation because it affects memory use, debugging, and
reconciliation behavior.

## First testable editor tranche

### Included operations

Apply the project access epoch to these editor flows:

1. Draft autosave through `savePublicationDraft`.
2. Explicit server reload through `getPublicationEditor`.
3. Restore-against-server reconciliation.
4. Draft rebase.
5. Draft promotion.
6. Publication-tag replacement.
7. Ambiguous-outcome reconciliation.
8. Follow-up editor reload after editor-initiated publish, retry, or
   cancellation.

The parent publish, retry, and cancellation mutations themselves remain outside
the first epoch tranche, except for their editor follow-up reads. New mutation
entry points are nevertheless blocked while access is unverified. Whether their
parent-level cache effects also need the same epoch is a validation question.

### Explicitly deferred

- Queue and calendar bulk operations.
- Channel lifecycle and publisher-connection operations.
- Media listing, upload, deletion, verification, and recovery flows.
- Approval operations.
- Notification mutations.
- Composer creation and composer server-draft queue.
- Global mutation wrapper or repository-wide epoch framework.
- Cache removal as an access fence.
- New SSE event, payload field, translation, or authorization policy.

## Proof to add after validation

### State-machine tests

Mock the single membership read and prove:

- one ambiguous signal causes exactly one verification read;
- duplicate signals do not cause additional reads;
- `200 owner/editor` restores confirmed access and updates the role;
- `200 viewer` restores confirmed access in read-only mode;
- `403/404` produces denied access without navigation or purge;
- technical failures produce technical error without automatic retry;
- stale epochs are ignored;
- explicit retry issues exactly one new verification;
- an isolated mutation failure does not start verification.

### Stream-contract test

Extend the existing revocation-stream coverage to assert that an authorization
lookup failure and a false authorization gate produce byte-identical
`project.access-revoked` frames. That pins the ambiguity rather than merely
demonstrating the same event kind.

### Browser proof

Use two isolated sessions and intercept the membership endpoint to count
requests:

1. Open an editor, create unsaved changes, and revoke access from the other
   session.
2. Prove that the ambiguous signal produces exactly one membership request.
3. Delay the in-flight draft response, release it after the transition, and
   prove that the editor is not marked saved and recovery is not deleted.
4. Revoke access and prove that no new draft write is dispatched after the
   freeze.
5. Restore access through a successful membership read and prove the resume
   order: role update, editor reconciliation, then autosave eligibility.
6. Force the verification read to fail technically and prove that an explicit
   retry issues exactly one additional read.
7. Downgrade editor to viewer and prove that writes are refused, visible
   permissions update, recovery remains intact, and no announcement is
   required for enforcement.

## Remaining decisions

1. Exact user-facing wording for unverified, denied, and technical-error states.
2. Whether denied access keeps a readable shell or navigates elsewhere.
3. Whether users may continue typing locally while unverified or whether the
   pre-signal draft is frozen exactly.
4. Whether a late successful envelope is discarded or retained for later
   reconciliation.
5. Whether parent publish, retry, and cancellation cache effects join the first
   tranche or remain deferred.
6. Whether confirmation performs only membership plus editor reconciliation or
   also runs the existing full project refresh.
7. How to classify a workspace manager whose membership read is absent.
8. Where the per-project access control state lives and how navigation resets
   it.
9. Long-term retention, export, or purging of buffers after permanent denial.
10. Whether a future role-change announcement is desirable; no such transport
    change is proposed here.
