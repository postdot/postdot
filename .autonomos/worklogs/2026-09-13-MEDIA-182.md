# MEDIA-182 — Define the scalable project media library contract

- Status: In progress (bounded browse and search slice)
- Branch: `codex/reui-calendar-spike`
- Owner: orchestrator
- Related issue: [ISSUE-104](../ISSUES.md#issue-104-define-the-scalable-project-media-library-contract)
- Predecessor: MEDIA-180

## Objective

Prevent the project media library from materializing an unbounded asset list,
while making the media work area an understandable drop target and keeping the
publication attachment picker compatible with existing selections.

## Decisions implemented in this slice

- The library reads project media newest-first with a stable `(created_at, id)`
  ordering.
- The API defaults to 24 records and caps a requested page at 100 records.
  Pagination uses a versioned cursor and returns `nextCursor`.
- Filename search is optional, bounded to 255 characters, and escapes `%`, `_`,
  and `\\` so search text is not interpreted as a SQL `LIKE` pattern.
- The management surface exposes a small filename search control and an
  explicit Load more action without adding a decorative toolbar surface.
- The media work area receives the headless Uppy dropzone handlers and
  `data-media-dropzone`; the page header remains outside that interaction
  surface, and a compact bottom hint communicates the capability without
  adding a bordered upload panel.
- Search keeps the current result set rendered while the debounced request is
  pending, then swaps the result set only after the response arrives. Load
  more is unavailable during that transition.
- The management library defaults to an image-forward gallery and offers a
  compact tile mode plus a single-column list mode. The preference is a
  versioned browser-local UI setting, independent from the project and from
  publication attachment selection; changing it never changes the fetched
  page or cursor.
- After a management import or image edit, the first page is re-read so a new
  newest asset cannot silently displace the item represented by the current
  cursor.
- Attachment mode remains separate from management mode. Selected assets that
  are outside the first page are hydrated individually through the existing
  metadata endpoint, so bounded browse reads do not make an existing draft
  appear broken.
- Uppy remains headless; no Uppy Dashboard or vendor styling is introduced.

## Delivered

- Added the bounded `listAssetsPage` store contract and versioned cursor.
- Extended `GET /api/projects/:projectId/media` with `limit`, `cursor`, and
  `search` query parameters and the `{ media, nextCursor }` response.
- Updated the web API client and media picker with debounced search, paginated
  loading, scoped drop handling, and selected-asset hydration.
- Added a clear header-level Import action wired to the same headless Uppy file
  input and moved the drop hint below the library content.
- Added an E2E regression covering a delayed search response so the visible
  result set cannot flash into a transient empty/loading state.
- Added localized search, count, loading, load-more, and no-results messages.
- Added DB and API coverage for ordering, cursor traversal, literal search
  matching, and the paginated response shape.
- Extended the media browser contract to cover search, no-results, and reset
  behavior after filtering.
- Added explicit gallery, compact, and list controls with a distinct active
  state, accessible names, and a persisted preference. The card component now
  owns the three presentation variants while attachment mode keeps its
  existing list-like layout.
- Refined the management toolbar after UI review: the view choices now use the
  shared `ButtonGroup` primitive, the active choice uses a nearby muted surface
  instead of the primary action color or an inverted foreground/background
  treatment, and the filename search field uses a light field boundary without
  a control shadow. Its placeholder is now the concise noun `Nom du fichier` /
  `Filename`.

## Deletion and Uppy findings for the next slice

- The deletion API already requests an archive rather than destroying an asset
  immediately. The asset leaves normal library results, remains readable while
  the grace period is active, and is physically purged only after the grace
  period when no reference or backup fence blocks it.
- The current purge guard intentionally treats references in source posts,
  working drafts, target revisions, execution snapshots, revision-media rows,
  and media audit records as one boolean. That is safe for storage, but not yet
  an adequate user-facing explanation: editable/upcoming references and
  immutable historical records should be distinguished before exposing a
  deletion action in the library.
- Uppy is currently used headlessly for normalized file intake, upload state,
  progress/error events, restrictions integration, and the React drop/file
  hooks; the visible Herald UI remains ours. Native browser drag-and-drop could
  provide the drop primitive alone, so Uppy’s larger value is the upload
  lifecycle and optional provider integrations rather than drag-and-drop by
  itself.
- Remote providers require Uppy Companion and provider-specific OAuth/config
  decisions. Golden Retriever is a separate recovery feature with browser
  storage/quota and privacy trade-offs. Uppy locale packs cover Uppy-rendered
  strings; Herald-owned headless UI remains under Herald i18n.
