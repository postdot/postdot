# REALTIME-513 — Preserve overlapping publication refreshes

## Outcome

Fixed a proven race in the project realtime bridge. A project refresh already in flight previously discarded subsequent refresh requests, including stronger publication-editor or reconnect scopes. A late signal could also arrive after the last read started and leave stale cached state.

The refresh queue now merges requested scopes and repeats the refresh after an overlapping signal. Different resource keys remain independent. Failed operations release their key. Existing editor reconciliation and local-edit protection are unchanged; no polling was added.

## Evidence and limits

- The isolated local API used a private temporary database, credentials and media root on port 3010. Shared user data and external providers were untouched.
- Ordinary manual publication already refreshed correctly before the change; the defect is not universal.
- Three deterministic concurrency cases fail under the previous coalescing behavior and pass under the replacement. A fourth verifies recovery after a failed read.
- Realtime transport and queue tests: 13 passed, 33 assertions.
- `bun run check:quick`: 20 workspaces passed after removing the obsolete cleanup reference.
- `bun run --cwd apps/web build`: passed.
- CUA verified the rebuilt Studio transitioning from manual delivery pending to Published following a separate local API request, without reloading. Passive background notice appeared. Screenshot: `/tmp/postbot-realtime-513-published.png` (local evidence, not a repository asset).
- The exact automatic Facebook/TLS proxy sequence has not been replayed. ISSUE-177 remains open with that limitation; this fix is not claimed as its exclusive cause.
- Test browser left the isolated application and the temporary API shut down gracefully.
