# ANALYTICS-234 — Add bounded Forem publication analytics collection

- Status: complete
- Issue: [ISSUE-138](../ISSUES.md#issue-138-deliver-provider-backed-publication-performance-in-project-workspaces)
- Owner approval: The project owner approved the ANALYTICS-233 recommendation on 2026-09-27.
- Scope: DEV.to/Forem lifetime article totals for already-published Herald destinations.

## Accepted boundaries

- Keep provider-owned performance separate from Herald operational analytics.
- Use the existing project-owned DEV.to publisher credential; never expose or log it.
- Query only provider article identifiers already recorded on Herald publications.
- Reads return stored observations only; collection is an explicit bounded action.
- Keep provider-specific metric names, units, periods, freshness, and availability.
- Do not add a scheduler, provider scopes, raw response storage, or retention-policy change.

## Investigation

- The Forem API documents authenticated `GET /api/analytics/totals?article_id=...` for lifetime views, reactions, and comments, and `GET /api/analytics/historical` for date-keyed provider periods.
- Forem history includes adaptive daily/weekly buckets. Persisting those values would create up to 180 daily points per supported metric and explicit refresh, while the existing table retains each fetch indefinitely and its uniqueness key does not include reporting periods. This task therefore records only the three lifetime totals; native date-range history remains deferred until its storage lifecycle has an explicit bounded design.
- Herald already encrypts DEV.to API keys in publisher credentials, records successful provider article IDs on publications, and stores provider metrics in project-scoped observations.
- The observation table is immutable per fetch instant and has no TTL. This task must not introduce automatic collection or claim a new retention policy.

## Implementation and verification

- Added a DEV.to provider analytics contract and authenticated `/api/analytics/totals` reader. It validates canonical positive article IDs and requires all three lifetime totals to be non-negative safe integers; absent or malformed values remain an explicit invalid response rather than becoming zero.
- Added a project-scoped API read route for persisted DEV.to observations and an editor-authorized explicit collection route. Collection resolves an existing connected credential and only the selected publication's already-recorded DEV.to article ID. It persists `page_views`, `reactions`, and `comments` as cumulative snapshots and does not return credentials or raw provider payloads.
- Added provider, API integration, provider-adapter conformance, and OpenAPI coverage. The integration test verifies a real zero remains measured, the secret is absent from the response, and subsequent API reads do not make another provider request.
- Files changed: `packages/devto/src/{contract.ts,publisher.ts,publisher.test.ts}`; `apps/api/src/modules/projects/{devto-analytics-service.ts,provider-analytics-models.ts,provider-analytics-routes.ts,provider-analytics-routes.test.ts,index.ts}`; `apps/api/src/{app.test.ts,index.ts}`; `apps/api/src/modules/workflow/providers/{devto.test.ts,conformance.test.ts}`; `packages/client/src/index.ts`.
- Validation: `bun run check` passed, including formatting, lint, CSpell, TypeScript and localization coverage (EN/FR 1417/1417), unit and script tests, all 36 browser E2E tests, both password-reset E2E tests, and production builds for all 17 packages. `git diff --check` passed.
- Deferred by the accepted boundary: Forem date-range history and recurring collection. The existing observation store retains each fetched snapshot indefinitely, so history or background refresh needs its own explicit storage lifecycle and cadence decision.
