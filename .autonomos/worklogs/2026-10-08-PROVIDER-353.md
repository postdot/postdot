# PROVIDER-353 — LinkedIn multiple-image publishing

Base: `60d2b3a0d`. Owner approved the proposed publishing sprint.

## Delivered boundary

The current LinkedIn profile is version 3, with up to 20 JPEG/PNG images and the
member-post-v3 execution contract. Text and one-image posts retain their existing
payloads. Multiple-image posts send one ordered content.multiImage.images array,
including each image alternative. Member and organization destinations use the
same established destination and permission boundaries; no new OAuth scopes,
service, public media URL or storage backend is introduced.

Production registers v2 alongside v3. The v2 adapter still rejects multiple
images; historical profiles and targets are not migrated. New channels use the
current profile. Existing v2 LinkedIn execution profiles can load the latest
LinkedIn template in their existing profile dialog, save it, preview impact and
confirm activation. Loading does not activate. The action follows execution,
including renamed/custom templates, and is disabled under unsaved edits. It uses
the existing starter preparation to preserve the custom-schema safety policy.
The profile identity/origin remains owned by the existing server draft contract.

Each image is uploaded sequentially through its existing durable media-delivery
row. The adapter validates the batch before upload and creates the post only when
all rows are confirmed. Retryable upload failures leave completed earlier rows
reusable; the next attempt uploads only unconfirmed images. A rejected final post
reuses the complete batch. Ambiguous upload outcomes stop before post creation
and remain ambiguous without automatic re-upload. Credential redaction and final
post classification use the existing shared request path.

## Evidence

Official provider contract checked 2026-10-08:
[MultiImage API, version 202608](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/multiimage-post-api?view=li-lms-2026-08).
It documents 2–20 images and per-image altText, with the existing member and
organization posting permissions. Particular application entitlements still need
a separately authorized live publication; no real account or provider was called.

Publisher tests cover ordered member/organization payloads, alternatives, maximum
count, malformed batches rejected before dispatch, and retryable/ambiguous post
responses. Existing single-image/text tests remain. Worker tests use real SQLite,
media storage and simulated Fetch: old v2 single image, v3 three images with a
retryable second upload and final-post rejection, and an ambiguous second upload
with no post or blind retry. A registry regression keeps v2/v3 distinct and rejects
multi-image input on v2 before media dispatch.

The existing composer spec adds one journey: an old execution template publishes
a manual historical target, explicitly adopts v3 through the actual dialog, then
creates a three-image draft via the media library. It checks unchanged historical
target, order, image alternatives and v3 profile. Final focused result: 1/1,
11.3 seconds (13.8 with harness), one worker, no retries.

Fixture corrections were confined to that scenario: HTTP creation accepts custom
profile objects rather than built-in objects; custom schemas must use prepared
starters (including bounded strings); the prior LinkedIn label was text-only;
activation requires Preview impact before Review activation. The production
loader now deliberately reuses templatesFromPresets; the label is LinkedIn post.

## Validation

Targeted publisher/worker/conformance checks passed (72 before the additional
ambiguity case; final worker file 12/12). Static checks passed during development.
The selector requires full coverage because production composition changed.
One complete `bun run check` attempt passed static checks and all unit suites,
then stopped after 93/96 browser scenarios passed (20.9 minutes). The three
failures were stale expectations: two selected the former LinkedIn text label;
one expected two images to exceed the former one-image limit. The label fixtures
now use LinkedIn post. The attachment-isolation journey keeps its source/sibling
preservation, editing, reload and promotion assertions, while accepting two
images under v3. This is a contract change, not a flake or a weakened isolation
assertion. The new explicit-upgrade journey passed in the complete run.

The three affected journeys passed in the targeted replay: 3/3, 1.3 minutes,
one worker, no retries. Remaining gate layers
are run separately: password-reset 2/2 (11.5 seconds), all 17 builds passed
(4.4 seconds), final static checks passed. No second complete browser replay
is warranted for these identified test-only fixture corrections. This is
aggregate coverage, not a claim that the final commit passed one uninterrupted
full command. `validated/full` remains unchanged. No container recovery:
container behavior is unchanged.

## Limits and next outcome

No GIF, video, PDF carousel, native-client mosaic reproduction, throughput claim,
new permission policy or silent channel migration. Large batches upload in order;
parallel transfer is not needed for this capability. Local/S3 are reused through
the same media-content port, not provider-specific public hosting.

Next recommended product outcome: actionable failure/ambiguity alerts outside the
application through one optional transport, using the existing durable notification
outbox. Choose recipients/preferences and the transport before implementation;
this sprint does not authorize that separate boundary.
