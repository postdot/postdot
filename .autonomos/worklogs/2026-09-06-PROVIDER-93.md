## Decisions applied

- X is a centralized built-in provider identified by `x` with execution
  contract `x@post-v1`.
- Authentication uses OAuth 2.0 Authorization Code Flow with S256 PKCE and
  confidential-client `client_secret_basic` at
  `https://api.x.com/2/oauth2/token`. Scopes: `tweet.read`, `tweet.write`,
  `users.read`, `offline.access`, `media.write`.
- The callback validates the PKCE verifier, exchanges the code, reads
  `GET https://api.x.com/2/users/me`, and persists the encrypted access
  token, refresh token, and expiry in the project-owned credential store.
- The destination is `{ type: 'account', id, name }` where `id` is the
  numeric X user ID and `name` is `@username`.
- Expired credentials refresh atomically at the execution boundary. A
  failed refresh marks the credential reconnect-required and fails
  permanently.
- Text posts go to `POST https://api.x.com/2/tweets` (280 characters).
- Up to 4 JPEG/PNG images (5 MB each) upload through the existing
  `MediaStore` and provider media-delivery ports with durable remote-media
  checkpoints before tweet creation. Alt text attaches via the metadata
  endpoint when present. Uncertain uploads are ambiguous, never silently
  retried.
- Outcome classification: 401 authentication_required (permanent), 403
  forbidden (permanent), 400/404/422 invalid_request (permanent), 429
  rate_limited (retryable), 409 conflict (retryable), 5xx/timeout/network
  on mutating effects ambiguous.
- X hosts are fixed (`api.x.com`, `upload.twitter.com`); there is no
  per-instance user-configurable destination, so the shared
  operator-controlled egress boundary for per-instance providers
  (ADR-043) does not apply. This matches the Discord precedent.
- Better Auth remains Herald application authentication only. No tokens,
  secrets, verifiers, or sessions appear in public errors.

## Review follow-up (2026-09-06, same task)

Addressed five PR review findings without touching unrelated work:

1. X is now a first-class built-in channel: `createChannelBody` accepts
   the `x` literal, `resolveChannelProfile` resolves it to
   `xChannelProfile`, and `app.test.ts` proves X channel creation through
   the API (201 plus active `x@post-v1` profile state).
2. Added dedicated X OAuth route integration tests with a loopback fake
   provider and an injected fake publisher: connection start (scopes,
   S256 PKCE challenge, callback URI), callback success, PKCE verifier
   delivery to the token endpoint, encrypted verifier persistence with
   single-use clearing on consume, invalid/replayed/mismatched-actor
   states, token-endpoint provider errors, token non-disclosure across
   responses and ciphertext, and project-owned credential/connection
   persistence surviving actor deletion.
3. Migrated media upload from deprecated v1.1 `upload.twitter.com` to the
   current v2 chunked flow on `api.x.com` (initialize with
   `media_category: tweet_image`, single-segment append, finalize,
   `POST /2/media/metadata` for alt text), same `media.write` scope.
   Contract tests pin every request shape, `expires_after_secs` mapping,
   and per-step classification (failed processing permanent, pending
   processing ambiguous).
4. Replaced naive 280-character validation with twitter-text v3 weighted
   counting (`packages/x/src/text.ts`: NFC, URLs 23, emoji/ZWJ/flags
   2, CJK 2, Latin ranges 1, invalid-character rejection) enforced by
   the adapter before any external effect; the profile static 280 bound
   is documented as a coarse authoring approximation with residual
   differences noted. Tests cover URLs, emoji clusters, CJK, NFC, and
   boundaries.
5. Documented and tested media identifier expiry/retry semantics: v2
   sessions expire per `expires_after_secs` (~24h); Herald reuses
   uploaded checkpoints younger than the conservative 20h horizon
   (`X_UPLOADED_MEDIA_REUSE_TTL_MS`, restart-safe via persisted
   `completedAt`) and requires explicit reconciliation for older ones;
   retryable upload failures re-upload on the next attempt; provider
   rejection of media identifiers at tweet creation is permanent
   `invalid_request`. The shared delivery store was not modified.

## Orchestrator correction (2026-09-06)

The review found that the previous chunked-media implementation and its tests did not
match the current public X v2 append contract. The in-progress worker change was retained
and completed by switching the current JPEG/PNG scope to the documented simple multipart
`POST https://api.x.com/2/media/upload`; chunked upload remains a future capability for
media types that require it. The publisher tests now assert the multipart fields and the
optional metadata request.

The previous expiry follow-up was also incomplete: `expiresAfterSecs` was returned by the
provider package but discarded by the workflow. The shared provider media delivery now
persists `remoteMediaExpiresAt` through migration `0019_flawless_greymalkin`, and X reuses
a checkpoint only while both the provider deadline (when available) and the 20-hour safety
horizon are fresh. Regression coverage covers persistence, propagation, provider-expiry
reconciliation, and the documented upload shape.
