# REALTIME-106 — Validate realtime restart, reconnect, and burst behavior

## Objective

Validate the post-commit project signal, durable journal replay, notification
projection recovery, and SSE waiter lifecycle without changing the realtime
architecture or adding a provider, broker, schema migration, or dependency.

## Scope and implementation

- Started `feat/realtime-validation` from `origin/main` at `447acf0b`.
- Added `apps/api/src/modules/projects/realtime-validation.test.ts`.
- Kept production code unchanged: no defect was found in the post-commit
  transaction boundary, project-scoped wakeup hub, notification projection, or
  cursor-aware stream.
- Tests use in-memory SQLite for local failure/isolation cases and unique
  temporary SQLite files for restart and burst cases. No shared server, real
  provider credential, or external provider action was used.
- `.autonomos/TASKS.md` and `.autonomos/ISSUES.md` were intentionally not edited
  per the mission instructions.

## Coverage

- Zero subscribers: a supported journal write projects immediately with no SSE
  waiter and no global recovery scan; a later stream reads the durable event.
- Project isolation: duplicate project ids are deduplicated, every waiter for
  project A wakes, and project B remains asleep until explicitly cancelled.
- Reconnect: events committed between stream lifetimes replay from the prior
  cursor exactly once; a stream starting after the newest cursor receives only
  the next committed event. Existing API coverage also retains malformed
  `Last-Event-ID` (`400 invalid_cursor`) and cursor-ahead (`409 cursor_ahead`)
  assertions.
- Restart: a committed event survives close/reopen of a temporary database;
  startup projection recovery recreates the inbox item and journal replay
  returns the event.
- Burst: 240 events commit in one transaction, preserve journal and SSE order,
  produce exactly one notification per source event across paginated reads, and
  leave 24 idle stream waiters at zero after cancellation.
- Failure: rollback emits no signal and leaves no event; an observer exception
  cannot fail a committed write; a projection trigger failure leaves the fact
  committed and a later run recovers the notification.

## Benchmark observation (not a CI assertion)

The 240-event temporary-database burst scenario completed in approximately
68 ms in the full local gate. The suite deliberately asserts ordering,
durability, deduplication, and cleanup only; it has no wall-clock threshold.

## Remaining limitation

The signal remains process-local by design. Supported Postbot writes are covered;
an external process or uninstrumented raw SQLite writer still requires a future
durable cross-process signal if multi-process deployment is introduced.
