# UX-335 — Overlapping Composer Upload Order

- Base: `7c16a4b6a`.
- Scope: diagnosis only, isolated browser harness, no provider calls.
- Status: diagnostic complete; selected, submitted and persisted order confirmed.

## Finding

Files within one upload batch are processed sequentially by the uploader in
`apps/web/src/lib/herald-media-upload.ts`. However, `files-added` in
`media-attachment-picker.tsx` starts `uppy.upload()` for each addition. Multiple
batches may overlap (`allowMultipleUploadBatches: true`). Each resolved batch is
appended to the current selection by `processUploadResult`, so completion order
can differ from addition order across batches.

A controlled browser probe added red/1, green/2, blue/3 images using the existing
canvas fixture. The first finalize request was held, the second file was added,
and its selection was required to become visible before releasing the first.
Three ready images were then read as green/red/blue at both 1280 and 390 px.
This reproduced on two runs (18.3 and 18.7 seconds for the scenario, approximately
21 seconds with harness). The normal completed-sequential-addition regression
from UX-248 remains unchanged and checks red/green/blue.

This is not an image-decoding explanation for the earlier swap: controlled
completion changes selected/rendered order. It is not evidence that a single
multi-file batch is reordered. No file loss was observed.

## Reproduction recipe

Use the destination-truthfulness fixture in
`e2e/web-124-outcome-states.spec.ts`, three colored numbered canvas assets,
and this gate before file additions:

```ts
let releaseFirst!: () => void
const released = new Promise<void>(resolve => { releaseFirst = resolve })
let firstReached!: () => void
const held = new Promise<void>(resolve => { firstReached = resolve })
let finalizations = 0
await page.route('**/media/uploads/*/finalize', async route => {
    if (++finalizations === 1) {
        firstReached()
        await released
    }
    await route.continue()
})
```

After adding the first file, await `held`; add the second, await one visible
preview image, release the first, then await two images before adding the third.
Read rendered colors with the existing loaded-image canvas method. Expect the
observed green/red/blue order for this diagnostic, not as a desired product
contract. The retained normal fixture is the positive control with each addition
fully completed before the next. No fixed sleep or retry is needed.

The temporary copy is removed after diagnosis rather than committing an assertion
that would enshrine the undesired completion-order behavior. A correction should
retain a regression asserting the chosen intended order under this same gate.

## Consequence and proposed next intervention

Adding another attachment while one is in progress can place the later-added
image first. The renderer follows selected order, so this can affect the intended
carousel sequence. The composer submission in dashboard context uses `sourceMedia`
without sorting; provider dispatch has not been exercised here.

Recommend preserving file-add order across overlapping batches while allowing
uploads to finish independently. Alternative: block further additions until the
current batch resolves, at the cost of interaction responsiveness. The first
option should be reviewed before implementation, including failed or removed
pending files, explicit user reordering, library selections and recovery. No
placeholder policy or UI behavior is decided in this diagnostic.
