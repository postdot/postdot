# OPS-140 — Enforce runtime quiescence before backup restore

- Status: completed
- Date: 2026-09-11
- Scope: API startup/shutdown, SQLite restore, media restore, recovery documentation, and regression coverage
- Related issue: [ISSUE-026](../ISSUES.md#issue-026-enforce-runtime-quiescence-before-backup-restore)
- Related task: [OPS-140](../TASKS.md#recovery-quiescence-follow-up)
- Related decision: [ADR-068](../decisions/ADR-068-runtime-quiescence-sidecar-lock.md) (proposed)

## Implementation

The API and restore primitives now share a database-specific sidecar lock:

- `acquireRuntimeQuiescenceLock` creates `<database>.runtime.lock` with an
  atomic exclusive filesystem operation before an owner opens or replaces the
  database.
- The API owns the marker for its full process lifecycle and releases it after
  stopping workers, stopping the HTTP app, and closing SQLite.
- Database-only and complete media restores own the marker from the beginning
  of validation through the final atomic replacement and release it on every
  success or failure path.
- The marker is fail-closed and is never reclaimed from PID metadata. A forced
  stop can therefore leave a marker that must be removed only after the
  operator verifies that no Postbot process is using that database.

The online backup path remains unchanged: SQLite snapshotting and the existing
media backup fence still support backups from a running application. This
change addresses restore quiescence, not a new requirement to stop for backup.

## Verification

- Runtime-lock unit coverage verifies exclusive ownership, stale-marker refusal,
  in-memory rejection, and release.
- Backup regression coverage verifies restore refusal while a server lock is
  held and successful restore after the lock is released.
- Root and database recovery documentation describe the stop, restore, restart,
  and forced-stop marker lifecycle.

## Follow-up

The proposed ADR-068 should be accepted or revised by the owner as part of the
next recovery/runbook review. No deployment needs an external lock service for
this boundary under the current single-process model.
