# DB-611 — PostgreSQL profile with engine parity (phase 2 of ISSUE-194)

Status: in progress (2026-11-06), branch `feat/postgres-storage-profiles`.
Decision record: [ADR-097](../decisions/ADR-097-selectable-storage-profiles.md) (proposed).
Owner direction (2026-11-06): break compatibility only where it simplifies the
work. The SQLite baseline regeneration (DB-610) waits until PostgreSQL parity is
proven, so the deployed alpha keeps upgrading in place.

## Checkpoint 1 — adapter and engine contract

- `sql/postgres-adapter.ts`: `PostgresSqlDatabase` on Bun's built-in `Bun.SQL`.
  - Every transaction runs at SERIALIZABLE isolation and is replayed (jittered
    backoff, 8 attempts) on SQLSTATE 40001/40P01. Stores were written against
    SQLite's single writer (read-then-write checks, claims, revision fences);
    serializable isolation keeps those outcomes. Replay is safe because
    transactions perform no external I/O (port contract).
  - Savepoints are issued as SQL on the transaction connection (unlimited
    nesting); concurrent sibling savepoints are refused as on SQLite.
  - Rows are normalized to the SQLite shape: `int8` arrives as BigInt
    (`bigint: true`) and becomes a number (values beyond 2^53 are rejected);
    unquoted `as camelCase` aliases, folded to lowercase by PostgreSQL, are
    restored from the statement text, so internal references keep working
    unquoted. JSON stays `text` columns, as on SQLite.
  - `iterate()` materializes results (Bun.SQL 1.4 has no cursor yet).
- `isUniqueConstraintError` reads the SQLSTATE from `errno` (Bun.SQL).
- `DatabaseHandle` (`{ sql }`) is the engine-neutral type every store accepts;
  `createPostgresDatabase(url)` / `closePostgresDatabase`. `PostdotDatabase`
  remains the SQLite database (Drizzle + `$client`) for SQLite tooling and tests.
  The credential-refresh queue is keyed by the port instead of `$client`;
  `runSync` is removed (no remaining use).
- `sql/test-engines.ts` + `sql/port.contract.test.ts`: the same 10 contract tests
  run on SQLite and, when `POSTDOT_TEST_POSTGRES_URL` is set, on a disposable
  PostgreSQL database per test. Both pass (20 tests) on PostgreSQL 18.6.

Local PostgreSQL for development: a disposable cluster under the ignored
`.tmp-db609/pg` directory (unix socket only, port 55432), never the shared
default port.

Next: PostgreSQL schema and baseline (domain, auth, triggers, views), Better Auth
on PostgreSQL, then the store suites on both engines.

## Checkpoint 2 — portable migrations and schema parity (ADR-097 §6 amended)

Owner decision (2026-11-06): Postdot owns its schema as portable SQL migrations;
Drizzle is retired rather than duplicated or converted.

- `packages/db/migrations/0000_baseline.sql`: one reviewed file. Sections
  `-- postdot:common|sqlite|postgres` run in file order.
  - Common DDL (70 tables, 161 indexes, 6 views, instance seed) is shared text:
    SQLite accepts PostgreSQL type names (`bigint`, `double precision`), and all
    foreign keys are `DEFERRABLE INITIALLY IMMEDIATE` (SQLite keeps immediate
    checks; PostgreSQL can defer like `defer_foreign_keys`).
  - PostgreSQL section: a `blob` domain over `bytea` and compatibility functions
    `unixepoch`, `json_valid`, `json_type` (SQLite type names) and `instr`, so
    defaults and CHECK constraints stay common; `audit_events` uses an identity
    sequence (`audit_events_sequence_seq`); the self-referencing
    `media_representations` key is added after its unique index; the 48 triggers
    are plpgsql functions (`RAISE(ABORT)` -> `raise exception`, SQLite `IS NOT`
    -> `IS DISTINCT FROM`).
  - SQLite section: `audit_events` with `AUTOINCREMENT`, the self-referencing
    table verbatim, the 48 original triggers.
  - Tables are ordered by foreign-key dependency, each followed by its indexes;
    views by dependency.
  - The file was drafted once from the migrated schema by a throwaway script in
    the ignored tooling folder; from now on it is edited by hand, with no generator.
- `sql/migrator.ts`: loads contiguous `NNNN_name.sql`, applies pending
  migrations in a transaction each, records `postdot_migrations(id, name,
  checksum, applied_at)`, refuses modified applied migrations, and takes a
  PostgreSQL advisory transaction lock so concurrent instances migrate once.
- `sql/schema-introspection.ts` describes a schema engine-neutrally (tables,
  columns with type class/nullability/default presence, primary keys, indexes
  with uniqueness/partiality/columns, foreign keys with delete actions, CHECK
  counts, views and their columns, triggers). PostgreSQL's 63-byte identifier
  truncation affects two index names and is normalized.
- `sql/schema-parity.test.ts`: (1) the portable baseline on SQLite equals the
  historical Drizzle chain 0000-0027 exactly; (2) PostgreSQL equals SQLite. Both
  pass (PostgreSQL 18.6).

Not yet switched: runtime and tests still migrate SQLite through the historical
chain; the switch and in-place adoption of up-to-date databases happen at merge.
Next: run the store suites on PostgreSQL (behavioral parity of triggers,
compatibility functions and SQL), then Better Auth on the port and Drizzle removal.

  - Fixtures still used `insert or ignore` (now `on conflict do nothing`).

## Checkpoint 4 — 13 store test files green on PostgreSQL

Converted (engine-selected databases, port statements instead of `$client`):
access, channel destination and lifecycle, event journal, post destinations and
source, publication moves, notifications and deliveries, provider analytics and
applications, workspace attribution and shared channels. On PostgreSQL: 81 store
tests plus the 20 port contract tests pass; SQLite stays green (361 db, 565 API).

Test helpers in `@postdot/db/testing`: `foreignKeyViolations` (SQLite
`foreign_key_check`; none possible on PostgreSQL) and
`installRejectingTrigger`/`dropRejectingTrigger` (temporary failure injection on
either engine).

Engine differences found and fixed:
- Scope cleanup triggers (`AFTER DELETE` on projects/workspaces) ran after
  PostgreSQL's key checks because both fire in trigger-name order. The three keys
  they satisfy (`actors` -> projects/workspaces, attachments -> projects) are
  `INITIALLY DEFERRED` on PostgreSQL, preserving SQLite's "cleanup after cascades".
- Upsert `set revision=revision+1` was ambiguous; it now names the table.
- The audit sequence high-water mark reads `pg_sequences.last_value`.
- `scalarMaxSql` repeats expressions on PostgreSQL, so an unnumbered `?` inside
  shifted every following parameter; the affected statement uses `?1`, and the
  helper now refuses unnumbered placeholders.
- Expression booleans (`exists`, comparisons) are normalized to 1/0 like SQLite.

SQLite-only (file-based features), kept as is: migrations history, backup/restore,
WAL recovery, runtime quiescence, legacy and conversion migrations, multi-process
concurrency, draft adoption (backup round trip) and resource lifecycle (restart on
the same file). Remaining conversions: suites relying on the Drizzle query builder
(manual store, workflow, first comments, publishers, analytics, domain schema,
media, OAuth attempts, media deliveries, credentials, avatars).

## Checkpoint 5 — the whole db suite runs on PostgreSQL

The remaining Drizzle-builder suites (manual store, workflow, first comments,
publishers, credentials, analytics, domain schema, media, OAuth attempts, media
deliveries, avatars) now use engine-selected databases and port statements. Full
db suite: 365 pass on PostgreSQL (6 SQLite-only skips), 360 on SQLite; API 565.
Schema assertions that used `pragma` read `describeSchema` instead, so they hold
on both engines.

Engine differences found and fixed:
- Production bug: the avatar reconciler referenced `user.id` unquoted; on
  PostgreSQL `user` is `current_user`, so the statement failed and the swallowed
  error left retired avatars in storage. Identifiers are now quoted (also in the
  local account recovery tool).
- Media filename search relied on SQLite's ASCII case-insensitive `LIKE`;
  `likeCaseInsensitiveSql` emits `ILIKE` on PostgreSQL.
- Tests opened manual transactions with `exec('begin')`, which a pooled
  PostgreSQL client refuses; they use `sql.transaction`.
- A historical-chain test lost its re-migration step during conversion; restored.

Open point for the PostgreSQL profile: text ordering follows the database
collation (the test cluster uses `en_US.UTF-8`), whereas SQLite compares bytes.
Results stay correct and keyset cursors consistent, but name ordering can
differ from SQLite (case/accents). Decide before release whether to require a
`C` collation, declare `collate "C"` on sorted columns, or accept the difference.

Next: Better Auth through the persistence port, then Drizzle retirement.

## Checkpoint 6 — Better Auth runs on the persistence port

`@postdot/auth` no longer uses Better Auth's Drizzle adapter. `postdotSqlAdapter`
(`packages/auth/src/sql-adapter.ts`) implements Better Auth's adapter contract with
engine-neutral SQL on `database.sql`:
- every operation runs in a port transaction (SQLite writer gate, PostgreSQL
  serializable retries); Better Auth transactions are port transactions, so hooks
  calling Postdot stores join them. The proxy that gated Drizzle is gone;
- tables and columns are the snake_case form of Better Auth names, checked against
  the Better Auth schema (a field outside it, e.g. a crafted `sortBy`, is refused);
- dates are epoch milliseconds, booleans 1/0, JSON and arrays text (as before);
- pattern operators are case-sensitive on both engines (`instr`/`strpos`,
  `substr`); the `insensitive` mode lowers both sides. Drizzle's `like` was
  silently case-insensitive on SQLite only.

`createAuth` takes a `DatabaseHandle`. The auth suite runs on either engine
(15 tests plus 5 adapter tests, green on SQLite and PostgreSQL); API 565 green.

Next: Drizzle retirement (API TypeBox schemas, remaining test usage, schema files,
migration chain switch with in-place adoption).

## Checkpoint 7 — Drizzle retired

Postdot no longer depends on Drizzle (`drizzle-orm`, `drizzle-kit`, `drizzle-typebox`
removed; schema files and `drizzle.config.ts` deleted).

- `createDatabase` returns `PostdotDatabase = { sql, $client }`: the port plus the raw
  SQLite client for SQLite-only features (backup, WAL, maintenance, fixtures).
- API row schemas are explicit TypeBox (`apps/api/src/modules/projects/persistence-schemas.ts`);
  the generated OpenAPI document is identical to the Drizzle-generated one.
- `runMigrations` (async) runs the portable migrations. A SQLite database whose legacy
  Drizzle chain is complete (27 entries, last `0026_postdot_identity`) and whose schema
  equals the baseline (`describeSchema`) is adopted in place: `0000_baseline` is recorded,
  later migrations apply. Incomplete or drifted legacy databases are refused before any
  change. Verified on a copy of the local development database (data intact, only
  `0001_adoption_sequence` applied).
- The legacy chain is frozen in `packages/db/legacy-migrations/` (SQL + journal only)
  for adoption and parity tests. The branch-only Drizzle migration 0027 became portable
  `0001_adoption_sequence` so databases deployed from `main` (at 0026) adopt cleanly.
- The migrator keeps the fail-closed behaviour: SQLite foreign keys off during the run
  and `foreign_key_check` before each commit, refusal inside a caller transaction,
  immutable applied migrations (checksums).
- Removed: transition tests inside the legacy chain (conversion, application, reply,
  attribution, identity migrations, rehearsal) and their fixtures; they describe upgrades
  that can no longer run. Tests of current behaviour in those files were kept
  (`workspace-channel-attachments.test.ts`).
- Deployment paths (`Dockerfile`, config default, e2e/scripts) point at `migrations/`;
  backup/recovery recognise `postdot_migrations` or the legacy history table.
- `bun` is classified as a builtin by the bundle probe (Bun.SQL import).
- The auth test asserting that a read waits for an open writer is SQLite-only
  (PostgreSQL reads a snapshot); invisibility of uncommitted rows is asserted on both.

Verification: check:quick; db 351 SQLite / 358 PostgreSQL; auth 20/20 on both; API 565;
web 304; client 5; scripts 117 (production bundle and startup/shutdown included).

Next: `POSTDOT_DATABASE_URL` runtime engine selection in the API (single image), API
suites on PostgreSQL, then DB-612 (topology enforcement).

## Checkpoint 8 — one image, engine chosen at startup

- `POSTDOT_DATABASE_URL` (`postgres://` / `postgresql://`) selects PostgreSQL; otherwise
  SQLite (`DB_FILE_NAME`). Both at once is refused. `POSTDOT_DATABASE_POOL_SIZE`
  (default 10). `config.database` is a discriminated profile.
- Single server per database on both engines: SQLite keeps the runtime lock file;
  PostgreSQL holds `pg_try_advisory_lock` on a dedicated session for the server's
  lifetime (released when the session closes, including on crash). A second server is
  refused at startup. DB-612 will relax this once realtime and runtime coordination
  work across instances.
- Shutdown awaits an async database close (pool, then the lock session).
- Recovery holds (SQLite restore) do not exist on PostgreSQL; the SQLite maintenance
  commands (backup, restore, recovery, media-previews) refuse with guidance to use
  PostgreSQL tooling. Offline password recovery remains SQLite-only (follow-up).
- API runtime types take `DatabaseHandle`.
- `scripts/postgres-profile.test.ts` starts the real API on a fresh PostgreSQL database:
  migrations applied, `/ready` 200, first account claims the instance through Better
  Auth (admin role), a second server is refused, SIGTERM exits 0.
- Installation docs gain a PostgreSQL section (PostgreSQL 18 is the tested version).

Next: run the API suite on PostgreSQL (39 test files open SQLite directly, 203 `$client`
uses), then DB-612.

Engine differences found and fixed:
- `sum()` over `bigint` is `numeric` on PostgreSQL, which Bun.SQL returns as a string;

- Tests: quoted `"user"`, portable rejecting triggers, `rowid` ordering removed, the
