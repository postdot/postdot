# ANALYTICS-229 — Review the project event-journal retention policy

- Status: complete; owner policy remains unchanged
- Date: 2026-09-26
- Issue: ISSUE-135
- Related decisions: ADR-028, ADR-037, ADR-042, ADR-048, ADR-060
- Scope: assess journal retention options; no data, schema, or runtime behavior changed

## Current contract

- ADR-037 already accepts retaining `audit_events` for the lifetime of their
  project. Project deletion cascades the project's journal. ADR-028 and the
  accepted design in ADR-060 preserve this lifecycle; neither introduces an
  automatic time-to-live or a separate archive.
- The journal stores actual project and publication workflow facts. The
  operational analytics endpoint reads those facts on demand; it does not
  persist analytics snapshots. Its historical query range is capped at 366 days.
- The audit API returns at most the latest 100 rows per request. The durable
  journal has wider responsibilities than that API response.

## Retention dependencies

- `notifications` and `notification_deliveries` reference source events with
  `ON DELETE CASCADE`. Pruning an old journal row would therefore erase the
  corresponding in-app notification and external-delivery record, including
  their read, retry, and delivery history.
- Analytics reads historical facts directly from `audit_events`. A short TTL
  would silently reduce the history available to queries within the documented
  366-day maximum.
- Project and user SSE streams reconnect with the durable global sequence. The
  current contract rejects malformed or future cursors but has no retention
  floor. Sequence gaps are normal for project-filtered streams, so a pruned
  interval cannot be treated as a detectable missing-event signal. Safe pruning
  would need an explicit floor/resynchronization contract and coordination with
  notification projection cursors.
- The media usage summary counts audit events for a `media_asset` entity, and
  the reference guard checks those rows. No current writer for that entity type
  was found, so this is a dormant compatibility point rather than evidence of
  an active retention dependency.
- Project deletion remains the existing complete lifecycle boundary; there is
  no need to retain a deleted project's journal independently of its project.

## Storage evidence

ANALYTICS-227 measured a disposable SQLite database using Herald's migrated
schema and 100,000 synthetic publication/execution facts. The closed database
file was 79,048,704 bytes (75.39 MiB), approximately 790 bytes per event with
the current indexes; insertion took about 0.6 seconds on that development
machine. This is a rough schema-scale measurement, not a production forecast:
payload sizes, notification rows, WAL behavior, backups, disk limits, and real
event rates vary. No production or shared user database was inspected.

## Options and recommendation

1. **Keep project-lifetime retention (recommended; current accepted policy).**
   This preserves audit facts, notification and delivery history, analytics,
   and replay semantics. The trade-off is database and backup growth with real
   project activity. The current evidence does not show that this growth is a
   deployment problem.
2. **Delete facts after a fixed age.** This can cap the hot database, but a
   window of 366 days or less contradicts the analytics range; even a longer
   window deletes source-linked notification and delivery records and requires
   explicit SSE and projection retention-floor behavior. A scheduled `DELETE`
   alone is not a safe implementation.
3. **Archive or compact old facts.** This can preserve history while reducing
   hot-database cost, but adds archive storage, backup/restore, project-delete,
   authorization, replay, and query lifecycles. There is no measured workload
   that justifies that complexity yet.

Recommendation: make no retention change. Continue retaining journal rows until
their project is deleted, as already accepted in ADR-037. Revisit only if real
deployment database or backup growth shows a concrete constraint, or if the
owner wants a different history promise. Any finite window must first define
which notification, audit, analytics, and replay history may be lost and add a
resynchronization boundary before pruning.

This recommendation does not decide whether analytics should be restricted by
project role. The current project-actor access boundary remains unchanged, and
the web surface remains deferred rather than permanently excluded.
