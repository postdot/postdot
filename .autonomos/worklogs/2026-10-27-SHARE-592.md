# SHARE-592 — Migration transaction and ownership preflight

Status: in progress. Continues the accepted ADR-095/SPEC-009 implementation and
the [preceding worklog](2026-10-26-SHARE-592.md).

## Changes

The migration runner previously checked foreign keys after Drizzle committed.
A failed check could therefore report an unsuccessful upgrade while leaving its
schema, data and migration-history changes persisted. A regression fixture
reproduced that failure before the correction.

The runner now applies SQL, history, foreign-key checks and optional domain checks
inside one immediate SQLite transaction. Any failure rolls back that transaction.
Drizzle still parses committed migration files; its existing history format and
timestamp ordering are preserved. Its stock runner has no pre-commit verification
hook, which is why transaction execution is owned here. Nested migration calls are
rejected before changing the connection's foreign-key setting.

An internal rehearsal entry point runs the same path and deliberately rolls back
after successful verification. It requires the same exclusive runtime boundary
as an upgrade; no new operator command or live-database access is introduced.

The legacy ownership planner reads only resource/project/workspace IDs. It refuses
unassigned projects, including empty ones, without assigning a default workspace.
Independent credentials for the same external account remain independent records.
It neither loads secret envelopes nor changes ownership. It is preparation for
the conversion, not a registered runtime migration.

## Workspace attribution and the shared journal

The registered `0021_workspace_attribution` migration extends existing actors and
`audit_events` with workspace scope. Each row has exactly one scope, enforced by
CHECK constraints and scope-matched actor foreign keys. Existing project actors,
facts and editorial references retain their original IDs and values. This is the
attribution part of the ownership conversion, not the channel-resource conversion.

`createWorkspaceActorStore` snapshots an actor only after resolving its real
project/workspace relation. The origin ID is provenance without a cascading link;
it confers no membership or permissions. Snapshot creation uses its actual time,
not a fabricated historical date. The existing project actor remains unchanged.

Workspace facts use the existing journal and global cursor through explicit
workspace append/read methods. Project reads remain project-only. The global
notification stream advances past workspace facts without converting or exposing
them as project updates. Notification project discovery excludes workspace-only
actors. No workspace broadcast or public sharing endpoint is added here.

SQLite actor deletion now happens in AFTER DELETE scope-cleanup triggers, after
other owned data has cascaded. Rebuilding actors exposed a pre-existing reliance
on sibling-cascade order: immediate RESTRICT references could reject legitimate
project deletion. Actor owner foreign keys now use NO ACTION, with cleanup in the
same deleting statement. Dangling references still reject and roll back deletion.
Workspace deletion uses the same ordering; workspace actors survive project deletion.

The generated table-copy SQL was corrected to select literal NULL for new scope
columns. The audit rebuild explicitly preserves `sqlite_sequence`, including a
high-water mark above every remaining event. Migration rehearsals and rejected
verification restore the original schema, rows, history and sequence together.

Historical fixtures now name historical actor columns. The destination-identity
SQL regression uses its named migration in isolation rather than assuming that
the newest journal entry is always the destination migration. Its assertions on
selected content, execution data and unknown legacy destination identity remain.

A worker sandbox exposed a real test-fixture deadline race: successful localhost
responses exceeded its five-millisecond budget and correctly became ambiguous.
The timeout response now waits on an explicit cleanup gate; ordinary I/O has a
100 ms budget. Published/retry/failure/ambiguity and timeout-reconciliation
assertions remain unchanged. No production timeout or dispatch rule changed.

## Ownership conversion candidate

The ownership SQL is staged at
`packages/db/migration-candidates/workspace-channels/0022_workspace_channels.sql`.
Its separate journal is used only by isolated migration tests. It is deliberately
absent from `packages/db/drizzle/meta/_journal.json` and the packaged startup
migration directory: existing stores still expect project-owned columns. This is
a tested conversion candidate, not an activated migration or delivered sharing.

The candidate converts channels, profiles, publishers, connections and credentials
to workspace ownership while preserving their IDs. It creates one migrated
attachment per existing channel, with migration-time provenance and no fabricated
historical sharing event. Only actors referenced by common resources are copied
into workspace scope; an existing snapshot for the same origin is reused.

An explicit `channel_managers` relation gives a channel one stable managing
project. Detaching/deleting that project removes the relation and promotes no
other project. Its foreign keys require the manager and channel to share the
workspace and an active attachment is required when assigning management.

`project_channel_profiles` and `project_channel_publishers` are derived attachment
relations, not additional owners or independent ACLs. They retain project/profile
and project/publisher referential guarantees for editorial and execution rows.
Project/post/content/actor relations remain project-scoped. Existing historical
references survive detachment; new common-resource bindings are derived only for
active attachments and restored when a project is explicitly reattached.

Source-project deletion cascades its content before attachment cleanup, while
workspace-owned resources and attribution remain. Scope lifecycle triggers are
preserved; common-resource guards refer to the workspace lifecycle. New effects
are fenced at `effect_started_at` for publications, replies and first comments.
Already-started records can finalize after detach. API authorization, queue
selection, friendly blocked-state handling and operational retirement remain store/
service work; SQL proofs do not establish those behaviors.

The candidate refuses unassigned projects and keeps duplicate external accounts
as independent credentials. Rebuilding dependent tables changes their references
to the derived attachment relations instead of dropping tenancy constraints.
It does not add a second credential pool, default workspace assignment or implicit
manager selection.

## Canonical channel commands and project-context read integration

Migration `0022_project_channel_contexts` registers read-only project-context views.
The existing stores now consume these views for channel/profile/publisher/connection/
credential reads, including editorial creation, worker targets, OAuth binding,
analytics and media-reference readers. Current source still writes project-owned
resource tables; this migration changes no ownership or data. Context projection
is a durable read contract, not schema detection or a second ownership path.

The inactive ownership candidate was renumbered from 0022 to 0023 before activation,
so it follows the registered read contract. It drops those views while rebuilding
their parents and recreates them from workspace resources and explicit attachments.
No applied startup migration was edited or removed.

`workspace-channel-store.ts` implements canonical creation, project/workspace lists,
filtered usage metadata, attach, detach and explicit management transfer. It is
constructed only against the candidate schema in tests; it is not exported through
the runtime package entry point or registered in HTTP services yet.

Command checks run inside the immediate write transaction through a request-bound
policy port. The port must be connected to the existing common session/key
permission path; it does not derive grants from workspace actor presence. Sharing
capability is separate from connection management. An owner's withdrawal from
its own project needs that project's scope, rather than requiring the unseen
managing project. Manager-originated changes and transfers check all affected and
request-context project scopes. These are policy-port tests, not end-to-end API-key
or session authentication acceptance.

Creation records the workspace channel, compiled profile, first attachment,
managing relation and workspace fact atomically. The prior profile-fingerprint
normalization is shared with the existing creation path, without changing its
validation. Channel revisions fence relation changes. A journal failure rolls back
the resource graph and emits no post-commit wakeup.

Removing the final active attachment requires an explicit archive choice. An
already archived channel can be withdrawn without repeating that decision or
rewriting its archive timestamp. Reattachment preserves original migration
provenance and does not restore management automatically. Transfer records both
previous and new managing project IDs in the workspace journal. Project/workspace
metadata masks unreadable manager names/IDs and never reports a hidden project
count; usage lists contain only readable projects. Workspace administration does
not grant project-content reads.

### Decisions made inside ADR-095 (flag for owner review)

- **Staged credentials.** Between OAuth completion and connection a credential has no
  attachment path. It is visible only to the project whose actor created it (via the
  workspace actor's origin) until a connection exists; afterwards visibility follows
  attachments. This is provenance, not authorization — live access is still checked
  above the store. A second view, `project_active_publisher_credential_contexts`,
  restricts revocation and management to active attachments; token refresh uses the
  historical context so an admitted effect can finish after detach. Alternative
  considered: create credential and connection atomically, which would restructure
  every provider flow.
- **Channel-wide blockers.** Archive, delete and disconnect now consider active work
  and attachments of every attached project. Delete adds a new `shared` blocker when
  other projects still use the channel (API schema, Studio type and EN/FR copy added).
- **Connecting queues work for all attached projects**, not only the caller's.
- **Project-scoped channel creation** keeps its existing contract and delegates to the
  canonical store with a policy admitting only that project; the policy is not an
  authorization grant — callers authenticate first.
- **Tests.** Fixtures that seeded project-owned rows now use `@postdot/db/testing`
  helpers. Historical-schema tests seed raw legacy columns on a truncated chain and
  upgrade through the real chain (`migrationsThrough`, `seedLegacyScheduledChannel`);

## Live authorization and the first sharing API

`createChannelAccessPolicy` (API) is the single decision for sessions and user API
keys: a key adds a capability and a project scope on top of the owner's live role
and never exceeds it. Reading needs `project:read`; creation and management need an
editor role and `channel:manage`; attach and transfer need an editor and
`channel:share`; withdrawing a project needs its owner and `channel:share`. A key
restricted to specific projects has no workspace-level authority, and sharing needs
scope for every affected project (context, current manager and target).
`channel:share` is a new capability in the key model, creation schema, Studio key
form (EN/FR) and the authentication reference; it grants no connection management,
dispatch or secret access.

Four routes expose the store through that policy: `GET .../channels/:id/sharing`
(callers see only readable projects and no hidden count), `POST .../attachments`,
`POST .../attachments/:project/withdraw` and `POST .../management`. Mutations report
`stale_revision` and `retirement_required` as 409 with the current revision. The
project-facing channel schema now exposes the attachment context `projectId` rather
than the workspace owner. `manualStore.contextFor` resolves the attribution actor
from the caller's live project actor; a caller without one is masked as not found.

Validation: three HTTP cases (session journey with attach, shared listing, stale
conflict, transfer, withdrawal and the last-project archive choice; key capability
and scope refusal; outsider masking), the route-to-capability map, the OpenAPI
inventory, API 527 and database 304 cases, and `check:quick`. No browser run: no
Studio presentation changed.

Not done: workspace-level channel listing and creation routes, anonymous shared
calendar occupancy, cadence, moving pending work, OAuth callback rechecks bound to
workspace/channel, Studio and CLI flows, and the container upgrade acceptance.

## Shared calendar occupancy

A project's calendar now shows time that other projects already use on its shared
channels. `sharedChannels.occupancy` reads publications of other attached projects on
the channels the project actively uses, in a bounded window (at most 500 items), and
reports only scheduled, ready, publishing, published (at the recorded time) and
ambiguous work. Drafts, cancelled and definitely failed work are never reported. Work of
a detached project occupies the channel only once published or ambiguous, since its
future work can no longer run. Each item is described in full only when the caller can
read that project (live role, key scope and `project:read`); every other item is
anonymous: slot, state and channel, with no project identity, title, content or count.
`GET /api/projects/:projectId/channel-occupancy?from&to` serves it to sessions and keys
under `project:read` and masks callers without project access as not found.

In Studio the entries appear beside the project's own work as muted, italic,
non-interactive items in month, week, day and agenda views (readable projects as
"title · project", others as "Time taken on {channel}"), with an explanatory sentence
under the calendar. They are excluded from selection and bulk actions by construction:
the selection maps are built from publication events only, and a click does nothing.
The calendar adapter's event data is now a union of publication and occupancy data.

## Optional channel cadence

Migration 0024 adds opt-in channel rules (independent rules revision, channel
timezone, daily and weekly maxima, minimum interval and last effect admission)
and attributed per-publication, single-effect spacing exemptions. No rule is
configured on existing channels. The managing project's timezone initializes a
new configuration; civil days and Monday-start weeks belong to that channel,
while project date entry keeps its existing timezone. The migration also indexes
channel planning time and recorded outcomes. Drizzle Kit generated malformed
quoting for the comma-separated expression index; its SQL was corrected while
preserving the generated schema snapshot.

Channel managers and workspace administrators configure rules through the live
request policy and `channel:manage`, using an expected rules revision. Read-only
callers need project read access. Configuration changes journal their workspace
actor and invalidate all attached project views; scheduler wakeups apply both
new restrictions and removed restrictions. Blank Studio limits disable each
rule independently. The channel menu opens this form; API configuration is
`GET/PUT /api/projects/:projectId/channels/:channelId/cadence`.

Creation, draft promotion, approval, bulk rescheduling and explicit failed-work
retry check planning inside their existing immediate write transaction. Relevant
scheduled, ready, publishing, published and ambiguous work participates; drafts,
cancelled and definitely failed items do not. Detached future work is excluded;
published/ambiguous history remains. Published manual work uses recorded
`publishedAt`, not its former requested schedule. Planning reads a bounded time
envelope around affected periods. A conflict exposes only channel, period, rule,
limit and publication count, without another project's identity or content.
Confirmation fingerprints bind the current rules, occupancy and publication/journal
revisions and the requested operation/times. Immediate approval binds the explicit
publish-now intent and its civil periods so an advancing request clock cannot
make confirmation impossible. New publication IDs are assigned only to the
successful write's audit metadata, not to a challenge that must survive retry.
A stale challenge returns a fresh 409. Replanning invalidates spacing exemptions;
confirmed maximum exceptions and exact affected publications/times are journaled
with the acting project actor. Studio presents the conflict and requires an
explicit confirmation; changing schedule/cancelling the dialog leaves work intact.
