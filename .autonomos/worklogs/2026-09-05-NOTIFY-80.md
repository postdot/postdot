# NOTIFY-80 — Persistent Project Notification Inbox

## Objective

Implement a durable, idempotent in-app notification projection for project human
actors without coupling publication workflows to presentation or future transports.

## Plan

1. Define the recipient, preference, notification lifecycle, and supported event
   contract.
2. Add migration-driven inbox, preference, and projection-cursor persistence with
   project isolation and idempotency tests.
3. Project an explicit allowlist of high-value publication outcome events and prove
   restart-safe cursor advancement.
4. Expose authenticated list, unread-count, read, archive, and preference operations
   through the typed API.
5. Run the complete repository gate and an independent read-only review before merge.

## Acceptance criteria

- Only project human actors are notification recipients; event actors remain
  attribution only.
- Reprocessing an event cannot duplicate an inbox item.
- Projection cursor advancement and inbox writes are atomic and restart-safe.
- Unknown event names or versions are skipped explicitly without blocking later facts.
- Preferences are project- and recipient-scoped and default safely when absent.
- Read and archive transitions are idempotent and project-isolated.
- No external provider call, web UI, or process-local event dependency is introduced.
