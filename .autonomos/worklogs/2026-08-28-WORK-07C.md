# WORK-07C — Durable Execution Outcomes, Retry, and Cancellation

## What Was Done

- Added a framework-independent workflow executor with a closed external-outcome
  contract: confirmed publication, known retryable failure without an external
  effect, known permanent failure without an external effect, and ambiguity.
- Added a configurable exponential retry policy with explicit attempt and delay
  bounds. Persistence contains no product-specific retry numbers.
- Added fenced SQLite transactions for confirmed success, scheduled retry, terminal
  failure, ambiguity, and pending cancellation.
- Connected the next-event scheduler, executor, and real SQLite store in a
  deterministic integration test.
- Extended the footprint command with a production-bundled, no-network publication
  fixture and five-process peak-memory sampling.

## Key Decisions and Why

- An exception from the external-effect callback is always ambiguous because the
  durable boundary has already been crossed and the remote outcome is unknown.
- Automatic retry requires the typed outcome to assert `effectOccurred: false`.
  Neither a timeout nor an unclassified exception can become a blind retry.
- A retry transaction returns the publication to `ready` and the same job to
  `pending`, preserving its attempt count while clearing attempt-scoped claim data.
- When the retry policy returns no next time, the job and publication fail
  atomically with the provider error retained.
- Pending cancellation updates the publication and job together and attributes the
  state change to the requesting project actor. Running work is not reported as
  prevented, especially after the external-effect boundary.
- Completion remains conditional on the claim token. Recovery or prior completion
  makes a stale completion a no-op.
- No dependency, schema migration, service, polling loop, provider adapter, or
  generic repository was added.

## External-Outcome Crash Matrix

| Crash or result point                          | Durable result                                  | Automatic retry |
| ---------------------------------------------- | ----------------------------------------------- | --------------- |
| Before claim                                   | Pending job remains due                         | Yes, by claim   |
| After claim, before effect boundary             | Expired claim returns to pending                 | Yes             |
| After boundary, before provider call            | Expired job fails; publication becomes ambiguous | No              |
| Provider may succeed, before local completion   | Expired job fails; publication becomes ambiguous | No              |
| Callback throws after boundary                  | Job fails; publication becomes ambiguous         | No              |
| Provider confirms no effect and retryable error | Job returns to pending within policy bounds       | Bounded         |
| Provider confirms permanent rejection           | Job and publication fail                         | No              |
| Provider confirms publication                   | Job succeeds; publication result is persisted     | No              |

The conservative false-ambiguity window before a request reaches the provider is an
accepted consequence of ADR-009. A future provider may reduce it with an
idempotency key or reconciliation API, but cannot weaken the default rule.

## Limitations and Next Steps

1. The M2 executor is a proven composition boundary, not yet a worker mounted in the
   API process. Runtime composition belongs with the first automatic publisher.
2. Real provider outcome mapping, idempotency behavior, and contract tests remain
   part of PUB-09; no provider behavior was guessed in this proof.
3. Retried jobs currently retain their attempt count but not an event per failed
   attempt. MANUAL-08 must add the accepted M3 audit-event persistence before the
   workflow becomes user-facing.
4. Proceed with MANUAL-08's REST, CLI, and minimal-dashboard vertical slice while
   preserving the completed workflow boundaries.

No `AGENT.md` was changed: the reusable safety rules are already captured by the
accepted ADR-006 and ADR-009, and the remaining observations are task evidence.
