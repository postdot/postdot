# PROVIDER-356 — First native MP4 video destination

Base: `50713cd30`. Status: completed; owner confirmed ready-to-publish MP4
without conversion. The owner accepted the video publishing sprint after NOTIFY-355.
The initial feasibility probe preceded implementation.

## Established gaps

The media model already carries family, dimensions and duration. Real acceptance
is narrower: default upload types are PNG, JPEG and WebP; the inspection registry
only reads image headers. Finalization scans all bytes for SHA-256 but keeps only
the first MiB for inspection. An MP4 movie index can be at the end of the file,
so accepting a filename or parsing the first header alone is insufficient.

LinkedIn v2/v3 execution adapters accept images only. Existing delivery rows
persist a remote identifier but do not retain multipart upload progress or a
processing stage. Image resumption treats an identifier as a completed upload;
that rule must never be inherited by video, where initialization already returns
an identifier before any bytes are sent.

## Proposed product boundary

One native MP4 video per LinkedIn publication, mutually exclusive with image
attachments. Ready-to-publish H.264 video; no automatic conversion, native binary,
thumbnail generation or caption editor in this first sprint. Preserve the current
100,000,000-byte installation storage default rather than silently increasing it.
Provider-specific constraints remain capped by installation storage. Validate
three seconds to thirty minutes before promotion. Audio codec acceptance needs
an explicit supported profile during implementation; MP4 container detection alone
is not a codec guarantee.

The owner confirmed ready-to-publish MP4 without conversion, using MP4Box.js
under Bun and retaining the installation storage default. Audio is limited to
AAC-LC when present; silent video remains supported.

## Concrete Bun feasibility probe

An isolated temporary directory installed `mp4box@2.4.1` with scripts disabled.
A locally generated four-second H.264 clip was inspected under Bun 1.4.2 in
16-KiB chunks using `createFile(false)`, `appendBuffer` and `onReady`. Both layouts
(movie index at the beginning and at the end) returned exactly 4,000 ms,
320 by 180 pixels, `avc1.64000c` and 96 video samples. Files were each 118,816 bytes.
The library installation was 2.2 MiB and introduced no transitive runtime package
in that isolated install. FFmpeg generated disposable fixtures only; it is not
proposed as a production dependency.

This proves basic Bun interoperability, not safe bounded parsing of adversarial
files. Implementation must bound metadata/track complexity, avoid retaining media
payloads and reject malformed/unsupported containers. Use an existing parser,
not an independent MP4 implementation. Temporary files are removed after evidence
capture; no provider credentials or external publication used.

## Delivery direction

- Add authoritative streamed inspection at the existing media finalization
  boundary; retain storage independence and byte/checksum verification.
- Add a new immutable LinkedIn execution revision, retaining v2 and v3. Existing
  channels adopt it through the accepted explicit profile-upgrade workflow.
- Persist stage information necessary to resume initialized/uploaded/finalized
  video safely. Never infer completion from a remote identifier alone.
- Respect provider byte ranges and ordered ETags when uploading parts; keep
  upload URLs/tokens private and redact error echoes. Handle ambiguous dispatch
  through existing reconciliation semantics rather than blind retries.
- Release the worker while provider processing is pending; use durable scheduled
  status checks, not a sleep loop or periodic browser polling. Create the post
  only after `AVAILABLE`; surface `PROCESSING_FAILED` as a useful failure.
- Complete media library, authoring selection and compact video preview together.
  Reject mixed image/video batches before upload and explain unsupported inputs.

## Delivered implementation

LinkedIn v4 (`member-post-v4`) accepts one MP4, exclusive of image batches.
Historical v2/v3 adapters remain registered and image-only; upgrades are explicit.
Family-specific size and duration constraints are enforced against pinned media.
Streamed MP4Box inspection accepts H.264 with optional AAC-LC, bounded metadata,
tracks and sample tables. It does not decode every frame or transcode files.
The BSD license is retained in the production image; FFmpeg is fixture tooling only.

The existing delivery row records the initialized video URN before transfer.
Contiguous provider ranges and ordered ETags drive multipart upload. Upload URLs
and tokens remain ephemeral. A resumed initialized upload is checked against the
provider status; an uncertain or incomplete upload is ambiguous rather than
blindly replayed. Finalized uploads wait durably for AVAILABLE, releasing the
worker for one-minute status checks, bounded to thirty minutes. Deferrals do not
consume failure attempts or generate failure alerts. No automatic part resumption
is claimed. The new deferred audit event refreshes the project through existing SSE.

Authenticated media reads support single byte ranges for native browser playback
and seeking. The existing media library, attachment list and destination preview
use native video elements; playback controls are provided in inspection surfaces.
No new service, public media endpoint or production native executable is required.

Principal files: core media/profile/executor contracts; DB MP4 inspection, media
finalization and workflow persistence; LinkedIn video transport and v4 profile;
API adapter, media range route and executor registration; existing web media
preview/viewer; Docker license inclusion. Durable tests cover inspection, range
reads, multipart checkpointing, processing statuses, repeated worker deferrals,
media family rejection and one browser authoring/playback journey.
