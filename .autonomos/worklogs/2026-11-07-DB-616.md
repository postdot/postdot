## Recovery policy

The API workflow scheduler opts into recovery only for PostgreSQL serialization
failure (40001) and deadlock (40P01), using the same classifier as transaction
replay. The adapter's eight transaction attempts and jitter remain unchanged.
The scheduler rereads durable state after 1, 2, 4, 8, 16 and then 30 seconds;
continued failures remain capped at 30 seconds. Successful execution resets the
failure count. New hints cannot bypass the wait. The scheduler exposes
`recovering`, and reports every error through its existing error handler.

Recovery is opt-in: other scheduler clients, SQLite, unknown errors, constraint
violations and connection failures retain their terminal error policy. This is
not a general database-outage recovery feature. There is no provider call replay,
new queue service, increased concurrency or relaxed transaction isolation.

The active batch drains before retry scheduling. Recovery timers are canceled by
stop, stale timer callbacks cannot restart stopped work, and active plans/effects
retain the existing drain barrier. Long timer caps do not cause early recovery.

## Deterministic evidence

Store-boundary fault injection simulates a conflict escaping transaction replay.
On both engines, a failure before the effect leaves a running claim without a
started effect: recovery waits for its lease, then executes it once. A failure
recording completion after provider success leaves the durable effect marker:
lease recovery marks it ambiguous and never calls the provider again. These tests
exercise real persistence and scheduler/executor behavior; they do not claim to
induce eight actual database serialization failures in a row.

Scheduler tests cover planning failure, repeated recovery, hint suppression,
backoff reset and shutdown with a stale timer. The worker policy tests whitelist
only the two transaction SQLSTATE codes and check the cap. A real PostgreSQL
worker test injects one failed planning read and verifies recovery to an empty
started scheduler. Existing terminal-error tests remain unchanged.

Qualification exposed an existing timing assumption in the immediate-backlog
stop test: a zero-delay stop could fire before PostgreSQL reached any effect.
The stop is now scheduled by the first effect. The test still requires the timer
to interrupt before all ten jobs drain, preserving its microtask-starvation check.

## Remaining limits

Scheduler recovery attempts continue at the capped frequency while classified
conflicts persist; the transaction replay count itself remains bounded. There is
no claim that overload has become fast, or that arbitrary database outages now
recover. No new production capacity ceiling is inferred from deterministic tests.
The next useful qualification is a longer overload/recovery soak with real
provider latency and cancellation, independently of this fault-injection proof.
