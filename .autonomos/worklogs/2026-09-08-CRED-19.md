# CRED-19 — Runtime provider application configuration

- Status: design recorded; implementation not started
- Date: 2026-09-08
- Scope: provider application configuration versus publisher credentials and
  channel connections
- Related issue: ISSUE-059
- Related decision: ADR-056

## Evidence

The current model supports multiple channels and multiple project-owned provider
credentials. Publishers are unique per project/channel; credentials are unique
per project/provider/external account; publisher connections index credentials
without making a credential globally unique. The remaining runtime friction is
that LinkedIn, X, and Bluesky OAuth application configuration is currently
resolved from environment variables during API startup.

The local Bluesky smoke test exposed this boundary: the analytics route can use
public provider data without an OAuth token, but the web connection action
returned `503` when the instance lacked `BLUESKY_CLIENT_METADATA_URL`. A local
development connection was created through the existing encrypted stores only
to validate analytics; it is not evidence that the OAuth flow is configured.

## Decision captured for implementation

Keep deployment bootstrap variables and the encryption root key, but move
provider application settings into an encrypted, instance-owned runtime store.
Allow multiple application configurations per provider, associate the selected
configuration with OAuth attempts and credentials, and preserve unlimited
project-level accounts/channels subject only to provider-specific policy.

## Non-goals

This work does not remove provider-side app registration, callback registration,
scope approval, provider quotas, or the operator's responsibility for the
encryption root key. It does not add a universal provider abstraction or change
the project/channel ownership model.

## Next implementation boundary

Design the schema and authorization policy first, then implement the runtime
resolver and OAuth integration behind tests for multiple configurations,
multiple accounts, project isolation, secret redaction, restart behavior, and
truthful `not_configured` readiness.
