## Operator outcome (what a channel operator actually meets)

Creating a custom channel starts from an editable full-definition JSON (template
copied verbatim, metadata included). Editing a profile draft starts from an
editable content-only JSON with identity, origin, version and both fingerprints
shown read-only. That split is real and visible, not just a server detail.

When custom creation input is semantically wrong, the dialog stays open and the
typed JSON is kept, but no field is named: the only signal is the page-level
`Channel action failed / The request could not be completed.` banner behind the
dialog. The same wrong definition in the draft editor names
`/capabilities/textFields/0/bindingId` with a localized correction and never
echoes the submitted value. Creation echoes the submitted binding value in its
message. The shipped `custom-manual` starter itself cannot be created as-is: it
lacks the required JSON Schema dialect, so the first attempt fails with a joined
`Custom schemas must declare ...` message the UI does not explain. Adding the
dialect and restoring the binding in the same open dialog succeeds and the new
channel appears.

## Q1 — Which creation metadata is input, derived, verified, or stored?

Demonstrated (store probe + API probe, both removed after measurement):

- All five are **required HTTP inputs** at creation: omitting `profileHash`
  (or deleting `capabilities` key) returns `422 validation_error / The request
  does not match the expected shape` before compilation. No `issues` field.
- All five are **stored verbatim** when present: a template copy (`version 1`,
  symbolic `sha256:herald-…` hashes) stores `version 1` and the same symbolic
  hashes; an arbitrary `version 999` with `sha256:operator-chosen-…` hashes is
  accepted and stored verbatim (`store.getChannelProfileState` confirms).
  Non-blank checks and `version >= 1` / `origin == 'custom'` are the only
  metadata checks; hash correctness is not verified.
- Draft editing is the opposite: metadata is omissible/legacy-tolerant,
  `id`/`origin` mismatches are rejected, `version` is ignored and replaced
  with `active.version + 1`, and both hashes are always re-derived as
  `sha256:<hex>` (see UX-328 regression). The UI hides them as read-only.

Comparison without transposition: a new channel has no active lineage to pin
to, so `version 1` as a starting version is not itself a defect, and creation
must accept some initial identity. The demonstrated obstacle is that the
operator must **author unverified fingerprints by hand** (copied from the
template, invented, or left stale), exactly the burden UX-328 removed for
drafts. Whether creation should mint server-owned identity/hashes for new
lineages, or keep caller-owned identity with explicit rules, is an open
product/identity decision — deliberately not transferred silently here (per the
UX-330 boundary).

## Q2 — What happens when one template creates several channels?

Demonstrated (isolated store + real `app.handle` API, counts verified):

- Identical reuse succeeds: two channels created from the same
  `id/version/hashes/schema` return `201`; both store the same profile `id`
  (e.g. two channels share `custom-manual`). Profile identity is therefore
  not channel-unique today.
- Same `id/version/hashes` with an edited schema (only `maxLength 1000 → 900`)
  fails: `400 invalid_content / The same immutable profile identity and schema
  hash resolved to different schemas`, no new channel (`3 → 3`). This is the
  useful immutability guard firing **across channels** because the cache key is
  global and the UI never tells the operator to change the hashes when editing
  the schema.
- The workaround (invent a new hash string) is accepted, as in pre-UX-328
  drafts, but nothing in the creation surface says so. The failure is generic
  (`Channel profile is invalid: …`), with no path and no repair hint.

Classification: the collision itself is legitimate; blocking the second
channel while the operator follows the visible template flow is an unnecessary
obstacle. The fix depends on the identity decision in Q1 (fresh server-owned
identity per new channel, channel-scoped cache, or explicit hash-ownership
guidance). It must not weaken the cache guard to make creation pass.

Additional demonstrated starter defect: the shipped `custom-manual` (and
`custom-webhook`) template in `apps/web/src/lib/channel-profile-presets.ts:80-111`
has no `$schema` dialect, while `templatesFromPresets` (`:118-136`) adds one
for built-in starters. The real browser starter therefore fails creation as-is
with `Custom schemas must declare https://json-schema.org/draft/2020-12/schema`.
The probe's unedited-template control returned `400`; adding the dialect in the
same dialog returned `201`. Code asymmetry makes accidental omission the likely
cause, but intent is not proven; the user consequence (every first custom-manual
attempt fails with generic copy) is demonstrated.

## Q3 — How are invalid definitions handled at creation?

Representative cases (store + API + one browser journey; valid control included):

| Submitted defect | Core `compile` | Creation store | Creation API | Draft API (same shape class) |
| --- | --- | --- | --- | --- |
| Missing `capabilities` key | `profile.object_required @/capabilities` | `DomainInvariantError invalid_content: Expected object`, no `issues` | `422 validation_error` (absent key fails body schema first) | `400` with `issues:[{/capabilities, profile.object_required}]` |
| `capabilities: null` (present) | same | same joined failure | `400 invalid_content: Expected object`, no `issues` | `400` with `issues:[{/capabilities, profile.object_required}]` (browser + API probe) |
| `fieldBindings: null` | `profile.array_required @/fieldBindings` | joined `Expected array` | `400`, no `issues` (present null reaches compiler) | `400` with path/code |
| Missing `execution` key | `profile.object_required @/execution` | joined `Expected object` | `422` (absent key) | `400` with `/execution` |
| Numeric binding `path: 42` | `profile.string_required @/fieldBindings/0/path` | joined `Expected string` | `400`, no path/code | `400` with path/code |
| Unknown binding `FAKE_SENTINEL_XYZ` | `capability.binding_missing @/capabilities/textFields/0/bindingId` | joined `Unknown binding ID FAKE_SENTINEL_XYZ` (echoes value) | `400`, body contains the sentinel verbatim, no `issues` | `400` with `{/capabilities/textFields/0/bindingId, capability.binding_missing}`, sentinel absent |
| Negative `maxLength` | `capability.limit_invalid` | joined limit message | `400`, no `issues` | `400` with path/code |
| Altered-schema reuse (same hashes) | `profile.schema_hash_conflict @/schemaHash` | joined conflict | `400` conflict, no `issues` | n/a (draft versions advance, hashes re-derived) |

Also demonstrated:

- HTTP/status contract: creation uses `400 invalid_content` (joined) or `422
  validation_error` (absent key) with `{error:{code,message}}` only. Draft
  invalid uses `400 invalid_content` with `{error:{code,message,issues,issueCount}}`.
  `409 write_conflict` semantics were not re-probed here; UX-330 already covers
  them for drafts and creation has no draft-revision concept.
- No `500` was observed for the tested malformed shapes: the UX-330 structural
  guard benefits creation too (failures are `400`/`422`, not crashes). This is a
  bounded statement about the tested shapes, not an exhaustive audit.
- No partial creation: every refused request left `listChannels` count unchanged
  (store `3 → 3`, API `1 → 1` / `3 → 3`); the browser journey kept the count
  before the corrected `201` (`n → n+1` only after the fix).
- JSON preserved: the creation dialog stays open with the exact invalid text
  after a `400` (browser `expect(json).toHaveValue(invalid)` green); the draft
  dialog behavior is unchanged from UX-330.
- Correction in the same flow works: browser invalid `400` → add `$schema` +
  restore binding → `201`, dialog closes, channel appears. Store/API valid
  controls also succeed after refusals.
- User-visible feedback gap: creation shows no field, no code, no repair; the
  inline dialog alert count is `0` and the global banner is the generic
  `Channel action failed / The request could not be completed.` Draft shows
  one summary plus per-field localized corrections and redacts submitted
  values; creation echoes them (demonstrated `containsSentinel=true`).

Per `herald-operational-ux`: creation conflates two intents in one surface
(create-channel vs author-profile) and answers a content error with transport
copy. The draft dialog keeps one dismissal, one summary, and field-anchored
repairs; creation keeps the dismissal and preservation but loses the repair.

## Demonstrated defects, intentional choices, product questions

Demonstrated defects (each with a concrete user consequence above):

1. Shipped `custom-manual`/`custom-webhook` starters lack the required
   `$schema` dialect, so the default custom creation fails before the operator
   changes anything. Likely an omission (built-in starters add it), but
   recorded as defect-with-consequence regardless of intent.
2. Creation requires hand-authored, unverified fingerprints and stores them
   verbatim (arbitrary strings and `version 999` accepted). Editing the schema
   without inventing new hashes blocks a second channel with a global
   `schema_hash_conflict` and generic copy.
3. Creation error contract is the pre-UX-330 shape: joined messages, no
   paths/codes, absent-key `422` vs present-but-invalid `400` with no field
   identity, and verbatim echo of submitted values (sentinel proved). The draft
   contract (ADR-081) already solves redaction, paths, bounds, and
   localization for the same compiler issues.

Intentional / to preserve (not defects):

- Explicit activation, historical definitions, execution policy, authorization,
  and the draft `409` concurrency guards were not touched and must stay
  untouched by any creation follow-up.
- `422` for a missing top-level key is the existing Elysia body-validation
  behavior, not a compiler crash; any change must keep a clear shape-vs-content
  boundary rather than collapsing both into one status.
- No `500` for the tested shapes is the UX-330 guard working as intended.

Product questions for the owner:

- What is the identity contract for a **new** custom channel? Fresh
  server-owned `id`/`version 1`/derived hashes per channel (draft-like
  derivation at creation), or caller-owned identity with explicit uniqueness
  and hash-ownership rules? Do not silently copy the draft-save rule; creation
  has no active lineage to continue.
- May two channels share one profile `id`? Today they can. If identity becomes
  server-owned per channel, sharing disappears; if it stays caller-owned, the
  global cache and the UX must say so.
- Should creation reuse the ADR-081 `issues`/`issueCount` projection (same
  codes/paths/bounds/redaction) once identity is decided? The codes already
  exist; the route, client formatter, and dialog copy are the remaining work.

Hypotheses (not claimed as defects):

- The `$schema` omission looks like an oversight because only one of the two
  template paths adds it, but no intent record was found; the failure itself is
  fact, the oversight label is hypothesis.
- Widening the draft feedback projection to creation is assumed feasible
  because both share the compiler issue shape, but no implementation was
  attempted here.

Not verified in this mission:

- `declarative_http`/`mapped_http`/`built_in` execution variants at creation,
  preset-literal creations, rename/archive/restore/delete interplay,
  concurrent creation races, non-manual capability families, French creation
  copy, narrow-layout creation review beyond the existing 390 px draft proof,
  and any migration/authorization/execution-behavior change (explicitly out of
  scope).
