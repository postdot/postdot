## Executive finding

Herald currently stores scheduling values as epoch-millisecond instants, but the
web authoring and calendar surfaces interpret and display those instants in the
browser's local timezone. That is a valid single-device convention, and it is
internally consistent for a user who stays in one timezone. It is not an explicit
project scheduling contract: two operators in different timezones can see different
wall-clock dates and times for the same scheduled publication.

This is a product semantics decision, not evidence that the current numeric storage
or durable scheduler is unsound. The existing scheduler can continue to operate on
instants after a timezone policy is accepted. Implementation should wait until the
project's source of truth for wall-clock scheduling is chosen.

## Observed behavior and evidence

### Domain and persistence use instants

- `packages/core/src/invariants.ts:38-46` validates timestamps as non-negative,
  safe integer epoch-millisecond values.
- `packages/core/src/model.ts:81-114` models `Publication.scheduledAt` and
  `Job.runAt` as `Timestamp` values with no timezone component.
- `packages/core/src/model.ts:280-317` validates a scheduled publication against
  `input.now` as an instant and does not interpret a wall-clock timezone.
- `packages/core/src/model.ts:342-384` applies the same instant-based validation to
  job execution times.
- `packages/db/src/domain-schema.ts:851-878` persists
  `publications.scheduled_at` as an integer. There is no project timezone field in
  `projects` at `packages/db/src/domain-schema.ts:40-48`.
- `packages/db/src/domain-schema.ts:1203-1230` persists `jobs.run_at` as an
  integer and indexes it for due-event lookup.
- `packages/core/src/scheduler.ts:106-140` computes timer delays from the next
  numeric event time and the current numeric clock. It has no timezone dependency.

The current representation is therefore suitable for preserving an instant across
restarts and devices. It does not, by itself, say what a user-entered local time
means for a shared project.

### Web authoring uses the browser timezone

- `apps/web/src/lib/date-time.ts:1-5` parses a `datetime-local` value with
  `Date.parse`. The value has no offset, so the JavaScript runtime interprets it in
  the browser's local timezone.
- `apps/web/src/lib/date-time.ts:7-12` converts an instant back to a
  `datetime-local` value by applying `Date.getTimezoneOffset()`.
- `apps/web/src/components/publication-target-list.tsx:177-189` labels the field
  `Local browser time.` and renders the `datetime-local` input.
- `apps/web/src/lib/dashboard-context.tsx:175-180` uses the same parser before
  submitting a scheduled publication.
- `apps/web/src/lib/publication-authoring.ts:1-19` creates default schedule values
  through the same browser-local conversion.

The editor therefore round-trips the same instant for one browser, but the same
displayed wall-clock input submitted from another timezone represents a different
instant.

### Calendar and labels also use the browser timezone

- `apps/web/src/lib/publication-calendar.ts:21-53` builds month boundaries with
  `getFullYear()` and `getMonth()`.
- `apps/web/src/lib/publication-calendar.ts:56-66` groups scheduled publications
  using `new Date(publication.scheduledAt)` and local `getFullYear()`,
  `getMonth()`, and `getDate()` through `toDateKey` at lines 87-92.
- `apps/web/src/components/publication-calendar-view.tsx:235-247` formats day and
  time labels with `Intl.DateTimeFormat` without an explicit `timeZone` option.
- `apps/web/src/components/dashboard-publication-parts.tsx:204-207` and
  `apps/web/src/components/publication-editor.tsx:1083-1089` use
  `toLocaleString()` without an explicit timezone.
- `apps/web/src/lib/publication-calendar.test.ts:35-56` explicitly describes and
  tests grouping by local date. `apps/web/src/lib/date-time.test.ts:5-15` verifies
  local round-tripping but does not test different runtime timezones or DST
  boundaries.

There is no current API or CLI project-timezone contract in the inspected
application, package, or script surfaces.

## User-visible consequence

Assume a publication is stored for `2026-09-10T09:00:00Z`.

- An operator in `Europe/Paris` sees 11:00 during summer time.
- An operator in `America/New_York` sees 05:00.
- Near midnight, the publication can appear on different calendar dates.

The worker still executes at the same instant in all cases. The ambiguity is in
authoring and presentation: a user who enters “09:00” means browser-local 09:00,
not a project-defined 09:00.

## Credible policy alternatives

| Policy | Meaning of an entered wall-clock time | Strengths | Costs and risks |
| --- | --- | --- | --- |
| Browser/device local | The authoring device defines the timezone | Smallest change; familiar for a single operator | Shared projects are unstable across devices, travel, and DST; calendar dates differ |
| Project IANA timezone | The project defines one named zone such as `Europe/Paris` | Deterministic shared schedule; matches a publication manager's project-level intent | Requires persistent project setting, explicit UI labels, IANA validation, and DST rules |
| UTC | All authoring and display use UTC | Fully deterministic and simple for machines | Poor human authoring experience; users must reason in UTC |
| Actor/user timezone | Each operator sees and authors in their own zone | Convenient for personal views | A shared schedule has no single wall-clock meaning; edits can surprise collaborators |

## Recommendation for owner review

Adopt a project IANA timezone as the source of truth for scheduling wall-clock
semantics, while keeping persisted `scheduledAt` and `runAt` values as epoch
milliseconds. The default calendar and editor should format and interpret values in
the project timezone and label that timezone clearly. A future explicit “view in my
timezone” mode can be added without changing the stored instant or execution
semantics.

This preserves the current compact storage and scheduler design. It does require a
small project timezone field and a single well-tested conversion boundary; it does
not justify a general date abstraction across the whole codebase.

## External reference check

The owner feedback exposed a legitimate hybrid model: a business project can have
one civil-time context while clients still render an absolute instant in a viewer's
local timezone when that is useful. The following primary references support that
distinction:

- [RFC 3339](https://www.rfc-editor.org/rfc/rfc3339.html) recommends UTC for
  interoperability because local civil-time rules change, and requires a stated
  relationship to UTC for interoperable timestamps.
- [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545.html) models a fixed calendar
  time either as UTC or as a local date-time with a `TZID`; an unqualified local
  date-time is floating time and has no shared timezone meaning.
- The [IANA time zone database theory](https://www.iana.org/time-zones/theory)
  describes named zones as the representation of civil-time histories and future
  rule changes, including daylight-saving transitions.
- The [Google Calendar event model](https://developers.google.com/workspace/calendar/api/concepts/events-calendars)
  accepts an IANA `timeZone` alongside a date-time and states that the internal
  event instant remains the same. A timezone is required to expand recurring local
  times consistently.
- The [TC39 Temporal model](https://tc39.es/proposal-temporal/docs/) separates an
  exact `Instant` from a timezone-aware `ZonedDateTime`, and exposes explicit
  disambiguation for local times affected by daylight-saving transitions.
- The [`datetime-local` control](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/datetime-local)
  does not carry a timezone by itself. A web application must therefore supply the
  timezone context separately instead of treating the control value as a complete
  interoperable timestamp.

These references do not prescribe Herald's product policy, but they converge on a
useful separation: transport and execution use exact instants; human scheduling
uses a named civil-time context.

## Refined recommendation after owner feedback

The recommended Herald contract is now:

1. Keep `scheduledAt` and `runAt` as epoch-millisecond instants in the domain,
   database, scheduler, and worker.
2. Store an IANA timezone at project level as the default context for authoring and
   calendar presentation. This is a project/business setting, not the server's
   operating-system timezone.
3. Let the web editor display and interpret `datetime-local` values in the project
   timezone by default, with the timezone shown to the operator. A later explicit
   viewer-local display can coexist with this default.
4. Require API and CLI machine requests to provide an absolute timestamp (UTC or a
   numeric offset). A human-oriented request may instead provide a local date-time
   together with an explicit IANA timezone; a timezone-less local value must not be
   accepted as an interoperable schedule.
5. Resolve a one-time schedule to its exact instant once. Changing a project
   timezone must never silently move an already scheduled publication; any change
   that affects how an existing schedule is presented or re-authored must be
   explicit.
6. If recurring schedules are introduced later, preserve the local wall-clock rule
   and its IANA timezone in addition to each calculated execution instant. UTC alone
   cannot express “09:00 in New York” across daylight-saving transitions.

This gives a French operator working on an American project a default view such as
“09:00 America/New_York”, while the worker receives and executes the corresponding
UTC instant. The operator may later choose a personal-local view without changing
the schedule.

The remaining product decisions are limited to the initial project-timezone default,
the visibility and review flow for a project-timezone change, and the DST policy.
The recommended DST policy is to reject nonexistent local times and require an
explicit choice or offset for ambiguous local times rather than silently guessing.

## Decisions still required

The following points cannot be inferred safely from the current code:

1. Accept project IANA timezone semantics, or deliberately retain browser-local
   semantics for the foreseeable product scope.
2. Choose the initial project timezone behavior: require it at project creation,
   assign a browser-derived default once, or provide an explicit project setting
   before scheduling is enabled.
3. Define the treatment of a local wall-clock time that does not exist during a DST
   spring transition and one that occurs twice during a DST fall transition. The
   safe baseline is to reject nonexistent times and make ambiguous times explicit
   rather than silently guessing.
4. Preserve existing stored instants if a project timezone is introduced, or run an
   explicit operator-reviewed reinterpretation. The recommended default is to
   preserve existing instants; changing only their display is not a data migration.

## Implementation boundary after approval

Do not change date parsing, schema, or calendar code until the policy above is
accepted. Once accepted, implement the smallest boundary in this order:

1. Persist and validate the project IANA timezone.
2. Convert a project-local wall-clock input to an epoch instant in one tested module.
3. Format editor, calendar, dashboard, API-facing labels, and recovery buffers with
   the same explicit timezone context.
4. Keep the scheduler, job claims, retries, and provider execution instant-based.
5. Add cross-timezone, DST, device-change, and existing-schedule integration tests.

The conversion boundary must not be approximated by applying a fixed offset: IANA
zones have seasonal transitions and historical changes. `Intl` is useful for
formatting, but arbitrary local-wall-time-to-zone parsing needs its own tested
mechanism or a deliberately selected Temporal-compatible implementation.

## Test matrix

- Round-trip a project-local time in at least two IANA zones.
- Verify that two devices show the same project wall-clock time while their local
  zones differ.
- Verify calendar grouping around midnight in the project timezone.
- Verify DST nonexistent and ambiguous local times according to the accepted rule.
- Verify a project timezone change does not mutate persisted instants unless an
  explicit migration operation is selected.
- Verify scheduler due-event selection and retry timestamps remain unchanged by
  presentation timezone.
- Verify API and CLI payloads continue to transport instants without implicit
  device-local reinterpretation, or document and test any intentionally humanized
  input format.

patched in this review, and no timezone policy was selected implicitly.
