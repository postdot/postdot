# UX-270 — Administration forms: workspace membership pass

Status: partial; workspace membership slice complete.

## Outcome

- Workspace members stay at the top of the page. Add a member opens the shared
  Base UI dialog rather than an always-visible invitation form.
- Create group opens a focused dialog beside the Groups heading, replacing the
  form at the bottom of the page. Both dialogs retain input after dismissal,
  close after success and prevent dismissal while a request is pending.
- Pending invitations appear only when present. Their heading no longer repeats
  the workspace identity or an invitation form heading.
- Group surfaces use the same raised material and shared radius as the members
  and invitations sections, replacing translucent nested group foundations.
- Failed creation stays inside the active dialog, without duplicate background
  feedback. Retry preserves the email, group and group name.
- Base UI selects now receive explicit value-to-label mappings for invitation
  groups, group members and workspace roles. An isolated browser assertion
  exposed the previous technical team identifier in the selected value.
- Read-only membership disables role selection as well as mutation handlers.

## Boundaries

No API, membership model, grants, credentials, real accounts or real workspace
records changed. Existing owner/self protection and server permission checks
remain. Tests use isolated synthetic accounts and local development services
remain available.
