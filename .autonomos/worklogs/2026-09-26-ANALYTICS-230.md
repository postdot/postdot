# ANALYTICS-230 — Record the operational analytics access boundary

- Status: complete; owner approved retaining the current project-actor boundary
- Date: 2026-09-26
- Issue: ISSUE-135
- Scope: verify and record current authorization; no application behavior changed

## Decision

The owner approved keeping the existing authenticated, read-only, project-scoped
analytics API available to actors who can access that project. Do not introduce
an editor-only restriction. An API-key request remains bounded by the key's
configured project scope. Keep the current aggregate response; it does not
expose raw journal payloads or persist query snapshots.

The web analytics surface remains deferred, not permanently rejected. Keep the
accepted project-lifetime journal policy in ADR-037; this review does not add
sampling, a TTL, deletion, or archival behavior. Revisit these boundaries only
for a concrete workflow or measured data-lifecycle constraint.

## Evidence

- `apps/api/src/modules/projects/analytics-routes.ts` requires authentication
  and passes the authenticated subject to the store.
- `apps/api/src/plugins/auth.ts` checks an API key's permitted project IDs
  before dispatch and resolves the key to its owner identity.
- `packages/db/src/analytics-store.ts` requires a project actor and accepts the
  existing `human`, `agent`, and `api_token` actor kinds; it has no
  editor-only role filter.
- `ANALYTICS-227` established that the response contains aggregates computed
  from current state and journal facts and is not a persisted analytics stream.
- `ANALYTICS-223` records the owner's prior decision to defer a web page without
  permanently rejecting one.
- ADR-037 already defines project-lifetime journal retention with project
  deletion as the lifecycle boundary.
