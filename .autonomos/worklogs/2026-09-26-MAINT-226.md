# MAINT-226 — Characterize the Better Auth–Elysia type boundary

- Status: complete
- Date: 2026-09-26
- Issue: [ISSUE-134](../ISSUES.md#issue-134-contain-the-better-auth-and-elysia-type-integration-seam)
- Scope: Exercise the mounted authentication contract and document upgrade constraints without changing frameworks or broadening the adapter.

## Findings

The integration has two intentionally narrow conversions. `packages/auth/src/index.ts` assembles Better Auth's plugin-derived runtime instance behind Postbot's explicit server API types. `apps/api/src/plugins/auth.ts` mounts only `auth.handler` through Elysia; `apps/api/src/app.ts` composes that plugin after the domain routes so the inferred Eden client remains focused on Postbot's typed domain surface. The authenticated route macro separately models the session/API-key runtime union because Elysia's current beta inference cannot express it without collapsing route schemas.

No concrete incompatibility was reproduced. Replacing Elysia or Better Auth, spreading casts across the API, or removing the explicit server API contract would increase scope without evidence of a benefit.

## Changes

- Added an API integration test that creates an account through the Elysia-mounted Better Auth handler, then sends its session cookie through the same mount and verifies the resolved user. This covers request-body forwarding, response-cookie propagation, and cookie-based session lookup at the framework boundary.
- Documented package-specific upgrade checks in `packages/auth/AGENT.md` and `apps/api/AGENT.md`, including upgrading Better Auth with its API-key plugin, keeping the compatibility conversion local, rerunning auth and API tests/typechecks, preserving session/API-key route inference, and keeping dynamic auth endpoints outside the Eden domain contract.
- Closed ISSUE-134 and MAINT-226. No runtime behavior, schema, public route, dependency, or framework changed.
