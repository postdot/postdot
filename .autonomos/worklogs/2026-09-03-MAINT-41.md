# MAINT-41 — Extract project and channel persistence from the manual store

- Date: 2026-09-03
- Status: completed
- Scope: `packages/db` persistence composition and project/channel lifecycle
- Task: MAINT-41
- Related issues: ISSUE-016, ISSUE-020

## Objective

Reduce the responsibility concentration in `packages/db/src/manual-store.ts` by
extracting the project and channel lifecycle into a cohesive module without
changing the public store facade, domain ownership rules, or SQLite transaction
semantics. Keep channel-profile lifecycle extraction as a separately reviewable
follow-up because its activation impact assessment crosses drafts, publications,
media, and jobs.

## Baseline

- `packages/db/src/manual-store.ts` is 3,873 lines in the current checkout and
  contains project, channel/profile, post/draft, publication, media resolution,
  reconciliation, and audit concerns.
- The public API is consumed through `ReturnType<typeof createManualStore>` by
  the API modules and directly by SQLite integration tests.
- Existing accepted guidance forbids a generic repository layer and requires
  project-scoped relations and SQLite-specific persistence to remain explicit.

## Boundary and invariants

- Keep `createManualStore(database, options)` as the composition entry point so
  API wiring and existing consumers do not change in this task.
- Extract project and channel creation/listing as one use-case boundary.
- Keep channel-profile operations in the composition module for now because
  profile activation owns the impact assessment of drafts and pending target
  revisions; moving it in this slice would mix two different refactor seams.
- Keep transaction ownership inside the extracted boundary; do not split one
  atomic operation across independently committed stores.
- Preserve project/actor authorization checks, composite project relations,
  profile version immutability, audit events, and automatic-job side effects.
- Do not add a generic repository interface, a second database backend, or a
  line-count rule.

## Alternatives considered

- Rename only the existing file: improves naming but leaves navigation,
  cohesion, and test seams unchanged.
- Split mechanically by line ranges: reduces file size but creates hidden
  coupling and makes transaction ownership harder to review.
- Introduce a universal repository abstraction: would add ceremony and hide
  SQLite behavior without a second implementation or a concrete test seam.
- Extract a use-case boundary behind the existing facade: keeps compatibility,
  makes ownership visible, and allows later slices to follow evidence from the
  first extraction.

## Implementation

- Added `packages/db/src/manual-store/project-channel-store.ts` as the owner of
  project and channel creation/listing queries, transactions, validation, and
  audit writes.
- Added `packages/db/src/manual-store/project-channel-mappers.ts` for the
  project/channel row-to-domain mapping used by the extracted store and the
  remaining composition code.
- Moved the shared SQLite row shapes into
  `packages/db/src/manual-store/rows.ts` so the extracted store and the
  publication/profile composition can use explicit result types.
- Kept `createManualStore(database, options)` as the public composition surface
  and spread the extracted store into its returned facade.
- Preserved the original project listing order, duplicate suppression,
  authorization checks, profile validation error, audit actions, identifier
  generation order, and transaction ownership.

## Responsibility map after this slice

- `project-channel-store.ts`: project and channel lifecycle persistence.
- `manual-store.ts`: channel-profile evolution, posts, drafts, publications,
  worker-facing workflow, media resolution, reconciliation, and audit reads.
- `rows.ts`: explicit SQLite result shapes shared by those persistence seams.
- `project-channel-mappers.ts`: project and channel domain reconstruction.

## Acceptance criteria

- Project and channel persistence live in a focused, discoverable module with
  explicit dependencies.
- `createManualStore` remains the stable public composition surface.
- Existing project, channel, profile, publication, and worker integration tests
  remain green; focused tests cover the extracted boundary where existing tests
  do not provide sufficient evidence.
- No domain, API, schema, migration, or external workflow behavior changes.
- The resulting responsibility map is recorded for the next extraction instead
  of applying a blanket refactor to unrelated modules.
