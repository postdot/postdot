# OPS-271 — Serialized development API restarts

## Problem and implementation

Bun watch replacement can interrupt asynchronous shutdown before the runtime
quiescence lock is released. Replace the API development command with a small
Bun launcher that watches source/configuration changes, requests graceful stop
and awaits child exit before spawning a replacement. Rapid changes are debounced;
changes during drain are serialized. Operator interruption cancels replacements.
Standard output and error remain in the terminal. A failed startup waits for a
watched edit rather than spinning in a retry loop.

Production startup, lock ownership, worker/media drain and database teardown are
unchanged. The launcher does not delete locks, kill by timeout, create another
service or change runtime configuration. A crashed process still requires the
existing fail-closed operator procedure.

## Files

`scripts/dev-api.ts`, its tests, `apps/api/package.json`, README.md and TASKS.md.

## Evidence

Three deterministic tests cover drain ordering, changes during shutdown and
operator cancellation. A real subprocess test uses the actual runtime lock with
an intentionally delayed shutdown over four generations; each owns the lock
exclusively and all exit successfully. A separate real API exercise uses isolated
temporary database/media and ports: three source-change restarts become healthy
with distinct owner PIDs; final shutdown releases the lock. No owner data is used.
Shared API was gracefully stopped and started through the new launcher; API and
web health checks both return 200.

Full `bun run check` passed: 63 main browser journeys, two password-reset
journeys and 17 build tasks. Log: `/tmp/herald-restart-check.log`.
