# ANALYTICS-113 — Design a replayable SQLite analytics projection beyond the interactive envelope

## Objective

Define a repository-grounded, replayable operational analytics projection for
projects that exceed the provisional query-time envelope, while preserving
SQLite as the source of truth. The task must establish inputs, derived tables,
indexes, replay/idempotency, rebuild/cutover, checkpoints, retention, bounded
reads, observability, and the decision boundary for DuckDB.

## Evidence consulted

- Root `AGENT.md`, `DESIGN.md`, `.autonomos/PROTOCOL.md`, and
  `.autonomos/TASKS.md`.
- ADR-042 (durable fact journal), ADR-051 (operational/provider boundary),
  ADR-053 (SQLite-first optional engine), ADR-054 (query-time envelope), and
  ADR-055 (bounded Bluesky provider collection).
- ANALYTICS-107 through ANALYTICS-112 and ANALYTICS-114 worklogs.
- `packages/db/src/event-journal-store.ts`, `analytics-store.ts`,
  `execution-audit.ts`, `workflow-store.ts`, manual publication stores,
  notification projection stores, domain schema/migrations, and backup/restore.
- `scripts/benchmark-analytics.ts` and `packages/db/src/analytics-store.test.ts`.

## Findings

- `audit_events.sequence` is the correct project-scoped replay cursor and
  `audit_events.id` is the idempotency identity. Notification projections
  already demonstrate the required transactional cursor pattern.
- Current `publications` and `jobs` rows are authoritative for live snapshots,
  not historical facts. Historical provider/channel/delivery dimensions must
  come from event metadata or be reported as unknown/coverage gaps.
- The current reader's historical path parses JSON and reconstructs attempts in
  memory. The measured stress case is the reason to define a projection, but it
  does not by itself justify shipping another durable lifecycle.
- Provider-owned observations and Bluesky collection have separate ownership,
  freshness, availability, and retention semantics and must not enter the
  operational projection.
- SQLite database backups already include any future projection tables in one
  atomic file. A projection restore can therefore resume from its checkpoint or
  be rebuilt from the restored journal.

## Decision and result

Added the proposed ADR:

- `.autonomos/decisions/ADR-056-replayable-sqlite-analytics-projection.md`

The ADR defines a versioned, SQLite-backed target consisting of:

- per-project/version cursor and health state;
- normalized source-addressable facts with source-event idempotency;
- one derived attempt row per `(job_id, attempt)`;
- daily dimension rollups plus normalized edge facts for exact half-open ranges;
- side-by-side backfill, catch-up, reference comparison, cutover, rollback, and
  stale fallback;
- lifetime retention aligned with the durable journal until a separate policy
  proves a safe rebuild horizon;
- cursor/lag/quality/lock/backup observability and a SQLite-first DuckDB gate.

No migration, projector, API cutover, or new database engine was added. That is
intentional: the existing task evidence defines a design requirement but does
not supply a representative refresh/retention workload, and legacy facts do
not uniformly contain immutable historical dimensions. Implementing tables and
cutover before accepting those boundaries would make replay semantics appear
complete while depending on mutable current joins.

## Validation

- Read-only repository inspection completed for the event journal, analytics
  reader, execution metadata, projection cursor patterns, migrations, and
  backup/restore.
- `git diff --check` — passed after the documentation-only change.
- No provider calls, credentials, database restore, shared service, or external
  side effect was used.

## Follow-up

The lead agent should reconcile this proposed ADR with project governance and,
if the implementation gate is accepted, open the migration/projector work as a
separate bounded change. That implementation should first add failure-focused
tests and comparison tooling before changing the analytics serving path.
