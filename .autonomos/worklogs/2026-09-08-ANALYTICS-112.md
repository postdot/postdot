# ANALYTICS-112 — Implement the first Bluesky provider-owned observations slice

## Objective and scope

Implement a limited, reversible Bluesky provider-owned analytics vertical
slice. The scope is account counters (followersCount, followsCount, postsCount)
and counters for Bluesky posts already known by Herald (likeCount, replyCount,
repostCount, quoteCount, bookmarkCount). Operational analytics, publication
behavior, UI, general account discovery, real-time ingestion, recurring
synchronization, comments/messages, and cross-provider scoring remain out of
scope.

## What changed

- Added the framework-independent provider observation contract in
  packages/core/src/provider-analytics.ts.
- Added migration 0020_harsh_hairball and the project-scoped
  provider_analytics_observations table. The table stores typed observation
  metadata, explicit availability/freshness, optional reporting windows, and
  provenance without raw provider payloads or credentials.
- Added createProviderAnalyticsStore, which authenticates project access,
  persists immutable observations, reports inserted versus duplicate rows,
  reads bounded pages, and selects only known provider publication IDs.
- Added the Bluesky public AppView reader and collector in
  packages/bluesky/src/analytics.ts. The fetcher is injectable, sends no
  Authorization header, respects DID/handle, AT URI, and CID identity, batches
  at most 25 known post URIs, and maps malformed, blocked, not-found,
  unavailable, rate-limited, and network responses to explicit states.
- Added authenticated API routes for persisted Bluesky observations and an
  explicit bounded collection action. The existing provider-neutral
  /api/projects/:projectId/analytics response is unchanged.
- Added typed API/client response exports and tests for mapping, persistence,
  migration, project isolation, known-publication selection, repeated
  collection, credential non-disclosure, and the no-provider-call read
  boundary.

## Concrete decisions

- Use public app.bsky.actor.getProfile and app.bsky.feed.getPosts reads; no
  analytics credential or token resolution is introduced.
- Represent counters as cumulative snapshots with count units. Missing fields
  are not_reported, not zero. A real provider zero is retained as measured with
  value 0.
- Preserve history by deduplicating only the same project/provider/subject/
  metric at the same fetchedAt; later fetches create new rows.
- Limit collection to publications with a retained publications.external_id
  on a Bluesky publisher channel. Repeated provider URIs in one collection
  keep the first Herald publication association.
- Keep GET provider-free and make collection explicit through a bounded POST.
  No recurring scheduler was added.
- Keep ADR-052 proposed; this implementation does not silently promote
  governance state and does not modify ANALYTICS-111.

## Known limits

Bluesky public AppView counters are current provider snapshots rather than a
provider-guaranteed historical series. These endpoints do not expose a
provider observation timestamp for the counters, so observedAt is null and
freshness is unknown. bookmarkCount is retained as a known metric but is
not_reported when the public response omits it. Account and post availability
can change with AppView indexing, deletion, blocking, deactivation, rate
limits, and network state.
