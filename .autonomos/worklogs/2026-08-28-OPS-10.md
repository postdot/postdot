# OPS-10 — Package and validate the single-process V1 deployment

- Date: 2026-08-28
- Status: completed
- Scope: production serving, container packaging, SQLite recovery, and footprint
  evidence
- Related issue: [ISSUE-001](../ISSUES.md#issue-001-validate-the-complete-production-distribution-path)
- Related decision: [ADR-010](../decisions/ADR-010-use-bun-runtime-image-for-v1-packaging.md)

## Outcome

Herald now has a reproducible single-process production container. One Bun process
serves the Elysia API, OpenAPI routes, the built React dashboard, and the SQLite
database. The image contains no workspace dependency tree or environment secret and
runs as the non-root `bun` user.

## What was done

- Added the Elysia 2-compatible `@elysia/static@2.0.0-beta.2` integration for
  production-only dashboard serving. Browser routes use an SPA fallback while API,
  OpenAPI, health, and unknown asset paths remain explicit 404s.
- Made the migration and dashboard asset directories configurable through the
  existing TypeBox-backed environment configuration.
- Added a multi-stage `Dockerfile` that builds the workspace, copies the API bundle,
  dashboard assets, and committed migrations, then runs them from
  `oven/bun:1.4.0-slim`.
- Added a Docker healthcheck, a non-root runtime user, and `/data` as the SQLite
  volume.
- Added `backup` and `restore` maintenance commands to the production bundle.
  Backups use SQLite `VACUUM INTO` after integrity validation. Restores validate the
  Herald migration table, copy to a temporary file, validate again, and rename the
  replacement into place. Restoration requires the application to be stopped.
- Documented local container startup, health inspection, backup, and restore in the
  root and database package READMEs.

## Packaging finding

`bun build --compile` produced a smaller deployment shape, but the real compiled
binary failed while compiling `GET /health` because the current
`@elysiajs/openapi` integration dynamically resolves `typebox/type` from the Bun
compiled filesystem. Referencing the module from the application entrypoint did not
change that result. The regular Bun-targeted JavaScript bundle passes the same route
checks, so the current image uses the Bun runtime until a compatible OpenAPI release
or compiler behavior is available. This is recorded as a proposed decision in
[ADR-010](../decisions/ADR-010-use-bun-runtime-image-for-v1-packaging.md).

## Verification

- `bun run check`: passed formatting, warning-free lint, strict typechecking, all
  production builds, and 66 tests.
- `bun run measure:footprint`: passed on Linux amd64 with Bun 1.4.0. The API bundle
  is 1,447,935 bytes, initial web JavaScript is 106,159 gzip bytes, median cold start
  is 207.34 ms, median idle RSS is 79,744 KiB with an 80,812 KiB maximum, and the
  publication-job peak is 41,140 KiB median with a 1,364 KiB median increase.
- `docker build --tag herald:ops10 .`: passed. The image is 165,012,493 bytes
  uncompressed and 68,500,837 bytes as a `docker save | gzip` archive, below the
  100 MiB compressed-image target.
- A fresh Docker volume started successfully, applied all four committed migrations,
  passed the Docker healthcheck, and served `/health`, `/openapi/json`, `/`,
  `/dashboard`, and a built JavaScript asset.
- A real image backup was created while the application was running. After stopping
  the application, a sentinel table was restored away from the volume, and the
  restored image became healthy again.
- `git check-ignore -v apps/api/.env` confirms the local environment file remains
  ignored.
