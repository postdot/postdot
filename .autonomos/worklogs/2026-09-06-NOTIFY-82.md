## Objective

Create the durable secret boundary required before Herald can configure a real
external notification transport. Public destination configuration must remain safe
to inspect and delivery snapshots must remain useful without containing credentials.

## Accepted scope

- Extract a domain-neutral AES-256-GCM envelope primitive from the existing publisher
  credential cipher without changing publisher behavior.
- Store versioned notification destination secret envelopes separately from public
  destination configuration.
- Capture the active secret version when projecting a delivery and resolve it only
  through the claimed delivery boundary.
- Add deterministic coverage for rotation, isolation, tampering, and plaintext
  absence.
- Keep real provider requests, transport management routes, and web UI out of scope.

## Constraints

- Use the deployment-owned encryption key injected through an explicit cipher option;
  never persist the key in SQLite or backups.
- Do not attach notification secrets to Better Auth users or publisher credentials.
- Do not overwrite a secret version that an existing delivery may still reference.
- Do not make public destination metadata or immutable delivery history carry
  plaintext credentials.
- Use a migration-driven schema change and keep the complete repository gate as the
  integration boundary.

## Stop conditions

Stop before adding a real transport if the implementation requires choosing a
provider-specific credential format, exposing a management API, or deciding a secret
retention policy beyond retaining referenced versions. Those choices belong to the
transport task and require their own evidence.

## Plan

1. Add the generic encrypted-secret primitive and preserve the publisher cipher API.
2. Add versioned destination-secret and delivery-reference persistence.
3. Add storage and claimed-delivery resolution primitives with project/actor checks.
4. Add focused tests and regenerate/review the migration.
5. Run the complete repository gate, perform an independent read-only review, and
   crystallize the result before proposing integration.

## Implementation

- Extracted a domain-neutral AES-256-GCM envelope primitive while preserving the
  existing publisher credential cipher API and authenticated context.
- Added versioned `notification_destination_secrets` persistence with one active
  version per project destination, atomic rotation, deployment-owned key injection,
  and no plaintext secret fields in public destination or delivery records.
- Added delivery secret references captured at projection time and a claimed-delivery
  resolver that decrypts only the pinned version after project, destination, transport,
  state, lease, and claim-token checks.
- Added the composite database constraint that binds a delivery secret to the same
  project and destination as its delivery; the resolver repeats the destination check
  as a fail-closed defense in depth.
- Kept real provider requests, transport management routes, UI, and secret retention
  policy out of scope.

## Review

An independent read-only sub-agent review was attempted but could not complete because
the host reached its usage limit. A local security review found and corrected one
material issue: the first schema revision constrained `delivery.project_id` and
`delivery.secret_id` but did not constrain `delivery.destination_id` to the referenced
secret's destination. A composite foreign key, supporting unique index, resolver join
condition, and regression test now enforce that boundary.
