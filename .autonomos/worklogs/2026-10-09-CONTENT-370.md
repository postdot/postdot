## Established current behaviour

`publication-authoring-store.ts` updates the shared post source and increments its
source revision when source content changes. Each working draft retains its own
source revision and base source content. A save rejects a stale source revision;
rebase is explicit. Target/execution snapshots are separate from the mutable post.
`publication-creation-store.ts` creates destinations with the source revision and
adaptation against their channel profile. It does not enforce unique channels per
post. The schema likewise has no post/channel uniqueness constraint.
`publication-draft-lifecycle-store.ts` duplication creates a new post, so it is
not the proposed add-destination operation.

## Proposed implementation boundary

Read the existing post with its current source revision and destination summary.
Offer add destinations from a publication detail context, where post identity is
already available. Do not create a new independent content library merely to
expose this action.

The add request names the post, expected source revision, and destination channels
with explicit delivery modes. Within one transaction, check current revision,
project access, active channels, and current profile definitions; create working
drafts based on that exact current source. Invalid target content remains visible
as review-required under existing draft rules. Invalid structural input or missing
channels causes no partial additions. Do not schedule, approve, dispatch, mutate
the source, replace existing adaptations, or alter existing execution snapshots.
A stale expected source revision is a conflict, requiring a fresh read rather than
silently changing the source used for the addition.

Historical source selection is deferred: existing snapshot ownership should not
be repurposed into a new generic source history service. The first operation uses
only current source content and clearly identifies its revision.

## Accepted repeated-channel policy

Owner chose repeated channels with warning and explicit confirmation. Implemented
as a two-step UI action and `confirmExistingChannels` on the add request. The
transaction checks the current existing channels and duplicates within the batch,
so concurrency cannot bypass confirmation. No general uniqueness rule added.
