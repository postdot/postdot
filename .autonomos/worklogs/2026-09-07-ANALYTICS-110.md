# ANALYTICS-110 — Benchmark operational analytics cost and historical coverage

## Objective

Measure the current operational analytics read model on representative SQLite
histories, make historical coverage gaps observable, and decide whether a
materialized projection is justified. The benchmark must remain isolated from
provider-owned engagement analytics (ANALYTICS-109), must not use real
credentials, and must not change the public analytics contract.

Branch: `chore/analytics-110-benchmark`

## Fixture and method

`bun run benchmark:analytics` creates a temporary migrated SQLite database for
each scale, seeds one project and one automatic channel, and runs the actual
`createAnalyticsStore().getProjectAnalytics()` reader in a fresh worker process.
The fixture contains four supported facts per publication (`created`, `claimed`,
`effect_started`, and `succeeded`) plus deterministic coverage probes:

- 20% of publications use legacy-style facts without provider and logical
  `runAt` metadata;
- one unknown event version and one unsupported action are added every 250
  publications;
- the reader is warmed twice and then measured nine times; latency reports
  median and p95;
- first-query RSS/heap deltas are measured before any read-model result exists,
  while the database file size and coverage counters are recorded separately.

The measurements are local observations, not universal capacity guarantees:
Linux x64, Bun 1.4.0, SQLite, one process, no concurrent requests, no provider
network calls, and a synthetic one-channel workload.

## Corrective changes made before the final measurement

The benchmark exposed avoidable allocations in the original query path. The
read model now:

- iterates current publication and job rows instead of materializing filtered
  arrays and repeatedly scanning them;
- stores only `entityId` and `occurredAt` for a retained execution outcome,
  instead of retaining the complete SQLite row and its metadata string;
- does not keep a per-read fact-id `Set`: `audit_events.id` is unique and the
  publication/channel joins are one-to-one by schema, so the set could only add
  unbounded memory to this query. The existing `duplicateFacts` response field
  remains part of the contract and is reserved for a future query shape that
  can actually produce duplicates.

No migration, projection, provider adapter, UI, or external dependency was
added.

## Final measurements

| Publications | Facts | DB size | First query | Warm median | Warm p95 | First-query RSS delta |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 4,008 | 4.85 MiB | 245 ms | 234 ms | 244 ms | +43 MiB |
| 5,000 | 20,040 | 21.4 MiB | 1.36 s | 1.34 s | 1.60 s | +75 MiB |
| 20,000 | 80,160 | 84.0 MiB | 5.49 s | 5.02 s | 5.10 s | +177 MiB |

The measured results remained semantically complete at every scale:

- current publication count, historical created/published count, and
  successful execution count all matched the fixture publication count;
- legacy coverage was explicit rather than fabricated: at the 20,000 scale,
  16,000 missing historical dimensions, 8,000 incomplete latency pairs, and
  4,000 incomplete queue-delay pairs were reported;
- 80 unknown-version facts and 80 unsupported facts were skipped and surfaced,
  for 160 skipped facts total.

The first exploratory run before these allocation changes reached approximately
+477 MiB RSS at the 20,000-publication scale. Streaming the current rows and
retaining compact outcome references reduced that observed delta to
approximately +177 MiB. The remaining cost is still material at the upper
fixture size and must not be hidden behind a claim that the read is fully
bounded.

## Decision

The existing query-time contract remains the correct V1 boundary for now:
coverage is truthful, the journal is durable, and small-to-medium project
histories are readable without adding a projection lifecycle. A projection is
not added speculatively in this task.

The benchmark also establishes a concrete scale boundary: a 20,000-publication
project with 80,000 historical facts is not an acceptable interactive analytics
request at roughly five seconds and +177 MiB RSS. Before Herald promises long
history analytics for projects at that scale, the current aggregate path must
be hardened and the projection decision revisited against product retention and
refresh requirements. This is recorded as ANALYTICS-111 / ISSUE-057 rather than
being silently deferred.
