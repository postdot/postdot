# MEDIA-391 — Minimal video poster feasibility

## Authorization and scope

Owner authorized an isolated experiment, not production integration. No dependency,
Dockerfile, application code, private media or existing media database was changed.
The thumbnail remains optional; accepting this experiment does not authorize a new
production dependency or change the existing no-FFmpeg production boundary.

## Reproduction

Built official FFmpeg 8.0.1 release sources in a unique temporary directory on
Linux x86_64 with GCC and four build jobs. This pinned release is a feasibility
baseline, not a recommendation of the latest supported security release.
Source: https://ffmpeg.org/releases/ffmpeg-8.0.1.tar.xz
SHA-256: `05ee0b03119b45c0bdb4df654b96802e909e0a752f72e4fe3794f487229e5a41`.

```sh
./configure --disable-everything --disable-autodetect --disable-doc   --disable-debug --disable-network --disable-asm --disable-ffplay   --disable-ffprobe --enable-ffmpeg --enable-avcodec --enable-avformat   --enable-avfilter --enable-swscale --enable-protocol=file,pipe   --enable-demuxer=mov --enable-decoder=h264 --enable-parser=h264   --enable-encoder=mjpeg --enable-muxer=image2pipe   --enable-filter=scale,format,buffer,buffersink --enable-small
make -j4
./ffmpeg -v error -nostdin -filter_threads 1 -threads 1 -ss 1   -i input.mp4 -map 0:v:0 -an -frames:v 1   -vf "scale=w='min(768,iw)':h='min(768,ih)':force_original_aspect_ratio=decrease"   -threads 1 -f image2pipe pipe:1 > poster.jpg
```

No audio decoder, video encoder or network protocol is enabled. JPEG output can be
fed into the existing Bun image processor for WebP variants and placeholders.
Configuration reports LGPL 2.1 or later; production distribution obligations must
be handled when packaging, not inferred away because the binary is small.

## Measurements

Final stripped binary: 2,498,152 bytes (2.38 MiB); gzip: 1,045,022 bytes (1.00 MiB).
FFmpeg libraries are linked into it; dynamic dependencies are libc, libm and the
system loader only. These measurements do not include a Docker layer, source
archive, compiler, Bun runtime or temporary input files. No fully static executable
or cross-platform portability claim is made.

Three serial extractions per case, seeking to one second, single decoder/encoder
and filter thread. Wall time measured around child launch and wait; peak RSS from
Linux wait4 per child. Local files and warm filesystem caches; no S3 transfer.

| Case | Time range | Peak RSS range | JPEG bytes |
| --- | --- | --- | --- |
| Herald 320x180 High-profile fixture | 15.2–15.3 ms | 8.9–9.0 MiB | 8,146 |
| Synthetic 1920x1080 MP4, index first | 130–137 ms | 31.4–31.7 MiB | 22,610 |
| Synthetic 3840x2160 MP4, index last | 512–527 ms | 73.4–73.8 MiB | 19,898 |

Synthetic files were created using the host FFmpeg solely as fixture tooling, with
three seconds of testsrc2, 30 fps, libx264 ultrafast, yuv420p. Source sizes were
5,802,006 and 23,651,894 bytes. These cases do not establish worst-case resource
bounds for every accepted H.264 stream.

Bun.spawn successfully received JPEG via stdout; Bun.Image decoded it as 768x432.
Repeated final 1080p outputs had identical SHA-256. Output inspected visually
against the host FFmpeg reference. No Herald test matrix was needed for this
external feasibility experiment.

## Discovered limitation

The first build used --disable-x86asm only. It exited successfully but produced
corrupted, inconsistent images on the synthetic inputs. Setting -cpuflags 0 yielded
correct images. The final build instead disables all assembly with --disable-asm;
its outputs are visually correct and repeatable. The specific optimization causing
the first failure was not diagnosed. Do not ship that earlier configuration or cite
its measurements as successful extraction. Future optimized builds require their
own pixel correctness checks.

## Conclusion and next step

A minimal FFmpeg build is materially smaller than the measured general host
installation (203.5 MiB including linked libraries). Server extraction is feasible
without that general package. This does not eliminate subprocess restrictions in
edge runtimes, security updates, binary distribution or architecture-specific builds.

Recommend a bounded packaging probe in the actual Bun slim container before any
product integration: verify executable compatibility, incremental image size and
same valid extraction. ARM, rotation metadata, malformed files, remote storage
transfer, time/memory enforcement and process cancellation remain untested. If
adopted, poster failure must not block a verified original; persist derived ownership
and preserve cleanup/backup semantics. Keep the processor optional and original
publication bytes untouched.

Only this worklog and TASKS were modified. No architecture decision was accepted.
