# META-60 — Pilot serialized orchestration with parallel Codex worktrees and review agents

- Date: 2026-09-04
- Status: completed with follow-up
- Issue: ISSUE-024
- Scope: one controlled pilot with two isolated review worktrees and one independent high-reasoning judge
- Branch: `ops/meta-60-agent-collaboration-pilot`

## Objective

Test whether Codex worktrees and visible agent tasks can support safe parallel
analysis under one orchestrator without competing for shared development
services, local runtime state, credentials, external providers, or integration
authority.

## Pilot rules

- The orchestrator owns the canonical checkout, shared servers, browser checks,
  external effects, integration, pull requests, merges, and branch cleanup.
- The two worker missions are read-only, isolated, non-overlapping, and limited
  to repository evidence. They must not start servers, access secrets, use
  provider credentials, edit files, commit, push, or merge.
- The independent judge receives only the pilot context and worker reports. It
  must not edit, execute external effects, or assume that the pilot is correct.
- Findings are evidence for the orchestrator; they do not silently become
  product or architecture decisions.

## Missions

1. Review the provider boundary after the current LinkedIn and custom HTTP
   work, looking for concrete readiness risks before another built-in channel.
2. Review parallel-work and local-runtime safety, including ports, SQLite and
   media paths, container assumptions, test commands, and environment files.
3. Ask a separate high-reasoning Sol reviewer to judge the operating model and
   both reports with a neutral prompt.

## Acceptance criteria

- Each worker runs in its own visible isolated worktree/task.
- No worker changes `main`, starts a shared service, reads secrets, or triggers
  a provider or other external side effect.
- The missions produce distinct, evidence-backed reports.
- The independent judge uses the explicitly selected high-reasoning Sol profile
  and remains read-only.
- The orchestrator records the outcome, unresolved risks, and the next safe
  action before closing the pilot.

## Worker reports

### Provider boundary review

- Medium: built-in provider dispatch is centralized in the workflow worker;
  assess a small provider contract before adding another built-in channel.
- Medium: the custom HTTP media path does not compare the pinned checksum;
  track this as a product correctness issue.
- Low/clarification: distinguish profile recompilation from full execution-time
  content validation before treating that concern as a defect.

### Local runtime isolation review

- High: the E2E temporary data root is shared and deleted by startup/teardown;
  overlapping runs can destroy one another's state.
- High: restore does not enforce that the live runtime is quiescent before
  replacing database and media state.
- Medium: ordinary development defaults to shared ports and repository-local
  database/media paths, so worker-launched services must remain prohibited until
  an isolated runtime profile exists.

## Independent judge

The high-reasoning Sol review judged the model **accept with changes**. It
confirmed the orchestrator ownership boundary, dedicated worktree isolation,
read-only independent review, and serialized shared-resource validation. It
identified two pilot gaps: the worktree-task path did not provide durable task
identity, and the pilot did not exercise implementation, stale-base handling,
integration, full validation, merge, and cleanup. It also required explicit
mission contracts, semantic ownership rules, a safe-check matrix, and a serial
integration lifecycle before permanent adoption.

## Outcome

- `META-60` is complete as a guarded methodology pilot, not as permanent policy.
- The root agent guidance now records the refined pilot rules and explicitly
  reserves shared governance files, central hotspots, shared runtime checks,
  and integration authority for the orchestrator.
- The two worktree reviews remained read-only and produced distinct reports;
  no secrets, provider credentials, servers, browsers, or external effects were
  used.
- `ISSUE-025` through `ISSUE-028` track the concrete Postbot findings separately
  from the orchestration decision.
- `META-61` is the next task: exercise one complete implementation-to-cleanup
  lifecycle, including a stale-base or overlap case, then decide whether the
  protocol can become permanent.

## Handoff

The pilot is ready for orchestrator review. Both temporary worktrees were
verified clean and removed, and neither review branch was published. No
