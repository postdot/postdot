# AUDIT-307 — Unexpected error-text propagation diagnosis

Scope: diagnosis only (ISSUE-152). No implementation changes, no new filtering
policy, no ambiguity/retry rule changes. No real credentials or provider calls;
all probes used fictitious secrets and were removed afterwards.

## Entry point (confirmed)

`packages/core/src/executor.ts:212-216` (`describeUnknownExternalOutcome`):
an unexpected throw after the effect boundary becomes an `ambiguous` outcome
whose message is the raw `Error.message` prefixed with a fixed sentence.
There is no sanitization at this boundary by design (core owns no secrets).

## Empirical probe (temporary, deleted)

A temporary `packages/db` test drove `processNextWorkflowEvent` with a throw
carrying a fictitious bearer token and `client_secret` value through the real
workflow store (in-memory SQLite, since removed):

- `jobs.error_message` carries both fictitious values verbatim: true
- `publications.error_message` carries both verbatim: true
- `audit_events.metadataJson` carries both verbatim: true

The persistence boundary is therefore transparent: whatever unexpected text
reaches the executor is stored durably in three places.

## Downstream exposure (code-verified)

| Boundary | Finding |
| --- | --- |
| Publication REST responses | `publicationSchema = Type.Unsafe<Publication>` serves the stored `errorMessage` to project actors and scoped API keys (Queue, detail) |
| Audit history REST responses | `auditEventSchema` serves raw `metadataJson`, including the stored message |
| Dashboard | `publication-lifecycle-panel`, `publication-outcome-panel`, `publication-editor`, and `publication-activity-timeline` (audit `metadata.errorMessage`) render the stored text verbatim to project viewers |
| In-app notification inbox | PROTECTED — `packages/core/src/notification.ts` uses fixed title/body templates; raw outcome text never enters notifications |
| External delivery outbox | Same fixed templates via the recording transport; real Ntfy/Telegram adapters remain deferred |
| CLI | Only operator-supplied `--error-message` input and client-side request-failure formatting; no server-secret surface |
| Analytics report | Aggregate counts only (ANALYTICS-230 boundary); no message text |
| Realtime SSE | Cursor/signal payloads only; clients re-read via the API above |

All exposed surfaces share one trust boundary: authenticated project actors.
There is no anonymous or cross-project reader for these fields.

## Upstream inventory (all protected)

| Source | Handling |
| --- | --- |
| Custom HTTP transport | Every failure path redacts the connection secret (raw and URL-encoded) and bounds length; echoed secrets in remote `externalId`/`externalUrl` yield a generic message, never the echo |
| LinkedIn provider text | `redactSecrets(body, [accessToken, ...])` before use |
| Bluesky / X / Discord / DEV.to / Mastodon publishers | Fixed messages or remote-controlled response text (500-char bound); network exceptions mapped to fixed strings; SDK error objects classified by status only, message discarded |
| OAuth session restore and token refresh (Bluesky, X, LinkedIn, per-instance Mastodon) | Bare `catch` with fixed messages, including rogue-instance-safe refresh failures |
| Credential resolution and envelope cipher | Fixed codes/messages (`decryption_failed`, etc.); no key material |
| Media storage, public-URL signing, mapped HTTP validation | Fixed validation messages; worker maps storage failures to fixed strings |
| oauth4webapi / atproto internals | Library-controlled messages; refresh paths are shielded by the adapter-level fixed messages above |

## Conclusion: no actionable gap, no correction proposed

Superseded by the reopened finding below: a gap was demonstrated after this
section was written. The original inventory stands, except for the
remote-diagnostic rows, which are corrected there.

## Reopened finding: rogue-echo gap demonstrated (follow-up review)

An independent probe (reproduced here with `createMastodonPublisher`, a mocked
fetcher, and a fictitious token, then kept as a repo test) shows an HTTP 500
whose body echoes the `Authorization` header producing an ambiguous outcome
whose `errorMessage` contains the token verbatim:

- Mastodon `responseMessage` (remote `error` field): demonstrated, kept test
  in `packages/mastodon/src/publisher.test.ts`.
- X `responseMessage` (remote `detail` / `errors[0].message`): demonstrated
  with the same probe shape (throwaway script, since removed).
- Discord `responseMessage` (remote `message` field): demonstrated the same
  way.

Threat model: a rogue or compromised per-instance server (Mastodon instances
are operator-configured URLs; custom receivers are arbitrary) or a
misbehaving proxy echoing request headers into an error body. The echo then
flows through the already-proven transparent chain (jobs, publications, audit
metadata, project-scoped API and dashboard). This supersedes the earlier
"remote-controlled text is not our secret" reasoning for these three
adapters: the text is remote-shaped but can carry our secret back.

Demonstrated vs envisioned:

- Demonstrated: Mastodon/X/Discord remote-text paths echoing the in-scope
  bearer/bot token into ambiguous (and, for non-500 statuses, retryable or
  permanent) outcomes.
- Still protected, re-verified: custom HTTP (redacts the connection secret on
  all failure paths plus echo detection), LinkedIn (redacts access token),
  DEV.to and Bluesky (fixed messages only), OAuth refresh/restore (bare
  `catch` with fixed messages), credential resolution/cipher (fixed codes).
- Envisioned only, no evidence: oauth4webapi/atproto internals echoing
  request secrets (refresh paths are shielded by fixed messages); storage/S3
  errors carrying credentials (identifiers and paths only by construction).

## Bounded proposal (not yet implemented — awaiting owner review)

Redact in-scope secrets at the adapters that own them, following the
established LinkedIn/custom-http precedent; no generic filtering in core:

- In `packages/{mastodon,x,discord}/src/publisher.ts`, redact the request
  access token (raw and URL-encoded) from remote diagnostic text before it
  enters an outcome — at each `responseMessage` call site or inside it with
  the secret passed in, LinkedIn-style.
- Keep outcome codes, types, length bounds, classification, retry, and
  ambiguity semantics exactly as they are; only secret substrings are
  replaced.
- Flip the kept Mastodon echo test to the redacted expectation and add
  equivalent fictitious-token tests for X and Discord.
- Explicitly out of scope: core/executor changes, DEV.to/Bluesky/LinkedIn/
  custom-http (already safe), any generalized secret-filtering policy.

Registered as PROVIDER-308 (todo, not started) and linked from ISSUE-152,
which returns to open pending the implementation decision.

## PROVIDER-308 completion and exact limits

Implemented as proposed, with all remote-diagnostic paths covered:

| Path | Coverage |
| --- | --- |
| Mastodon `responseMessage` (remote `error` field) | Redacted; all request paths flow through the single `request()` threading |
| X `responseMessage` (remote `detail`, `errors[].message`, `title`, `error`) | Redacted via one shared extraction; all four fields covered by tests |
| X `readProcessingError` (media `processing_info.error.message`) | Redacted; reached with the upload access token |
| Discord `responseMessage` (remote `message` field) | Redacted; all request paths flow through the single `request()` threading |

Exact limits:

- Only the request access token in scope is redacted (raw and URL-encoded),
  before the existing 500-char truncation. Secrets from other scopes
  (OAuth client secrets, other users' tokens, tokens arriving only in an
  encoded form that does not match raw or URL-encoding) are not covered.
- Redaction replaces substrings; a redacted message keeps its position and
  the `[redacted]` marker counts toward the length bound, so surrounding
  diagnostics stay readable.
- `registerApplication` (Mastodon, no token in scope) passes an empty secret
  set: behavior identical to before.
- Outcome codes, types, classification, retry, and ambiguity semantics are
  unchanged; only secret substrings are replaced. Verified by 16 new tests
  (raw, encoded, multiple, limit-straddling, ordinary utility per adapter)
  plus the untouched existing suites.
- Untouched by design, each re-verified out of scope: core/executor,
  DEV.to and Bluesky (fixed messages only), LinkedIn and custom HTTP
  (already redact), OAuth refresh/restore, credential resolution, media
  storage, notification templates, analytics aggregates.
- The transparent executor→persistence→API chain itself is unchanged: any
  future secret-bearing text from an uncovered path would still persist
  verbatim. New adapters or new diagnostic fields must redact in-scope
  secrets at their own boundary, following this precedent.

## Adjacent observation (not a secret boundary)

Provider-controlled response text (e.g. Mastodon/Discord/X `message` fields)
is persisted and rendered as operator-facing diagnostics. That is untrusted
input, not credential exposure, and is out of scope for this mission; it is
recorded here only so a future UI-trust review can find it.
