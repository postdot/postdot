# PROVIDER-115 — AT Protocol loopback OAuth and deployment profiles

- Date: 2026-09-08
- Status: completed; awaiting review and integration
- Task: `PROVIDER-115`
- Issues: `ISSUE-061`, `ISSUE-043`
- Decisions: `ADR-036`, `ADR-056`

## Objective

Remove the unnecessary local Bluesky OAuth tunnel requirement without weakening
the public HTTPS deployment contract or confusing AT Protocol OAuth with other
provider application models.

## Delivered

- Added the official `@atproto/oauth-types` loopback metadata builder to the
  Bluesky adapter.
- Made a nullable Bluesky client metadata URL an explicit loopback mode and
  exposed the derived `oauthMode` in the provider-application API.
- Added a SQLite schema migration that accepts both Bluesky configuration
  shapes while preserving existing public-web configurations.
- Added runtime construction of a `http://localhost` client identifier and an
  exact `127.0.0.1`/`[::1]` callback, with a fail-closed same-origin check for
  host-bound Herald sessions.
- Added localized settings controls for loopback versus public HTTPS mode.
- Documented common and provider-specific deployment requirements.

## Verification

- Bluesky OAuth, provider-application store, migration, and runtime tests pass.
- API tests, package typechecks, and English/French localization coverage pass.
- No provider credential, tunnel, real OAuth authorization, or real provider
  action was used.
