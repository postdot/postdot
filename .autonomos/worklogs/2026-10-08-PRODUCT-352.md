## Proposed next sprint: LinkedIn multiple images

Desired outcome: compose and schedule one post containing multiple JPEG/PNG images
for an existing LinkedIn member or organization destination, with order and image
alternatives retained, then inspect the truthful outcome through the usual UI.

The official MultiImage API describes 2–20 images, an ordered images payload and
member/organization publishing permissions. This makes a provider-backed path
credible, not guaranteed for a particular configured application's entitlements.
Source checked 2026-10-08:
[LinkedIn MultiImage API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/multiimage-post-api?view=li-lms-2026-08).
Current Herald API version is 202608. No new public image hosting service is implied:
images are uploaded to LinkedIn through its existing image API.

Start with a short contract review within the implementation mission: confirm
permissions and payload, profile/execution revision compatibility, per-image upload
reuse, and partial failure semantics. Preserve immutable historical targets; never
silently reinterpret old execution revisions. Reuse the media-store and durable
provider delivery seams. Then deliver server and UI support together.

Exclude PDF/document carousels, video, GIF, a new provider, redesigning the editor,
and decorative LinkedIn-preview fidelity. Those are different capabilities.

Evidence should address ordered payloads, text/one-image regression, per-image
alternatives, failed uploads not creating a post, and retry without repeating a
completed upload where the existing contract permits reuse. Use focused adapter/
executor tests and one existing browser journey for composition/validation. Follow
ADR-077 gates on the final change set, with a full gate only where triggered; do
not multiply diagnostic and full-suite runs at each intermediate edit. A real
publication requires explicit authorization and the chosen account; do not make
external side effects an automatic test gate.
