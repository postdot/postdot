## Owner direction recorded

The project owner has clarified the following requirements for the boundary under
review:

- Herald is developed continuously; the first durable implementation must not be
  shaped as a temporary V1 or MVP cut.
- Media must be a durable, extensible part of the publication architecture rather
  than a text-only first implementation with a later retrofit.
- A channel must be able to express the capabilities and constraints that matter
  for its destination without turning Herald into a universal provider schema.
- A shared source should cover the common publication primitives, while each
  channel publication may carry a precise adaptation.
- The web editor should expose destination limits and compatibility reactively.
  API, CLI, and MCP requests remain server-validated and must reject an invalid
  publication before an external effect.
- A publication persists the content snapshot that it represents.
- Local storage and an S3-compatible backend must share an interchangeable Herald
  storage contract from the first media implementation. The single-process
  self-hosted deployment and small footprint remain primary constraints.
- Competitor analysis is deliberate product research. It must inform decisions
  without becoming feature-parity work.
- Herald remains a publication manager whose primary destinations are social and
  adjacent publishing platforms. Custom channels broaden destination coverage but
  do not replace that product purpose.
- Custom channels may define a complete data schema at runtime. Presets are editable
  accelerators, not a closed set of supported channel shapes.
- Built-in providers and custom channels share one generic persisted target-content
  boundary. Built-ins can use code-owned TypeBox schemas; custom channels use
  validated, versioned runtime schemas and bounded declarative request mappings.
- A publication explicitly chooses automatic or manual delivery, independently from
  whether a channel connection is currently available.
- Web auto-save must preserve the latest draft without promoting an intermediate
  working state to the scheduled target. Explicit scheduling or update promotes a
  validated target revision, and the execution revision becomes immutable when an
  external effect starts.

The exact media kinds, content vocabulary, custom-channel transport mapping, and
schema-change handling remain subject to the acceptance of SPEC-004.

## Method

Postiz, OpenPost, and Mixpost were cloned into a disposable directory outside the
Herald repository. The study inspected their schemas, content contracts, provider
validation, media lifecycle, scheduling boundaries, and storage implementations.
Dependencies were not installed and competitor code was not copied into Herald.

The study also checked the current Bun 1.4 runtime behavior and the current official
documentation for Bun storage and FlyDrive. The relevant external references are
listed at the end of this worklog.

## Findings from comparable projects

### Postiz

The inspected Prisma schema models one `Post` with one `Integration`. A `group`
value associates the destination-specific rows that came from one composer action.
The post stores plain content, an image reference payload, and a provider-specific
settings payload. Provider settings are selected through a discriminated TypeScript
and `class-validator` DTO union. The server validates those settings, provider
media rules, empty content, and provider character limits before scheduling.

This gives Postiz a practical destination-specific contract and a responsive editor,
but it couples the primary post model to the integration row and provider payload
conventions. The inspected schema has no dedicated immutable publication or
rendition snapshot model. Its NestJS, Prisma, Temporal, and broader SaaS-oriented
surface also sits outside Herald's single-process footprint target.

Useful lesson: provider-specific validation belongs at the destination boundary,
but a provider settings payload should not become the common publication document.

### Mixpost

Mixpost separates `mixpost_posts`, the selected account pivot, and
`mixpost_post_versions`. The original version and account-specific versions each
store JSON content containing ordered body/media entries. The UI creates an account
version by copying the original version, then watches the active account's text and
media limits.

`SocialProviderPostConfigs` exposes common constraints such as minimum and maximum
text length, photos, videos, GIFs, mixed-media policy, and whether text is required
alongside media. Provider classes specialize those values. Media is a first-class
record with disk, path, size, MIME type, conversion metadata, and generated
derivatives. Laravel's filesystem abstraction hides local and remote disks, while
remote conversion work may require a temporary local copy.

Useful lesson: destination-specific versions and reactive capability feedback are
valuable patterns. The JSON version document is convenient, but it leaves more
invariants to runtime validation and makes a durable snapshot contract less explicit.

### OpenPost

OpenPost is the closest architectural comparison. Its current model separates:

- a source `Publication` and ordered canonical segments;
- one destination `Rendition` per account and provider target;
- rendition segments and inherited or overridden media;
- workspace-owned media attachments;
- provider media delivery state;
- provider delivery projections and append-only write attempts.

Its capability catalog is typed rather than being an arbitrary JSON schema. A
capability can describe output profiles, content limits, media MIME/count/size/
dimension/duration constraints, settings, dependencies, conflicts, public-URL
requirements, and validation issues. The resolver returns the available formats,
active constraints, compatible state, and machine-readable issues used by the editor
and by server-side validation.

OpenPost also snapshots selected destinations when a publication is created. Its
media service supports local storage and an S3-compatible backend, with upload
sessions, metadata analysis, lifecycle protection, trash retention, and provider
delivery records.

The model is evidence that the boundary is real, not evidence that Herald must copy
every table or migration. Its migration history shows the cost of adding format
profiles, normalized segments, media delivery, recovery, and connector support
incrementally. Herald already models one `Publication` per `Channel`, so that
relationship is a candidate target boundary; it should be tested against future
multi-target and multi-format requirements rather than rejected merely because a
separate `Rendition` aggregate is more complex.

Useful lesson: separate source intent, target snapshot, media asset, and provider
delivery state. Evaluate each of those primitives for Herald, without importing an
entire competitor stack or dismissing a needed foundation as too complex.

## Cross-provider evidence

LinkedIn and Mastodon both demonstrate that media is not just a field on the final
post request. LinkedIn initializes an image upload and then references the returned
media URN in the post payload. Mastodon uploads media separately and later supplies
provider media IDs to the status endpoint; polls and media also have provider-specific
constraints. A common content model therefore needs ordered media references and
provider delivery state, while adapters own upload sequencing and payload mapping.

## Proposed Herald direction for review

This section is a recommendation, not an accepted specification or decision record.

### Content boundary

Keep the existing Herald distinction:

```text
Post (shared source intent)
  -> Publication (one channel target and its persisted snapshot)
       -> Publisher (optional automation capability)
```

Use reusable source content for shared publication primitives, including ordered
media references and the metadata required by the accepted content model. “Source
content” names authoring intent; it does not imply a file format or force every
destination into one document shape. Provider or channel modules define precise
target adaptations through the shared typed contract. Do not persist raw provider
request payloads as the source of truth, and do not reduce the common model to a
temporary least-common-denominator representation when the cross-provider
requirement is already known.

The publication target revision is the exact content selected for scheduling,
retries, manual completion, and reconciliation. The web editor auto-saves a separate
mutable working draft. Scheduling or applying changes explicitly validates and
promotes that draft; until promotion succeeds, the previous scheduled revision
remains selected. Once an external effect starts, its execution revision is
immutable.

Herald's `Publication` already has one channel target and may serve as the target
snapshot boundary. This is a mapping to verify, not a reason to exclude the
conceptual separation represented by OpenPost's `Rendition`. A future subdestination
or multiple target variants may require a separate aggregate; provider delivery and
retry records remain distinct concerns either way.

### Capabilities and custom channels

The channel row should identify the destination and remain project-owned. The
provider or channel module should expose a typed capability descriptor for the
selected destination, including at least:

- supported common content profiles;
- body constraints such as minimum, maximum, and recommended length;
- media count, MIME, byte-size, dimension, and duration constraints where relevant;
- whether a public HTTPS-readable media URL is required;
- a bounded set of provider-specific options with explicit types and validation;
- a capability revision used to invalidate stale snapshots when rules change.

The descriptor is metadata for the UI and a validation input for the API. The server
remains authoritative, and API, CLI, and MCP use the same validation path. No client
may bypass a failed capability check by supplying an opaque provider payload.

A manual custom channel remains a normal channel with no executable publisher, but it
may still use a runtime schema so its planned work is structured and validated. An
automated custom channel uses the same runtime schema plus a bounded declarative HTTP
mapping; APIs that require provider-specific code, complex OAuth, signatures, or
multi-step media processing need a separately governed connector protocol. A channel
row must never become an arbitrary executable schema or plugin host.

### Media foundation recommendation

Do not impose a JPEG/PNG-only or local-only architecture. Model media as a first-class
project-owned asset with type-specific metadata and provider compatibility rules.
The initial supported media families and processing features should be chosen from
the actual publication workflows and provider capabilities, while the model remains
open to additional media kinds without replacing the storage or publication
contract.

The minimum media metadata should be:

- project ownership and a stable media ID;
- storage backend and object key;
- MIME type, byte size, and checksum;
- width and height when the asset is an image;
- processing state and a safe failure reason;
- default accessibility text with a publication-level override when needed.

The exact common formats, upload limits, processing operations, and derived asset
semantics need owner acceptance before the schema is changed.

### Storage boundary recommendation

Introduce a small Herald-owned `MediaStore` interface at the actual storage seam.
The domain should not expose `BunFile`, `S3File`, provider SDK objects, or storage
credentials. The initial operations should be limited to the needs of the media
lifecycle, such as put, open/read, stat, delete, and a controlled URL or presign
operation when a provider requires public access.

Bun 1.4 provides native local-file and S3-compatible primitives. `BunFile` and
`S3File` share the relevant Blob-based read/write surface, while S3 adds presigning
and remote metadata behavior. They are similar enough to keep the adapters small,
but not identical enough to leak either object through the application contract.

Implement local storage and Bun's S3-compatible storage client behind the same
Herald-owned contract when media storage is introduced. Local storage may remain the
default deployment configuration, while S3/R2 is available without a later media
rewrite. Cover both implementations with the same contract tests and use provider-
appropriate integration tests for S3-compatible services. FlyDrive remains an
evaluated alternative, but it is not required when Bun's native primitives satisfy
the chosen boundary.

2. Define the shared content, capability, and media contracts, with provider or

3. Replace the flat publication content persistence with a schema that can enforce

## Owner clarification received after the initial draft

The initial draft used “V1” to describe a first implementation cut and recommended
still images plus local-first rollout. The owner rejected that framing. Those limits
are withdrawn: they were not accepted product decisions. The current direction is
continuous development with complete foundations, including an interchangeable local
and S3/R2 media boundary from its first implementation and a capability architecture
that can represent real provider differences without a central provider catalog.

The owner also clarified that Herald remains a publication manager. Blog-like and
other adjacent publishing destinations are within that scope; unusual custom
channels extend the destination model rather than turning Herald into a generic
workflow product. A custom channel may define a complete runtime schema, while a
preset only accelerates creation and remains editable.

The owner accepted the explicit automatic/manual delivery distinction and the
draft-versus-target revision boundary. Browser auto-save is required for zero-loss
editing, but an intermediate auto-saved draft must not replace a scheduled target
until an explicit validated scheduling or update operation promotes it. Once an
external effect starts, its target revision remains immutable.

## Follow-up evidence and design refinement

The current official provider documentation confirms that the capability boundary
must describe composition and workflow, not only file formats. LinkedIn exposes
separate content profiles for images, videos, documents, articles, multi-image posts,
and polls, with profile-specific availability and upload rules. Mastodon combines
status fields, media, polls, visibility, replies, and quote behavior; media may be
processed asynchronously and carries accessibility and focal-point metadata.

The resulting design proposal is to keep destination knowledge in provider or channel
modules while defining one serializable capability protocol and one shared validation
issue shape. A module can add imperative validation for rules that cannot be expressed
declaratively, but the web editor and non-UI clients consume structured results from
the same server authority.

The data proposal separates the project-owned media asset, derived media variants,
the ordered media references in a publication revision, and provider-specific media
delivery state. The storage proposal defines local and Bun S3/R2 adapters behind one
`MediaStore` contract from the first implementation. Upload intent, finalization,
verification, and orphan cleanup are explicit because SQLite and object storage do
not share a transaction.

The publication model still needs a deliberate mapping between Herald's one
publication-per-channel relationship and OpenPost's rendition concept. A separate
aggregate is not being rejected; it is only deferred until the actual fan-out and
multi-output requirements are established.

The remaining decisions are now expressed as concrete alternatives rather than open-
ended questions:

- the proposed structural one-request HTTP mapping;
- the proposed media families, format registry, variants, lifecycle, and delivery
  separation;
- the proposed immutable channel-profile evolution and explicit migration behavior;
- the instance-level outbound-network policy for automatic custom channels.

## Runtime-schema feasibility check on 2026-08-30

The runtime profile was tested against the repository's installed TypeBox 1.3.20.
`Schema.Compile` accepted native JSON Schema 2020-12 objects and produced accelerated
validators for both a custom microblog profile and a long-form project-blog profile.
The validators accepted representative payloads and returned structured JSON Pointer
errors for an oversized body and an oversized tag collection. This confirms that
built-in TypeBox schemas and stored custom schemas can share one validator
implementation.

The JSON Schema security guidance requires resource limits for untrusted schemas and
instances. It also identifies catastrophic regular-expression backtracking and
unsafe processing of encoded content as application concerns. The proposed Herald
profile consequently excludes remote references, executable formats, content
decoding, and stored JavaScript regular expressions; it compiles only after both
meta-schema and Herald policy validation.

The concrete proposal added to SPEC-004 separates `contentSchema`, Herald-owned
`fieldBindings`, and optional one-request HTTP `transport`. It uses JSON Pointer for
typed value selection and response extraction, keeps credentials in the channel
connection, and routes multi-step uploads, signing, or provider OAuth to a built-in
module or future connector contract. The open security decision is whether private
network destinations are denied by default or enabled for trusted operators, since
private self-hosted blogs are a valid use case but unrestricted URLs create an SSRF
boundary.

The refined common-content proposal is intentionally smaller than the target
schemas. A source revision carries optional plain-text or Markdown body content, an
optional publishable headline, language, and ordered project media references. Exact
target revisions keep destination-only concepts. Shared field bindings seed new
target drafts and expose incompatibilities without silently truncating or discarding
source content. Versioned source-profile families remain an alternative if this
semantic vocabulary proves too small.

The owner accepted this small semantic source vocabulary on 2026-08-30. ADR-015
records the decision and keeps exact channel content in independently validated
target revisions.

The owner accepted the bounded JSON Schema runtime profile on 2026-08-30. ADR-016
records the standard dialect, TypeBox compilation path, separate field bindings,
normalized issue shape, prohibited schema features, and resource-control posture.

The refined media proposal recognizes image, video, audio, and document families
without baking a permanent global MIME enum into the database. It preserves originals
and models derived variants, extracted publication-revision references, and provider
media delivery separately. Stored bytes are inspected before readiness; channel
profiles own exact format and composition limits. Heavy processors remain explicit
capabilities instead of silently enlarging the base deployment image.
