# TAXONOMY-101 — Define project categories and publication tags

## Objective

Define a deliberately small, extensible taxonomy policy before implementation.
The policy must distinguish project identity from destination-publication
workflow metadata, preserve Herald's project boundaries, and remain compatible
with the existing route, localization, import/export, and analytics decisions.

## Evidence reviewed

- `AGENT.md`, `DESIGN.md`, and `.autonomos/PROTOCOL.md` for product boundaries,
  decision discipline, project isolation, and governance status.
- `SPEC-003` and `SPEC-005` for the lightweight self-hosted orchestrator
  position, distinct `Project`/`Post`/`Publication` responsibilities, and the
  rule that deferred features must not create throwaway foundations.
- `SPEC-007` and `ADR-057` for the route jobs: project orientation, source
  fan-out authoring, time scanning, and queue prioritization.
- `packages/core/src/model.ts` and `packages/db/src/domain-schema.ts` for the
  current absence of taxonomy fields/tables and the existing project-scoped
  publication model.
- `ADR-042`, `ADR-051`, `ADR-054`, and the ANALYTICS-107 through ANALYTICS-114
  records for the query-time operational analytics source boundary and the
  separate provider-owned engagement boundary.
- Existing project/channel/publication persistence and API access checks for
  the current project-scoped actor model and the unresolved instance-admin
  dependency tracked by ACCESS-116.
- Recent WEB-118/WEB-119 and AUDIT-125 records for progressive disclosure,
  URL-authoritative route context, and the need to keep Queue, Calendar, and
  Compose differentiated.

## Findings

- Herald has no existing category/tag schema or vocabulary to preserve, so
  migration can be additive and must not infer labels from existing content.
- A project category and a publication tag answer different questions. Making
  both generic labels would blur the accepted `Post`/`Publication` boundary.
- A single project category is enough for project-list orientation. Publication
  tags need many-to-many semantics because one source can fan out to destination
  versions with different operational needs.
- The current analytics contract intentionally groups by stable channel/provider
  and delivery dimensions. Taxonomy metadata has no safe historical metric
  semantics yet and should remain outside the operational analytics API.
- The existing route/UX contract supports compact contextual metadata and
  filters, but does not justify a new taxonomy-heavy route or repeated
  explanatory cards.
- Shared category definitions require an instance-level administration decision
  that the repository has not accepted yet. The taxonomy policy records that
  dependency instead of inventing a role model.

## Resulting policy

ADR-059 proposes:

- zero or one optional instance-scoped primary category per project;
- zero or more project-scoped tags per Publication;
- no tag-count business quota;
- stable opaque IDs, Unicode NFKC/whitespace/case-insensitive uniqueness;
- unordered tags with deterministic API ordering;
- active/archived lifecycle, recoverable archive/restore, and identity-preserving
  rename; no hard delete in the first slice;
- project-scoped authorization for tags and an explicit instance-admin
  dependency for shared category-definition administration;
- Queue filtering by stable tag IDs with `all selected tags` semantics first;
- no automatic provider hashtags, content mutation, analytics dimensions, or
  provider-engagement meaning;
- additive, no-inference migration and a future versioned export/import contract.

## Herald daily-workflow examples captured

The ADR includes a product-update fan-out where LinkedIn and a manual community
publication receive different tags, a Queue filter combining
`customer-facing` and `needs-review`, a Calendar planning filter, and a
rename/archive example that preserves publication references without rewriting
target content or execution history.

## Phased implementation proposal

1. Accept ADR-059 and resolve instance/category authority with ACCESS-116.
2. Add core validation and additive SQLite storage for nullable project category,
   project tag definitions, and publication-tag assignments; preserve backup,
   restore, and project-isolation invariants.
3. Add typed API CRUD/assignment/filter contracts with stable IDs, deterministic
   ordering, archived-state handling, and supported machine access.
4. Integrate category into project context/settings, tags into Compose and
   publication detail, and compact tag filtering into Queue; keep Calendar
   filtering evidence-driven and preserve URL/realtime/localization contracts.
5. Validate null migration, round-trip backup/export behavior, lifecycle changes,
   import conflicts, direct routes, and narrow-screen/English/French behavior.
6. Revisit source tags, multi-category projects, saved boolean filters, provider
   mappings, assignment history, and taxonomy analytics only through separate
   decisions with concrete evidence.

  settings needs to follow that authority decision.

  evidence before inclusion.
