# WEB-566 — Complete the web JSON client contract migration

## Scope and implementation

Completed one integration batch across the entire web API module rather than
separate tasks for equivalent wrappers. Removed 96 explicit unwrap type arguments
and 109 Promise return annotations so the server contract flows through the
checked helper into every Eden-backed method. No unchecked response conversion
was added. Existing call parameters and UI adapters remain in place.

Migrated the eight remaining application JSON fetches: channel profile presets,
avatar removal, media usage, deletion, permanent deletion, restoration, batch
deletion and URL import. Permanent deletion still returns its status string;
restoration still resolves without a value. Batch deletion copies readonly ids
before passing them to the typed request. Raw media/avatar upload bytes remain
on their existing transfer path. Better Auth's passthrough routes retain their
separate session contract.

Derived shared media query/page types, publication sort, recovery state, LinkedIn
destination, Facebook page choices, custom channel/profile inputs, custom HTTP
authentication and draft-adoption input from server routes in the client package.
Locally materialized profiles refine the server input by requiring fingerprints.
Composer draft metadata now derives from the server response while its opaque
content still passes the existing runtime validator before UI use. Removed the
unused AccessProjectMembership declaration rather than inventing a new alias.
The web API shrank from 2,034 to 1,666 lines.

The remaining raw-fetch helper accepts only Better Auth paths or the two binary
transfer path families at compile time. It is explicitly named requestBoundary;
ordinary application JSON calls use Eden. Fifteen additional compile-time
assertions cover migrated contracts and include global guards rejecting unknown
or any application results or extracted request contracts. Intentional opaque content
inside server-defined fields remains opaque.

Recorded the owner's coherent-batch workflow direction in root AGENT.md. No
runtime dependency, server route, query-cache strategy, rendered component or
compiler setting changed.

Also derived the remaining 23 body/query contracts through WebApiRequests,
including replies, first comments, uploads, provider connections, posts, draft
updates, notifications, analytics, publication filtering and API-key updates.
Query subsets and readonly-array adaptations remain explicit; no handwritten
inline input/body/options object declarations remain in the web API module.
The narrower optional title accepted by createPost remains preserved.

## ISSUE-188 architectural balance

The prototype exposure and duplicated application JSON response contracts are
addressed by WEB-557 through this task. Authentication and binary transfers are
explicit transport boundaries, not unfinished ordinary JSON migrations.

ADR-047 already accepts TanStack Query for the production boundary. Current
source imports confirm that TanStack DB and query collections are used only by
the development prototype and its tests; they are not competing production data
stores. Dependency removal is optional prototype cleanup, not a prerequisite for
a new data-layer decision.

The substantial remaining work is route-scoped data ownership and component
boundaries. The project parent loader still calls loadProjectData on every
project route; it fetches channels, due publications, publisher connections,
publication lists, tags and current membership together. DashboardContext remains
876 lines and combines data, mutations, publisher actions and composer state.
The API wrapper remains a large module despite its now inferred contracts.
These are structural concerns, not additional sets of fetch wrappers.

Recommended next implementation batch: move feature data/mutations out of the
project-wide dashboard context into route-owned Query hooks while retaining the
shared project identity/role and navigation needs in the parent. Define the
acceptance scenarios for route loading, realtime invalidation, drafts and access
revocation together before changing those lifecycle boundaries. Preserve the
accepted Query strategy; a framework or data-layer replacement is unnecessary.
