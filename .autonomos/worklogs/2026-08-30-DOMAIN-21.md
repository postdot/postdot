# DOMAIN-21 — Revision Persistence and Profile Ownership

Date: 2026-08-30
Status: completed
Task: Persist drafts, immutable target and execution revisions, profile versions, and review state

## Context

The accepted publication content boundary had executable core contracts, but the
database still stored mutable text columns on `posts` and `publications`. Jobs and
the LinkedIn worker read that text directly. Channels had no persisted profile, so
validation could not be reproduced for a manual publication before a publisher was
connected.

The owner accepted the following boundary for this task:

- a channel owns its resolved immutable profile version;
- a custom profile is a validated runtime schema copy, while presets are creation
  accelerators only;
- a publisher adds automation and never owns or changes the channel contract;
- delivery mode is explicit and independent from publisher availability;
- auto-saved working drafts are mutable, target revisions are immutable, and an
  execution revision is pinned when the external effect starts;
- this young unreleased repository may regenerate its transitional schema rather
  than preserve compatibility with discarded text-only choices.

## Plan

1. Replace the transitional text columns with persisted source content, profile
   versions, working drafts, target revisions, and execution pins.
2. Adapt channel and publication creation so every target is validated against the
   channel-owned profile and records explicit delivery mode and review state.
3. Make the worker claim and external-effect boundary use the immutable execution
   snapshot, while retries and manual reconciliation keep the same pinned revision.
4. Add database and API integration coverage for project ownership, atomic
   promotion, immutable snapshots, review gating, and retry pinning.

## Baseline evidence

- `packages/db/src/domain-schema.ts` stored `posts.content` and
  `publications.content` as non-empty text and had no profile or revision tables.
- `packages/db/src/manual-store.ts` created publication text inline and inferred
  executable work from publisher presence.
- `packages/db/src/workflow-store.ts` claimed scheduled publications and marked the
  effect boundary without persisting a separate execution snapshot.
- `packages/db/src/publisher-store.ts` returned publication text directly to the
  LinkedIn worker.

## Implementation

- Replaced the transitional text persistence with JSON source content and a
  `source_revision` on posts.
- Added immutable channel profile snapshots, one mutable working draft per
  publication, append-only target revisions, and one execution revision pinned to a
  job before the external-effect boundary.
- Made delivery mode (`manual` or `automatic`) and review state explicit. A target
  is created only after profile validation; invalid drafts remain editable but
  cannot be promoted or scheduled.
- Materialized built-in/manual and LinkedIn profile definitions at channel creation.
  The preset is copied into the channel profile snapshot and is not consulted as a
  live source later.
- Added deterministic JSON serialization and content hashes for target snapshots.
  Working-draft writes use both the draft revision and the post source revision as
  compare-and-swap fences, so stale editors receive `write_conflict` instead of
  replacing newer work.
- Kept the currently selected target unchanged during autosave. Promotion appends a
  new target revision, updates or creates the pending job atomically, and cancels
  pending work when a scheduled automatic target becomes unscheduled.
- Made the worker read the execution snapshot rather than the mutable publication;
  a retry reuses the first pinned target even if the selected publication target was
  subsequently changed.
- Regenerated the young project's transitional SQLite migration as one clean
  migration. The repository does not preserve discarded text-only compatibility.

The channel and target pointers intentionally remain application-maintained rather
than direct SQLite foreign keys because their parent rows and child rows form
creation-time cycles. Store transactions write and query the complete project,
channel, profile, publication, and target relationship together; lookup paths fail
closed when a pointer does not resolve to the expected project and owner.

## Open implementation boundaries

Media assets and provider-specific media delivery remain under MEDIA-22 through
MEDIA-24. DOMAIN-21 persists content as validated JSON and preserves media
references inside revisions; it does not invent a static directory or prematurely
couple the revision tables to one storage backend.

The public draft/editor endpoints and zero-loss browser editor remain under
EDITOR-27. Profile activation, impact assessment, and profile migration remain under
CHANNEL-25. Declarative custom-channel transport and restricted egress remain under
CHANNEL-26.
