# OPS-73 — Make populated SQLite schema-rebuild migrations safe

## Objective

Make SQLite migrations that rebuild referenced tables work against populated local
databases without weakening foreign-key enforcement during normal application work.

## Findings

- `apps/api/.env` points the development API at `apps/api/herald.sqlite`.
- The database had applied migrations `0000` through `0010` and contained existing
  projects, channels, and publications.
- Migration `0011_deep_captain_britain.sql` rebuilds `channels` and requests
  `PRAGMA foreign_keys=OFF`.
- Drizzle wraps SQLite migrations in a transaction. SQLite does not change the
  `foreign_keys` setting from inside that transaction, so the table drop failed when
  child rows existed.

## Implementation

- Disable foreign-key enforcement before Drizzle begins its migration transaction.
- Run the committed migrations without changing their SQL contract.
- Check `PRAGMA foreign_key_check` after migration execution.
- Restore the connection's previous foreign-key setting in a `finally` block.
- Keep the existing fail-closed error for conflicting schema objects.
- Extend the migration fixture so the channel rebuild is tested with foreign keys
  enabled after the legacy schema is reconstructed.

## Verification

- `bun test packages/db/src/migrations.test.ts`
- `bunx oxfmt --check packages/db/src/migrations.ts packages/db/src/migrations.test.ts`
- Existing `apps/api/herald.sqlite` migrated successfully from 11 to 12 migration
  entries.
- The migrated database retained 3 projects, 5 channels, and 8 publications.
- `PRAGMA foreign_key_check` returned no violations.
- A fresh database connection reports `foreign_keys=1` after `runMigrations`.

## Boundary

This task does not add automatic database reset or legacy-data deletion. A database
whose schema is not represented by the committed migration history still fails closed
and requires an explicit operator decision.
