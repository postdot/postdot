# DEV-412 — API termination during startup

## Plan

1. Map statically the startup window between the runtime-quiescence lock acquisition and the process signal-handler registration.
2. Reproduce the termination behavior in a parent-owned isolated fixture: fresh temporary database/media directory, dynamically allocated loopback port, synthetic environment, no normal data or credentials.
3. Establish the observed outcome — exit status, retained runtime marker, and the effect on an immediate restart — before proposing any change to the fail-closed policy.
4. Correct only a proven defect, with proportionate checks, then record the evidence and the durable guidance.

## Scope and boundaries

Recommended next task from the DEV-411 worklog: "a bounded isolated check of termination during API startup; establish actual behavior before proposing any change to the existing fail-closed policy."

The fail-closed runtime marker policy itself (`packages/db/src/runtime-quiescence.ts`) is out of scope for change in this pass. No stale-marker recovery, no automatic marker removal, and no weakening of the exclusion is authorized. The pre-existing `herald.sqlite.runtime.lock` marker in the repository root is owner state and must not be read for authority, removed, or reused as a fixture.

Delegation note: the owner asked for this pass to run directly in the orchestrator instead of delegating to the MiniMax worker, because the orchestrator already runs that model. The standing delegation preference in the root `AGENT.md` is unchanged.

## Static map of the startup window

`apps/api/src/index.ts` before the correction:

- `startServer()` acquired the runtime quiescence marker at its first statement (`acquireRuntimeQuiescenceLock`, line 119) and released it only if the rest of the startup threw.
- `startServerWithRuntimeLock()` then performed the whole startup: database creation, migrations, installation email settings, realtime runtime, media store and `media.reconcile()`, auth, provider registry, worker, app composition, `app.listen()` (line 364) and `registerServingHandle` (line 365).
- The `SIGINT`/`SIGTERM`/`SIGHUP` handlers were registered last, at lines 385-387, after `createShutdownHandler` was built at line 367.

Every signal delivered between the marker acquisition and line 385 was therefore handled by the platform default disposition, not by the application drain path, and the marker was retained on disk.

## Observed behavior before the correction

Parent-owned reproduction, isolated fixture per trial (fresh temporary data directory, OS-allocated loopback port, synthetic environment and secrets, no normal database, media root, credential file or running service touched). The signal was sent as soon as the runtime marker appeared, which marks the beginning of the startup window.

| Trial | Signal sent | Exit | Marker retained | Next start |
| --- | --- | --- | --- | --- |
| control (signal after the API served) | after readiness | 0 | no | n/a |
| interrupted 1..5 | ~505-514 ms after spawn | 143, `signalCode: SIGTERM` | yes | exit 1 |

Five of five interrupted trials behaved identically. The interrupted child produced no shutdown diagnostics at all, which confirms the application never saw the signal: the platform default disposition killed it. The control trial drained in order and exited 0.

The next start of the same database failed with exit 1 and the operator-visible message:

```text
error: Cannot acquire Postbot runtime lock for <database>: <database>.runtime.lock is already held.
Stop the active Postbot runtime, or verify and remove this exact stale marker after a forced stop, before retrying.
```

Consequence: a development restart that lands in the startup window leaves the API unable to start, and only an operator can clear it. The pre-existing root `herald.sqlite.runtime.lock` marker shows that a forced stop has already produced this state once in this repository.

## Correction

`apps/api/src/index.ts` and `apps/api/src/shutdown.ts`:

- The process signals are now handled before the runtime marker is acquired, so no signal can reach the platform default disposition. The marker acquisition is synchronous, so the handler can only observe it after the assignment.
- The drain steps are assigned as their resources are created, through `createShutdownDependencies` in `src/shutdown.ts`. A step whose resource does not exist yet stays a no-op, which keeps the existing exit-code contract intact: an interrupted startup has nothing to drain, so it completes as an orderly shutdown with exit 0.
- A termination requested during startup no longer starts the worker, the maintenance runtimes, the notification projection or the HTTP listener.

The fail-closed policy is untouched: the marker is still released only through the token-checked `release()` of the lock that created it, no marker is ever reclaimed by another path, and no PID-based or automatic stale-marker recovery was added.

## Evidence after the correction

Same reproduction, same trigger:

| Trial | Exit | Marker retained | Shutdown diagnostics |
| --- | --- | --- | --- |
| control | 0 | no | drain completed, exit 0 |
| interrupted 1..5 | 0 | no | drain completed, exit 0 |

The API never served in the interrupted trials, and the next start of the same database became healthy instead of failing on a retained marker.

## Regression coverage

- `apps/api/src/shutdown.test.ts`: the late-bound drain contract — a step assigned after the handler exists is the step that drains, a resource that does not exist yet drains as a no-op, and the marker release reports the outcome it is given.
- `scripts/dev-api.test.ts`: a real-process regression. The signal is sent as soon as the runtime marker appears, the API must never serve, the process must exit 0, the marker must be released, and a second API on the same database must become healthy and shut down cleanly.

Old-source negative control: with `apps/api/src/index.ts` temporarily restored to its pre-correction version, the new process regression fails with `Expected: 0, Received: 143`, the platform default disposition. The file was restored byte-for-byte afterward.
