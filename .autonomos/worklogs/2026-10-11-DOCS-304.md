# DOCS-304 — Documentation framework recommendation

## Scope

Owner requested a comparison before creating the documentation site. No app,
framework dependency, hosting account or public site was added.

## Recommendation (not yet accepted)

Use Next.js with Fumadocs and static export, hosted as static files on Cloudflare.
Keep search browser-side with a build-generated index. Avoid a request-time server,
SSR adapter or authentication for the first documentation site.

The owner's two existing Next.js/Fumadocs projects are a concrete reuse advantage,
not merely a typing preference: layouts, content components, search configuration,
accessibility fixes and maintenance practices can carry across projects. Agent
implementation does not remove these maintenance economics. Inspect the actual
projects before assuming their custom components are portable to static export.

Fumadocs currently documents all three candidates:

- Next.js: documented static export; Cloudflare Pages has a direct static-hosting
  guide. This does not require Vercel or a running Next.js server.
- Astro: supported through React islands and Astro content collections. The
  reference integration hydrates the Fumadocs layout. Astro's general low-JavaScript
  advantages do not prove this particular integration faster without measurement.
  Strong alternative for a new primarily editorial site without existing reuse.
- TanStack Start: supported, with prerendering/static options and Cloudflare
  hosting. Familiar Router/Vite tooling is helpful, but Start introduces a distinct
  rendering/build lifecycle; sharing a router alone is not a decisive docs benefit.

No performance ranking is claimed: there are no equivalent site builds to compare.
The decisive first boundary is static output versus a server, not framework brand.
Reconsider if the owner wants an independent Astro content architecture more than
shared components with their existing documentation projects.

## First site scope

Proposed: installation, first project/manual publication, provider configuration,
source/destination concepts, media, API/CLI entry points, and backup/update limits.
Keep content in the same repository and independently deployable; do not bundle
this public site into the Herald runtime image. Branding/domain and publication
remain owner decisions. Reuse installation content instead of maintaining two
contradictory guides. No announcement or public release date is implied.

## Owner-approved local foundation (2026-10-11)

The owner selected Next.js/Fumadocs reuse and Motion. Read both existing docs
workspaces; reused their collection/static architecture, not their product copy
or GSAP integration. Added `apps/docs`, independent of the application runtime,
with eight documentation pages and a landing candidate. The design comparison
is recorded separately in DOCS-304-design; this does not amend DESIGN.md.

Installation is generated from the existing canonical operator guide. The other
pages establish the verified workflow and vocabulary; exhaustive provider recipes
and a generated API reference remain follow-up content. Search is an exported
static index. No server, public domain, hosting account or deployment was created.
Indexing is disabled while the site remains a private candidate.

Compatibility: the initial borrowed Fumadocs versions failed Markdown compilation
with the resolved Markdown utility. Updating the docs-only Fumadocs packages to
16.17.1/MDX 15.4.7 resolved this, under Bun. Node reproduced the original failure,
so changing runtime was not a solution. Documentation rendering resolves compiled
bodies from the typed collection by the loader's file path; loader metadata remains
responsible for routes and navigation. Declaration output is disabled for this
non-library Next.js workspace, with strict checking retained.

Validation: static export succeeded (home, search and eight docs routes), focused
browser smoke passed (destination selection, search results, installation, theme
switching, 390px without overflow, no page errors). Inspected desktop/light/dark,
mobile and documentation screenshots. Exported internal links resolve. Root
`check:quick` passed. Fresh AMD64 production image built from a clean tracked
context plus the new workspace; Docker builds only API/dashboard, excluding the
public site. No whole application E2E matrix, provider call, push or publication.
Fumadocs emits two upstream CSS parser warnings for search `::highlight`; build
succeeds and search works. Do not suppress these with global validation changes.

DOCS-304's local foundation is complete; the site is not release-complete.
Next recommended pass: owner review of this concrete visual candidate, then add
focused provider setup content using the existing canonical requirements. Bun and
Elysia maintenance is a separate pass, with explicit version and compatibility
checks rather than speculative upgrades during design work.
