# UX-406 — Composer recovery across account and access changes

Status: complete
Related contracts: DESIGN.md composer recovery; SPEC-010 JRN-02/COH-02; follows UX-405

## Reproduced behaviour

- **Same-browser account switch.** Recovery keys identified the project but not the author. After the original author's autosave failed (503) and they signed out, a second author with editor access to the same project signed in and was offered the first author's local text. The new regression failed on the unexpected recovery dialog.
- **Stale tab on the previous account.** Browser cookies are shared across tabs. A tab left on author A, with account B signed in from another tab, kept sending autosaves with B's cookie. When A's tab had no saved draft yet (revision 0, no draft id) the guards added in UX-405 did not apply, and A's text was written into B's server draft. A tab that already had a saved draft was refused by the revision/identity guard, so only the unsaved variant failed.
- **Access withdrawal** and **same-author reconnection** behaved correctly before any change; they are now covered by regressions.

## Changes and decisions

- Recovery keys now carry the author: `postdot:publication-composer:v1:<project>:user:<author>`, read, written and cleared by author in both the tab-local and shared stores. Entries written under the earlier unscoped key are neither read nor removed. Their bytes are retained without being attributed to any account (no migration, to avoid assigning ownership by guess). They are now inert, and remain until the browser clears storage.
- `PUT` body gains optional `expectedUserId` and `DELETE` gains an optional `expectedUserId` query guard. A mismatch returns 409 `account_changed` before any store access, so no draft is read, written or removed. Omitting it stays compatible, like the earlier optional guards.
- The Studio always sends the author it rendered for. On `account_changed` the composer pauses autosave and creation, and shows an alert titled "Your account changed in another tab" with a Reload page action. It does not offer the conflict comparison, which would read the other account's draft through the stale tab. The local copy remains under the original author's key, and the text stays in the page.
- Existing end-to-end specs that inspected the legacy key (`new-publication-recovery.spec.ts`) now match the project's key for any author. This is an obsolete mechanism replaced deliberately; assertions are unchanged.

## Validation

- New `e2e/composer-account-isolation.spec.ts`: four scenarios — account switch and return to the original author (restore works, second author's server draft untouched), saved and unsaved stale tab after an account change (409, alert, no write to the signed-in account), and access withdrawal (server write refused, text and author-scoped local copy kept, no server draft). All four pass.
- Focused run of the isolation spec and four adjacent recovery/composer specs (37 journeys, before the access-withdrawal scenario existed): four failed from the legacy-key assumptions above; after the spec update `new-publication-recovery.spec.ts` passes 6/6, and the other 33 passed in that run. The complete isolation spec then passed 4/4 on the final code.
- Unit: web 296 and API 558 tests pass, including a new per-author storage test (legacy key retained) and the API guard test. `bun run check:quick` (format, lint, spelling, typecheck, i18n coverage) passes.

## Limits and next scope

- Creating a publication from a stale tab is only blocked client-side after an `account_changed` response; publication creation itself has no `expectedUserId` guard, so a stale tab that submits before any autosave refusal would create the post under the signed-in account. Not changed here: it needs an API contract decision for `createPost`.
- The conflict comparison dialog reads the saved draft as the current cookie's account; if the account changes while it is open, the dialog can show that account's draft. Not reproduced or fixed.
- Legacy unscoped recovery entries are never offered again; there is no import path.
- No physical-device, screen-reader or full browser-matrix acceptance is claimed. The full default matrix was not run.

Recommended next task: guard publication creation and other composer-adjacent mutations against account changes in a stale tab (shared `expectedUserId` decision for `createPost`), and consider detecting the session change proactively on focus.
