# OPS-213 — Production backup and restore execution

- Status: complete
- Date: 2026-09-25
- Base: `origin/main` at `811949a4`
- Related issue: ISSUE-123

## What was done

- Reproduced that the documented `backup --media` and `restore --media` Docker
  commands failed before maintenance began because the production entrypoint
  required web-authentication, signed-media-URL, and publisher-encryption secrets.
- Extracted shared database and media-store environment definitions and added a
  maintenance configuration that does not parse unrelated server settings.
- Kept S3 bucket, region/endpoint, and access-key validation in the maintenance
  path when S3-compatible media storage is configured.
- Passed the normalized database path and optional media store into the
  maintenance command instead of reading process environment there.
- Updated the operator guide to describe local defaults, S3 credentials, and
  the publisher key's separate role when starting the restored application.
- Added a disposable production-image acceptance script to CI. It builds a
  unique image, starts the server with test-only secrets and temporary data,
  stops it cleanly, runs media backup and restore with no server secrets, starts
  the restored database, and removes its uniquely named image and temporary
  files. The temporary bind-mount roots are writable by the image's unprivileged
  user even when the host runner UID differs; a root cleanup container removes
  files and nested directories created by that image user before host cleanup.
- Reopened and resolved ISSUE-123 with the reproduced defect and its correction,
  retaining OPS-208's earlier resolution as historical evidence.

## Follow-up verification

The first GitHub recovery-test runs exposed host-runner ownership differences:
the container's unprivileged `bun` user could not write to runner-owned bind
mounts, and the runner could not remove nested files created by that user. The
test now makes only its disposable bind-mount roots writable beneath a private
temporary parent, then uses the image as root to remove only the three named
fixture directories before host cleanup.

- `bun run check:quick` — passed after the cleanup change.
- `bun run test:container:recovery` — passed locally after the cleanup change.
- GitHub validation of the cleanup follow-up is tracked in PR #203.
