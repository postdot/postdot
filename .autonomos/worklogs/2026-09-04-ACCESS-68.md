# ACCESS-68 — Expose project machine access through supported operator clients

## Objective

Complete the operator-facing part of project machine access without changing
the existing database, migration, Better Auth, publisher credential, or token
ownership boundaries. Humans must be able to manage project tokens through the
supported clients, while scripts and agents must be able to use a project
bearer token for ordinary project operations.

## Delivered

- Extended `@herald/client` with an explicit project-token option that sends an
  authoritative `Authorization: Bearer` header while preserving cookie-based
  human sessions.
- Added typed web API helpers for project token metadata listing, creation, and
  revocation.
- Added an authenticated project Access route using the existing dashboard
  project context and shared UI primitives. The full token is held only in
  component memory after creation, shown once, and removed from the DOM when
  dismissed. Metadata rows expose only the prefix, lifecycle state, and dates.
- Extended the supported CLI with `access-tokens list|create|revoke` commands.
  Token management requires `HERALD_SESSION_COOKIE` or `--cookie`; ordinary
  project operations accept `HERALD_PROJECT_TOKEN` or `--token`.
- Kept token-management requests on a separate human-session client so a
  machine token cannot accidentally be used to create, list, or revoke tokens.
- Added focused client and CLI tests plus a real API-backed client integration
  path for bearer propagation, human-only management, project isolation, and
  one-time secret handling.
- Added an isolated browser E2E flow covering token creation, one-time display,
  DOM removal after dismissal, metadata rendering, confirmation, and revocation.

## Command and authentication matrix

| Surface | Ordinary project operations | Token management | Secret behavior |
| --- | --- | --- | --- |
| `@herald/client` | `createHeraldClient(..., { token })` | Human-session request to typed access-token routes | The client does not persist token material |
| CLI | `HERALD_PROJECT_TOKEN` or `--token` | `HERALD_SESSION_COOKIE` or `--cookie` with `access-tokens` commands | Create prints the plaintext once; list and revoke print metadata only |
| Web dashboard | Existing human session | Project Access route through the human session | Full value is shown once in memory and removed on dismissal |

Machine-authenticated requests remain unable to manage access tokens, create
projects, or start interactive publisher OAuth. The bearer token is scoped to
the project and remains distinct from Better Auth's human email/password
session.

## Security and redaction evidence

- No token schema, migration, encryption boundary, or actor ownership code was
  changed in this task.
- The client and CLI tests assert that bearer credentials are sent only on
  ordinary operations and that token-management calls do not receive a bearer
  header.
- Creation tests assert that the plaintext is returned only by the creation
  response and is absent from subsequent metadata output.
- The browser test verifies that the full value is no longer present in the DOM
  after the operator dismisses the one-time disclosure.
- No real provider credentials, external provider action, default database, or
  shared development server was used.
