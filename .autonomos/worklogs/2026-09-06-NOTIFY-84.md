# NOTIFY-84 — Notification preferences and local projection verification

## Objective

Expose the existing project-scoped in-app notification preferences in the web
inbox and prove that a local publication outcome reaches that inbox through the
durable event journal and projection runtime.

## Decisions

- Keep the first preference surface limited to the three supported publication
  outcome kinds: delivered, failed, and ambiguous.
- Preferences affect future projections only. Existing inbox notifications are
  preserved so a user cannot hide already-recorded history by changing a
  setting.
- Keep external destinations such as Ntfy and Telegram out of this task. The
  notification runtime and transport-neutral delivery boundary remain the
  extension point for those later integrations.
- Use the existing Base UI/shadcn primitives and Solar Icons Bold. No custom
  notification settings route or second settings subsystem was introduced.

## Implementation

- Added the shared Base UI `Switch` primitive in `@herald/ui`.
- Added an inbox preferences panel with project-scoped loading, updates,
  stale-request protection, loading/error states, and accessible switch labels.
- Added a browser integration assertion for opening, changing, and returning
  from notification preferences.
- Extended the API integration flow so an actual manual `publication.published`
  audit event is consumed by `createNotificationProjectionRuntime`, then read
  back through the authenticated notification API.
