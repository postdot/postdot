# WEB-313 — Why cache removal is not enough after access loss

Diagnosis only. No product behavior, transport, translation, purge, retention
strategy, authorization policy was changed. The existing WEB-312 evidence is
reused; no new product test was added in this pass.

## Method

I traced everything that can continue to feed the interface after targeted
cache removal: TanStack Router loader snapshots, project and editor React
state, already-started writes, autosave timers, and local recovery buffers. I
then checked whether `project.access-revoked` distinguishes genuine revocation
from an authorization-control failure, and modeled an explicit state without a
global purge or silent local loss. The downgrade was completed from a real role
change, without deciding on a new event or policy.

## 1. Cache removal does not remove access state

`removeQueries` operates only on the TanStack Query cache: it removes matching
entries without rebuilding components, invalidating router loaders, stopping
already-started promises, or touching browser storage. The TanStack Query
documentation says removal deletes queries without refetching them, while its
migration guide warns that removing an active query can produce a harsh loading
state rather than a safe state. The TanStack Router documentation separately
describes loader data as retained under its own lifecycle, apart from external
query data.

Consequently, the following sources survive targeted removal even when it is
limited to the affected project.

### Loader snapshots and fallback to initial data

- The `/dashboard/projects/$projectId` loader loads the project list and
  `loadProjectData`, then passes the result as `initialData` to the project
  context (`apps/web/src/routes/dashboard/projects/$projectId.tsx:15-45`).
- `ProjectDashboardProvider` uses `projectDataQuery.data ?? initialData`
  (`apps/web/src/lib/dashboard-context.tsx:229-237`). After removal or a failed
  refetch, the previous role can therefore become the value used to render
  actions again.
- Local write handlers (`setProjectData`) can recreate an entry after removal
  (`apps/web/src/lib/dashboard-context.tsx:252-256`).
- The global loader keeps projects, workspaces, session, and instance rights in
  local state (`apps/web/src/routes/dashboard.tsx:120-145`).
- The editor loader retains the editor, tags, and related publications; the
  route then uses
  `editorQuery.data?.editor ?? editor`
  (`apps/web/src/routes/dashboard/projects/$projectId/publications/$publicationId.tsx:39-84`).
  Cache removal therefore does not remove the copy shown on screen.
- The `access-revoked` handler does not call `router.invalidate`
  (`apps/web/src/lib/project-realtime.tsx:517-521`). Without navigation, no
  loader reruns.

### Neighboring caches and already-scheduled refreshes

- The notification area uses `['notifications', projectId]`, a key outside the
  `['project', projectId, ...]` prefix
  (`apps/web/src/components/notification-inbox.tsx:62-69`,
  `apps/web/src/lib/project-realtime.tsx:5-23`).
- Preferences use a global user-scoped key, while analytics remain under
  provider-specific keys.
- The same handler schedules four delayed refreshes at 0, 80, 240, and 800 ms
  (`apps/web/src/lib/project-realtime.tsx:132`, `:401-446`). Removal inserted
  between those steps can therefore be followed by an already-scheduled
  refresh.
- A visible-tab change also invalidates editors
  (`apps/web/src/lib/project-realtime.tsx:491-498`), independently of earlier
  removal.

### Editor, composer, selection, and media state

- The editor retains the document, source content, target text, expected
  revision, dirty state, save state, messages, tags, media, and operation
  indicators (`apps/web/src/components/publication-editor.tsx:150-227`).
- The composer retains its content, targets, media, server draft, save queue,
  and timer (`apps/web/src/components/new-publication-page.tsx:91-160`,
  `:344-399`).
- Publication selections, open dialogs, filters, calendar view, and search
  parameters remain React and router state. They do not depend on the removed
  cache.
- Already-loaded media and files tracked by the Uppy instance remain in memory
  or browser recovery
  (`apps/web/src/components/media-attachment-picker.tsx:121-140`,
  `:159-281`).

### Already-started writes and autosave

- Dashboard mutations are direct promises, not cancelable TanStack mutations.
  Once started, `removeQueries` cannot interrupt them or prevent their
  continuations from rewriting cache or state.
- The editor uses a 650 ms timer, a request generation, and a pending-save
  indicator (`apps/web/src/components/publication-editor.tsx:226-227`,
  `:496-556`). The timer can be cleaned up, but an already-sent request runs to
  the server.
- Promotion, server reload, rebase, retry, manual publication, cancellation,
  and reconciliation retain their own in-flight indicators and continuations
  (`apps/web/src/components/publication-editor.tsx:608-984`).
- The composer retains a save queue and a 900 ms timer; work already placed in
  the queue can continue after a state transition
  (`apps/web/src/components/new-publication-page.tsx:344-399`).
- The web API currently uses no `AbortController` for these writes; the search
  finds no such mechanism in `apps/web/src/lib/api.ts` or the client used.
  The proposed block must therefore prevent new sends and ignore or quarantine
  late responses, without claiming to cancel HTTP already in flight.

### Local buffers

- The editor buffer is written on every local change and removed only when
  there are no local changes or after a successful operation
  (`apps/web/src/components/publication-editor.tsx:470-494`,
  `:878`, `:920`, `:962`).
- The composer buffer follows the same principle
  (`apps/web/src/lib/publication-recovery.ts:70-105`,
  `apps/web/src/components/new-publication-page.tsx:401-429`).
- Cache removal reaches neither `localStorage`, Uppy-recovered files, nor React
  state already containing the text. It preserves local work incidentally, but
  does not explicitly protect it: a later restore or operation can still
  replace or delete it.

Conclusion: targeted cache removal must not be presented as sufficient without
browser proof. Such proof should verify, after the signal and after every
delayed refresh, that project data has left the cache, that no stale role
controls the interface, that no late write is applied, and that the local
buffer remains intact.

## 2. The `access-revoked` signal does not distinguish the cause

The project-stream gate calls only
`access.canAccessProject(projectId, userId)`
(`apps/api/src/modules/projects/realtime-routes.ts:207-213`), with the implicit
minimum role `viewer`. The rank comparison therefore accepts `viewer`,
`editor`, and `owner`
(`packages/db/src/access-store.ts:1841-1848`,
`:393-396`).

Then `ensureAuthorized` treats a refusal and an exception the same way:

```ts
try {
    if (await isAuthorized()) return true
} catch {
    // Treat an authorization lookup failure as a revocation. A stream
    // must fail closed rather than continue serving project events.
}
closeWithAccessRevoked(controller)
```

(`apps/api/src/modules/projects/realtime-routes.ts:409-421`).

The emitted signal is always fixed:

```text
event: project.access-revoked
data: {"projectId":"<project>","reason":"access_revoked"}
```

(`apps/api/src/modules/projects/realtime-routes.ts:391-407`).

The project client checks only `projectId` equality and does not use the reason
(`apps/web/src/lib/project-realtime.tsx:180-185`). The user client requires
the same constant reason before closing its stream
(`apps/web/src/lib/project-realtime.tsx:288-293`). The existing test already
shows both paths producing the same signal
(`apps/api/src/modules/projects/access-revocation-stream.test.ts:39-103`).

It is therefore verified: genuine revocation and authorization-control
unavailability currently produce the same observable signal. No cause is
carried and none is interpreted. Local state must not call this situation
“access revoked,” but “access unverified.”

## 3. Proposal: an explicit unverified-access state

This proposal is an interaction model, not a data or transport policy. It does
not purge the client, decide displayed copy, create a new event, or change
server authorization.

### Minimum shape

Keep per-project control state outside the TanStack Query cache, separate from
data:

- `active`: current behavior;
- `access-unverified`: a signal or authorization failure prevents trusting the
  displayed permissions.

Storing it outside the cache is essential: if this flag lived in a removed
entry, the protection would disappear with the cleanup it is meant to govern.
Reactivate it only after a successful direct read or a fresh navigation, so a
transient failure is not confused with revocation.

### Blocking without local loss

On entering `access-unverified`:

1. Increment a project-scoped write epoch.
2. Refuse every new send: autosave, promotion, rebase, server reload, tags,
   reconciliation, manual publication, retry, cancellation, creation, and
   uploads.
3. Keep existing fields readable and copyable without accepting new changes, so
   no additional unsaved work is created during uncertainty.
4. Suspend local-buffer writers instead of deleting them.
5. Gate timers, queues, and continuations by the current epoch: ignore or
   quarantine any response arriving after the block, without applying its
   result to cache, visible state, buffers, or navigation.
6. Do not call `queryClient.clear()` and do not prune caches first. Any
   targeted cleanup, if retained, must come after freezing, after buffer
   verification, and with browser proof.
7. Leave consultation, navigation, and preview unchanged, absent a contrary
   product decision.

This model preserves local work because it neither resets nor replaces the
editor. It does not claim to prevent an already-sent request: it prevents only
new requests and use of their late responses. The server remains the final
authority for accepting or refusing a write.

### Remaining decisions

- Should the tab stay in a readable shell or navigate elsewhere?
- What wording explains an unverified situation without asserting revocation?
- What should happen to a late successful response: ignore it permanently or
  retain it as an unconfirmed operation until access returns?
- Is one direct corroborating read acceptable after the signal, without
  creating periodic polling?
- Should the local buffer stay silent, offer local copying, or be purged after
  an explicit action?

## 4. Downgrade: permission update without announcement

The existing pass already performs a real role change:
`PATCH /api/projects/:projectId/members/:memberId` with `{ role: 'viewer' }`
returns 200, then `GET /membership` returns the `viewer` role
(`e2e/web-312-live-access-revocation.spec.ts:187-206`).

That response updates authorization data, but emits no announcement:

- the PATCH route receives only authentication and the access store, with no
  realtime hub or journal
  (`apps/api/src/modules/projects/member-routes.ts:199-203`,
  `apps/api/src/modules/projects/index.ts:134-138`);
- `grantProjectUserAccess` updates the grant without calling the journal and
  without registering a project with the commit observer
  (`packages/db/src/access-store.ts:1720-1764`);
- no `member`, `membership`, or `role` subject exists in the event vocabulary
  (`apps/api/src/modules/projects/realtime-routes.ts:24-65`).

Then a `viewer` role still satisfies the stream gate, whose implicit minimum is
`viewer`. The stream therefore stays open and silent. The visible update in the
browser comes from a successful project-data reload, whose `loadProjectData`
reads the current role
(`apps/web/src/lib/dashboard-context.tsx:53-80`). The browser test proves the
final result — creation actions disappear — but does not isolate the trigger,
especially since the development proxy already disturbs SSE reconnects. The
diagnosis must therefore distinguish:

- **permission update**: a real and immediate server-side change, reflected in
  the client only during a successful read;
- **announcement**: absent from the current path for a downgrade.

No new role event is proposed here: that would be a transport and data
decision, explicitly excluded from this pass.
