# REALTIME-104 — Replace per-connection journal polling with a process-level wakeup

## Objective

Remove the idle SQLite read loop duplicated by every open project SSE stream.
Keep the durable event journal as the correctness source, wake the notification
projection when new committed events are discovered, and preserve reconnect,
heartbeat, authorization, and payload-safety behavior from REALTIME-102 and
REALTIME-103.

## Decision

ADR-049 accepts one lazy watcher per API process with one global journal cursor
and a project-scoped in-memory wakeup hub. The watcher starts when the first
SSE stream waits and stops when the last waiter leaves. It scans the durable
SQLite journal at a bounded 250 ms interval, notifies only affected project
waiters, and lets each stream replay its own authoritative project rows after
the wakeup. The browser still receives payload-free SSE invalidations and
refetches through TanStack Query.

The notification projection receives the same affected project set and runs its
existing durable projection immediately. Its five-second periodic run remains
the recovery mechanism. No process-local signal is trusted as the durable
record, and no Redis, broker, WebSocket, WebRTC, or schema migration is added.

## Implementation

- Added `readAfterGlobal` to the event journal store so one runtime cursor can
  observe all projects in append order without creating a second journal.
- Added `ProjectRealtimeRuntime` with a single scan timer, project-scoped
  waiters, bounded batches, cancellation, shutdown cleanup, and isolated
  projection callback errors.
- Wired the runtime into the production API process and passed its hub to the
  authenticated project SSE route.
- Changed SSE idle behavior: with the production hub, a connection waits until
  a project wakeup or its 15-second heartbeat deadline; it no longer performs a
  250 ms journal read per connection. The old bounded poll remains available
  only as a compatibility fallback for isolated route tests/consumers that do
  not provide the hub.
- Added targeted notification projection execution through `runProjects` while
  retaining the existing periodic recovery loop.
- Recorded the task under ISSUE-050 and added runtime, route, and journal
  regression coverage.

## Limits and follow-up

- The process-level watcher still has a measurable 250 ms discovery bound while
  SSE is active. This is a single bounded recovery scan per API process, not a
  per-connection loop. A later direct post-commit signal can reduce normal
  latency further once every audit-event write path shares a common post-commit
  boundary.
- The runtime is intentionally process-local. A future multi-process Herald
  deployment will require one watcher per process plus a durable cross-process
  signal or an explicitly supported broker.
- The SSE transport remains an invalidation channel; authoritative data stays
  in the existing API read models and notification projection.
