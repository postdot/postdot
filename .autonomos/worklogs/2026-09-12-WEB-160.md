# WEB-160 — Calendar column density and event treatment

## Status

Complete.

## Owner direction

The Week improvements should carry through to the other calendar views without
turning the calendar into a rigid appointment grid. Dense publication days need
room to express their content, while Month should keep the same deliberate
gutter and border rhythm. Publication colors are useful as state signals, but
the publication surface itself should stay quiet and consistent with Herald's
design language.

## What changed

- Added a bounded day-column model to the Week/Day time grid: columns start at
  9.5rem, Week keeps a deliberate 64rem reading floor, and an operator can
  resize each non-terminal column between 9.5rem and 22.5rem.
- Added accessible separators with a complete pointer hit area and keyboard
  controls (`ArrowLeft`, `ArrowRight`, `Home`, and `End`). Widths are persisted
  in local storage per project and calendar view; invalid or unavailable storage
  never blocks the calendar or an empty project.
- Kept the header label truncation inside its own child so overflow cannot clip
  the separator. This specifically fixes the pointer dead zone at the right
  side of the old hit area.
- Applied the Week rhythm to Month: 2px header/row/cell gutters, compact cell
  padding, borderless rounded cells, and a 60rem minimum reading width that
  scrolls intentionally on narrow surfaces.
- Removed the publication event's accent background, inset ring, and shadow.
  Publication state remains visible through one small token-backed marker, so
  status color is preserved without making every post a colored note.
- Rejected automatic `fit-content` tracks after the empty-project regression:
  an empty project could give the first day an unbounded width and make the
  calendar unusable. The final behavior has an explicit minimum, bounded user
  resizing, and horizontal overflow when the content requires it.
