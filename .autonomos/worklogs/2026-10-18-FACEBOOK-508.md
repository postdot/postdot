# FACEBOOK-508 — Confidential OAuth adapter and encrypted pending-state access

## Outcome

Added an isolated Facebook OAuth adapter and a server-only database primitive for reading encrypted pending provider state. This is groundwork for explicit Page selection, not a working Facebook connection in Studio. No API route, application configuration, connection persistence, profile activation or worker registration was added.

## Implementation and rationale

The adapter retains shared authorization-state and callback validation, and adapts the standards library's token request to Meta's documented fixed-endpoint confidential web exchange. The selected flow uses client-secret authentication without PKCE; other providers and shared defaults are unchanged. It also exchanges the initial user token before returning the longer-lived token and actual expiry. Both requests reject redirects and caching, have timeouts, and expose static errors without upstream messages, tokens, request URLs or exception causes. No internal retries occur.

The current manual-login guide supports the server exchange. The archived official Meta SDK corroborates the long-lived exchange parameters; it is not current live acceptance evidence. The current long-lived guide returned HTTP 429 during verification. A real installation still requires provider acceptance testing. No credentials or real accounts were used.

The existing authorization-attempt store already encrypts provider state and supports expiry and single-use consumption. Added a bound pending read that checks actor, provider, callback, active association and expiry without exposing the PKCE verifier. It allows repeated server-side Page discovery while preserving final consumption as the decisive single-use boundary. It does not itself authorize a browser request or persist a Page connection; the future application service must enforce session and project editor access.

The initially planned complete Page-selection lifecycle was narrowed to these independently testable primitives. Avoided adding an unused API dependency or exposing an incomplete connection flow. No database migration was needed. The remaining orchestration is explicitly tracked separately.
