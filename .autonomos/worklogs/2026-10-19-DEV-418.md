# DEV-418 — Prove the production image passes the whole container acceptance

## Plan

1. Reproduce the acceptance scenario of `scripts/production-container-recovery.ts` against a production-equivalent image, using the host network instead of a published port, because this environment has no bridge networking.
2. Record what the scenario proves and what remains unconfirmed.
3. Close the task with the evidence, or with the correction the scenario demands.

## Why the scenario was reproduced rather than run

The repository's container acceptance publishes the API on a loopback port. This environment cannot create a bridge network: `docker run` fails with "failed to add the host (veth…) pair interfaces: operation not supported". The image build also needs the network, because its poster layer downloads and compiles ffmpeg.

The scenario was therefore reproduced against an image derived from a locally available image that already carries the runtime contract of the repository `Dockerfile`: the same entrypoint `bun /app/postbot.js`, the `bun` user, `STOPSIGNAL SIGTERM`, the same `HEALTHCHECK` command with the same intervals, the same environment, and the packaged poster decoder at `/usr/local/bin/postbot-poster`. Only the bundle, the migrations and the dashboard assets were replaced with the current ones, and the bundle was built with bun 1.4.2, the version the `Dockerfile` pins.

## Observed scenario

| Step | Result |
| --- | --- |
| The packaged poster decoder and the native preview | the decoder produced a frame, a placeholder and a 256 px WebP preview |
| The source server | `/ready` 200, `/health` 200, PID 1 is `/usr/local/bin/bun`, the session route answers `null`, the recovery is not held, the dashboard answers 200 |
| The graceful stop of that server | exit 0 in 65 ms, the runtime marker released |
| The media backup and the restore | both completed |
| The restored server | the recovery is held, a write is refused with 503, the dashboard answers 200 |
| The graceful stop of the restored server | exit 0, the runtime marker released |
| The forced stop | exit 137, the runtime marker retained |
| The refused restart | the server refuses to start and cites "is already held" |

Every step of the acceptance scenario passes against the production-equivalent image with the DEV-416 correction in place.

## What remains unconfirmed here

- The image build itself: the poster layer downloads and compiles ffmpeg, which needs the network. The locally available image carries an equivalent decoder, built earlier from the same source, but the repository build was not replayed.
- The published-port path: the acceptance publishes the API on a loopback port, which this environment cannot create.

Both are properties of the CI runner rather than of the code, and the CI image run remains the confirmation.

## Evidence

- The production path is verified end to end apart from the image build and the network mode.
- The correction of DEV-416 is what makes it pass: before it, the same scenario answered every compiled route with 500.

## The Playwright matrix, observed

The full `bun run check` also runs the Playwright matrix, which the previous passes had never run. Two web specs fail, and both reproduce in isolation on a tree where the DEV-416 static wiring is removed, which means they are pre-existing and unrelated to the API lifecycle and production image work:

- `e2e/web-122-populated-states.spec.ts:323`, "keeps calendar titles readable across intermediate workspace widths";
- `e2e/web-124-ambiguous-recovery.spec.ts:5`, "resolves an ambiguous publication without retrying the provider", which waits for a "Create channel" button that the current channel dialog no longer offers under that name.

They are web interface concerns outside this session's scope, and they are recorded as the recommended next task.
