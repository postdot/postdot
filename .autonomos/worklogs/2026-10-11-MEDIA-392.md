# MEDIA-392 — Bun container poster feasibility

## Authorized scope

Isolated packaging and failure probes following MEDIA-391. No application code,
production Dockerfile, dependencies, live database, private media or server changed.
Poster production remains a separate implementation. The test controller below is
not evidence that Postbot already implements background scheduling or failure isolation.

## Build and size

Built FFmpeg 8.0.1 using the exact MEDIA-391 configure flags, including disabling
all assembly, inside oven/bun:1.4.2-slim. Source checksum matched MEDIA-391.
Base manifest: sha256:cb3bbbb08e13a4a2ff400f24c7a2a1d5efa83f6ef8544d52d95a519631e2fc61.
Platform: Linux x86_64. Build stage installed build-essential and xz-utils with
no recommended packages. Runtime stage copied only the stripped executable.
No compiler, source archive or build dependency was copied into runtime.

Comparable Docker image sizes, with the same user and entrypoint configuration:

| Image | Uncompressed bytes |
| --- | ---: |
| Bun slim baseline | 169,848,875 |
| Baseline plus poster executable | 172,305,995 |
| Increment | 2,457,120 (2.34 MiB) |

This is the Docker-reported uncompressed incremental size, not registry transfer
size or complete Postbot image size. The executable differs slightly from the host
build because it was built in the container toolchain.

BuildKit measured dependency installation at 11.2 seconds, source extraction at
0.9 seconds, configure plus compilation at 15.9 seconds and image export at one
second. The base was already cached; these are not universal cold-build timings.
A second identical build reused dependency installation, source, compilation and
runtime-copy layers. Production must keep this stage independent of application
sources to preserve this cache behavior.

## Runtime probes

Ran as UID 1000, network disabled, read-only root filesystem, read-only fixture
mount, 128 MiB memory limit and one CPU. Bun.spawn receives JPEG on stdout and
Bun.Image decodes it. No FFmpeg network protocols were enabled.

| Case | Observed outcome |
| --- | --- |
| Valid Postbot H.264 fixture | Exit 0, 8,146-byte JPEG, 320x180, 22 ms |
| Invalid text file | Nonzero exit 183, zero output bytes, 2 ms |
| Missing executable | Spawn failure caught by isolated controller |
| Input pipe held open | 100 ms timer killed child; exit 137, zero bytes, 101 ms |
| Valid fixture after failures | Exit 0, valid JPEG again, 14 ms |

The command uses one decoder, encoder and filter thread and the bounded scale
expression from MEDIA-391. Timeout probe instead supplies pipe input without
closing it, causing a deliberate wait, and kills that exact child process.
Failure controller consumes stdout/stderr, clears its timer, and continues to the
next probe. No live Postbot process was subjected to a resource limit or signal.

## Conclusion and remaining work

The minimal executable runs in the actual Bun slim base and adds approximately
2.34 MiB. Failure handling and cancellation are feasible through Bun subprocesses.
The packaging concern is resolved for this Linux x86_64 base; this is not an ARM,
edge-runtime, arbitrary-codec or worst-case malformed-file compatibility claim.

Recommend implementation of an optional server poster queue: original ready state
must not await extraction, missing poster renders a static placeholder without video
preloading, one extraction at a time, bounded execution/output, durable derived
ownership and retry policy, cleanup coordination and original publication bytes
preserved. Package sources and license obligations and select an appropriate
supported release before distribution; the experimental version is not a release
maintenance decision. Rotation metadata and other accepted H.264 profiles still
need scoped integration coverage.

Validation was limited to the container experiment. No application suite rerun was
needed. Temporary probe files and tagged runtime images were removed after recording
results; shared build caches and preexisting images were preserved.
