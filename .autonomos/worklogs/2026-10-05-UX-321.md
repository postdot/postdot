# UX-321 — Incompatibility after a profile evolution

## Question

A channel profile activation flags a working draft `review_required` and leaves a scheduled manual publication that cannot be claimed for delivery. UX-321 asked what the **interface** does with that state, whether it distinguishes a saved draft from a publication cleared for delivery, which actions survive, whether the content is preserved, and whether the user has a **real path** to resolve the incompatibility rather than only meeting a refusal.

No contract, schema, publication rule or profile evolution logic was changed. No provider was contacted, no import or restore path was used, no draft was deleted.

## Method

Reused the isolated path already established in [UX-299](2026-10-05-UX-299.md): a publication with a selected execution target, a channel profile at version 1 (`title@/title`, `body_markdown@/body_markdown`, `media@/media`), a scheduled publication with a promoted target, then a profile evolution to version 2 where `primary_text` moves to `article@/article` and `body_markdown` moves to `/article/body`.

A temporary Playwright probe drove only the real interface (open publication detail, evolve the profile through the channel profile editor, read the editor) and read state back through the public publication API. The probe was deleted once the evidence was recorded.

## What the user is told

**Before the evolution**

| Signal | Value |
| --- | --- |
| Publication state | `scheduled` |
| Draft `reviewState` | `compatible` |
| Promotion action | `Update scheduled publication`, enabled |
| Channel customization disclosure | collapsed, no badge |

**After the activation returned 200**

| Signal | Value |
| --- | --- |
| Publication state | `scheduled` |
| Draft `reviewState` | `review_required` |
| Draft validation issues | 3 — `schema.required` `article`, `schema.boolean` at `/body_markdown`, `schema.additionalProperties` |
| Channel customization disclosure | **automatically opened** |
| Badge in the disclosure summary | `Review required` |
| Source field | `Selected revision body.` with `Check this value.` |
| Validation panel | `The profile reported validation issues` and `Validation details` |
| Promotion action | `Update scheduled publication`, **disabled** |
| Message beside the action | `Resolve the profile validation issues before applying this draft to the selected target.` |
| Selected target content | preserved, unchanged |
| Draft content | preserved, unchanged |

So the block is not silent. The interface opens the affected section on its own, badges it, lists the profile's own validation errors, keeps the offending source visible, disables the promotion action and states the reason next to it. The published revision and the working draft both survived the activation byte for byte.

## Which actions remain available

Only `Cancel publication` and the disabled `Update scheduled publication`. The configured channel editor and the source editor stay interactive, and the advanced JSON editor is present, so the user is not locked out of the draft.

## Does a saved draft differ from a publication cleared for delivery

Yes, and the interface reflects it: editing the draft re-enables the action and reports `Saved`, but the action still means *apply this draft to the selected target*. Nothing in the interface claims the scheduled delivery is ready. The refused claim path recorded in UX-299 (`Due manual publication not found`) is the server-side confirmation of the same separation.

## Does the user have a real repair path

Yes, and it works. Typing into the configured `body_markdown` field of the channel editor and letting it save:

| Signal | Value |
| --- | --- |
| Draft `reviewState` | `compatible` |
| Draft validation issues | 0 |
| Draft content | `{"body_markdown":"Repaired body under v2.","media":[],"title":"Original headline"}` |
| Promotion after the repair | `200` |
| Selected target content | still the original revision |

## What the repair actually does — the open decision

The repaired content was written to a **top-level** `body_markdown`, not to `/article/body`. That shape is invalid under the activated version 2, which requires `article` and forbids additional properties, yet it validated as `compatible`. The draft was therefore assessed against **version 1**, its own `profileVersionId`, which never moved.

In other words the user's repair does not adopt the evolution: it restores the previous shape under the previous profile and clears the flag. The promotion then succeeds, so a channel running version 2 can be handed a version 1 payload, and the interface says nothing about it. The `Check this value.` marker and the `Review required` badge describe a validation problem, not the actual cause, which is a profile version that did not follow the channel.

Closing that requires a business rule, so it is presented rather than implemented.

### Options

1. **Keep the current behaviour and make it explicit.** The draft keeps its own profile version by design; a flagged draft is restored by re-editing under that profile. Presentation only: one message next to the badge stating that the channel profile changed and that the draft is still assessed against version *N*. Smallest change, matches observed behaviour, but leaves the silent version-2/version-1 payload.
2. **Require adoption.** While a draft is flagged, refuse promotion and require the draft to be migrated or re-authored under the activated version before the selected target can be updated. Needs a migration or re-approval rule, and a decision about which pending work is in scope.
3. **Choose the handling at activation time.** The owner picks, per activation, whether affected drafts are migrated, flagged for re-authoring, or left untouched. Needs the choice persisted and displayed, and a rule for pending targets already on the publication.

## The two UX-299 precisions, carried forward

1. **A draft patch was accepted carrying content invalid under its own reported profile version.** Confirmed here as the mechanism behind the repair: the editor writes to the draft's profile bindings, and the draft's `profileVersionId` still points at version 1. This is an editable-path question, not historical inspection.
2. **The data cannot distinguish "the draft was not migratable in that state" from "it was flagged for review instead of being wired".** Still unresolved, and now load-bearing: option 2 and option 3 above both need that distinction to be defined before either can be implemented.

## Refusals encountered, recorded rather than circumvented

- Profile identity change — `A channel profile draft cannot change profile identity from devto`.
- Binding id rename — `Unknown binding ID body_markdown; Unknown binding ID media`.
- Delivery claim while flagged — `404 Due manual publication not found` (from UX-299, re-confirmed).

## What was not verified

- Which of the two evolution impacts applies to a flagged draft, per UX-299.
- Capability-only evolutions and evolutions that touch neither the working draft nor the selected target.
- An activation racing a promotion.
- Whether the repaired version 1 payload is later rejected at the provider boundary; no provider was contacted.
- Import and restore paths.

## Cost

Four probe runs at 13.8 s each, plus the harness iterations needed to stop reading a contenteditable with `inputValue` and to fix two wrong assumptions in the probe itself (a `Needs review` locator, and a review-mention scan sampled after the repair had already cleared the flag). No production file was modified; the probe was removed.
