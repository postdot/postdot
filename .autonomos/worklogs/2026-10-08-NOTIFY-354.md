# NOTIFY-354 — Optional publication outcome email alerts

Base: `4275ccc87`. Status: complete; full integration and container recovery passed.
Owner accepted optional email alerts and explicitly chose personal enrollment per project, to the verified account email.

## Existing foundation

ADR-038 and ADR-039 are accepted: external delivery is independent of inbox
preferences, recipient-owned, projected transactionally from the journal, with
separate cursors, immutable snapshots, leases and effect ambiguity. The delivery
store exists but is not instantiated by production. The existing notification
projection runtime is event-driven through post-commit project wakeups. SMTP is
already configured for authentication email in the API email module; rendering
belongs in packages/email.

The delivery store resolves human actors and active destinations. Its projection
query does not independently prove current access; historical actors survive
membership removal. The production feature must use current AccessStore
permission checks before enabling and before dispatch, including group grants.
Do not treat preserved actors as current membership. Existing inbox preferences
are account-global in the current popover; project email preferences need an
explicit scope rather than silently reusing the global inbox toggle.

## Accepted product boundary

Personal opt-in per project, to the account's current verified email address.
Subscribe to failed and ambiguous publication outcomes only; disabled by default.
No arbitrary address input or automatic enrollment of all project members.
Use the existing SMTP configuration, not a new service or environment switch.
Missing SMTP is explained without allowing enrollment. An existing subscription
can still be disabled after SMTP becomes unavailable or verification is lost.
The owner explicitly selected this policy in the session question.

## Implementation sequence

1. Resolve the recipient policy and record only the accepted behavior.
2. Add a short HTML/plain-text alert using the existing email layout, with fixed
   outcome text and a publication URL based on the configured web origin. Do not
   include publication bodies, provider errors, secrets or arbitrary HTML.
3. Wire the existing outbox to one SMTP executor. Wake after committed facts,
   drain pending work on startup, schedule only the next due retry, and drain
   during graceful shutdown. No fixed polling or additional runtime.
4. Add human-session preferences and delivery availability in the existing
   notification surface. Use the current verified account address at dispatch;
   a removed member, disabled destination or unverified address cannot send.
5. Verify opt-in, terminal failure/ambiguity events, no duplicate projection,
   access removal and SMTP ambiguity using isolated deterministic tests, plus
   one local Mailpit journey. Run the required integration control once after
   the full implementation is stable, not after each intermediate edit.

## Delivered implementation

The database email store composes AccessStore, the existing outbox and account
lookup. Enrollment captures the journal sequence in one immediate transaction;
old facts are excluded without advancing the shared projection cursor. Disabling
keeps destination/delivery history. Reenabling creates a fresh destination and
future-event boundary, leaving the disabled backlog inert. Address, verification,
banned-account status and live project access are checked before dispatch and
again after rendering. Recipient ownership never follows the event actor.

The API exposes human-session-only GET/PATCH email-alerts per project, with the
shared project authorization macro. It exposes availability, verification,
current address, enrollment and the last active-destination delivery state.
No credential or raw SMTP/provider message is returned. The existing inbox
preferences remain independent. The popover offers the existing Better Auth verification request to accounts
created before SMTP was configured, then allows checking verification. It
identifies the selected project,
allows personal opt-in, explains prerequisites and displays a failure/uncertainty
notice. English and French copy is present.

The runtime reuses bounded notification projection and NextEventScheduler.
An explicit transport scope isolates its cursor, candidates, due claims, expired
lease recovery and scheduler timing from other outbox transports. A regression
proves both projections see their own fact and email cannot claim or recover a
foreign transport row.
Post-commit wakeups project facts; startup resumes durable work. Scheduling
includes unexpired running leases so a restart does not strand them when they
expire. SMTP effects use the shared fenced executor, bounded retries for explicit
4xx rejection, terminal failure for explicit 5xx rejection, and ambiguity for
unconfirmed socket outcomes. Nodemailer labels even socket timeouts CONN; that
label is not evidence that the effect never began. Raw error text is discarded.
The shutdown worker drain also awaits the optional email runtime before SQLite
closes. There is no polling, new runtime or new dependency.

Email rendering reuses React Email and the established layout for HTML and plain
text, with generic outcome wording and a publication link. It excludes post
content and provider error text. SMTP acceptance is not a promise of final inbox
delivery; unknown post-effect outcomes are not automatically resent.
