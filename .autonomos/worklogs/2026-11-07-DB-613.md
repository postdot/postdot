# DB-613 — Transfer between storage profiles

Owner decisions (2026-11-07): plan approved — two-step export/import through an
engine-neutral directory rather than a direct copy; the media transfer leaves the
source store untouched; source store described by `SOURCE_`-prefixed variables.

## Delivered

- `@postdot/db` `transfer/`:
  - `exportDatabase`: `manifest.json` (format, version, applied migrations with
    checksums, per-table columns/rows/SHA-256, generated-key high-water marks) and
    `tables/<name>.ndjson`. Values are encoded from the declared column type (blobs as
    base64; unsupported values refused), rows ordered by primary key in byte order
    (`collate "C"` on PostgreSQL), so SQLite and PostgreSQL export identical bytes.
    The export runs in one read transaction and refuses a database that is not at
    this release's migrations.
  - `importDatabase`: refuses a non-empty target (tables other than Postdot's, or rows
    beyond the migration seed in `instance_state`); migrates it; requires identical
    migrations and tables/columns; in one transaction suspends user triggers (SQLite:
    drop and recreate from `sqlite_master`; PostgreSQL: `disable trigger user`), defers
    foreign keys (PostgreSQL inserts parents first for the 11 non-deferrable keys),
    loads rows, restores the journal sequence (`sqlite_sequence` / `setval`), checks
    foreign keys, then re-exports every table and commits only on identical checksums.
  - `transferMedia`: refuses a destination with the source's store ID and any row in a
    third store; copies each referenced object (originals, previews, avatars; live
    states required, unfinished uploads optional) with size/SHA-256 checks against the
    database, refuses to overwrite a different destination object, reads back each
    copy, then rewrites `store_id` in `media_representations`, `user_avatars` and
    `resource_cleanup_objects` in one transaction. It can be run again; the source is untouched.
  - `openQuiescedDatabase`: SQLite runtime lock and recovery-hold refusal; PostgreSQL
    instance and leader advisory locks plus refusal while another client session is
    connected.
- API CLI: `export`, `import`, `media transfer` (with `--help`), configured target and
  `SOURCE_POSTDOT_MEDIA_*` source (`createPostdotTransferConfig`); a SQLite file created
  by a failed import is removed.
- Bug fixed from DB-611: the image and `compose.yaml` always set `DB_FILE_NAME`, and the
  configuration refused it next to `POSTDOT_DATABASE_URL`, so the documented PostgreSQL
  setup could not start from the image. The URL now takes precedence.
- Docs: new page "Move between SQLite and PostgreSQL" (operations); PostgreSQL and
  installation pages link to it instead of "not supported yet".
- CI: the PostgreSQL job also runs `scripts/profile-transfer.test.ts`.

## Evidence

- `packages/db/src/transfer/transfer.test.ts`: SQLite→SQLite, SQLite→PostgreSQL,
  PostgreSQL→SQLite, PostgreSQL→PostgreSQL round trips over a fixture with journal
  facts, trigger-derived bindings, an archived channel (its children would be rejected
  by triggers), encrypted blobs, media with previews and an avatar: re-export identical,
  schema equal to a fresh migration, journal continues at high-water + 1. Refusals:
  non-empty target, tampered file (target untouched), other schema version, foreign-key
  break (full rollback, triggers intact). Media: copy and relocation, no-op rerun,
  corrupted source object, conflicting destination object, same store ID.
- `scripts/profile-transfer.test.ts` (real CLI, three servers): SQLite + local → export →
  import into PostgreSQL → media transfer to an S3 stand-in → server on PostgreSQL + S3
  reads the same project and avatar with the original session cookie; refusal beside a
  running server on both engines; then PostgreSQL + S3 → SQLite + local and the same
  checks. Negative control: without the media transfer the avatar is 404 and the test fails.
- Development database copy (`apps/api/postbot.sqlite`, 314 rows, 70 tables):
  SQLite → PostgreSQL → SQLite re-exports byte-identical; import 268 ms.
- Suites: db 365 (SQLite) / 380 (PostgreSQL), auth 20/20, API 568/568, scripts 117 pass
  3 skipped, PostgreSQL script tests 3/3; `check:quick`, docs build and link check pass.

## Limits

- Export and import hold whole tables in memory; fine for the alpha's sizes, to stream
  if a large installation needs it.
- Objects queued for cleanup are relocated, not copied: their bytes stay in the old store,
  which the operator deletes after verification.
- No direct database-to-database copy; the export directory is the hand-off.
