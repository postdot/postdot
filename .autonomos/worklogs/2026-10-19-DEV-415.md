# DEV-415 — Container startup termination with the production image

<!-- cspell:ignore opencode xhigh -->

## Plan

1. Establish the parent ground truth with real images built from the production bundle.
2. Register a bounded delegated mission for the container-level check in the CI container script, and review it.
3. Execute the check in the canonical checkout against the corrected and the pre-correction image, integrate, and clean up.

## Context

DEV-414 proved the production guarantee as a measurement: the corrected bundle releases the runtime marker when it is terminated during its startup, and the pre-correction bundle does not. That measurement was made by the orchestrator with an ad hoc script, so nothing in the repository keeps it true.

`scripts/production-container-recovery.ts` is the CI entrypoint for the production image (`bun run test:container:recovery`, and the `container-candidate` workflow). It already proves that a serving container stops gracefully with exit 0 and a released marker, and that a SIGKILLed container keeps the marker and refuses a restart. It does not cover the startup window.

## Parent ground truth, established before the mission

Two local images built offline from the local `oven/bun:1` base, with the production bundle, the real migrations and a minimal `public/index.html`, and the same `ENTRYPOINT ["bun", "/app/postbot.js"]` and `STOPSIGNAL SIGTERM` as the repository `Dockerfile`:

| Image | `docker stop --timeout 10` | Container exit | Runtime marker | Container logs |
| --- | --- | --- | --- | --- |
| pre-correction bundle | 10072 ms, the whole grace period, then SIGKILL | 137 | **retained** | empty |
| corrected bundle | 125 ms | 0 | released | the orderly drain |

The empty logs of the defective run are the proof of the PID 1 behaviour: the kernel does not apply the default action of SIGTERM to PID 1, so without an installed handler the stop signal is ignored entirely and only the forced kill ends the container.

The check needs no published port: it observes the runtime marker inside the mounted data directory and the container's exit status. Running it with `--network none` therefore keeps it hermetic and independent of the host's network.

## Delegation decision

The standing owner direction in the root `AGENT.md` requires a bounded delegation to MiniMax M3.1 Flash Free through OpenCode for each subsequent task, with the highest advertised reasoning variant: `opencode/minimax-m3.1-flash-free` with `variant=max`.

The orchestrator keeps the container execution, the review, the integration and the cleanup. The delegated mission implements the check inside the existing container script, together with a focused mode so the check can run on its own against a supplied image.

## Implementation mission

- Owner: parent orchestrator. Worker: delegated MiniMax M3.1 Flash Free mission in a dedicated worktree.
- Allowed writes: `scripts/production-container-recovery.ts` only.
- Forbidden: every other file, product code, the `Dockerfile`, configuration, dependencies, lockfiles, governance, commits, merges, `main` writes, further delegation, browser and E2E runs, external network calls, and any change to the fail-closed runtime-marker policy.
- Acceptance: a container stopped while the API is still starting must exit 0, must release the runtime marker, and must show the orderly drain in its logs; a focused mode runs that check alone against a supplied image; the default mode keeps the existing scenario and adds the new check; every disposable data directory is removed with the test root, and a retained marker is only ever observed, never deleted by another path.
- Stop: the scoped uncommitted diff, the exact check results, the measured durations and exit codes for both the corrected and the pre-correction image, and the limitations. The parent executes the container validation.

## Round 1 and round 2

The worker delivered the startup-termination check and a focused mode, `POSTBOT_CONTAINER_TEST_SCENARIO=startup-termination`, in `scripts/production-container-recovery.ts`. The parent reviewed the whole diff and accepted the structure, the assertions, the failure messages, the focused mode, the container cleanup and the discipline that a retained marker is only ever observed.

The parent agreed with the worker's own limitation 1 and required it fixed: the check could not prove that the termination landed inside the startup window, because the API logs nothing when it begins serving, so on a loaded runner the check could silently exercise the serving-stop path instead. The parent measured a way to make the window observable: the API can be probed from inside the container, because `--network none` still gives the container a loopback interface, and 45 ms after the marker the probe answered `NOT_SERVING`.

The worker implemented the probe as a bounded attempt loop, and corrected the parent's own probe form: an image that answers the probe with HTTP 500 must count as `serving`, because a container that answers has passed `listen()`. The check now probes from inside the container, discards an attempt whose probe saw the API already serving, retries on a fresh container and a fresh disposable data directory, and fails loudly when no attempt lands inside the window. The elapsed time from the marker to the container's exit is reported, and the focused mode is documented in `.autonomos/archive/root-documentation-2026-10-25/source/docs/deployment/release-policy.md`.

## Parent acceptance

Parent verification in the canonical checkout, with the revised candidate and a faithful production-like image (the bundle built and run with bun 1.4.2, the version the repository `Dockerfile` pins):

- Focused mode with the corrected image: exit 0. "The production container stopped during the API startup exited 0 in 0.1s, released its runtime marker and logged its own orderly drain. The runtime marker appeared 113ms before the container exited, and the in-container probe confirmed 51ms after the marker that the API was not serving yet."
- Focused mode with the pre-correction image: exit 1, "exit code 137 after 10069ms. Exit code 137 means Docker SIGKILLed the container after the stop grace period instead of observing an orderly shutdown; as PID 1 the container ignored the stop signal, so the runtime marker survives in the data volume and the next deployment of that volume is refused until an operator removes the marker."
- `bun run check:quick`: format, lint, spelling and typechecks across the workspace pass without bypass.
- The full scenario could not be run end to end in this environment: the sandbox has no bridge networking, so the published-port steps of the existing scenario fail. The default-mode wiring was reviewed in the diff and by the worker up to the packaged poster probe; the CI image run remains the confirmation.

Residual limitation, stated by the worker and accepted: the probe is a sample. If the API began serving between the sample and the signal delivery, the check would exercise the serving-stop path without detecting it. The measured slack is about 55 ms.

The disposable images, the temporary bundles and the reproduction scripts were removed as well. No normal database, media root, owner credential, owner `.env` or existing service was touched.
