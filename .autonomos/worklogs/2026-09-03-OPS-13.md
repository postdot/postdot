# OPS-13 — Expose truthful liveness and readiness signals

- Date: 2026-09-03
- Status: completed
- Scope: API health routes, scheduler and media-maintenance runtime state,
  production serving, and operational documentation
- Related issue: [ISSUE-012](../ISSUES.md#issue-012-expose-truthful-runtime-readiness)
- Decision: [ADR-029](../decisions/ADR-029-separate-liveness-and-readiness.md)

## Objective

Replace the unconditional health claim with a small, explicit contract that
distinguishes an HTTP process that is alive from a single-process Herald
instance that is ready to execute durable work.

## Accepted boundary

- `/health` remains a public liveness check and does not depend on runtime
  readiness.
- `/ready` is a public readiness check for the SQLite database, publication
  scheduler, and media reconciliation runtime.
- Scheduler and maintenance state remain in their owning runtimes; the health
  module only observes and normalizes their public state.
- No metrics backend, heartbeat table, background monitor, or restart policy is
  introduced for this task.

## Evidence and decisions

The publication scheduler already exposes `idle`, `started`, `running`,
`stopped`, and `failed` states. Media reconciliation now exposes `idle`,
`started`, `running`, `recovering`, `stopped`, and `failed` without changing its
interval or error-recovery behavior. A database probe uses the existing Bun
SQLite client and returns only a stable status, never the underlying exception.

## Implementation

- `/health` remains a public liveness route returning 200 when the HTTP process
  can answer.
- `/ready` probes the live Bun SQLite client and observes the publication
  scheduler plus media reconciliation runtime. It returns 200 only when the
  database is reachable, the scheduler is started or running, and media
  maintenance is started or running; a recovering maintenance loop remains
  not ready. Otherwise it returns 503 with non-secret check states.
- The API composition root passes the real worker scheduler and media runtime
  into the health module before starting the listener. Production static serving
  treats `/ready` as a server path, so a missing readiness route cannot be
  mistaken for the SPA.
