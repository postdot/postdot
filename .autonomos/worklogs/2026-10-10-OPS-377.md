# OPS-377 — Controlled restart after restoration

Base: `cf832bd01`. Owner approved explicit resumption after restoration.

## Implementation

- Database-only and complete restore persist a restricted recovery marker beside
  SQLite before replacement. It survives database rollback and process restart.
  Each restore refreshes the acknowledgement token. Invalid marker content stops
  startup; an old administrator view cannot acknowledge a different restore.
- Normal startup without a marker is unchanged. Recovery startup skips initial
  media reconciliation and does not start publication, external email or media
  cleanup runtimes. Local notification projection remains available.
- The common HTTP request boundary rejects mutations with `503 recovery_hold`,
  except email/password login, logout/session access and explicit resumption.
  OAuth callbacks and account verification are also refused. SMTP dispatch has a
  separate guard covering auth messages, alert messages and SMTP tests.
- A session-only instance administrator endpoint acknowledges the current token
  and starts the suspended runtimes. Administration requires a checked statement
  about outstanding work and repeated deliveries; refused resumption stays inline.
  A dashboard notice explains the hold to other users.
- Readiness permits the deliberately idle executors during recovery, exposing
  `checks.recovery: held`; genuinely failed runtime states remain not ready.
- Offline `recovery hold`, `recovery status`, and `recovery resume --confirm`
  support external database restores and unavailable restored accounts. Changes
  require the runtime lock and refuse an active server.

## Responsibility and limits

No scheduling, retention, replication engine, provider reconciliation or new
service was introduced. Resumption acknowledges risk: it does not establish that
restored pending work has never been delivered. Cancellation and other application
writes remain suspended during inspection in this first version. The operator
must inspect provider-side state before acknowledging; no automatic deduplication
across a database rollback is promised.

The marker is outside the snapshot to avoid losing the hold during database
replacement. External restores must explicitly enter recovery before startup;
Herald cannot infer them reliably from restored data. No configuration key or
provider credential was embedded in the marker or exposed in its public status.

## Evidence

- Existing database and media restore tests now assert automatic recovery entry.
- Durable-marker tests cover database replacement, repeated entry, new restore
  token, stale acknowledgement, and malformed state.
- API integration covers read access, blocked writes, current administrator role,
  refused member resumption, stale token, one successful acknowledgement and
  restored creation afterward. OpenAPI inventory includes the new routes.
- SMTP tests prove zero transport calls while held and normal sending after release.
- Offline tests cover active-runtime refusal and mandatory confirmation.
- Readiness tests distinguish an intentionally idle recovery runtime from failure.
- Browser scenario at 390 px covers required acknowledgement, visible refusal,
  successful resumption and overflow. Recovery responses are intercepted for this
  UI proof; real server authorization and persistence are proved separately.
