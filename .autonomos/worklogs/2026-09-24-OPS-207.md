# OPS-207 — Add self-hosted Prometheus metrics

## Accepted boundary

- ISSUE-122 and the owner-approved direction call for an in-process, self-hosted Prometheus scrape endpoint. No hosted monitoring service is required.
- The deployment operator owns scrape cadence, retention, dashboards, and alert thresholds.
- Metrics must remain operational and bounded; application identifiers must not become labels.

## Implementation

- Added `@prometheus-io/client` 0.16.1 and an unauthenticated `GET /metrics` route using its Prometheus text registry and content type.
- Added process CPU time, memory, and uptime measurements, plus a one-hot scheduler state gauge and worker run count/duration metrics. Worker labels are restricted to the fixed `success` and `failure` outcomes; no user, workspace, project, channel, or provider identifiers are emitted.
- Verified that the library's default collector reports a Node.js runtime version under Bun. To avoid publishing misleading runtime data, the implementation uses the client primitives with Bun's `process` APIs for CPU, memory, and uptime instead.
- Documented the endpoint and a minimal scrape target. Because the endpoint is intentionally unauthenticated, the guide requires deployment-level network restriction.
