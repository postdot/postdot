# PROVIDER-69 — Built-in provider execution boundary review

- Date: 2026-09-04
- Status: implementation in progress; integration pending
- Task: `PROVIDER-69`
- Issue: `ISSUE-027`
- Review mode: orchestrator read-only inspection
- Canonical base: `b0027ac53984d63ac98a963a709932b3ef2661a2`

## Scope and method

The assigned read-only worker did not produce a terminal report. Its worktree was
cleaned without accepting any output. This report therefore contains only findings
verified in the canonical checkout. No provider, worker, database, or governance
file was changed for this review.

The review maps the current workflow/provider responsibilities, evaluates the
smallest credible boundary, and identifies what must remain outside a provider
adapter. It does not authorize adding another provider or introducing a universal
plugin language.

## Executive finding

The repository already has a useful provider seam: LinkedIn owns typed publisher
interfaces, provider HTTP details, response classification, and a channel profile
with a versioned built-in execution contract. The remaining problem is that the
workflow worker still performs provider selection, LinkedIn credential refresh,
destination validation, content extraction, media orchestration, and reconnect
handling in one central function.

This is not an immediate correctness failure. Existing LinkedIn behavior is covered
by real worker tests and custom HTTP is already a distinct execution path. It is a
structural risk before adding another built-in provider: a new branch would enlarge
the worker hotspot and could accidentally reuse assumptions that belong only to
LinkedIn.

## Responsibility map observed in the current code

### Generic workflow ownership already in place

- `apps/api/src/modules/workflow/worker.ts:82-151` composes the durable workflow
  store, scheduler, retry policy, claim token creation, media delivery store, and
  provider execution callback.
- `packages/core/src/executor.ts:4-25` defines the generic
  `ExternalEffectOutcome` union: published, retryable failure, permanent failure,
  and ambiguous outcome.
- `apps/api/src/modules/workflow/worker.ts:184-191` enforces the claim fence and
  loads the execution target through the project-scoped publisher store before an
  external effect.
- The worker keeps the durable workflow lifecycle and passes the result back to
  the core executor. These are appropriate generic responsibilities and should
  remain outside provider modules.

### Provider-specific decisions still centralized in the worker

- `apps/api/src/modules/workflow/worker.ts:154-175` defines
  `performExternalEffect` with LinkedIn publisher types, custom HTTP transport,
  LinkedIn OAuth configuration, and publisher persistence services in one input.
- `apps/api/src/modules/workflow/worker.ts:193-201` selects custom HTTP or rejects
  every non-LinkedIn built-in provider with a hard-coded provider check.
- `apps/api/src/modules/workflow/worker.ts:204-251` resolves LinkedIn credentials,
  decides whether they are expired, refreshes them through the LinkedIn OAuth
  configuration, persists replacement tokens, and marks reconnection on failure.
- `apps/api/src/modules/workflow/worker.ts:254-260` validates access-token presence
  and converts the generic destination to `LinkedInDestination`.
- `apps/api/src/modules/workflow/worker.ts:263-290` chooses LinkedIn text versus
  image publishing and applies LinkedIn-specific reconnect behavior to outcomes.
- `apps/api/src/modules/workflow/worker.ts:293-309` extracts LinkedIn commentary
  from the target content.
- `apps/api/src/modules/workflow/worker.ts:311-510` performs the LinkedIn-specific
  one-image upload and post sequence, including provider media delivery state.
- `apps/api/src/modules/workflow/worker.ts:512-527` validates LinkedIn member and
  organization destination identifiers.

The worker is therefore a valid orchestration owner but an increasingly large
provider dispatch owner. The issue is the responsibility concentration, not the
existence of provider-specific code.

### Existing provider module boundary

- `packages/linkedin/src/contract.ts:26-65` owns LinkedIn destinations and typed
  provider outcome codes while extending the generic external-effect outcomes.
- `packages/linkedin/src/contract.ts:84-134` exposes typed text and image publisher
  contracts; the access token is an execution input, not persisted by this package.
- `packages/linkedin/src/publisher.ts:28-85` and `:89-268` own LinkedIn HTTP
  requests, timeouts, payload creation, response handling, and provider-specific
  failure classification.
- `packages/linkedin/src/channel-profile.ts:3-59` owns the built-in channel
  content schema, capability declaration, and versioned execution identity
  (`contractId: 'linkedin'`, `revision: 'member-post-v2'`).

This separation is worth preserving. A new boundary should compose these existing
contracts rather than replace them with an untyped provider framework.

### Execution target and persistence boundary

- `packages/db/src/publisher-store.ts:83-107` exposes a fully pinned
  `PublisherExecutionTarget` containing the project, execution revision, profile,
  content, destination, credential identity/state, endpoint/authentication data,
  and pinned media references.
- `packages/db/src/publisher-store.ts:758-785` loads that target only with a job
  claim token and verifies that the pinned media reference count is complete.

The database store is already the source of truth for the immutable execution
context. A provider adapter should consume a narrow execution context derived from
this target; it should not take ownership of database schema or publication state.

### Custom HTTP is a separate execution kind

- `apps/api/src/modules/workflow/worker.ts:193-198` routes
  `CUSTOM_HTTP_PUBLISHER_KIND` to `performCustomHttpEffect`.
- `apps/api/src/modules/workflow/worker.ts:529-590` validates the declarative HTTP
  profile, connection, secrets, and pinned media before delegating to the custom
  transport.

Custom HTTP should remain a runtime-defined execution path. It should not be forced
into a built-in provider registry, and a built-in adapter must not become an escape
hatch for arbitrary scripts or network behavior.

## Credible alternatives

| Direction | Benefit | Cost or risk | Assessment |
| --- | --- | --- | --- |
| Keep central dispatch | Smallest immediate diff; current provider works | Worker hotspot grows; provider assumptions leak; harder isolated reviews | Acceptable temporarily, not a good boundary before the next built-in provider |
| Explicit built-in adapter port and registry | Small typed seam; provider ownership remains visible; incremental migration | Requires careful credential and media context design | Recommended |
| Universal provider DSL or strategy object | Appears extensible for many providers | Weakens type safety, hides provider semantics, duplicates the custom-channel problem | Reject without concrete evidence |
| Separate provider process/service | Isolates failures and scaling | Violates current single-process/self-hosting posture and adds coordination | No evidence justifies it |

## Recommended boundary

Introduce a small registry for code-owned built-in execution contracts. The registry
should be keyed by the versioned built-in execution identity, not by an arbitrary
string branch scattered through the worker. A provider adapter should own:

- matching its `contractId` and supported revision;
- provider-specific credential preparation, including refresh through a narrow
  injected credential port;
- provider-specific destination validation and content extraction;
- provider-specific sequencing such as LinkedIn image upload followed by post
  creation;
- mapping provider results to the generic `ExternalEffectOutcome` while retaining
  provider diagnostics and permanent/retryable/ambiguous distinctions.

The generic worker should retain:

- claim fencing and durable execution lifecycle;
- loading the pinned execution target;
- generic retry and completion semantics;
- media-reference integrity and provider-media delivery persistence where those are
  part of the shared execution invariant;
- explicit routing of runtime-defined custom HTTP execution;
- redaction, audit attribution, and error handling around the adapter boundary.

Channel profiles remain the owner of channel capabilities and target-content
validation. The registry must not become a second capability catalog, and it must
not infer project ownership from a user or authentication account. The adapter may
receive a narrow credential resolver/rotator interface, but the encrypted
credential persistence remains Postbot's project-scoped database responsibility.

The first implementation should register only the existing LinkedIn contract and
move behavior without changing its external semantics. It should be possible to
prove the seam with one provider before adding a second provider. Custom HTTP stays
outside this registry as its own execution kind.

## Unresolved contract details

These details need to be settled in the implementation design, but do not justify a
larger framework:

1. Whether the adapter receives a generic `PublisherExecutionTarget` or a narrower
   provider-neutral projection of it.
2. Whether provider media delivery reservation remains in generic worker code or is
   exposed as an explicit media execution capability for adapters with multi-step
   uploads. The current LinkedIn image path is evidence that a single “publish”
   method is not sufficient for every provider.
3. Whether credential refresh returns an updated access token only or a typed
   provider credential context with expiry and reconnect outcomes.
4. How the registry rejects an unknown contract, an unsupported revision, or a
   provider/profile mismatch. All must fail closed before an external request.

These should be resolved by the smallest typed port that preserves current
behavior, not by designing every future provider in advance.

## Existing verification to preserve

`apps/api/src/modules/workflow/worker.test.ts` already exercises the real worker
boundary for LinkedIn text at lines 195-369, LinkedIn image delivery at lines
480-679, custom HTTP at lines 679-976, and pinned-media validation at lines 977
onward. The new seam must retain or improve coverage for:

- successful LinkedIn text and image publication;
- access-token refresh and reconnect-required transitions;
- permanent, retryable, and ambiguous provider outcomes;
- claim-loss and retry behavior around the adapter call;
- custom HTTP webhook and mapped-media paths remaining unchanged;
- unknown built-in contract and unsupported revision failing before a network call;
- no access token or provider secret appearing in logs, audit events, or generic
  outcomes.

## Implementation sequence after approval

1. Write the accepted adapter/registry contract and responsibility map as a
   decision record before changing dispatch code.
2. Extract LinkedIn execution behind the contract with no database or schema
   changes.
3. Move or add focused contract tests, keeping the existing worker integration tests
   as regression coverage.
4. Run package-local checks, then the full repository gate and orchestrator-owned
   real-provider checks if the behavior remains eligible for them.
5. Only after the seam is stable, consider the next built-in provider.

## Review conclusion

PROVIDER-69 is ready for owner approval of the explicit adapter/registry direction.
The current implementation is not disposable, and no provider behavior was changed
by this review. The recommended refactor is incremental and should be rejected if
its concrete contract starts duplicating the custom-channel DSL or changing
publication semantics.

## Owner feedback

On 2026-09-04, the owner accepted the separation direction: built-in provider
execution should be extracted behind a small, typed, versioned adapter boundary.
ADR-033 records the accepted contract; implementation follows in the next pass.

## Implementation pass

The owner accepted ADR-033 after the review pass and PR #69 was merged into
`main` as `f60e97a7`. This implementation keeps the existing LinkedIn behavior
while moving provider-specific execution behind the accepted boundary.

### Changes

- Added a typed built-in provider registry keyed by `contractId` and `revision`.
- Registry resolution also requires the target provider and connection kind to
  match the adapter, and rejects duplicate identities during composition.
- Moved LinkedIn credential refresh, destination validation, text/image dispatch,
  provider media delivery sequencing, and provider outcome handling into a
  dedicated adapter module.
- Moved shared pinned-media verification and outcome constructors out of the
  workflow worker.
- Kept claim fencing, execution-target loading, generic retry/completion flow,
  custom HTTP routing, and custom HTTP media validation in the worker.
- Added registry contract tests and retained the real worker regression suite.

### Verification

- `apps/api`: typecheck, lint, format, registry tests, and worker tests pass.
- `packages/linkedin`: lint passes.
- The worker file is reduced from the provider-dispatch hotspot to generic
  orchestration plus custom HTTP execution; no database schema or migration was
  changed.
