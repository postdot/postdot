# EVENT-79 — Durable domain-event journal

## Objective

Turn Postbot's existing append-only audit persistence into an explicit, versioned fact
journal that future notification and analytics projections can consume without adding
a duplicate event history or weakening transactional state changes.

## Plan

1. Define and test a framework-independent domain-event envelope.
2. Add persisted event version, correlation, and causation context to `audit_events`.
3. Add an ordered, project-isolated journal reader for internal consumers.
4. Route existing audit inserts through the versioned persistence shape while keeping
   the public audit response compatible.
5. Validate schema migration, rollback behavior, ordering, and the full repository gate.

## Acceptance criteria

- Every new audit fact persists a positive event schema version.
- Optional correlation and causation identifiers survive a database round trip.
- A consumer can read facts strictly after an opaque SQLite append cursor in stable
  append order and cannot cross project boundaries.
- Invalid identifiers, versions, timestamps, and payloads fail before persistence.
- Existing state transitions still roll back when their fact cannot be appended.
- No notification inbox, external transport, broker, or event-sourced aggregate is
  introduced in this task.

## What was done

- Added the `DomainEvent` envelope and strict JSON payload validation to
  `@postbot/core`.
- Evolved `audit_events` with a positive event version, optional correlation and
  causation identifiers, and an indexed `AUTOINCREMENT` sequence.
- Added an internal event journal store with opaque cursors, project isolation,
  bounded reads, and transaction-compatible appends.
- Correlated automatic publication execution facts by durable job ID.
- Kept internal event fields out of the public audit response schema.
- Added a populated migration that preserves existing audit rows and stable order.
- Added regression coverage for envelope validation, ordering, project isolation,
  persisted cursor parsing, transaction rollback, migration backfill, and cursor
  non-reuse after project deletion.

## Key decisions

- Audit and domain events share one physical fact journal because duplicating the same
  transition in two append-only tables would add ambiguity and rollback surfaces.
- Notifications are not audit records: the next slice will persist recipient,
  presentation, acknowledgement, and deduplication state separately.
- `AUTOINCREMENT` is intentional despite its tiny SQLite metadata cost because project
  deletion can remove the current maximum row and must never make a durable consumer
  cursor skip a reused sequence.
- The application remains current-state based; this journal does not introduce event
  sourcing.
