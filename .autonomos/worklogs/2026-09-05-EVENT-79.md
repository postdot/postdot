# EVENT-79 — Durable domain-event journal

## Objective

Turn Herald's existing append-only audit persistence into an explicit, versioned fact
journal that future notification and analytics projections can consume without adding
a duplicate event history or weakening transactional state changes.

## Plan

1. Define and test a framework-independent domain-event envelope.
2. Add persisted event version, correlation, and causation context to `audit_events`.
3. Add an ordered, project-isolated journal reader for internal consumers.
4. Route existing audit inserts through the versioned persistence shape while keeping
   the public audit response compatible.
5. Validate schema migration, rollback behavior, ordering, and the full repository gate.

## Acceptance criteria

- Every new audit fact persists a positive event schema version.
- Optional correlation and causation identifiers survive a database round trip.
- A consumer can read facts strictly after an opaque SQLite append cursor in stable
  append order and cannot cross project boundaries.
- Invalid identifiers, versions, timestamps, and payloads fail before persistence.
- Existing state transitions still roll back when their fact cannot be appended.
- No notification inbox, external transport, broker, or event-sourced aggregate is
  introduced in this task.
