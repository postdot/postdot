# ANALYTICS-108 — First operational analytics read model and API

## Objective

Implement the first usable provider-neutral operational analytics surface behind
`GET /api/projects/:projectId/analytics`, following the accepted direction of
ADR-051. The implementation must distinguish current Herald state from ranged
historical facts and must not turn absent provider telemetry into zeros.

Branch: `feat/analytics-108-operational-read-model`

## Decision and implementation

Implemented a query-time hybrid read model:

- Current publication inventory and execution/workload snapshots come from
  project-scoped `publications` and `jobs` rows, observed at one UTC
  `observedAt` value.
- Historical publication, execution, retry, recovery, lifecycle, and latency
  measures come from the bounded, project-scoped `audit_events` journal.
- No analytics tables, migrations, materialized projections, collectors,
  brokers, provider polling, UI, or external dependency were added.
- The existing authenticated route now returns a versioned typed response with
  separate `current`, `historical`, and `coverage` sections.
- Publication creation, promotion, outcome, and automatic execution writers
  now attach only the minimal non-secret delivery mode, provider kind, and
  logical `runAt` metadata required for honest future historical reads. Missing
  provider snapshots remain `unknown`; automatic reconciliation copies the
  provider snapshot from the ambiguity fact that caused the reconciliation and
  does not rewrite history from current configuration.
- The historical journal scan now uses SQLite's row iterator. Facts are
  processed one at a time, so a 366-day window does not materialize every
  journal row in the JavaScript heap; only the deduplication and latency-pair
  state needed to produce the response is retained.

## Metric vocabulary and counting semantics

Current snapshot fields are not filtered by the historical range:

- `current.publications` counts current publication rows by exact lifecycle
  state, delivery mode, and `(channelId, provider, deliveryMode)` dimension.
  Manual publications always use provider `manual`; automatic rows without a
  current publisher use `unknown`.
- `current.executions.scheduled` is pending automatic job depth; `due` is its
  `runAt <= observedAt` subset; `running` is running automatic job depth;
  `retryablePending` is pending work whose latest supported execution fact is
  `retry_scheduled` (later claim/effect/recovery facts supersede it);
  `succeeded` and `failed` require the corresponding current job and
  publication states; `ambiguous` is current ambiguous publication depth with
  durable execution evidence.
- `current.workload` reports manual scheduled publications due now, ambiguous
  reconciliation depth, oldest due run, next run, future scheduled depth, and
  overdue depth. Manual scheduled publications are never counted as automatic
  executions.

Historical fields use supported facts whose occurrence time is in the requested
half-open interval `[from, to)`:

- `publications.created` is distinct publication ids with a supported
  `publication.created` fact.
- `publications.published` is distinct publication ids from canonical manual
  `publication.published`, automatic execution success, or reconciliation to
  `published`. Retries and repeated success facts cannot inflate it.
- `publications.lifecycleTransitions` counts supported facts entering a
  publication state, not distinct publications. Created uses its recorded
  state; promotion uses its recorded schedule state; ready, effect start,
  publication, execution outcomes, and reconciliation use their recorded
  target state. Missing target state is omitted and exposed as a coverage gap.
  Failed and ambiguous publication values are transition counts and therefore
  may include multiple transitions for one publication.
- `executions.claimed` counts supported claim facts once per `(project, job,
attempt)`; a pre-effect lease recovery is still a claim. `attempts` counts
  distinct effect-boundary facts, so a claim that recovers before the external
  effect is not an attempt.
- `executions.succeeded`, `failed`, `retryable`, `ambiguous`, and `cancelled`
  count one non-contradictory terminal outcome per attempt. Retry scheduling is
  not failure. `ambiguous` is the total of direct ambiguity and
  post-effect-boundary `ambiguity_recovered`; those two dimensions remain
  separately available. `claimRecoveries` is pre-effect recovery and
  `ambiguityRecoveries` is post-effect recovery.
- `retries.scheduled` equals accepted retry scheduling facts;
  `retries.rate = retryable / attempts` for the same event window and is null
  when there are no attempts; `attemptsPerPublication` divides effect-started
  attempts by distinct automatic publications represented in that window.
- Latency summaries contain only complete non-negative samples. Queue delay is
  effect start minus the durable attempt `runAt`; effect duration is outcome
  minus effect start; scheduled-to-outcome uses schedule points from durable
  creation, promotion, or retry facts; manual completion is manual schedule to
  manual `publication.published`. Missing endpoints never become zero.
- Daily buckets are keyed by the project IANA timezone and include the local
  date plus UTC start/end boundaries. Dimension keys use stable channel ids;
  channel names are display metadata and do not split historical totals.

The first filters are `channelId`, provider kind, and delivery mode. They are
applied independently to current rows and historical dimensions; there is no
arbitrary group-by or cross-project query surface.

## Range, authorization, retention, and performance

- All timestamps are UTC epoch milliseconds. Explicit `to` cannot be later than
  `observedAt`; `from <= to`; the maximum interval is 366 days. Omitted ranges
  default to the preceding 30 days ending at `observedAt`.
- Project access is checked through the existing project actor boundary before
  publication, job, publisher, or journal reads. Every read is bound to the
  requested project id; an inaccessible project follows the existing not-found
  behavior.
- There is no analytics-specific retention or rebuild job. The read model
  reruns against retained project rows and journal facts, and project deletion
  remains the lifecycle boundary.
- Prepared reads are bounded by project and historical time range, select only
  the requested publication subjects, and stream every fact through the
  accumulator so supported, unsupported, and unknown-version facts all
  contribute to coverage without an unbounded result array. The 366-day guard
  bounds history work; no migration was needed.

## Provider data boundary

This API contains only Herald operational facts: publication lifecycle, queue
depth, execution attempts, retries, failures, ambiguity, recovery, dimensions,
and durable latency. Likes, impressions, clicks, reactions, follower counts,
and similar provider-owned engagement values are intentionally absent. A future
provider module must expose its own scoped observation/provenance/freshness
model and explicit availability states; it must not mutate or become the source
of truth for this operational response.

## Coverage and known limitations

The response exposes supported event versions and data-quality counters for:

- unknown event versions and skipped facts;
- invalid metadata, missing lifecycle state, missing attempt metadata, and
  missing historical channel/provider dimensions;
- incomplete queue-delay, scheduled-latency, and effect-latency pairs;
- contradictory terminal outcomes, duplicate journal facts, and duplicate
  attempt facts.

Unknown versions are never coerced to version 1. All in-range publication facts
are read, while the accumulator counts and skips known-version actions outside
the supported action set so `unsupportedFacts` and `skippedFactCount` remain
truthful. Historical facts written before this change can have unknown provider
or delivery dimensions, missing logical run times, and incomplete latency pairs;
the response reports those gaps rather than joining current publisher
configuration to rewrite history. Automatic reconciliation now retains the
provider snapshot from its originating ambiguity fact when that fact contains
one; legacy ambiguity facts without it remain unknown. Percentiles, histograms,
provider engagement, and current-state history beyond the journal contract
remain deferred.

## Follow-up recommendations

Create a separate centrally assigned follow-up task to standardize or backfill
immutable provider/run-time metadata for older journal facts, benchmark this
query-time reader with representative project history, and decide whether a
versioned projection is justified by measured latency or memory. A separate
provider-specific task can define engagement observation contracts only after a
provider API, authorization, freshness, and retention policy is selected.
