# DB-614 — Recover missed wakeups and measure the worker path

## Scope and decision

Owner approved wakeup hardening without a new dependency, PostgreSQL extension
or queue service, and requested capacity measurements. npm publication remains
with another agent. Work is isolated on `fix/postgres-wakeup-recovery`.

PostgreSQL notifications remain low-latency hints. Every subscriber also runs
one safety recovery pass 30 seconds after the previous pass completes. Listener
reconnects request the same recovery, coalescing requests during an active pass.
Callbacks return their asynchronous work, errors are reported and the next pass
still runs, and close cancels queued work and drains an active pass. API recovery
refreshes subscribed project journals and persisted email settings; only the
leader runs notification projection, worker planning, previews and email planning.
Shutdown suppresses new API recovery work.

The interval is not a hard delivery deadline: query time, a busy event loop and
an active recovery pass add latency. Ephemeral draft signals are not reconstructed.
This does not reset a scheduler already in its existing failed state after an
execution or planning failure, nor claim to recover from an unavailable database.
SQLite keeps its existing in-process coordination.

## Failure evidence

- Real PostgreSQL rejects an oversized `work` NOTIFY. With no successful signal
  or reconnect, the elected leader's previously idle `NextEventScheduler` finds
  a committed row on its safety pass and processes it once.
- Negative control: moving the safety pass outside the test's deadline produces
  the expected failure (zero executions). Restoring recovery passes.
- Unit checks cover retry after a failed recovery callback, coalesced reconnects,
  non-overlap, shutdown drain, queued cancellation and no work after close.
- Existing real-server checks pass for PostgreSQL singleton enforcement, two
  servers, cross-instance streams and leader takeover after SIGKILL.

## Reproduce measurements

Use an isolated test server where the supplied PostgreSQL role can create and
remove disposable databases. Never run load probes on a production/shared server.
Both scripts create and remove their own databases. Without the PostgreSQL
variable, the workflow probe measures SQLite only.

```sh
POSTDOT_TEST_POSTGRES_URL=postgres://postgres@127.0.0.1:5432/postdot \
  bun scripts/benchmark-workflow.ts --samples 30 > workflow.json
POSTDOT_TEST_POSTGRES_URL=postgres://postgres@127.0.0.1:5432/postdot \
  bun scripts/benchmark-coordination.ts > coordination.json
```

Workflow cases use the real persistence port, migrations, claim, target validation,
effect-start and completion/audit pipeline. Effects are synthetic (0 or 100 ms).
Each case starts with 100, 1,000 or 10,000 due jobs in a fresh file/database.
Only 30 attempts are measured; there is no warmup. By default both engines run
`ANALYZE` after seeding. Use `--cold-statistics` to omit it and reproduce the
fresh bulk-insert case. Raw sample durations preserve
the effect of cold SQL plans. The probe measures a burst drain, not sustained
arrivals, full HTTP traffic, media, provider rate limits or network failures.
CPU/RSS describe the Bun client, not the PostgreSQL server. Initial scheduler
planning and API admission/fairness queries are outside the executor measurement.

All jobs share one project/channel. The API currently admits one active task per
project and at most two projects globally. Four-consumer cases deliberately
bypass that admission policy to expose contention; they are not the current API
worker configuration. Their serialization failures must not be presented as
failures of supported production admission.

Coordination cases send bursts of 1, 100 and 1,000 signals between two clients,
measure takeover after graceful leader release, and commit a marker without
publishing any signal. The last case measures the periodic recovery using its
production 30-second interval. It does not measure crash detection or cross-region
latency. The existing server test separately covers a hard process crash.

in a local disposable Docker container with fsync and synchronous_commit enabled,

measurements, not a cross-machine engine ranking or a production sizing promise.

Without an explicit ANALYZE after bulk insertion, the PostgreSQL 10,000-job case
has p50 142.60 ms but p95 16110.73 ms. Its raw samples include
four initial calls around 16 seconds, followed by substantially faster calls.
The statistics-controlled rerun materially changes that tail. This identifies
planner/statistics sensitivity to investigate with EXPLAIN; it does not prove a
specific JIT cause or a universal 10,000-job limit. Automatic database maintenance remains
at server defaults and may refresh statistics during the cold run. See ISSUE-195.

Four competing consumers on the same project show exhausted serialization retries
in PostgreSQL (7/30 attempts with a zero-ms effect; 4/30 with 100-ms effects in
the statistics-controlled run). Pending work remains in the database. These
stress cases bypass current API admission; do not infer a production concurrency
failure or increase the supported worker parallelism from their throughput.

The coordination probe delivers all 1,101 signals across the three bursts; the
1,000-signal burst has p95 16.95 ms. Graceful leadership
handover takes 1970.60 ms. An unannounced committed marker is
recovered in 27983.05 ms with the production 30-second
interval (one recovery read). No notification errors occur in that probe.

## CI follow-up: Mailpit port collision

Run 42387201287 fails in the script suite: the mail-enabled runtime receives
only three distinct ports instead of four. The allocator forgot to add its
automatically chosen web port to the exclusion set before selecting SMTP/UI
ports. A closed probe socket can be offered again by the operating system.

Record the web port before the remaining allocations. A supplied allocator in
the regression test deterministically models immediate reuse of a freed port;
it preserves the production allocator and all existing assertions. Removing the
one-line fix makes the regression fail; restoring it passes all seven runtime
resource tests. The complete script suite passes: 118 pass, three optional
PostgreSQL tests skipped without a server, zero failures. Other processes can
still claim a released probe port before service startup; this correction covers
the missing exclusion within one runtime, not cross-process port reservation.
