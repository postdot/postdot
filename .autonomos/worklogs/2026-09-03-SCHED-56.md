# SCHED-56 — Verify schedule input persistence through ordinary browser interaction

- Date: 2026-09-03
- Status: completed
- Scope: Native `datetime-local` authoring, promotion persistence, browser reload
- Branch: `fix/schedule-input-persistence`

## Objective

Determine whether the scheduling observation from the live validation was a
product defect or an automation-specific limitation. Verify the complete user
path from changing a schedule to persisting and reading it after a reload.

## Findings

The integrated browser tool can change the visible DOM value of a native
`datetime-local` input without delivering the corresponding React change state
to the application. Promoting immediately after that operation therefore used
the previous application value. This is not evidence that ordinary browser
input loses the schedule.

The repository's Playwright journey exercises the same publication editor with
a real browser page: it fills `#deliver-at`, promotes the draft, asserts the
selected value, reloads the page, and asserts the value again. The complete
quality gate passed this scenario. The editor also preserves a local recovery
copy explicitly when one exists, which can intentionally take precedence over
the server value until the copy is resolved.

## Decision

No product defect was confirmed and no application code change is required for
this task. The integrated-browser behavior remains a tooling observation to
revisit only if it can be reproduced through ordinary user input or a standard
browser integration test.
