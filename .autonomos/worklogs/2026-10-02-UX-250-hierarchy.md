# UX-250 — Publication detail notice priority

## Scope and finding

Continued ISSUE-144's staged hierarchy work. The failed mobile first frame stacked
an actionable delivery failure and a passive server freshness notice before the
source editor. Those facts need different prominence: a failure needs a decision;
a successfully received background update does not.

## Changes and decisions

- Classify a background update explicitly when setting editor feedback, rather
  than guessing its intent from translated message text.
- Place passive background feedback after the composer, as a plain muted line
  with a polite status announcement. Remove its separate surface and glyph.
- Keep save errors, source conflicts, recovery decisions and lifecycle feedback in
  their existing prominent positions. A conflict/error cannot use the passive
  presentation even if a stale passive flag is present.
- Preserve the entire message, with no timeout, automatic dismissal or data loss.
  Editing, autosave, revisions, recovery, delivery and access semantics are intact.

## Evidence and validation

remain before the source; the informational update no longer pushes editing down.
The existing detail journey also renders source conflict, local recovery, scheduled
and manual-due states. Added structural assertions that a passive update follows

The conflict resolution button still opens and focuses technical details.

Full `bun run check` passed: format, lint/spelling, typing, unit tests,
