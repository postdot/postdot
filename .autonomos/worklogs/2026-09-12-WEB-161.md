# WEB-161 — Calendar label containment follow-up

## Status

Complete.

## Owner direction

The calendar should expose the publication and its scheduled time first. A
channel name is useful destination context, but it must not force a compact
Agenda row wider than the viewport or compete with the primary publication
label. The complete value still needs to remain available without adding
explanatory UI.

## Review evidence

- The integrated browser contained one populated project, `Calendar review
  workspace`, and no separate empty project. Selecting no project correctly
  returned to the project-picker dashboard rather than rendering a misleading
  project calendar. The dedicated empty-state E2E scenario remains the source
  of truth for an empty project.
- Six publications sharing one timestamp remained individually visible in
  Week (six 67px blocks in a 427px occupied slot), Day (six 40px blocks in a
  270px occupied slot), and Agenda (six 40px rows). Week exposes a real
  horizontal scroll range (1134px content in an 803px viewport), so the seven
  minimum-width columns are not silently clipped.
- Month keeps five visible events before a `+1` overflow affordance and uses
  the same compact 2px rhythm as the time grid. This remains a scan-oriented
  view; Week, Day, and Agenda are the complete reading modes for dense work.
- The original Agenda row used a `shrink-0` channel-name item. That was the
  remaining long-label risk: a realistic destination name could consume the
  row's available width or cause overflow on the mobile reading mode.

## What changed

- Made the Agenda channel label shrinkable, capped it at 35% of the row, and
  added ellipsis plus a native title for intentional hover access. The
  publication button's accessible name continues to include the complete
  publication, channel, and time values.
- Changed the dense browser fixture to use a deliberately long channel name
  and asserted at 390px that the Agenda has no horizontal overflow and every
  row keeps the bounded truncation styles.

## Density decision

A global vertical density/zoom control is not justified by this review. Empty
time slots already use the compact 2rem baseline, occupied slots grow with
their content, and no publication is hidden in Week/Day/Agenda. Adding a
second scale control now would introduce a new persistent preference without
solving a demonstrated information loss. Individual row resizing remains
deferred because it would distort the time scale; the 24-hour start/scroll
behavior deserves a separate product decision backed by realistic working
hours before it is changed.

## Follow-up

The next useful calendar decision is the vertical reading model: whether the
default should keep the complete 00:00–23:00 timeline, offer an explicit
working-hours anchor, or add one global compact/comfortable scale. That should
be tested with a realistic multi-day schedule before implementation.
