# DESIGN-175 — Reframe new-publication authoring around the operator’s job

- Status: Done
- Branch: `codex/reui-calendar-spike`
- Owner: orchestrator
- Scope: Information hierarchy and vocabulary of the authenticated
  `/dashboard/projects/$projectId/publications/new` authoring page.
- Related issue: ISSUE-099
- Predecessor: DESIGN-173, WEB-174

## Problem

The implementation correctly models one shared post fanning out to independent
channel publications, but the first frame presents that internal model as two
equal panels: `Source` and `Destinations`. Shared delivery defaults appear
before channel selection, and the active channel card repeats destination
terminology. This makes a normal writing task read like a technical assembly
workflow.

## Operator jobs

1. Write the publication’s shared content and attach media or tags.
2. Choose the channels that should receive it.
3. Confirm when and how those channels should publish.
4. Only when needed, adapt content or delivery for one channel.

The page should make this order legible without adding instructional prose.

## Accepted direction

- Keep the dedicated route and existing API/draft model from WEB-174.
- Use `Content` / `Contenu` for the primary authoring section.
- Use `Publish to` / `Publier sur` for the channel scope section.
- Give the content editor the larger, visually primary column on wide screens;
  keep the publication controls in a narrower subordinate column.
- Present selected channel tabs before shared delivery settings. The tabs answer
  “where will this go?” before the settings answer “how and when?”
- Label the shared settings as applying to all selected channels, and use
  `Channel content` / `Contenu du canal` only for an explicit adaptation.
- Replace user-facing `source` fallback language with `shared content`; keep
  source/target terminology in domain code and validation internals.
- Remove the redundant `Destination N` line from the active channel card. The
  selected channel name and status already identify the object being edited.
- Do not add a preview or rich editor in this slice. Those are valuable follow-up
  work, but mixing them into the hierarchy change would make the first result
  difficult to evaluate.

## Interaction contract

- Existing channel tabs remain the compact way to switch the active channel.
- Add/remove behavior, one-selection-per-channel validation, shared defaults,
  per-channel overrides, connection links, and scheduling remain unchanged.
- Channel-specific content and delivery settings stay collapsed/implicit until
  the operator explicitly customizes them.
- Empty-channel and narrow-width states remain actionable and localized.

## Verification plan

- Add structural browser assertions for the `Content` and `Publish to` headings,
  channel-first order, and absence of the old user-facing Source/Destinations
  hierarchy.
- Retain the existing multi-channel narrow-flow and media scenarios.
- Verify English and French message coverage, then run the full repository gate
  and inspect the authenticated local route.

## Next step

WEB-176 implements this contract. Reassess the page in the browser before
deciding whether the next authoring slice should be the preview or the editor’s
channel-specific adaptation model.

## Resolution

The accepted hierarchy is now implemented: the page leads with `Content`, gives
it the dominant column, presents `Publish to` channel selection before shared
delivery settings, and keeps channel-specific overrides in the active channel
card. The copy no longer exposes Source/Destinations framing or a redundant
destination label. Preview, rich editing, and new scheduling semantics remain
explicitly deferred.

## Verification

- Structural browser coverage confirms the new headings, channel-first order,
  absent user-facing Source/Destinations headings, and narrow-flow behavior.
- English and French message coverage remains 100%.
- WEB-176 records the focused and full repository verification.
