# OPS-371 — Scheduled full backup evaluation

Status: evaluation complete; automation proposal withdrawn after owner discussion on 2026-10-10. No runtime changes.

The current direction is application-aware backup and restore tooling with administrator-owned scheduling and retention. See [OPS-376](2026-10-10-OPS-376.md). The proposal below is historical, not an implementation instruction.

## Existing mechanism

`apps/api/src/maintenance.ts` already exposes database-only and complete media
backup commands. `packages/db/src/backup.ts` creates a SQLite snapshot using
`VACUUM INTO`, copies retained media representations and avatars from the
configured media store as streams, checks integrity, writes a manifest, and
renames a temporary bundle into its final destination. A leased database fence
coordinates media backup and cleanup. Failures remove the temporary bundle.
Restoration remains a separate maintenance operation with runtime quiescence.

## Proposed first implementation

- Disabled by default, administrator settings persisted in SQLite.
- Daily complete backup to an explicitly configured dedicated filesystem folder;
  container installations supply a mounted volume. S3 source media still use the
  existing bundle copy path. No separate service or mandatory external account.
- Retain seven successful automatic bundles by default, configurable by count.
  Delete only bundles owned by this scheduler, after a new successful backup.
  Never treat arbitrary manual bundles or unrelated files as retention candidates.
- One backup at a time; reuse the existing fence for maintenance concurrency.
  Schedule the next deadline rather than scanning every few seconds. After
  downtime, perform at most one overdue run, not a backlog of daily runs.
- Administrator action to run now, with current progress state, last success,
  last failure and next scheduled run. Report failure in the administration
  surface; do not silently create project notifications for an instance concern.
- Keep restoration manual. A successful copy is not a proven recovery guarantee.

## Implementation concerns to resolve in the delivery

The SQLite snapshot is synchronous. Do not move a potentially long `VACUUM INTO`
onto the HTTP event loop without measuring its effect; a Bun worker is an
in-process option, not a new deployed service. The fence refresh currently occurs
between object copies: a single slow stream can outlive its lease. Integrating
scheduled backups must account for that lifecycle, shutdown and interruptions.
A backup folder on the same disk does not cover loss of that disk. Bundles contain
private database content and media and must not be served as public assets.

## Alternatives and decision

An external scheduler can already invoke the maintenance CLI, but lacks a
first-party status and configuration surface. Direct S3 backup destinations are
credible, but expand the current bundle destination contract and credential
configuration. The owner was asked to choose the dedicated-folder first version
or investigate S3 first. Neither choice has been silently accepted.

## Evidence and next step

Read-only review of maintenance, snapshot, bundle publication and fence code;
no backup executed against the development database, no runtime tests replayed.
Next: after owner scope confirmation, implement scheduled complete backups as a
single operator outcome with administration settings, lifecycle and retention.
