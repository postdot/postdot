# ANALYTICS-227 — Evaluate operational analytics and telemetry boundaries

- Status: decision brief delivered; owner policy decision pending
- Date: 2026-09-26
- Issue: ISSUE-135
- Scope: establish what Herald measures, what it persists, how operational analytics overlaps with Prometheus, and who can access it; no application behavior changed

## Conclusion

The concern is not a stream of analytics snapshots being written on every scrape or page view. The project analytics API computes aggregates when requested from existing publication/job state and the durable `audit_events` journal. That journal records actual product/workflow events, not periodic measurements, and also supports realtime and notification projections. Separately, `/metrics` exports in-process Prometheus metrics; Herald does not persist those scrape samples.

The current arrangement is coherent as two distinct scopes, with limited overlap: process/operator telemetry belongs at `/metrics`; project-level publication delivery and execution history belongs in the authenticated project API. The web page is deferred as requested. No additional analytics sampler or table is justified by this review.

## What is measured and where

### Process/operator metrics

When explicitly enabled with `HERALD_METRICS_TOKEN`, the process registry exports:

- process CPU seconds, memory by RSS/heap/external/array buffers, and uptime;
- the current publication-scheduler state;
- worker-run totals by outcome and a duration histogram by outcome.

The registry lives in process memory and resets on process restart. `/metrics` requires its dedicated bearer token and exposes no project or publication labels. A Prometheus server may scrape and retain a time series externally; that storage is not Herald's SQLite database.

### Project operational analytics

`GET /api/projects/:projectId/analytics` is authenticated and project-scoped. It calculates current publication/job/workload counts and historical publication/execution outcomes, retries, recoveries, latency, daily buckets, and coverage quality. The historical range defaults to 30 days and is capped at 366 days. The response is aggregate-only; it does not return the raw event payloads or persist a query result.

The current values come from `publications` and `jobs`. Historical facts come from `audit_events`. The query path only reads these tables. It does not poll the worker, take periodic snapshots, or insert analytics rows.

### Durable event journal and retention

`audit_events` records individual project actions and workflow transitions, including publication lifecycle changes and automatic execution attempts. The row contains action, actor, entity, time, optional metadata, and correlation fields. It is not a high-frequency CPU/resource sample table.

The journal is also consumed by project realtime replay, in-app notification projection, and external notification delivery projection. Notifications and deliveries refer to source events with cascading foreign keys. Deleting a journal row can therefore delete dependent notification/delivery records and remove history needed by analytics or replay. Project deletion cascades the project's journal. No automatic TTL or individual-event purge was found.

## Storage measurement

A one-off, disposable database was migrated using Herald's actual SQLite schema and populated with 100,000 synthetic `audit_events` rows. The six-row pattern used actual publication/execution action names, UUID-sized identifiers, and representative automatic-execution metadata. The closed database file measured 79,048,704 bytes (75.39 MiB), approximately 790 bytes per event with the journal's five current indexes; insertion took about 0.6 seconds on this development machine.

This is a rough schema-scale check, not a production forecast. Real payloads vary; the measurement excludes the rest of the database, dependent notification/delivery rows, media, WAL/checkpoint effects, filesystem behavior, and backups. The useful conclusion is proportionality: the database grows with real journaled activity and retry history, not with Prometheus scrape frequency or analytics page reads. Whether a given deployment reaches 100,000 events quickly depends on its actual publication and retry volume.

## Access boundary

- The project analytics route requires authentication. Its store checks that the requester has a project actor (human, agent, or API token); it does not apply an editor-only role check. Project viewers therefore have access to the aggregate report as well as editors/owners. The response contains aggregates and channel/provider dimensions, not journal payloads.
- `/metrics` is instance-wide, disabled by default, and protected by its separate monitoring bearer token. It has no project-role authorization because its audience is the instance operator/scraper.
- There is no web analytics page or CSV export. The HTTP project API is the only user-facing operational analytics surface at present.

## Options and recommendation

1. **Keep the project report API-only for now (recommended).** Preserve the existing read-only, project-scoped aggregate endpoint. It adds no periodic database writes, and keeps project delivery history distinct from process telemetry. This matches the owner's decision to defer a web page.
2. **Add a web page later if a recurring project workflow needs it.** The page should report delivery/execution performance, not pretend to be provider-reported reach/views and not duplicate process diagnostics. The existing API can be evaluated before adding a new collection model.
3. **Change event-journal retention only as a separate data-lifecycle decision.** Do not delete old rows merely to reduce “analytics” storage: the journal is a source for multiple features, and source-event foreign keys cascade. First agree what history notifications, replay, audit/debugging, and project analytics must preserve; then design and test a bounded retention/compaction policy.

Recommendation: keep the current API-only report and `/metrics` as separate interfaces; do not add analytics sampling or a new persistence layer. Treat eventual journal retention as the real database-growth question. The owner can decide that policy later; this review does not imply indefinite retention is mandatory or permanently rejected.
