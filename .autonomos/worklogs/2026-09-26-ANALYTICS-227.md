# ANALYTICS-227 — Define publication-performance analytics boundaries

- Status: decision brief delivered; owner policy decision pending
- Date: 2026-09-26
- Issue: ISSUE-135
- Scope: clarify the product meaning, inspect the existing provider-observation path, measure a bounded SQLite growth scenario, and recommend surfaces and access; no application behavior changed

## Conclusion

The owner's intended analytics product is coherent for Herald: show what social providers report about the performance of Herald publications (for example, views where available, comments, reactions, and reposts). It is distinct from operational analytics, which reports Herald's queue, execution, delivery, retry, and reliability facts. The operational analytics page remains deferred; that does not defer or reject publication-performance analytics.

The existing provider-analytics collector is a foundation for the latter, not a Prometheus-style application monitor. Its records are normalized provider observations stored in Herald's SQLite database. They are not collected continuously today.

## Current implementation evidence

- The only application collection entry point found is the authenticated `POST /api/projects/:projectId/analytics/provider/bluesky/collect` route. The route asks the existing service to collect explicitly; there is no periodic collector or scheduler, and no web UI invokes the route.
- Each request reads one Bluesky profile and up to 25 already-known Herald publications. It does not search or discover outside content. A full request writes at most 128 observation rows: three account counters and five counters for each of 25 posts. The post metrics currently mapped are likes, replies, reposts, quotes, and bookmarks; account metrics are followers, follows, and post count. Missing or unavailable counters are represented as availability states, not fabricated zero values.
- Rows contain normalized values, provider identities, source/fetch timestamps, provenance, freshness, and availability; raw API payloads and credentials are not stored. An identical metric at the same `fetchedAt` is deduplicated. A later fetch timestamp creates another retained snapshot. The project foreign key cascades on project deletion, but no automatic observation TTL, compaction, or purge policy exists.
- `GET /api/projects/:projectId/analytics/provider/bluesky` reads the persisted observations and does not call Bluesky. Reads are project-actor scoped; collection additionally requires the editor role. There is no analytics UI or CSV export in the web app. The route is paginated, defaulting to 100 observations and allowing at most 500 per response.

## Storage measurement

A one-off synthetic database was created in the system temporary directory, migrated with the repository's actual SQLite schema, populated with the current maximum Bluesky-shaped observation set, measured, and deleted. It contained ten channels, 365 daily snapshots per channel, and 25 posts per snapshot: `10 × 365 × (3 + 25 × 5) = 467,200` rows. The resulting closed SQLite file was 277,024,768 bytes (264.19 MiB); insertion took about 5.5 seconds on this development machine. This includes the current table and its four indexes.

This is a deliberately high, measured scenario—not the current runtime behavior or a forecast. It assumes every channel has 25 known eligible publications in every daily sample and retains every snapshot for a year. Synthetic identifiers are shorter than production UUIDs, so the size is not a guaranteed upper bound; real traffic, WAL/checkpointing, backups, media, and other application tables are also outside this measurement. The result is sufficient to reject an unbounded “poll everything continuously and keep it forever” default, but not to claim that normal use will quickly exhaust storage.

For scale, one explicit full-cap collection currently produces at most 128 rows; ten daily full-cap collections for a year produced about 264 MiB in this stress fixture. A less aggressive policy, fewer eligible posts, or provider-supplied period aggregates changes that growth substantially. No byte-size claim should be inferred from row count alone.

## Product and lifecycle options

1. **Latest value only:** refresh on an explicit user action or page visit and retain/replace the latest provider value per metric. This keeps history small and answers “what does the provider report now?” but cannot show a trend. Replacing observations would require a deliberate retention/model change; today's store appends later snapshots.
2. **Sparse, bounded history:** collect provider history when the API provides it; otherwise sample selected posts at a small number of agreed ages after publication. Apply a retention or compaction policy so row growth is predictable. This supports useful trends without pretending to be real-time, but requires a cadence, retention, and retry policy before automatic collection.
3. **Frequent indefinite polling:** retain every recurring snapshot. This provides more points but increases provider traffic, rate-limit exposure, database and backup growth, and scheduler complexity. It is not recommended for Herald's current needs.

Provider metrics cannot be treated as a uniform contract. Mastodon's status representation documents reply, boost, favorite, and quote counts, but not view counts in that entity. LinkedIn documents impressions, reach, reactions, comments, and other post metrics, while requiring the restricted `r_member_postAnalytics` permission and imposing different support for daily aggregation by metric. These examples make provider-specific availability and meaning a product constraint, not just an adapter detail. Sources: [Mastodon Status](https://docs.joinmastodon.org/entities/Status/); [LinkedIn Member Post Statistics](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/members/post-statistics?view=li-lms-2026-09).

## Recommendation

- Keep publication-performance analytics under the project context and keep Herald operational analytics separate. Do not call provider performance snapshots “Prometheus metrics”; they have different owners, semantics, refresh behavior, and storage.
- Treat the authenticated web app as the primary human surface, backed by a project-scoped API with the same provider-native observations. CSV export can be added later from that same read model if a concrete workflow calls for it; it is not an alternative to the UI or API.
- Let project readers view available results; require editor or owner authority to trigger provider reads or change collection policy. Preserve API-key project restrictions. Do not aggregate across projects the actor cannot access.
- Do not begin high-frequency automatic polling. First define which provider metrics are actually available and useful. Prefer provider-supplied history where available; otherwise use sparse post-age samples only if the owner wants trends. Add retention/compaction before automatic collection, rather than accumulating snapshots indefinitely.
- Keep metrics provider-native and mark source, freshness, coverage, and unavailable values clearly. Do not invent one cross-platform score or promise views/reach on every network.

## Owner decision still needed

The product's broad purpose is now clear, but implementation policy is not accepted. Before a collector, storage policy, or UI is implemented, choose between latest-value-only and sparse historical snapshots; if sparse history is selected, agree on sample ages and retention/compaction. Provider-by-provider scope can then be accepted based on current access and API evidence. No decision about a hypothetical release or final provider set is implied.
