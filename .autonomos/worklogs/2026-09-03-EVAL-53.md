# EVAL-53 — Define and exercise a safe real-use publication validation loop

- Date: 2026-09-03
- Status: completed
- Issue: ISSUE-021
- Scope: dashboard, API, CLI, manual publication, automatic publication, and recovery evidence
- Branch: `eval/eval-53-real-use-loop`

## Validation contract

The real-use pass is an operational validation of the publication manager, not a
replacement for the deterministic test suite. Each pass records which surfaces
were exercised and separates local evidence from provider evidence.

The pass uses these stages:

1. **Preflight** — confirm the intended local API origin, authenticated dashboard
   session, `/health`, `/ready`, and a clean application log. No provider action
   is implied by a healthy runtime.
2. **Dashboard authoring** — create or edit one disposable source publication,
   select a manual destination, allow autosave to complete, reload the editor,
   and confirm that the source and target draft remain intact. Promote the draft
   only after the content and schedule are reviewed.
3. **CLI handoff** — use the CLI to list the due manual work, record the manual
   completion with an intentionally non-sensitive test URL, list the project
   audit events, and confirm the resulting state in the dashboard. The session
   credential used by the CLI must be supplied by the operator and must not be
   written to a repository artifact.
4. **Automatic provider** — only after an explicit action-time approval, use a
   provider connection owned by the operator and a controlled test destination.
   Start with one uniquely identifiable text publication, verify the provider
   acknowledgement and Herald audit outcome, and never retry an ambiguous result
   before reconciling the external destination.
5. **Recovery** — exercise one deliberately selected failure or edit boundary,
   verify the expected durable state through the dashboard, API, and CLI, and
   record whether recovery was automatic, manual, or intentionally unavailable.

The pass must not use a live destination merely as a health probe. Media,
multiple providers, and destructive cleanup are separate decisions; they are not
silently added to the first pass.

## Safety boundary

- Local authoring and manual completion are reversible development data changes,
  but they should use a disposable project or an explicitly identified test
  publication rather than silently altering a production-like destination.
- Connecting an automatic provider starts an OAuth flow and may grant Herald
  access to an external account. It requires an operator-approved provider,
  callback, account, and destination at action time.
- An automatic publication is a representational external action. The first
  provider pass is text-only and must use a controlled destination; no LinkedIn
  agency page is a default test target.
- Provider identifiers, tokens, session cookies, and personal account details do
  not belong in this worklog, issues, commits, or logs.

- No automatic provider connection or external publication was attempted. The
  inspected project has no connected publisher, and the provider phase remains
  gated by an action-time destination and content approval.

  in this pass, so automatic-provider failure recovery remains separate and gated.
- Expand recovery evidence when a concrete non-ambiguous recovery scenario is
  selected. Source editing, target preservation, the local recovery buffer, and
  reload behavior are covered by this pass.
