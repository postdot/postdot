## Objective

Expose built-in and runtime-defined channel onboarding and lifecycle behavior
through the authenticated web application without creating a second channel
model or weakening the existing versioned profile and impact-assessment
contract.

## Contract inspection

The current server already exposes the following supported boundaries:

- `GET /api/projects/:projectId/channels` and
  `POST /api/projects/:projectId/channels` for channel listing and creation;
- `GET /api/projects/:projectId/channels/:channelId/profile` for active and
  draft profile state;
- `POST .../profile-drafts` for optimistic draft creation/update;
- `POST .../profile-drafts/:profileVersionId/preview` for impact assessment;
- `POST .../profile-drafts/:profileVersionId/activate` for version activation.

The creation contract accepts the existing built-in profile identifiers and a
bounded runtime profile definition. The profile lifecycle is therefore usable
from a web client once an authoring surface is designed around these routes.

## Resolved foundation gap

`ISSUE-033` also identified missing channel lifecycle actions: rename, archive,
restore, and deletion. `CHANNEL-71` has now integrated the project-scoped API,
database guards, revisions, blockers, and audit semantics required by the web
client. The web implementation must consume those routes instead of inventing
client-side state transitions.

The consequences are domain decisions, not presentation details:

- renaming needs an attributable mutation and a concurrency/audit policy;
- archiving needs a state contract for new authoring, scheduled work, publisher
  connections, and existing publications;
- deletion needs an explicit policy for publications, credentials, profile
  history, audit records, and irreversible data loss.

The `CHANNEL-67` mission contract still forbids database/API changes. The
foundation is now available on `main`, so this task can remain isolated to the
authenticated web application and its client-side interaction tests.

## Options for the next decision

1. **Recommended — split the foundation first.** Define and implement a small
   channel lifecycle API/domain task, including rename/archive/delete semantics,
   then resume CHANNEL-67 for the web onboarding and lifecycle UI.
2. **Narrow CHANNEL-67.** Limit this task to custom profile onboarding and the
   existing draft/preview/activate profile lifecycle, and create a separate
   channel CRUD lifecycle task later.
3. **Expand CHANNEL-67.** Allow the current mission to change API/DB contracts.
   This would combine domain policy, persistence, and UI work and would violate
   the current isolation contract; it is not recommended without an explicit
   revision of the sprint plan.
