# WORK-07B — Next-Event Scheduling and Startup Reconstruction

## What Was Done

- Added a durable query for the nearest automatic publication event, considering
  both pending execution times and running-claim lease expirations.
- Added a deterministic scheduler that keeps at most one timer and rebuilds that
  timer entirely from durable state.
- Added explicit replanning for schedule mutations without introducing a polling
  interval or an in-memory queue.
- Covered empty state, earlier-event replacement, overdue events, restart
  reconstruction, long timer delays, and visible processing failures.
- Proved reconstruction against a file-backed SQLite database closed and reopened
  between scheduler instances.

## Key Decisions and Why

- SQLite remains the source of truth. The timer is disposable process state and
  carries no information required for recovery.
- The next event is the minimum of pending automatic jobs' `run_at` values and
  running jobs' `lease_expires_at` values. Manual channels remain outside the
  automatic worker.
- A wake-up rereads durable state before processing. This safely handles deleted or
  postponed work and lets capped long timers replan without firing an event early.
- JavaScript's maximum reliable timer delay is handled by capping each timer at
  2,147,483,647 milliseconds and consulting SQLite again when it wakes.
- Scheduler failures transition to an explicit `failed` state and call the supplied
  error handler. They do not create a hidden retry loop.
- No dependency, schema, service, background polling loop, or generic persistence
  abstraction was added.
