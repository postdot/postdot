# WEB-563 — Instance-access contracts

## Outcome and decisions

Derived twelve instance-access types from the server through Eden, including the
initial setup status, access summary, membership update input and invitation
responses. Migrated nine web wrappers with inferred results; existing imports
continue through web re-exports. Sixteen compile-time assertions preserve response
envelopes, nullable membership, roles and states. The separate project invitation
acceptance through Better Auth remains unchanged.

Treaty cannot distinguish the public GET token parameter and authenticated DELETE
invitationId parameter at the same dynamic path: it requires both parameters and
produces a union without either callable method. A small invitation client uses
Eden Fetch's explicit typed paths for these two operations. This preserves server
routes and OpenAPI parameter names, uses the same installed SDK, encodes each
parameter and supplies same-origin credentials per request. DELETE sends an empty
object matching its inferred body schema. Its portable return annotation selects
data/error/status from the SDK response type using the exact server responses;
no response contract or unchecked conversion is introduced. The existing Treaty
factory is unchanged. The helper exposes neither retries nor transport selection
to product components.

## Validation

- Static gates passed: formatting, lint, spelling and types, including client
  declaration portability and all sixteen web type assertions.
- Production web build passed after the final changes.
- 285 web tests, 13 access-route tests and 4 client tests passed: 302 total,
  zero failures. The access tests include administrator safety, session/API-key
  authorization and matching-user invitation acceptance.
- A permanent isolated HTTP test verifies reserved-character encoding for both
  explicit paths, distinct GET/DELETE methods, successful preview decoding and
  a single request returning the original 409 error envelope.
- Five isolated browser scenarios passed without retries in 41.7 seconds:
  both access-132-instance-access cases, both web-312-live-access-revocation
  cases and a temporary instance-wrapper acceptance.
- The temporary acceptance exercised all nine wrappers through the actual web
  module: setup status, access/member reads, invitation creation/list/preview,
  revocation and acceptance. Repeated revocation returned normalized ApiError
  409 invitation_not_pending; a revoked preview returned 404 invalid_invitation.
  Disabling the current administrator returned a 409 safety refusal and preserved
  enabled membership. The permanent UI scenarios also cover member exclusion
  from instance administration and live project access withdrawal.
- Removed the temporary browser file after verification. Permanent browser tests
  and configuration remain unchanged.
- Focused validation covers the bounded instance-access changes and additive
  invitation helper. No full matrix/container replay: the existing shared client
  factory, dependencies and server runtime remain unchanged.
