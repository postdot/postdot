# Affected E2E validation

`bun run test:e2e:affected` reports which Playwright scenarios a change set can
affect, or the full matrix with the reason it fell back. It reports a command;
it does not wire itself into `check`, the pre-commit hook, or CI, and it never
changes workers, retries, or wait settings.

## Workflow on `main`

The selector reports what changed since a base. On `main` there is nothing to
diff against unless you name a base, so record the mission base once before
touching anything.

```bash
# 1. Before any edit, on main, record the base of the mission.
git rev-parse HEAD | tee .git/herald-mission-base
```

That file is inside `.git/`, so it is never committed. The selector does not read
it implicitly; pass it as the base so the comparison is explicit and reproducible:

```bash
bun scripts/e2e-affected.ts --base "$(cat .git/herald-mission-base)"
```

Without `--base`, the selector compares against `main`. On `main` that range is
empty, so only uncommitted work shows up. Recorded-base comparison is what
surfaces changes you committed during the mission.

Work as usual, including uncommitted work: the selector unions committed, staged,
unstaged, and untracked paths, so there is no need to commit early to get a
correct answer.

```bash
# 2. While iterating.
bun run check:quick                                       # format, lint, typecheck (~5 s warm)
bun run test:unit                                         # every unit test in every package (~11 s cold)
bun scripts/e2e-affected.ts --base "$(cat .git/herald-mission-base)"   # selection and reasons
```

## Two separate E2E commands

The selector prints one Playwright command for the standard matrix. Mailpit is a
different harness and stays a separate, explicit command.

```bash
# Standard matrix: whatever the selector retained, or the full suite when it fell back.
bun scripts/e2e-affected.ts --base "$(cat .git/herald-mission-base)"
bunx playwright test e2e/access-134-project-access.spec.ts e2e/web-314-editor-access-state.spec.ts

# Mailpit variant: docker compose, its own API and web runtime, its own ports.
bun run test:e2e:password-reset
```

Never fold the Mailpit spec into a `playwright test` invocation. `playwright.config.ts`
ignores `access-219-password-reset.spec.ts` unless `HERALD_E2E_MAILPIT=true`, and
`test:e2e:password-reset` is what sets it up and tears it down. If the selector
retains that spec, it prints a note saying the Mailpit command is still needed.

## Reading the output

```
Selection: targeted (8 of 37 scenario files, 1 changed paths)
Functional domains matched by the changed paths:
  access-control
    apps/web/src/lib/project-access-verification.ts
Scenarios retained, with the reason each one was retained:
  e2e/web-314-editor-access-state.spec.ts
    - access-control: Roles, project and instance access, invitations, API keys
Command: bunx playwright test e2e/... e2e/...
```

A `full matrix` result is not a failure. It is the safe answer for a change set
that touches shared foundations (`packages/db`, `packages/core`, `packages/client`,
`packages/email`), the API composition root, shared dashboard transport or context,
harness and CI configuration, the commit gate, or governance records. The reason
line names the path and why it is transversal.

An empty or unmapped change set also returns the full matrix. The selector never
reports "nothing to run".

### Base override and machine output

```bash
# Compare against any explicit base, for example a mission base or a review branch.
bun scripts/e2e-affected.ts --base <sha>

# Inspect a hypothetical change set without touching the tree.
bun scripts/e2e-affected.ts --paths apps/web/src/lib/project-realtime.tsx,packages/x/src/x-client.ts

# Machine-readable, for a scratch note or a later gate.
bun scripts/e2e-affected.ts --json
```

## What the selection does and does not guarantee

Guarantees: every unit test, every static gate, and the browser journeys of the
affected functional domains.

Does not cover: cross-spec interference, unaffected domains, container wiring, or
the full 84-test matrix. A domain that genuinely overlaps a change selects most
of the suite; that is intended. Treat a large selection as information, not as a
reason to skip it.

## Adding a change

Adding a domain means editing `FUNCTIONAL_DOMAINS` in `scripts/e2e-affected.ts`.
Two invariants are covered by `scripts/e2e-affected.test.ts` and will fail if
violated: every domain declares at least one scenario and one pattern, and every
pattern resolves to at least one domain. Adding a new spec file without adding it
to a domain makes it unreachable by selection, which the audit noted as an
explicit cost of a name-free mapping; wire it into the domain that owns its
capability in the same change.
