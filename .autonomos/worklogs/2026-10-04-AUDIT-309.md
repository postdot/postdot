# AUDIT-309 — Authorization enforcement audit (diagnosis only)

Scope: build the permission matrix that is actually enforced, confront it with
the dashboard's possibilities and existing tests, and classify the results. No
permission was changed. Fixtures were in-memory SQLite plus a disposable local
media root; no real account, provider, or user data was involved. The temporary
investigation probe was removed; one reproduction test is kept.

## Enforcement model (as implemented)

## Demonstrated defects

### D1 — API keys keep project read access after their owner is removed (high)

Reproduced by the kept test
`apps/api/src/modules/projects/access-revocation-regression.test.ts`:

- An owner grants `editor`; the member creates one `all`-scope key and one
  `selected`-scope key.
- The owner removes the member. Post-removal state is unambiguous:
  `project_user_grants` count 0, `access.canAccessProject` false,
  `access.getProjectMembership` null.
- The removed member's session is correctly hidden on project routes (`404`
  for channels, analytics, and media).
- The removed member's API keys still receive `200` for `GET channels`,
  `GET publications`, `GET publications/due`, `GET analytics`,
  `GET analytics/provider/bluesky`, `GET tags`, `GET publishers`, and the
  project still appears in `GET /api/projects`.
- Mutations remain denied with `403`, and a key whose owner was never a member
  is correctly hidden with `404`, which isolates the gate to membership history.

Mechanism: the key path checks stored scope and action ceilings only, then read
routes delegate to a store lookup keyed on `subjectId`
(`manual-store/project-channel-store.ts:467-475`,
`packages/db/src/media-asset-store.ts:1704-1705`,
`packages/db/src/analytics-store.ts:461-473`) that matches the durable `actors`
attribution row. Removing a project grant deletes the grant but deliberately
keeps the actor row for audit history, so the actor check still passes.
Mutation routes are unaffected because they re-check current membership through
`canAccessProjectRole`.

Why the existing tests missed it: ACCESS-143 and every removal test assert the
session path, and the only stale-credential HTTP test
(`apps/api/src/modules/access/routes.test.ts:608-684`) exercises
`POST /channels`, which is editor-gated.

Impact: a revoked collaborator retains read access to publications, analytics,
taxonomy, media metadata, and publisher connections for as long as the
credential exists; there is no automatic key revocation. Dispatch, delivery, and
all mutations remain denied.

### D2 — WITHDRAWN: the project list was already membership-filtered (my error)

The original finding claimed `GET /api/projects` is actor-based. That was wrong:
I read `modules/projects/routes.ts:36-52` and missed the filter at lines 56-64,
which keeps only projects where `access.canAccessProject(...)` **or**
`access.canManageWorkspace(...)` holds.

The reproduction had also misled me: additional-signup fixtures are workspace
owners by default, so my "removed member" still satisfied
`canManageWorkspace` and legitimately kept list visibility under the documented
access-surface policy. Re-running with the fixture explicitly demoted to an
ordinary workspace member, plus direct assertions
(`canManageWorkspace(workspaceId, userId) === false`), shows the removed
member's list omits the revoked project for both the session and the API key,
while the retained project stays listed.

Conclusion: D2 is not a defect, and workspace-administrator visibility is left
exactly as it is. Only D1 required a fix.

## Documented, intentional behavior (not defects)

- Cross-project access is hidden as `404`, never `403`, so non-membership never
  confirms existence (`apps/api/src/app.test.ts:2658-2660`).
- Unrestricted keys dynamically inherit the owner's project actions
  (ACCESS-236). The intent is correct; D1 is a missing enforcement of that
  intent, not a change to it.
- `publication:manage` may propose a schedule but never approve, schedule, or
  dispatch (PUB-238).
- Workspace `owner`/`admin` may view and manage project access without being
  project members (`index.ts:44-50`, `member-routes.ts:122-131`).
- The notification inbox and the external delivery outbox are recipient-owned
  and session-only, and never expose another actor's project data.
- Analytics reads are intentionally available to any authenticated project
  actor, including scoped keys (ANALYTICS-230).
- Removing a member keeps `actors` rows for historical attribution; a fix must
  not delete them.

## UI versus server divergences (UX findings, not authorization defects)

- The Overview calendar offers `New publication` to viewers because it only
  checks for channels (`publication-calendar-page.tsx:167-182`), and the route
  then redirects them to Queue (`new.tsx:31-40`).
- The Overview calendar renders bulk reschedule and cancel for viewers with no
  role gate (`publication-calendar-page.tsx:220-254`), unlike Queue, so the
  server answers `403` with no tailored UI state.
- The project Configuration link is rendered for every role and the access and
  invitation routes have no viewer guard, so viewers meet raw
  `access_action_failed` alerts.
- After live revocation the dashboard keeps previously fetched project data
  visible (`staleTime: Infinity`) and shows a generic error on refetch instead
  of a removed-from-project state.

## Test coverage gaps (no defect demonstrated)

- Notification routes: no second-actor, removed-member, or cross-project inbox
  filter test.
- Audit events: only the key-versus-session `403`; no cross-project or
  removed-member read.
- Analytics and provider analytics: happy path only, with no denial assertions,
  including the `analytics:refresh` ceiling over HTTP.
- Media: no cross-project or viewer/editor matrix; only `401` and public-URL
  tampering coverage.
- Realtime SSE: no viewer/editor/owner subscribe test and no removed-member HTTP
  test (unit-level reauthorization only).
- Downgrade enforcement: no test performs an editor action, downgrades the actor
  to viewer, then re-attempts it. The probe confirmed the behavior is correct
  (`403`).
- Publisher OAuth: no cross-project callback-state test.

## Product questions requiring an owner decision

1. When a member is removed, should their API keys be revoked automatically, or
   only scope down to the projects they still own? The accepted contract implies
   scope-down; automatic revocation is a stronger, separate policy.
2. Should a workspace `owner`/`admin` who is not a project member see the project
   in the dashboard list? The list and the documented access-surface reach agree,
   so this is a product preference rather than an inconsistency, and the owner
   explicitly left administrator visibility unchanged in this mission.
3. Should a removed member's dashboard present an explicit "you no longer have
   access" state instead of a `404` error page?

## Proposed first bounded fix (not implemented, awaiting approval)

One seam, no new infrastructure, and no change to any role or classification:

1. Add one read accessor to `AccessStore` that lists the project ids a user can
   currently access, built on the existing effective-role resolution.
2. At the existing key-authentication callback
   (`modules/projects/index.ts:78-103`), resolve the key's effective project set
   as the intersection of its stored scope with the owner's current access, so
   an `all`-scope key becomes dynamic exactly as ACCESS-236 describes and a
   `selected`-scope key drops projects the owner no longer holds.
3. Reuse the existing hidden `404` when the request's project is outside that
   set, which makes every read route consistent with the session path by
   construction.

This closes D1 for all read routes at once and keeps actor attribution intact.
D2 is deliberately left as a separate follow-up so the two changes stay
reviewable, and the three product questions above remain owner decisions.
