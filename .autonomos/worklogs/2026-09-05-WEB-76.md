## Objective

Define and implement the authenticated Herald web client as a coherent
operational application. This workstream owns information architecture,
navigation hierarchy, task composition, density, responsive behavior,
accessibility, and component ownership. It is not a landing-page exercise or a
visual reskin performed page by page.

## Owner constraints already accepted

- The web client is an application, not a public marketing site. Public home,
  about, and documentation pages remain out of scope unless separately accepted.
- The client remains a thin consumer of the existing API and domain contracts.
  It must not introduce a second publication, scheduling, or channel model.
- The authenticated shell must preserve project context and make the source to
  destination relationship legible across Overview, Calendar, Compose, Queue,
  Channels, Media, Access, and publication detail.
- Desktop should minimize unnecessary page scroll while retaining readable
  authoring space. Tablet and mobile may stack or drawer secondary regions.
- `@herald/ui`, shadcn/Base UI, Tailwind tokens, Recursive Variable, Solar Icons
  Bold, Graphite/Ash surfaces, purposeful depth, and the accepted motion policy
  remain the implementation foundation.

## Initial code inventory

- The route tree currently contains an authenticated dashboard index, a shared
  project shell, seven project task routes, and a nested publication editor.
- `DashboardShell` currently owns the product rail, project selector, workspace
  navigation, channel list, account actions, header, theme toggle, and shell
  layout behavior. Its responsibility boundary must be checked before further
  feature work is added.
- The largest web components are `publication-editor.tsx` (about 54kB),
  `dashboard-shell.tsx` (about 26kB), `publisher-connection-panel.tsx` (about
  25kB), `publication-target-editor.tsx` (about 19kB), and
  `media-attachment-picker.tsx` (about 15kB). These sizes are signals for
  decomposition and testability, not automatic reasons to split files.
- Project data is loaded and shared through `dashboard-context.tsx`; the
  information architecture must keep data ownership and route ownership
  explicit rather than moving domain decisions into presentational components.
- The existing `DESIGN.md` already accepts route-oriented workspace surfaces,
  task-dependent density, a sticky header in the main scroll region, and a
  shadcn/Base UI component source with Herald-owned visual tokens.

## First phase

1. Map each existing route to one primary operator job, its required context,
   its secondary context, and its next action.
2. Compare the current rendered shell and page compositions at wide desktop,
   tablet, narrow mobile, dark theme, and light theme sizes.
3. Identify duplicated page framing, accidental scroll containers, overloaded
   components, and controls that should become shared primitives or route-level
   compositions.
4. Write the accepted information-architecture contract before changing broad
   production surfaces. Each implementation slice must have a clear user job,
   a measurable validation point, and a bounded migration boundary.

## Guardrails

- Do not add another page, panel, card, or heading pattern merely because a
  local surface needs content.
- Do not preserve the current layout solely to avoid a refactor; this task exists
  because incremental composition has already produced avoidable complexity.
- Do not turn `@herald/ui` into a dumping ground for page-specific composition.
- Do not claim completion from screenshots alone: route behavior, keyboard use,
  responsive layout, loading/error/empty states, and the existing quality gate
  must remain covered.

## Next checkpoint

The next worklog revision will record the route/job matrix and the first accepted
shell and navigation contract. No broad production UI migration is considered
complete until that contract is reviewed against the actual application.
