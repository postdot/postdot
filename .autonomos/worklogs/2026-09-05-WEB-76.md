## Objective

Define and implement the authenticated Herald web client as a coherent
operational application. This workstream owns information architecture,
navigation hierarchy, task composition, density, responsive behavior,
accessibility, and component ownership. It is not a landing-page exercise or a
visual reskin performed page by page.

## Owner constraints already accepted

- The web client is an application, not a public marketing site. Public home,
  about, and documentation pages remain out of scope unless separately accepted.
- The client remains a thin consumer of the existing API and domain contracts.
  It must not introduce a second publication, scheduling, or channel model.
- The authenticated shell must preserve project context and make the source to
  destination relationship legible across Overview, Calendar, Compose, Queue,
  Channels, Media, Access, and publication detail.
- Desktop should minimize unnecessary page scroll while retaining readable
  authoring space. Tablet and mobile may stack or drawer secondary regions.
- `@herald/ui`, shadcn/Base UI, Tailwind tokens, Recursive Variable, Solar Icons
  Bold, Graphite/Ash surfaces, purposeful depth, and the accepted motion policy
  remain the implementation foundation.

## Initial code inventory

- The route tree currently contains an authenticated dashboard index, a shared
  project shell, seven project task routes, and a nested publication editor.
- `DashboardShell` currently owns the product rail, project selector, workspace
  navigation, channel list, account actions, header, theme toggle, and shell
  layout behavior. Its responsibility boundary must be checked before further
  feature work is added.
- The largest web components are `publication-editor.tsx` (about 54kB),
  `dashboard-shell.tsx` (about 26kB), `publisher-connection-panel.tsx` (about
  25kB), `publication-target-editor.tsx` (about 19kB), and
  `media-attachment-picker.tsx` (about 15kB). These sizes are signals for
  decomposition and testability, not automatic reasons to split files.
- Project data is loaded and shared through `dashboard-context.tsx`; the
  information architecture must keep data ownership and route ownership
  explicit rather than moving domain decisions into presentational components.
- The existing `DESIGN.md` already accepts route-oriented workspace surfaces,
  task-dependent density, a sticky header in the main scroll region, and a
  shadcn/Base UI component source with Herald-owned visual tokens.

## First phase

1. Map each existing route to one primary operator job, its required context,
   its secondary context, and its next action.
2. Compare the current rendered shell and page compositions at wide desktop,
   tablet, narrow mobile, dark theme, and light theme sizes.
3. Identify duplicated page framing, accidental scroll containers, overloaded
   components, and controls that should become shared primitives or route-level
   compositions.
4. Write the accepted information-architecture contract before changing broad
   production surfaces. Each implementation slice must have a clear user job,
   a measurable validation point, and a bounded migration boundary.

## Guardrails

- Do not add another page, panel, card, or heading pattern merely because a
  local surface needs content.
- Do not preserve the current layout solely to avoid a refactor; this task exists
  because incremental composition has already produced avoidable complexity.
- Do not turn `@herald/ui` into a dumping ground for page-specific composition.
- Do not claim completion from screenshots alone: route behavior, keyboard use,
  responsive layout, loading/error/empty states, and the existing quality gate
  must remain covered.

## Next checkpoint

## Shell findings

- The shared shell correctly owns project context, workspace navigation, channel
  visibility, account actions, and the main scroll region. It should remain the
  only owner of those concerns.
- The current shell presents the project in the sidebar, breadcrumb, and page
  metadata. The next contract should define where project identity is primary
  and where it is merely supporting context, instead of removing context
  opportunistically from individual pages.
- The header and sidebar already use the shadcn/Base UI primitives, but page
  routes still repeat a page-header pattern. A page title plus compact metadata
  and a task action should be the default; overline, icon, and explanatory copy
  must be earned by the task.
- The sidebar's channel list is useful for orientation only. It must not become
  a second channel-management surface, and status badges must not crowd or
  displace channel names.
- The app currently has one main scroll region and a sticky header. This is the
  correct structural direction; the next pass must remove accidental nested
  scroll and reduce authoring depth rather than introducing another fixed panel.

## Proposed information-architecture contract

1. `Overview` answers “what should I know or do next?” It is a landing surface
   inside the authenticated workspace, not an analytics dashboard and not the
   only place to create content.
2. `Calendar` answers “when is destination work planned?” It scans time and
   starts dated work, while Queue remains the state and priority surface.
3. `Compose` answers “what is the source and how does it become each target?”
   Source editing and target review are one workflow. Desktop may use a
   two-region composition; mobile may stage the same decisions sequentially.
4. `Queue` answers “what publication needs a decision or execution?” It should
   favor comparison, filtering, and next actions over large explanatory blocks.
5. `Channels` answers “where can this project publish and is each destination
   ready?” Channel definition and connection state stay related but must not
   obscure one another's ownership or destructive actions.
6. `Media` answers “which verified assets can this project reuse?” It is a
   project library with a direct path back to the authoring workflow.
7. `Access` answers “which machines may operate this project?” It is deliberately
   separate from publisher connections and account authentication.
8. Publication detail remains a project-scoped destination review route. Its URL
   and domain semantics stay stable while its oversized component is split into
   source, target, scheduling, and execution sections with explicit ownership.

## Implementation order

- First, stabilize the shell and route-level composition contract, including
  scroll ownership, project context, navigation states, and responsive behavior.
- Next, recompose Overview, Queue, and Calendar as the read/triage surfaces that
  orient the operator before authoring.
- Then recompose Compose and Publication detail around the source-to-target
  workflow without changing API/domain semantics.
- Finally, align Channels, Media, and Access and complete keyboard, responsive,
  loading, empty, error, and partial-failure validation across the route tree.

## First implementation slice

- The authenticated navigation now separates `Work` (Overview, Calendar,
  Compose, Queue) from `Project` (Channels, Media, Access). The channel list
  remains a separate orientation aid rather than a duplicate management route.
- The existing mobile and desktop navigation contract is covered by the E2E
  layout assertions: each navigation group keeps stable link counts and
  distinct vertical positions, while the collapsed desktop rail remains
  centered.
- The sticky main header was extracted into `DashboardHeader`. The shell still
  owns the scroll region and supplies the route/project/session state, while the
  header owns account actions, theme switching, and route context presentation.
  This is a responsibility boundary only; no route or API behavior changed.
- The full repository quality gate remains the acceptance boundary for this
  slice. The focused E2E flow passed after its navigation expectations were
  updated to the new two-group contract.
- The shell's sidebar responsibility is now isolated in `DashboardSidebar`.
  It owns the product rail, project selector, work/project navigation, channel
  orientation list, and shell footer actions; `DashboardShell` remains the
  composition boundary for scroll ownership, route context, errors, and page
  content. This decomposition intentionally leaves the rendered contract
  unchanged so later IA work can change page composition without reopening the
  shell's navigation logic.
- Queue now has a client-side triage contract for the data it already loads:
  all work, needs-attention work identified by durable due ids, scheduled work,
  and manual work. Filtering is intentionally local and presentation-only; it
  does not create a second API query or change publication state. The filter
  predicate is isolated and unit-tested so future server-side filtering can
  replace the source without changing the route's interaction contract.
- The queue filter row keeps the full accessible labels while using a shorter
  mobile rendering for the attention filter and a bounded horizontal list. This
  avoids turning the primary queue surface into an accidental horizontal-scroll
  layout on narrow screens.
- Queue no longer reserves a large empty attention panel when there is no due
  work. The actionable panel still appears when manual decisions exist, while
  Overview remains responsible for the persistent orientation summary. This
  keeps Queue focused on triage instead of duplicating an empty Overview state.
- The Channels surface now gives its two operator jobs separate visual zones:
  channel definitions use a raised, shadowed list and publisher connections use
  a second raised list. The rows no longer rely on decorative dividers; hover
  feedback and spacing preserve scanability without adding a border to every
  item. The channel definition row is isolated in `ChannelRow`, keeping page
  composition separate from lifecycle actions and profile metadata. No route,
  OAuth, connection, or channel API behavior changed.
- Overview no longer renders an empty `Needs attention` panel when there is no
  due manual work. The summary still reports the count, while the primary
  recent-publications surface uses the available width. The attention surface
  remains present when it has an operator action to expose, and the E2E shell
  assertion protects the empty-state contract.
- Calendar now links its unscheduled-publication notice directly to the
  project Queue. The calendar remains a time-scanning surface, while the
  Queue remains the place to review unscheduled work. Existing calendar unit
  coverage protects the classification that drives this notice, and the full
  publication flow remains green.
- Compose destination cards no longer use uppercase tracked labels for their
  ordinal marker. This removes a remaining generic dashboard treatment and
  keeps the source-to-destination hierarchy aligned with the accepted type
  contract without changing target editing behavior.
- Publication detail now isolates the source authoring and explicit promotion
  sections in dedicated components. `PublicationEditor` still owns the
  synchronization state, recovery, conflict handling, and domain actions;
  the extracted sections only render their existing controls through explicit
  callbacks. This reduces the route component's responsibility without
  changing the API contract, persistence semantics, or rendered workflow.
- The extracted publication-editor sections passed the web lint, typecheck,
  unit tests, and the end-to-end publication/media flow.
- The channel-target section is now isolated as well. It owns the target
  profile badge, structured editor, raw JSON error, and profile validation
  feedback, while the parent keeps only target state transitions and the
  persistence callbacks. The source, target, and promotion responsibilities
  are now explicit at the route composition level.
- The publication-detail context rail is isolated in `PublicationEditorSidebar`.
  It owns the selected-target snapshot, capability feedback, and conflict
  recovery controls; the route component passes the current editor state and
  explicit recovery actions. This preserves the existing two-column workflow
  while preventing conflict UI from becoming entangled with authoring fields.
- The schema-driven target editor now delegates field-family rendering to
  `PublicationTargetFieldControl`. The target editor remains responsible for
  profile field discovery, target JSON state, and the advanced JSON escape
  hatch; text, number, boolean, enum, list, media, and constraint presentation
  stay together behind one field-control boundary.
- `PublisherConnectionPanel` now composes the Bluesky and custom HTTP
  connection dialogs instead of owning their form state and validation. The
  panel remains responsible for channel/connection rows and callback wiring;
  each dialog keeps its existing provider-specific fields, validation, reset
  behavior, and confirmation flow.
- The dashboard sidebar's project context is now isolated in
  `DashboardProjectContext`. Project selection and creation remain controlled
  by the shell through explicit callbacks, while the sidebar itself is left
  responsible for navigation, channel orientation, and footer actions. This
  is a presentation boundary only: the project and route contracts are
  unchanged.
- The focused web quality gate passed after the extraction: lint, typecheck,
  and all 30 web unit tests (76 assertions).
