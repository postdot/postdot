## Verification matrix

### 1. Custom HTTP endpoint paths

**Classification: capability gap to design, not a confirmed P0 defect.**

`normalizeCustomHttpEndpoint` intentionally accepts an origin only. ADR-018
defines that the connection owns a fixed origin while a bounded mapped request
may construct a path and query beneath it. `mapped_http` already supports bounded
path segments, query values, request bodies, media, and response mapping.

Allowing arbitrary path-bearing connection URLs as the audit proposes would put
path credentials used by common webhook receivers into ordinary endpoint metadata
and would weaken the accepted secret boundary. The current connection contract
also has no approved way to use the encrypted connection secret as a path value.
Therefore the proposed change is not applied. A separate design issue is needed
for path-authenticated receivers or other onboarding gaps while preserving origin
validation, secret handling, and SSRF controls.

### 2. Project bearer tokens

**Classification: confirmed surface gap, with the API foundation already present.**

The database, bearer authentication, OpenAPI routes, and integration coverage are
present. The web API client and dashboard expose no token-management surface, and
`scripts/herald.ts` supports only `HERALD_SESSION_COOKIE` / `--cookie`. ADR-030
explicitly establishes project tokens as the machine boundary and describes the
CLI as a supported future consumer, while ACCESS-14 intentionally delivered the
storage and API foundation rather than a complete token-management UI.

This is follow-up product work, not a reason to change Better Auth or publisher
credential ownership.

### 3. Multi-human project sharing

**Classification: intentional sequencing, not a defect in the current scope.**

ADR-030 explicitly keeps the initial project access model creator-only and defers
memberships and invitations until a concrete collaborative workflow requires
them. The report's suggestion is valid future product input, but it does not
contradict the accepted current contract and does not create an implementation
task during this reconciliation.

### 4. Channel-management UI asymmetry

**Classification: confirmed product-surface gap.**

The API accepts built-in manual/LinkedIn profiles and runtime-defined custom
profiles, while the current web creation selector exposes only manual message and
LinkedIn. The current channel list has no channel lifecycle controls. Publisher
disconnect exists separately, but channel onboarding and profile management do
not yet present the full runtime-defined channel model.

This needs a scoped design and implementation task; it should not be solved by
duplicating provider-specific forms or by weakening the profile compiler.

### 5. Calendar authoring

**Classification: valid feature proposal, not a correctness defect.**

The current calendar is a planning/read surface. Empty days do not yet create a
publication or pass a date into composition. This is consistent with the existing
planning-surface task boundary, but it is a useful next authoring affordance and
should be tracked separately from audit defects.

### 6. Timezone semantics

**Classification: unresolved product contract.**

The browser currently renders and edits timestamps in its local timezone. The
repository does not yet expose a project timezone policy or a user-facing choice.
This requires a product decision before implementation because it affects how
scheduled timestamps are authored, displayed, and interpreted across devices.

### 7. MCP, presets, and broader built-in coverage

**Classification: future opportunities.**

An MCP server, channel presets, and additional built-in providers may be valuable,
but the report does not demonstrate a current defect. They remain roadmap input
until a concrete workflow and ownership boundary are accepted.
