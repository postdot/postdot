# WEB-224 — Identify the next MediaAttachmentPicker extraction seam

- Status: complete; proposal only
- Date: 2026-09-26
- Issue: ISSUE-119
- Scope: map remaining responsibilities and evidence; no component refactor

## Evidence

- `apps/web/src/components/media-attachment-picker.tsx` is approximately 2,000 lines and serves both the project media-management route and publication attachment workflows through `selectionMode`, `variant`, and related conditional behavior.
- It already delegates the media-library management rendering to `MediaLibraryManagementSurface`, attachment browsing to `MediaAttachmentLibraryDialog`, upload mechanics to `herald-media-upload`, and the editor/viewer/info/deletion interactions to dedicated components. These are existing boundaries and should not be duplicated.
- The parent still owns an isolated media-management lifecycle cluster: bulk selection and resolution, move-to-trash, restore, permanent deletion, partial bulk-delete results, pending/error state, and refresh/status propagation. This code only applies when `selectionMode` is `manage`; publication attachment selection does not expose these destructive operations.
- `MediaLibraryManagementSurface` currently receives the lifecycle state and callbacks along with its presentation props, while the controlling API mutations and confirmation-dialog state remain in the parent. This is a concrete behavior/ownership gap, not a case for another generic wrapper.
- Existing browser evidence in `e2e/publication-media.spec.ts` covers search/view and bulk actions, trash retention, permanent-delete confirmation/cancellation, restoration, and deletion blocking for media still in use. The tests exercise the real route and database rather than an isolated component contract.

## Bounded proposal

Extract only the management-mode asset lifecycle into a focused owner (for example, `useMediaLibraryAssetLifecycle`): move the trash/permanent-delete/restore/bulk-delete state and API workflows together, and expose the minimum state/actions needed by `MediaLibraryManagementSurface` and its confirmation dialogs. Keep shared upload, search/pagination, attachment ordering/selection, and viewer/editor behavior in their current owners for this pass.

This boundary is limited to destructive and restorative media-library actions, is inactive in publication authoring, and can be verified against the existing browser journey plus focused tests for partial failures and used-media blocking. Do not preserve the current picker props as a public compatibility layer; update the known internal callers directly if the extraction changes their contract.

## Verification and non-changes

- Inspected `MediaAttachmentPicker`, its three route call sites, the extracted management surface, upload controller, and the media E2E scenarios.
- No source, test, or UI code changed. This worklog records a proposed next implementation boundary only.
