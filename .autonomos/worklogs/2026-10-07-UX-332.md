## Operator outcome

The custom creation dialog now starts from a starter that works as shipped
(dialect declared) and no longer shows technical fingerprints to author: the
editable JSON keeps the declared identity, origin and version the operator
owns, while both hashes are derived on the server. Saving the same starter
twice, or editing the schema before a second creation, succeeds with correct
fingerprints.

A wrong definition now names the field beside the JSON with a localized
correction (English and French), keeps the typed text, and clears stale
feedback on edit — the same repair pattern as draft editing. Definition
errors appear only in the dialog; the page banner stays reserved for generic,
access, and other failures. Correcting in the same open dialog creates the
channel.

## Implementation boundaries

- Store (`packages/db/src/manual-store/project-channel-store.ts`):
  `normalizeCreationProfile` runs before compilation and persistence and
  reuses the existing `fingerprintChannelProfile` derivation with the same
  `node:crypto` SHA-256 wiring as the draft boundary — no second
  implementation. It applies only to `origin === 'custom'`, preserves
  declared `id`/`origin`/`version`, and always replaces supplied (or missing)
  hashes. Non-JSON values become a structured `profile.invalid_json_value`
  issue. Compilation failures throw the existing
  `ChannelProfileValidationError` (same code/message compatibility for other
  call sites) instead of the joined plain error. Built-in defaults and stored
  definitions are untouched.
- API body (`apps/api/src/modules/projects/models.ts`): `profileHash` and
  `schemaHash` are optional for custom creation; `id`, `version >= 1`,
  `origin: 'custom'` and the content keys stay required, so absent-key shape
  failures remain `422 validation_error` while fingerprint omission is
  permitted. `resolveChannelProfile` is unchanged (verbatim cast; the store
  normalizes).
- API route (`apps/api/src/modules/projects/channel-routes.ts`): catches
  `ChannelProfileValidationError` and returns the existing
  `profileValidationFeedback` projection (`400` with `issues`/`issueCount`),
  mirroring the draft route. Other errors keep their existing paths.
- Starters (`apps/web/src/lib/channel-profile-presets.ts`): the shared custom
  content schema declares the required dialect. Built-in provider presets and
  `templatesFromPresets` (which already added it) are untouched; no general
  starter audit was performed.
- Client (`apps/web/src/lib/api.ts`): new `CustomChannelProfileInput`
  (hashes optional) widening `ChannelCreationProfile`, and
  `ChannelCreationOutcome` (`created` plus `profileIssues`/`profileIssueCount`).
  `ApiError` already preserved structured issues; `formatApiError` is
  unchanged.
- Dashboard (`apps/web/src/lib/dashboard-context.tsx`): `handleCreateChannel`
  returns the outcome; definition failures (`400 invalid_content` with
  issues) return inline details without setting the global banner, while
  generic/access/other failures keep the existing global error. Success still
  appends the channel and repairs the first empty composer target.
- Dialog (`apps/web/src/components/channel-creation-dialog.tsx`): starter
  text omits both hashes via `creationTextForTemplate`; renders the shared
  per-field alert (same copy as draft editing, unknown codes fall back to the
  general message); preserves JSON after refusal; clears stale diagnostics on
  name, text, or template edits. Client-side shape checks are unchanged.
- Selector (`scripts/e2e-affected.ts`): the new creation spec joins the
  existing channels-and-connections domain.

Out of scope, preserved: explicit activation, historical definitions,
execution contracts, authorization, transactions, built-in behavior, cache
guard, and the `422`/`400` shape/content split. No migration, automatic
adoption, dependency, or service.

## Finishing: stale diagnostics on profile switch

Review reproduced a leftover from the first implementation: `selectProfile`
changed the chosen profile without clearing `validationError`,
`definitionIssues`, or `definitionIssueCount`. The retained browser journey
now proves it — a definition error is asserted visible (positive control),
then switching to a built-in profile must remove the alert, and returning to
the custom choice must restore the exact invalid JSON without reshowing a
stale diagnostic. The red run failed on the removal assertion, confirming the
bug; the fix clears all three diagnostic states only on an effective choice
change and never touches the preserved custom text. Green in `8.3 s`
(`10.6 s` with harness), with the remainder of the journey unchanged.
