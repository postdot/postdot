# AUDIT-317 — Validation cost and reliability

No test was deleted, no gate was changed, no retry or delay was added, and no
worker setting was modified. The audit itself was diagnosis only; the selector
under "Selector" was added afterwards as the first measurable fix, reporting a
command without wiring itself into any gate.

## Measured costs

All numbers below come from existing traces or from single sanctioned runs;
no full suite was rerun for this audit.

| Step | Cost | Source |
|---|---|---|
| Pre-commit hook (`check:quick`: format, lint, typecheck) | ~5 s warm | timed run |
| Unit tests, all 17 packages, cold (`turbo test --force`) | ~11 s wall | timed run, 0 failures |
| Single E2E spec incl. harness boot | ~25 s wall | timed `account-settings` run |
| Harness boot alone (API + migrations + vite dev) | ~10–15 s inferred | single-spec total minus test time |
| Production web build, forced (`turbo build --filter=@postbot/web --force`) | ~3 s | timed run (`vite built in 960ms`) |
| Password-reset script | ~12 s | full-gate trace |
| Full E2E suite, 84 tests in 36 spec files, `workers: 1` | 18–29 min | three full-gate traces |
| Container recovery (docker build + backup/restore) | minutes, unmeasured here | script analysis; prior runs observed in the low minutes |

Unit tests cost milliseconds each; turbo overhead dominates the 11 s. The E2E
suite cost is the tests themselves (real waits, multi-session flows), not the
harness: booting API + web for one spec costs about 25 s total.

## Findings

### 1. No package/consumer selection exists

`bun run check` always runs everything: format, lint, typecheck, all unit
tests, all 84 E2E tests, password-reset, then build. There is no mapping from
changed files to relevant specs, so a one-line locator fix costs the same
18–29 minutes as a cross-cutting change. The E2E inventory is 37 spec files (84 tests; the 37th file is the
mailpit-only password-reset spec, excluded from the default run);
typical missions in this thread touched 1–4 of them (~2–6 min) while paying
for all 84.

### 2. Turbo cache entries are valid, including across packages

Hypothesis tested and refuted: `test` has no `dependsOn`, but a probe edit in
`packages/db/src/access-store.ts` still forced `apps/api:test` to a cache
miss, and the control run without changes hit cache. Turbo hashes internal
dependency sources into the task key, so cross-package staleness does not
occur through this path. `lint`, `format`, and `typecheck` additionally carry
explicit `^` dependencies. Remote caching is disabled and `.turbo/` is
gitignored, so CI always recomputes from cold; local runs reuse the warm
cache. `test:e2e`, `test:scripts`, password-reset, and container recovery are
not turbo tasks and always execute fully, which is correct for them but is
exactly why selection matters.

### 3. E2E relevance is knowable by change type

The suite clusters cleanly: `access-*` (roles, invitations, keys, sessions),
`design-121-*` (shell, navigation, filters, empty states), `web-31*`
(Overview/calendar/access), `publication-*` and `editor-*` (authoring flows),
`realtime-*` and `publisher-*` (streams, connections), `channel-*`, media,
queue, approvals, settings. A change-type → spec mapping is constructible from
filenames plus the one-line test titles, without running anything.

### 4. Single worker is a documented requirement, not a tunable

`playwright.config.ts:60-66` pins `workers: 1` because all specs share one
API/database runtime and parallel workers can mutate instance bootstrap state
across tests. Parallelization is therefore not an available lever; wall time
scales with test count and per-test waits.

### 5. SSE breaks and long waits dominate E2E time and flakes

Corrected by SSE-318: this attributed the failure to the vite proxy. The proxy
only reported an upstream reset. Bun ends a connection idle for ten seconds while
the SSE heartbeat interval is fifteen, so every quiet stream was torn down before
its first heartbeat and the proxy surfaced that as `502`. The waits and ceilings
below were real and correctly measured; only the cause was wrong.

The vite proxy surfaces an upstream reset as 502 / socket hang up, so stream
discovery degrades to heartbeat-bounded waits with 60–90 s timeouts. The suite
holds 14 fixed sleeps (`waitForTimeout` 50 ms–5 s, mostly 3–5 s stability
windows added in WEB-314) and per-test timeouts up to 300 s. Observed flakes
all trace to this environment, never to masked retries (`retries: 0`):
a `times: 1` interception consumed by background traffic, shared-endpoint
request counting polluted by flap-driven refetches, and a timing-sensitive
save indicator under suite load. Each was fixed by making the test
deterministic, never by waiting longer.

### 6. Duplications are small and mostly by design

- The pre-commit hook runs `check:quick`; CI runs the full `check`. Overlap
  is intentional (fast local signal, authoritative remote verdict) and cheap
  when cached (~5 s warm hook).
- `check` chains with `&&`, so the first failing step stops the run; no work
  is spent past a failure.
- `i18n:compile` + coverage rerun as uncached npm lifecycle pre-scripts for
  test, typecheck, and build on every invocation (seconds each). Minor
  repetition.
- Container recovery duplicates dependency install and the full build inside
  Docker with no shared cache. Justified (it validates image wiring, backup,
  restore, and lock behavior that host runs cannot), but it is the most
  expensive repeated step after E2E.

## Proposed three-level validation

### L1 — fast local loop (seconds)

`bun test <file>` for the touched unit, one affected Playwright spec at most,
plus `oxfmt`/`oxlint` on changed files. Guarantees: immediate logic and style
feedback. Does not cover: cross-package effects, other surfaces, browser
journeys beyond the chosen spec, container image, or the full matrix.

### L2 — targeted validation before commit (minutes)

All unit tests stay in L2. They are the cheapest layer in the repository
(~11 s for 17 packages at 0 failures, and cache-warm on repeat), so scoping
them by package would trade a real cross-package guarantee for seconds.
L2 is therefore: `bun run check:quick`, `bun run test:unit` (full), then the
E2E scenarios reported by `scripts/e2e-affected.ts`, then `turbo build
--filter` for the touched packages when runtime code changed.

Typical cost: hook (~5 s) + units (~11 s) + 1–8 specs (~1–4 min).
Guarantees: every unit test, every static gate, and the browser journeys of
the affected functional domains. Does not cover: cross-spec interference,
unaffected domains, container wiring, or the 84-test matrix.

### L3 — full integration control (tens of minutes)

`bun run check` plus `test:container:recovery`, on CI for every push/PR and
locally only before merge-worthy milestones. Guarantees: the whole contract
as CI sees it. Does not cover: production traffic or multi-user concurrency
beyond one worker. Note that the mailpit mail-delivery variant is *not* a
blind spot: `test:e2e` ignores `access-219-password-reset.spec.ts` by default
but `test:e2e:password-reset` starts Mailpit through Docker Compose and runs
that spec, at the price of a second API/web runtime boot.

## Ten slowest scenarios, and what their time is made of

From the last green full gate (84 tests, 23.1 min wall; 83 timed entries
excluding the separately-run password-reset script). Observed duration is
wall time in that run; fixed wait is summed `waitForTimeout` inside the test
body; max timeout is the effective `test.setTimeout` / assertion timeout
in force, falling back to the Playwright default of 30 s.

| # | Scenario | Observed | Fixed wait | Max timeout |
| - | -------- | -------- | ---------- | ----------- |
| 1 | `web-124-outcome-states.spec.ts:156` reviews mixed operational work across responsive locale and theme combinations | 96.0s | 0.0s | 180s |
| 2 | `publication-media.spec.ts:942` persists mixed and media-only publications through the dashboard | 49.8s | 0.0s | 90s |
| 3 | `editor-composer-pilot.spec.ts:6` recovers composition text, target formatting and media through the existing draft contract | 43.8s | 0.0s | 90s |
| 4 | `publisher-connection-recovery.spec.ts:99` targets connection repair from automatic publication detail | 41.7s | 0.0s | 90s |
| 5 | `access-135-workspace-invitation.spec.ts:8` joins the selected group and unlocks its project access | 39.2s | 0.0s | 150s |
| 6 | `settings-workspace-continuity.spec.ts:9` keeps personal and installation settings open when changing workspace context | 31.6s | 0.0s | 90s |
| 7 | `web-310-overview-viewer-actions.spec.ts:5` withholds viewer create and bulk actions while keeping consultation | 30.4s | 0.0s | 180s |
| 8 | `account-settings.spec.ts:9` edits personal identity and safely changes the password across settings layouts | 29.6s | 0.0s | 90s |
| 9 | `publication-detail-actions.spec.ts:5` keeps publication detail actions aligned with the scheduled lifecycle | 29.3s | 0.0s | 45s |
| 10 | `publication-media.spec.ts:72` keeps dashboard and composer media journeys reliable | 25.9s | 0.0s | 60s |

Reading of that table:

- The top ten account for 7.0 min of 22.9 min (30.4%) — a long tail, not a few
  pathological tests.
- **None of the ten contains a fixed wait.** Their time is real browser and
  server work plus expectation polling. Fixed waits live elsewhere: 14 calls
  totalling 39.8 s (2.9% of wall) across only 4 of 83 spec files. So no sleep
  was hiding cost in the slow tail, and removing the remaining sleeps would
  buy at most ~3% of suite wall time.
- **Max timeouts are ceilings, not costs.** Summed across the suite they reach
  114 min against 22.9 min observed, so timeout reduction cannot shorten a
  passing run; it only shortens failures. Median effective ceiling is 45 s,
  and only 7 tests exceed 30 s observed.
- The practical conclusion for cost: reduce *selection*, not waits. SSE
  stabilization is still the right next mission for reliability, but it is not
  a wall-time lever.

## Limits of the cache probe

The cross-package probe was: append a comment line to
`packages/db/src/access-store.ts`, run `turbo test --filter=@postbot/api`,
revert, and re-run.

- Observed: forced `cache miss, executing 48b493457e75d99c` on
  `apps/api:test`; control run returned `cache hit, replaying logs
  9704eae8a506ea59`; the reverted tree was clean afterwards.
- What it proves: `test`, which declares no `dependsOn`, still incorporates
  internal dependency sources into its task hash, so the documented
  `dependsOn: ["^test"]` hardening is not required here for correctness.
- What it does not prove: it is a single pair of observations for one task in
  one package pair. It does not establish hashing behavior for
  `.env*` inputs, for root-level files outside any package (those invalidate
  broadly by design), for a `remote` cache, or for a task whose real inputs
  live outside the package (an E2E run, or a script reading the working tree).
  `test:e2e`, `test:scripts`, password-reset, and container recovery are not
  turbo tasks at all and are never cached.
- It also says nothing about whether a cache hit implies the same *coverage*:
  a hit replays logs from a previous run under different data.

## Selector: `scripts/e2e-affected.ts` (this mission)

`bun run test:e2e:affected` reports the scenarios a change set can affect, or
the full matrix with the reason it fell back. Behavior:

- **Mapping by functional dependency.** Ten domains (identity/recovery,
  access control, authoring, lifecycle, media, channels, overview, shell and
  locale, realtime, workspace) each own the API modules, routes, components,
  and packages a capability depends on. A file serving several journeys
  belongs to several domains, so `publication-routes.ts` selects both
  authoring and lifecycle scenarios. A co-located `*.test.ts(x)` resolves
  through the module it exercises, across the `.ts`/`.tsx` boundary.
- **Reasons are reported.** Every retained scenario lists the domain and
  label that selected it; a changed spec is retained with the reason
  "scenario file changed".
- **Unknown or transversal path → full matrix.** Transversal covers
  `packages/db|core|client|email`, the API composition root, shared dashboard
  transport and context, harness and CI configuration, the commit gate, and
  governance records, each with its own stated reason.
- **Never an unreliable empty selection.** No changed path, a change set with
  no attributable scenario, and a spec with no domain entry all return the
  full matrix instead of "nothing to run".
- **New, deleted, and uncommitted changes.** Change collection unions
  committed (merge-base to `HEAD`), staged, unstaged, and untracked paths, so
  the working tree is never half-invisible. A deleted spec is excluded from
  both targeted and fallback output; a deleted *code* path still selects its
  domain, because deleting it is itself a behaviour change.
- **Deterministic.** Reasons are de-duplicated, sorted, and independent of
  input order. 28 tests in `scripts/e2e-affected.test.ts` cover glob
  semantics, the four fallback rules, deleted-file handling, cross-domain
  membership, order independence, and change collection against a real
  temporary git repository.
- **No gate change.** It reports a command; it does not wire itself into
  `check`, the hook, or CI, and it touches no worker, retry, or wait setting.

Measured selections on real change sets from the WEB-312…316 series:

| Change set | Selected | Observed cost |
| --------- | -------- | ------------- |
| `project-access-verification.ts` alone | 8 of 37 specs | ~2.7 min |
| `media-library-page.tsx` alone | 3 of 37 specs | ~3.4 min |
| `packages/x/src/x-client.ts` alone | 6 of 37 specs | ~2.6 min |
| WEB-314 hardening (9 files) | 22 of 37 specs | 15.3 min |
| `packages/db/src/schema.ts` | 37 of 37 specs (transversal) | full, ~23 min |

Costs are reconstructed from the recorded per-test times of the last green
gate, not from new runs. The lesson is deliberate: domains that overlap a
real mission (WEB-314 touched the editor, which authoring and lifecycle share)
select most of the matrix, and the honest answer is then a large selection
rather than a narrow one that under-covers.

## Proposed update to the integration rule in `AGENT.md`

Superseded as a proposal by [ADR-077](../../decisions/ADR-077-two-validation-obligations.md),
which separates the local commit obligation from the full validation obligation
and deliberately drops merge-to-`main` as an automatic trigger. The draft text
kept below is retained only for provenance; ADR-077 is the version to review.

### The distinction being proposed

The current rule (lines 21–25) names only one obligation — run the full
`bun run check` — so it reads as "after every pass". The proposal separates two
different acts that happen to be governed by the same sentence today:

- **Commit locally.** A working, self-consistent checkpoint on a mission branch.
  Its gate is the cheap, honest one: `check:quick` (the pre-commit hook already
  enforces this), all unit tests, and the scenarios the selector reports.
- **Full validation.** An authoritative statement that the repository is
  healthy, taken once per validated state rather than once per pass.

Nothing is weakened: `check` stays the authority, and the selector falls back to
the full matrix whenever it cannot justify a narrower answer.

### Triggers for the full control

A full `bun run check` (plus `test:container:recovery` when container behaviour
is involved) is required when:

1. A mission ends and its work is about to be integrated into `main`.
2. The change is transversal by the selector's own report — anything under
   `packages/db`, `packages/core`, `packages/client`, `packages/email`, the API
   composition root, shared dashboard transport or context.
3. A dependency, lockfile, toolchain, harness, or CI configuration changed.
4. A change touches authentication, sessions, authorization, or access
   revocation, including provider protocol packages.
5. The selector retained a domain overlap large enough that the selection is not
   materially cheaper than the suite — a rule of thumb is more than half the
   matrix, or more than ten minutes of expected runtime.
6. Any previously observed flake is implicated, or the targeted run is not
   reproducible on a second attempt.
7. The mission claims an invariant that only the whole matrix observes, such as
   cross-spec interference or a shared-runtime ordering assumption.

Between triggers, `check:quick` plus all unit tests plus the targeted scenarios
is the expected evidence for a commit.

### Tracing the last fully validated commit

Two records, one in git and one in Autonomos, so the answer survives both a
`git log` and a session handover:

```bash
# The commit that last passed the full control.
git tag -f validated/full -m "bun run check green" HEAD   # or a dated annotated tag
git rev-parse validated/full                                # read it back
```

The tag name and the marker convention are the owner's to choose; what matters
is that one ref answers "what is the newest state known to be fully validated".
CI already re-establishes the same fact on every push, so a stale tag is
detectable rather than silently trusted.

In `.autonomos/TASKS.md`, each completed task records the validated ref next to
its evidence, and the session worklog records the same SHA with the command that
was run. A commit that is newer than `validated/full` is, by definition, only
locally validated.

### Proposed text

> - **Integration (temporary owner direction):** Until the owner changes this
>   direction, integrate completed work directly into local `main`. Do not open
>   pull requests or wait for GitHub Actions. Local integration must not depend
>   on publishing `main` to the remote.
> - **Two validation obligations.** A local commit requires `check:quick`,
>   `bun run test:unit`, and the scenarios reported by
>   `bun scripts/e2e-affected.ts --base <mission base>`, which falls back to the
>   full matrix for an unknown or transversal path. A full validation requires
>   `bun run check`, plus `bun run test:container:recovery` when container
>   behaviour is involved, and is required at integration, for transversal or
>   dependency, harness, or CI changes, for authentication, session, authorization,
>   or access-revocation changes, when the retained selection is not materially
>   cheaper than the suite, and whenever a flake is implicated. Never narrow the
>   full control itself and never weaken a check to make a targeted run pass.
> - **Validated ref.** Keep the newest commit that passed the full control on a
>   `validated/*` ref, and record that SHA in the task entry and the session
>   worklog. Any commit newer than it is locally validated only.
