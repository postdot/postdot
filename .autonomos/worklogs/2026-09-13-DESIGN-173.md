# DESIGN-173 — Clarify Publication Authoring IA and Vocabulary

- Status: Done
- Branch: `codex/reui-calendar-spike`
- Owner: orchestrator
- Scope: Audit the creation entry points and user-facing language around the
  multi-channel publication authoring flow.
- Related issue: ISSUE-098
- Related decision: ADR-057

## Context

The current route is named `/compose` and is exposed in the project sidebar as
`Composer`. Overview, Calendar, Queue, and empty states also link to the same
creation flow through labels such as `New publication`. The route is not a
decorative duplicate: it creates one shared post/source and one or more
channel-specific publications, then captures delivery mode and schedule per
destination. The concern is whether that capability is presented through a
mental model and vocabulary an operator would naturally choose.

## Initial audit

- `apps/web/src/components/publication-composer.tsx` presents two peer sections,
  `Source` and `Destinations`, then exposes shared defaults, channel tabs, an
  optional channel copy override, delivery mode, and schedule.
- `apps/web/src/components/dashboard-sidebar.tsx` presents `Composer` as a
  persistent peer beside Overview and Queue, even though the same creation job
  is available from overview/calendar/queue actions.
- `apps/web/src/routes/dashboard/projects/$projectId/compose.tsx` is a new
  authoring route with optional calendar date/time context. The URL is an
  implementation detail and need not determine the visible label.
- `apps/web/src/components/publication-editor.tsx` is the later editing surface
  for an existing publication and uses a related but more technical vocabulary:
  source document, structured target payload, source revision, and promotion.
  A label change on the new-flow page must not make this lifecycle incoherent.
- `apps/web/src/lib/dashboard-context.tsx` confirms the user job: one source
  content object can create several publication inputs, each tied to a distinct
  channel and schedule/delivery mode. The first active channel is preselected,
  while the default schedule is generated automatically.

## Direction under review

The dedicated creation route should remain as the reusable full authoring
surface, including calendar date/time deep links, but its status as a permanent
sidebar destination is a product decision rather than a technical necessity.
The initial candidates are:

1. Keep it as a primary navigation destination, but replace `Composer` with
   user vocabulary and make all other creation actions converge on it.
2. Keep the route and all contextual creation actions, but remove it as a peer
   navigation item; add or retain one clearly available global creation action
   where the shell needs it.
3. Fold creation into a broader Publications destination and reserve the route
   for a clearly named new-publication state, if the resulting information
   architecture remains simpler than the current one.

The accepted direction is option 2: preserve the route and multi-destination
capability, but treat the route as a task surface rather than a peer in the
Work navigation. The route is renamed to `/dashboard/projects/$projectId/publications/new`;
the private development application does not need a `/compose` compatibility
alias. A primary `New publication` action is available in the project sidebar,
and project creation moves into the project selector because it is workspace
setup rather than daily work.

For language, prefer terms already used consistently by the product (`publication`,
`canal`, `planification`) and avoid exposing `payload`, `target`, or `source`
unless the term explains an actual decision. Candidate labels such as `Nouvelle
publication`, `Rédiger`, `Publication`, or a localized equivalent remain options
to evaluate against the whole flow, not isolated button replacements.

## Open decisions

- Is the sidebar item a destination users revisit, or only a creation action?
- Should the page lead with the publication task and progressively reveal shared
  content/channel adaptation, rather than presenting Source/Destinations as two
  equal panes?
- Which term best names a channel-specific version without implying a separate
  post or technical target?
- Where should the default schedule and manual/automatic delivery decision live
  so the primary action remains obvious without hiding important consequences?
- How should the new-flow vocabulary align with the existing publication editor
  and queue without adding repeated explanatory copy?

## Resolution

The owner clarified that the route name must be corrected at the same time as
the visible page name, and that the existing “Create project” control should
not compete with daily work in the sidebar. The accepted vocabulary is based on
the product’s established noun `publication`, not on the literal example
“Créer une publication”. WEB-174 implements only this entry-point and sidebar
slice; the Source/Destinations information architecture remains a separate
authoring UX decision.
