# DEV-417 — Guard the production bundle against escaping runtime dependencies

## Plan

1. Establish the parent ground truth on the image's real runtime contract and on the bundle's remaining external requires.
2. Register a bounded delegated mission for a permanent, Docker-free regression that fails whenever the bundle would again depend on something the image does not carry.
3. Review the candidate against the acceptance criteria, execute it in the canonical checkout with the old-source negative control, and integrate.

## Context

DEV-416 corrected the production image: Elysia's runtime route compiler had kept five external `require("typebox/...")` calls in the bundle, the image carries no `node_modules`, and every compiled route answered HTTP 500. The correction wires the namespaces statically. A checkout could never have caught it, because the repository's `node_modules` resolves the require.

That makes the defect class, not the single defect, the thing worth guarding: a runtime dependency that escapes the bundle is invisible to every host-side test and fatal in the image.

## Parent ground truth

The bundle built from the corrected source keeps no external runtime require: a scan for `require("specifier")` with a literal specifier finds none outside relative paths and Node builtins, there is no non-literal `require` call site, no native module reference, and no `import.meta.require` with a variable argument.

The image's real runtime contract was then reproduced locally with an image built from the local `oven/bun:1` base, which is bun 1.4.2, the version the repository `Dockerfile` pins, and carrying the same `ENTRYPOINT`, `STOPSIGNAL`, environment, `USER bun`, `/data` ownership, named volume and `HEALTHCHECK`:

| Property | Observed |
| --- | --- |
| Container user | `uid=1000(bun) gid=1000(bun)` |
| Named volume mounted on `/data` | owned by `1000:1000`, inherited from the image directory |
| Database and runtime marker | created by the `bun` user in the volume |
| `GET /health`, `GET /ready` | 200 |
| The image's own `HEALTHCHECK` | `healthy` |
| The DEV-415 startup-termination check | passes, marker released, 115 ms margin |

The packaged poster decoder could not be exercised here: the repository image builds ffmpeg from source and that build needs the network. It is unchanged by the correction and remains the CI confirmation.

## Implementation mission

- Owner: parent orchestrator. Worker: delegated MiniMax M3.1 Flash Free mission in a dedicated worktree.
- Allowed writes: one new test file under `scripts/`, and a temporary, byte-for-byte restored replacement of `apps/api/src/index.ts` for the negative control.
- Forbidden: every other file, product code, configuration, dependencies, lockfiles, governance, commits, merges, `main` writes, further delegation, Docker, the network, the owner's `.env`, real database, real media root, default ports and real credentials.
- Acceptance: the test builds the production bundle, runs it from a directory where no module can resolve, and asserts that `/health` and `/ready` answer 200 and that an invalid request body is rejected with 422 rather than 500; and it inspects the built bundle and fails when an external runtime require survives.
- Stop: the scoped uncommitted diff, the exact check results, the negative-control evidence and the limitations. The parent reviews and executes the test in the canonical checkout.

## Round 1 and round 2

The worker delivered the guard in one file, and the parent reviewed it whole. The parent accepted the behaviour, the messages, the module-less verification and the metafile comparison, and required two revisions: the hand-written require scanner had to leave the behaviour test and become a named module, and its non-vacuity had to be committed as unit tests instead of ad-hoc probes.

The parent also corrected its own original specification: the requirement that the bundle "contains no external runtime require" was wrong, because the corrected bundle still contains Elysia's dead fallback code. The rule the worker established, and the parent accepted, is that a literal require of a package is always a violation, a dynamic require of a package the bundle does not carry is a violation, and a dynamic require of a carried package is not reported statically, because only the serving check proves it is unreachable.

The final shape is three files: `scripts/bundle-requires.ts` (the scanner, with its rule and its limits documented), `scripts/bundle-requires.test.ts` (ten unit tests over source fixtures, which pin the detected shapes and the known limits), and `scripts/production-bundle-dependency.test.ts` (the two behavioral checks).

## Parent acceptance

Parent verification in the canonical checkout:

- `bun test scripts/bundle-requires.test.ts scripts/production-bundle-dependency.test.ts`: 12 pass, 0 fail, 28 assertions, under a second.
- Negative control with the REAL pre-correction `apps/api/src/app.ts`: both behavioral checks fail with the accepted messages, "The production bundle answered GET /health with 500" and "The production bundle requires packages the image does not carry: typebox/system (dynamic require), typebox/compile (dynamic require)".
- `bun test scripts`: 91 tests, 90 pass. The single failure is the pre-existing, unrelated `scripts/postbot.test.ts` expectation that omits the `facebook` entry of `oauthReadiness`; it fails identically on a clean tree.
- `bun run check:quick`: format, lint, spelling and typechecks across the workspace pass without bypass.

The module-less condition is verified rather than assumed: every ancestor of the bundle's working directory is scanned for `node_modules`, and a `bun --no-install` probe resolves every package specifier the bundle carries, which is 87 of them, and must resolve none.

## Evidence

- The defect class is now guarded: a runtime dependency that escapes the bundle fails the repository's own test suite, on a checkout, without Docker.
- The worktree and its branch were removed after the parent confirmed that the canonical files match the accepted candidate. The disposable images and the temporary bundles were removed as well. No normal database, media root, owner credential, owner `.env` or existing service was touched.

## Next steps

The remaining production confirmation is the repository's own container acceptance against the real image, which needs a runner with bridge networking and the network access its ffmpeg build requires. The packaged poster decoder was not exercised locally for the same reason.

Recommended next task: run the container acceptance on the CI image and confirm the whole scenario, including the packaged poster decoder, the backup and restore round trip, the graceful stop, the startup-termination check and the forced-stop probe.
