# MEDIA-179 — Prototype a Herald-owned media workspace and standalone image editor

- Status: Complete (prototype)
- Branch: `codex/reui-calendar-spike`
- Owner: orchestrator
- Scope: Reusable browser media primitives and editor integration boundary; no vendor Dashboard UI.
- Related issue: [ISSUE-101](../ISSUES.md#issue-101-establish-a-herald-owned-media-authoring-and-editing-boundary)

## Starting evidence

`MediaAttachmentPicker` currently owns library loading, the project
`reserve → upload → finalize` flow, selection, accessibility text, compact
previews, and ordering. The compact surface has no full-size viewer and uses
fixed arrow controls for ordering. `packages/media` is correctly server-side
storage-only and must not become a React package.

Uppy remains a credible upload-orchestration candidate, especially through its
core/headless direction, but its Dashboard is not a Herald surface. Its image
editor is documented around Dashboard, so it is not assumed to be the final
editor. A standalone React cropper/editor and a Herald-owned viewer will be
tested against the existing upload boundary.

## Working contract for the prototype

- Originals remain immutable.
- An edited image is uploaded as a new verified asset during the experiment;
  the selected attachment is replaced only after verification succeeds.
- Crop, zoom, and rotation are editor state, not provider payload fields.
- Reordering must have a pointer path and a non-drag alternative; permanent
  left/right controls are not the primary visual treatment.
- The production UI uses Herald tokens and Base UI primitives. No Uppy
  Dashboard CSS or visual shell is part of the candidate integration.
- The existing API lifecycle remains authoritative until a competing adapter
  proves a concrete recovery or performance advantage.

## Comparison to run

1. Uppy core/headless plus its image-editor capability, with no Dashboard.
2. A React-oriented standalone editor (first candidate: `react-easy-crop`)
   plus the existing Herald upload lifecycle.
3. A lightweight full-size viewer and sortable attachment strip that can be
   reused by the publication form and the Media route.

The comparison records editor control quality, keyboard and screen-reader
behavior, mobile interaction, output fidelity, upload/retry behavior, client
bundle impact, and how cleanly the result maps to immutable assets.

## Next step

The prototype is accepted as the first media slice. Keep the composition in
`apps/web` for now: it still depends on the app API client and `MediaReference`,
and a new package would only move those product boundaries without a second
consumer. Extract a generic `@herald/media-ui` package when the Media route and
publication authoring share a stable, API-independent contract.

## Delivered evidence

- Added a Herald-owned full-size viewer with a single built-in dismissal path,
  an explicit image edit action, and a generic non-image preview fallback.
- Added a standalone image editor with source, square, portrait, and landscape
  crop modes, pointer crop positioning, scroll zoom, ninety-degree rotation,
  reset, visible keyboard-focusable controls, and light/dark semantic surfaces.
- Saved edits through the existing `reserve → upload → finalize` lifecycle as a
  new verified asset. The original remains immutable; a selected source is
  replaced only after verification succeeds.
- Added native attachment dragging plus visible-on-focus and mobile arrow
  controls as the non-drag alternative. Selection and preview actions are
  separate accessible controls, and the order hint is localized.
- Lazy-loaded the viewer/editor module. The production build keeps the picker
  at 24.31 kB (8.45 kB gzip) and loads the 41.48 kB editor chunk (13.81 kB gzip)
  only when the viewer/editor is opened; the editor stylesheet is also split.

## Deliberate production boundary

Uppy Dashboard was not adopted. Uppy core/headless remains a candidate only if
the upload workflow later needs resumability, remote sources, or more advanced
retry orchestration than the current project-scoped API requires. The current
editor proof uses `react-easy-crop` because its cropper is React-native enough
to keep the presentation and tokens owned by Herald; it is not yet a promise
that provider-specific image variants or a generalized media package are done.
