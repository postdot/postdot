---
title: Authentication
description: Choose API-key access, understand its limits and identify session-only operations.
---

Use a Postdot API key for a script, agent or integration. Studio authenticates
people through a session. Both methods remain subject to the server's access
checks; an API key does not replace the project permissions of its owner.

## Use an API key

Create a key in Studio under **Settings**, then **API keys**. Select the projects
and actions the integration needs. Copy the secret when it is shown and keep it
in your tool's secret configuration or environment.

Send it in the authorization header:

```http
Authorization: Bearer YOUR_POSTBOT_API_KEY
```

Replace the placeholder with the secret. Do not commit a real key or include it
in a shared prompt. You can change the limits or revoke the key from Studio.

### Choose action limits

For a draft-only integration, select `project:read` and `publication:manage`.
Leave `publication:dispatch` out to prevent scheduling and delivery actions.

| Action                       | What the integration can request                                             |
| ---------------------------- | ---------------------------------------------------------------------------- |
| `project:read`               | Read supported project resources, including channels and publications        |
| `project:manage`             | Archive and restore projects with the required live role                     |
| `project:permanently_delete` | Request permanent project deletion with impact confirmation                  |
| `publication:manage`         | Create and edit drafts                                                       |
| `publication:dispatch`       | Schedule publications and request delivery actions                           |
| `channel:manage`             | Manage supported channel configuration operations                            |
| `media:manage`               | Import, upload and manage media, including deletion requests and restoration |
| `media:permanently_delete`   | Request permanent deletion of eligible trashed media                         |
| `analytics:refresh`          | Request a refresh of supported provider analytics                            |

These limits allow requests; the server still checks project roles, resource state
and operation-specific requirements. For example, media deletion remains subject
to reference and retention checks.

A key's effective access combines its project selection, action limits and the
owner's current access. If the owner loses access to a project, the key loses it
too. Selecting all actions does not grant administrator rights or access to
session-only routes.

Follow the [draft-only CLI walkthrough](/docs/automation/#create-a-draft-for-review)
for a complete example with limited permissions.

## Operations that require a session

API-key management, access administration and built-in provider account
connections require a human session. Complete these through Studio; an API key
cannot perform them even if it has all available actions.

Provider credentials are separate from Postdot API keys. A Bluesky authorization
or a Discord bot token connects a publishing destination; it does not authenticate
a script to the Postdot API. See [provider connections](/docs/providers/) for those
workflows.

## Read authentication in the reference

The generated reference names the authentication schemes `bearerAuth` and
`sessionCookie`. Read the operation's security declaration before choosing a
credential.

| Security declaration            | Meaning                                                                                                        |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `bearerAuth` or `sessionCookie` | Either a Postdot API key or a session can authenticate; authorization checks still apply                       |
| `sessionCookie` only            | A human session is required; an API key is insufficient                                                        |
| Empty security requirements     | The operation does not require these authentication schemes; it may still validate signed URLs or other inputs |

An operation can inherit the schema's default security or declare its own.
`bearerAuth` and `sessionCookie` are alternatives in the default declaration, not
two credentials you must send together. An operation appearing in the reference
is not a grant of access.

## If a request is refused

- **401:** check that the credential is present and valid. A key may have expired
  or been revoked.
- **403:** check the operation's authentication method, the key's project and
  action limits, and the owner's current project role. Session requests can also
  fail origin checks.

Use the error code and message returned by the server to narrow the cause. Avoid
adding permissions until you know which requirement the request failed.

## Request approval without scheduling

A key with `publication:manage` can submit a publication approval request with
`expectedDraftRevision` and `proposedScheduledAt` in Unix milliseconds. The proposal
is inert: the publication remains a draft without an executable schedule. A human
session must review it. API keys cannot approve/reject, and an overdue proposal
does not automatically publish. Editing the draft supersedes pending review.

Direct scheduling requires `publication:dispatch` and the existing revision/state
checks. An HTTP success confirms the requested operation, not provider delivery.
See the approval-request operations in the [API reference](/docs/reference/).
