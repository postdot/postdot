Providers accept different content and expose different engagement data. Inspect
the selected channel's active profile and connection in Studio before preparing
a publication. The table describes implemented support; it is not proof of live
acceptance for every format, account entitlement or permission grant.

| Destination | Publishing                                                | Saved performance / conversations                             |
| ----------- | --------------------------------------------------------- | ------------------------------------------------------------- |
| Bluesky     | Text, images, MP4, link card or thread                    | Post observations and public conversation snapshots/replies   |
| Mastodon    | Text, images, MP4, poll or thread                         | Status observations and public conversation snapshots/replies |
| DEV.to      | Markdown article with optional cover                      | Article observations; no conversation workflow                |
| Discord     | Message with images or MP4                                | No native performance/conversation surface                    |
| X           | Weighted text, images or thread                           | No native performance/conversation surface                    |
| LinkedIn    | Member/organization text, images or MP4                   | No native performance/conversation surface                    |
| Telegram    | Message, photo/video, album or anonymous text-answer poll | No native performance/conversation surface                    |
| Facebook    | Page text, link or up to ten photos                       | No native performance/conversation surface                    |
| Instagram   | One JPEG or 2–10 JPEGs in a carousel                      | No native performance/conversation surface                    |
| Manual      | Record your own delivery result                           | No native provider collector                                  |
| Custom HTTP | Profile-defined request and response interpretation       | No native provider collector                                  |

[First comments](/docs/first-comments/) are a separate automatic-delivery feature
for native Bluesky and Mastodon publications. They do not add comment support to
every destination or turn the stored conversation view into an account-wide inbox.

Existing channels keep their active profiles until you load and activate the
shipped template in the channel profile editor. Selected publication versions
retain their historical profiles. Adapt a pending draft explicitly when it
should use the new capabilities.

Facebook's ten-photo limit is Postdot's application envelope, not a universal
provider maximum. A link and photo attachments remain separate Facebook formats.
See [Instagram](/docs/providers/instagram/#publishing-and-media-requirements) and
[Bluesky link cards](/docs/providers/bluesky/#add-a-link-card) for format details.

## Write a thread

X, Bluesky and Mastodon support destination-specific threads of up to 25 messages
in Postdot. Open a publication and choose **Add a reply** below the editor. Write
and reorder the replies, then select or schedule the version as usual. Each
message has its own destination text limit. The shared source remains the first
message; each destination owns its continuations.

Attachments, polls and link cards belong to the first message. Replies contain
text. Mastodon keeps the thread’s visibility, language and content warning;
choose public, unlisted or followers-only visibility rather than direct messages.
Existing channels need the shipped thread-capable template and an explicitly
adapted draft before these controls appear.

Automatic delivery sends each reply after its predecessor. A confirmed message
is retained if a later message fails. Studio shows the confirmed message count;
the started thread keeps its original version. **Retry** continues from the saved
receipts. Postdot marks the publication published only after every message is
confirmed and retains the first message as its external identity. Performance
observations therefore describe that first message, not an aggregate of the thread.

If an outcome is uncertain, inspect the named message on the platform. Confirm
that it was sent, supplying its identifier, or confirm that it was not sent.
Bluesky also requires the sent message’s CID, the record version used to attach
subsequent replies. Then retry the publication. Postdot never automatically
resends an uncertain message.

For API authoring, add continuations to the destination’s `targetContent`:

```json
{
    "text": "The first message",
    "media": [],
    "thread": [{ "text": "The second message" }, { "text": "The third message" }]
}
```

## Read delivery history

Open **Performance** to see recorded publications, failures, uncertain outcomes
and scheduled retries. Choose the last 7, 30 or 90 days and, optionally, one
destination. The comparison uses the immediately preceding period of the same
length. Daily activity uses the project's timezone; the first and last days can
be partial.

Delivery history includes manual publications. A publication can have a failure
or an uncertain outcome before it is eventually published, so those categories
overlap. They describe recorded history rather than the queue's current state.
If events cannot be interpreted, the page warns that totals may be incomplete
and omits the comparison.

**Saved engagement** keeps provider measures below the delivery report. Its tag
filter and CSV export have their own scope. Loading or reloading either report
reads saved Postdot data. Only an explicit provider refresh collects new measures
from a platform.

The API accepts `GET /api/projects/{projectId}/analytics?days=30`. `days` is a
server-anchored rolling window of 1–366 days; it cannot be combined with explicit
`from` or `to` timestamps. Existing timestamp queries remain supported.

## Read saved observations carefully

Performance uses available saved provider observations with their collection time.
Missing values differ from measured zero. A read of saved results is distinct
from a provider refresh, which makes a real external request and requires the
appropriate permission/access.

Tag filters use current publication assignments, not historical membership.
Several selected tags require all of them, without duplicating a publication.
Destination metrics retain their own meanings; they are not summed into unique
reach or a cross-provider audience. Export uses saved results and does not itself
refresh providers. An export is not a transactional historical snapshot.

## Prerequisites and evidence

Provider application permissions, account type, connection state and public media
reachability can constrain a working integration. Synthetic tests establish local
protocol behavior; a real delivery verifies only the account/format tested.
Do not infer entitlement or free provider reads from an OAuth grant alone.
See [connections](/docs/providers/) and
[deployment configuration](/docs/provider-configuration/) for setup boundaries.
