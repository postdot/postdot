title: Installation
description: Install Postdot with Docker Compose and configure persistent storage.
---

Postdot runs its API, dashboard, publication worker and scheduler in one Bun
container. SQLite and local media share one persistent volume. The current release is
`0.1.0-alpha.4`. This guide uses release-matched Compose/configuration files and the public
`ghcr.io/postdot/postdot:0.1.0-alpha.4` image, accepted on Linux AMD64 and ARM64.
Upgrade from `0.1.0-alpha.3` and restoration of its pre-update backup have been
validated on both platforms; see the [release record](/docs/releases/).

## First installation

Before starting, have these available:

- Docker Engine with Compose v2.20 or newer.
- curl to download the deployment files.
- OpenSSL to generate the deployment secrets.

Create a new installation directory and download both files from the image's
[source revision](https://github.com/postdot/postdot/tree/e7af5550ffa446f9264ec13159e0ed9e263e1495):

```sh
mkdir postdot
cd postdot
POSTDOT_SOURCE=e7af5550ffa446f9264ec13159e0ed9e263e1495
curl --fail --location --output compose.yaml "https://raw.githubusercontent.com/postdot/postdot/$POSTDOT_SOURCE/compose.yaml"
curl --fail --location --output compose.env.example "https://raw.githubusercontent.com/postdot/postdot/$POSTDOT_SOURCE/compose.env.example"
```

Run subsequent commands from this directory. Installing the published image does
not require a source checkout or Bun on the host.

### 1. Configure the instance

```sh
cp compose.env.example .env
chmod 600 .env
openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32
```

Paste the three generated values into the empty `BETTER_AUTH_SECRET`,
`POSTDOT_MEDIA_PUBLIC_URL_SECRET` and `POSTDOT_PUBLISHER_ENCRYPTION_KEY` entries,
respectively. Use independent values and retain this file securely. Losing the
publisher key makes stored connection credentials unusable; replacing it is not
an ordinary configuration update.

The defaults serve [http://127.0.0.1:3000](http://127.0.0.1:3000). If this port is occupied, change
`POSTDOT_HTTP_PORT` and the ports in **both** origin variables. Keep `.env` out of
Git and never publish the output of `docker compose config`, which includes secrets.

### 2. Pull, start and check readiness

```sh
printf '\nPOSTDOT_IMAGE=ghcr.io/postdot/postdot:0.1.0-alpha.4\n' >> .env
docker compose config --quiet
docker compose pull
docker compose up -d --no-build --wait
curl --fail http://127.0.0.1:3000/ready
```

The readiness request must succeed before you continue. If startup fails, inspect
`docker compose logs --tail 100 postdot` before changing the configuration.

For reproducible content, replace the tag in `POSTDOT_IMAGE` with
`ghcr.io/postdot/postdot@sha256:eceecc8898aa1d1b27c4e5b91fe53b8d78afebf74be410bd4b8f7d4751d5ee9e`.
See the [release record](/docs/releases/) for its matching source and limits.

To build from source instead, obtain the full repository in a separate directory:

```sh
git clone https://github.com/postdot/postdot.git postdot-source
cd postdot-source
git checkout e7af5550ffa446f9264ec13159e0ed9e263e1495
```

Repeat the configuration step there, leave `POSTDOT_IMAGE` unset, run
`docker compose build`, then `docker compose up -d --wait`. The default remains
`postdot:local`. This alternative requires Git and the full checkout; the two
files downloaded above are sufficient only for the published image.

### 3. Create the administrator account

Open the dashboard and create the first account. It becomes the installation
administrator; public signup then closes. Create your project and first channel.
A manual channel lets you prepare and schedule content without configuring a
provider account. Invite additional users through the application.

### Offline administrator provisioning

The image supports non-interactive first-administrator provisioning; the browser
setup above remains available.

Stop Postdot before provisioning. Create a private `bootstrap.json` file outside
version control with exactly these fields, replacing the example values:

```json
{
    "name": "Administrator",
    "email": "admin@example.com",
    "password": "replace-with-a-unique-long-password"
}
```

Use a password of 8 to 128 characters. Restrict access to the host file and make
it readable by the container's unprivileged user through a read-only mount. Do not
pass the password as a command argument or environment variable.

```sh
docker compose stop postdot
docker compose run --rm --no-deps \
  --volume "$PWD/bootstrap.json:/run/secrets/bootstrap.json:ro" \
  postdot account bootstrap --database /data/postdot.sqlite \
  --input /run/secrets/bootstrap.json
docker compose up -d --wait
```

The command initializes a new database or claims an existing unclaimed instance.
It creates the first installation administrator and closes public signup, without
starting a server. A configured instance or an occupied runtime lock causes it to
refuse. Repeating the command does not reset the account or change its password.
Sign in through the dashboard, then remove the private provisioning file when you
no longer need it. For an existing account, use the interactive
[password recovery procedure](/docs/operations/#recover-an-existing-account-password).

### Public HTTPS deployment

For a public deployment, keep the container bound to loopback and place an HTTPS
reverse proxy on the host in front of it. Set `BETTER_AUTH_URL` and
`POSTDOT_WEB_ORIGIN` to the same public HTTPS origin before starting. A proxy running
in another container needs an appropriate private network configuration instead
of this host-loopback example. Complete initial account setup before exposing the
installation. Provider OAuth and media delivery have additional reachability
requirements: see [provider requirements](/docs/provider-configuration/).

## Persistent data and ordinary operation

Compose owns a `postdot-data` volume under its project name. `/data/postdot.sqlite`
contains application state; `/data/media` contains originals, previews and avatars.
Keep the Compose project name stable so a later invocation uses the same volume.
The image contains committed migrations, which apply automatically at startup.

### Check and control the container

```sh
docker compose ps
docker compose logs --tail 100 postdot
docker compose restart postdot
docker compose stop postdot
docker compose up -d --wait
```

`/health` checks HTTP liveness; `/ready` checks durable-work readiness. After a
restore, readiness can succeed while recovery hold deliberately suspends delivery.
Read the administration recovery state before assuming work has resumed.

### Identify the installed release

With a current source build, run:

```sh
docker compose run --rm --no-deps postdot --version --json
```

Studio also displays the version and source commit under installation settings;
`GET /api/version` returns the same fields. These values come from the packaged
image. A build without release metadata reports `null` for unknown fields. The
CLI can read them without opening the database or starting a server.

`/health` checks availability, and the OpenAPI schema version describes the API;
neither identifies the running release. The image labels
`org.opencontainers.image.version` and `org.opencontainers.image.revision` carry
the same identity.

### Protect the volume and runtime lock

`docker compose down` keeps the data volume. **`docker compose down --volumes`
deletes it.** Do not use the latter to troubleshoot or update an installation.
Graceful stop has 30 seconds to drain. If a forced termination leaves a runtime
lock, verify that no process uses the database before removing only its exact
`.runtime.lock` marker; never remove a live process's lock.

## Optional email and S3

### Email delivery

SMTP is optional. Without it, automatic verification/password-reset email and
email publication alerts are unavailable. Configure the commented SMTP group in
`.env` when using a relay, then recreate the container:

```sh
docker compose up -d --force-recreate --wait
```

Port 587 normally uses `POSTDOT_EMAIL_SMTP_SECURE=false` with STARTTLS; implicit
TLS on port 465 uses `true`. Username/password must be supplied together. Use the
relay's actual settings and test delivery. There is no bundled production mail server.

### S3-compatible media storage

Local media is the default. To use an existing S3-compatible bucket for a **new
installation**, replace `POSTDOT_MEDIA_STORE` and `POSTDOT_MEDIA_STORE_ID` in `.env` and add
the following settings before starting:

```dotenv
POSTDOT_MEDIA_STORE=s3
POSTDOT_MEDIA_STORE_ID=primary-media
POSTDOT_MEDIA_S3_BUCKET=your-bucket
POSTDOT_MEDIA_S3_REGION=us-east-1
POSTDOT_MEDIA_S3_ENDPOINT=https://s3.example.com
POSTDOT_MEDIA_S3_ACCESS_KEY_ID=replace-with-access-key
POSTDOT_MEDIA_S3_SECRET_ACCESS_KEY=replace-with-secret-key
POSTDOT_MEDIA_S3_PREFIX=postdot
# Optional, only for temporary credentials:
# POSTDOT_MEDIA_S3_SESSION_TOKEN=replace-with-session-token
```

Replace the endpoint, region and credentials with your storage service's values.
For AWS S3, omit `POSTDOT_MEDIA_S3_ENDPOINT` and set the bucket's region. A custom
service requires a region or endpoint; follow its signing-region requirements.
The optional prefix isolates Postdot's object keys within the bucket. Use
credentials that can read, write and delete those objects. The container must be
able to reach the endpoint; `localhost` inside it refers to the container itself.

`POSTDOT_MEDIA_STORE_ID` identifies the storage location in saved media records.
Choose it once and keep it stable across restarts, updates and maintenance commands.
Changing it can make existing media inaccessible. Changing bucket, prefix or
storage backend does **not** migrate stored objects or update saved media records.
Plan a migration separately for an instance that already contains media.

Compose passes `.env` to both the server and maintenance commands. SQLite still
uses the persistent `/data` volume when media uses S3. After configuration, upload
an image through Media, reopen it, restart the container and verify that it remains
available. Configuration validation alone does not prove storage compatibility.

## Backup and restoration

Backup scheduling, off-host storage and retention belong to the administrator.
Postdot offers a consistent portable bundle containing SQLite and stored media.
Preserve deployment secrets separately; they are not included in the bundle.

### Create and copy a backup

Create a uniquely named backup while Postdot is running, then copy it outside the
application volume:

```sh
docker compose exec postdot mkdir -p /data/backups
docker compose exec postdot bun /app/postdot.js backup --media --output /data/backups/pre-update.bundle
umask 077
mkdir -p backups
docker compose cp postdot:/data/backups/pre-update.bundle ./backups/
```

`compose exec` runs the explicit Bun command; `compose run` below uses the
normal image entrypoint.

Protect the host backup directory and move the copied bundle to independent
storage. A backup left only in `/data` does not protect against loss of that volume.
Use a new output name for each backup. Inspect a representative restore periodically;
a successful backup alone does not prove your recovery procedure.

### Restore and review before resuming

Stop the application before restoring. The commands below use the bundle still
available under `/data/backups`:

```sh
docker compose stop postdot
docker compose run --rm --no-deps postdot restore --media --input /data/backups/pre-update.bundle
docker compose up -d --wait
```

`compose run` applies the normal image entrypoint. Restoration enables **recovery
hold**: sign in, inspect recovered publications and provider-side effects, then
explicitly resume through Administration. Restoring local history cannot undo
remote publications and may otherwise repeat work performed after the snapshot.
For off-host bundles and externally restored databases, follow the
[backup and restoration boundary](/docs/operations/).

## Update and rollback

### Prepare and apply an update

Before adopting a new release, read its migration notes and validation record,
back up data/secrets and retain the previous image. Never replace an immutable version tag.

For a source-built installation, record the source commit before building an update:

```sh
git rev-parse HEAD
docker image tag postdot:local postdot:before-update
# Update the source checkout to the intended commit, then:
docker compose build
docker compose up -d --wait
curl --fail http://127.0.0.1:3000/ready
```

### If you need to roll back

A failed update is not a reason to delete the volume. Returning to an older image
alone may fail after database migrations; schema downgrade is not supported.
Rollback requires a compatible image **and** its pre-update data/configuration,
with restoration and recovery hold as above. Consult the target release record
for validated upgrade paths and platform acceptance.

## Move from the Postbot names

Releases up to `0.1.0-alpha.3` were called Postbot. Updating keeps your data,
encryption key, API keys and provider connections. Only names change:

- **Variables.** Rename each `POSTBOT_` prefix to `POSTDOT_` in `.env`. The old
  names still work and log a deprecation warning when the matching new name is
  unset; they will stop working in a future release. Keep the same encryption key
  and key ID values.
- **Database file.** The default is now `/data/postdot.sqlite`. At startup, an
  existing `postbot.sqlite` in the same directory is renamed once, with its journal
  files, while the runtime lock is held. A custom `DB_FILE_NAME` is never renamed.
- **Compose.** Download the new `compose.yaml`. The service is now `postdot`, and
  the data volume is named `postdot-data`. To keep the volume you already have, set
  `POSTDOT_DATA_VOLUME` in `.env` to its existing name, for example
  `POSTDOT_DATA_VOLUME=postdot_postbot-data` when your Compose project is
  `postdot`. Run `docker volume ls` to find it. Never start the new file against an
  empty volume while the old one holds your data.
- **Observability and integrations.** Metric names start with `postdot_` instead
  of `postbot_`. Custom HTTP webhooks send `x-postdot-*` headers and the
  `postdot_webhook` contract mode; update receivers that verify the old headers.
- **API keys.** Keys issued earlier keep their `postbot_pat_` prefix and continue
  to work. New keys start with `postdot_pat_`.
- **Shell scripts.** The CLI and the agent skill still read `POSTBOT_URL` and
  `POSTBOT_API_KEY` when the `POSTDOT_` names are unset.

Back up the database and media before updating, as for any release.
