title: CLI reference
description: Inspect destination contracts, manage drafts and media, and control publication state.

The Bun CLI uses the existing `@postdot/client` Eden Treaty factory. Request types
come from the Elysia application; no separate REST schema or generated SDK is
maintained. Eden Fetch offers a different typed calling style, and OpenAPI remains
available to external consumers. Neither requires a second transport in this CLI.
See [Eden Treaty](https://elysiajs.com/eden/treaty/overview),
[Eden Fetch](https://elysiajs.com/eden/fetch), and
[OpenAPI](https://elysiajs.com/patterns/openapi).

Use `POSTDOT_URL` and `POSTDOT_API_KEY` for machine authentication. Connections and
provider credentials stay in Postdot. Existing project roles and API-key action
ceilings apply; scheduling requires the corresponding dispatch permission.

## Create a source and its destinations

```json
{
    "title": "Release announcement",
    "sourceContent": {
        "body": { "text": "The release is ready.", "format": "plain_text" },
        "media": []
    },
    "publications": [
        {
            "channelId": "YOUR_CHANNEL_ID",
            "deliveryMode": "manual",
            "targetContent": { "body": "The release is ready.", "media": [] }
        }
    ]
}
```

```sh
bun run postdot posts create --project "$PROJECT_ID" --input post.json --json
```

`--input -` reads stdin. Inputs are bounded to 1 MiB and must contain a JSON object.
Elysia performs authoritative schema and domain validation. Destination content
must match the channel profile, which can be inspected with `channels list` or the
existing API. The example is for a manual message channel, not a universal payload
for every platform. `scheduledAt`, when supplied per destination, is an epoch
millisecond timestamp; omission creates an unscheduled publication.

## Inspect and schedule

```sh
bun run postdot publications list --project "$PROJECT_ID" --json
bun run postdot publications show --project "$PROJECT_ID" --publication "$PUBLICATION_ID" --json
bun run postdot publications promote --project "$PROJECT_ID" --publication "$PUBLICATION_ID" --expected-revision 1 --at "$EPOCH_MS" --json
bun run postdot publications schedule --project "$PROJECT_ID" --publications "$PUBLICATION_ID" --at "$LATER_EPOCH_MS" --json
bun run postdot publications cancel --project "$PROJECT_ID" --publications "$PUBLICATION_ID" --json
```

`list` returns one page of at most 100 publications plus `nextCursor`; pass
`--cursor` for another page. It never silently loops over the entire project.
`show` returns the editor state including source, draft, target, and lifecycle.
`promote` requires the inspected draft revision and creates the execution target.
`schedule` changes queued publications; it does not substitute for draft promotion.
`cancel` and `schedule` accept comma-separated publication IDs under the existing
server batch limit. `publications save --input draft.json` forwards the draft PATCH
contract, including `expectedRevision`, optional `sourceContent`, and optional
`targetContent`. A stale revision is refused rather than overwritten.

`publications retry --publication <id>` requests the existing retry of a failed
automatic publication. It cannot retry arbitrary states. The existing
`publications publish` command still marks a due **manual** publication as
published; it does not mean automatic dispatch. Existing reconciliation commands
remain available for ambiguous outcomes.

## Output and failures

With `--json`, success writes the API JSON to stdout. Failure writes one
`{"error":{"code":"...","message":"...","status":409}}` object to stderr;
`status` is present only when an HTTP response was received. Exit 0 is success,
1 is an API/transport/command failure, and 2 is invalid local input. Human mode
uses concise confirmations; inspection commands display formatted JSON.

Requests have a 30-second transport deadline by default; `--timeout-ms` sets a different positive per-request deadline (useful for larger uploads). The CLI never automatically retries
writes. A transport failure has code `transport_error`; the write may already
have succeeded on the server. Inspect state before submitting it again. The
CLI does not add idempotency keys or promise exactly-once submission.

## Import and inspect media

```sh
bun run postdot media policy --project "$PROJECT_ID" --json
bun run postdot media upload --project "$PROJECT_ID" --file image.png --alt "Release dashboard" --json
bun run postdot media import-url --project "$PROJECT_ID" --url "https://YOUR_HOST/image.png" --json
bun run postdot media show --project "$PROJECT_ID" --asset "$ASSET_ID" --json
bun run postdot media list --project "$PROJECT_ID" --json
bun run postdot media finalize --project "$PROJECT_ID" --intent "$INTENT_ID" --json
```

File upload checks the current server policy, reserves an asset, streams the raw
file bytes, and asks the server to inspect/finalize them. `--content-type` overrides
the filename-derived hint when necessary; it never bypasses inspection or converts
the file. The upload size limit comes from Postdot, not the 1 MiB JSON-input limit.
Use `--timeout-ms 120000` when a transfer needs a longer deadline.

URL import uses Postdot's existing server importer: it downloads and stores a copy,
not a permanent external reference. URL/network restrictions, supported formats,
and image/video inspection remain server-owned. MP4 files must satisfy Postdot's
existing ready-to-publish video policy; no conversion is added.

Exit 0 acknowledges a successful API operation, not necessarily a ready asset.
Check `status`: `ready` includes `media.asset.id` and representations; `pending`
includes the reservation and intent ID. `failed` exits 1 with
`media_inspection_failed`. To attach a ready asset, use its ID in source media and
the destination's declared media field, for example `[{"assetId":"..."}]` for a
manual message channel. Do not attach pending or failed assets.

The CLI does not poll. Inspect with `media show`, or explicitly finalize a known
intent again when appropriate. A transfer failure after reservation includes
`error.media.assetId` and `error.media.intentId` in JSON stderr. Use them to inspect
state before retrying; an unknown result is not proof that the bytes were lost.
No automatic repeat or deletion is performed. A URL request whose response was
lost may not expose an asset ID; inspect the library before importing it again.
`media list` exposes the server cursor rather than silently downloading all pages.

## Discover a destination contract

Before constructing a destination payload, inspect its channel profile:

```sh
bun scripts/postdot.ts channels list --project <project-id> --json
bun scripts/postdot.ts channels profile --project <project-id> --channel <channel-id> --json
```

The response is the existing API contract: `channel`, `active`, and nullable
`draft`. Read the definition under `active.profile` for schema, declared bindings,
text capabilities, and media requirements. The active version is distinct from a
profile draft awaiting activation. Keep the version reference when preparing a payload;
server validation and promotion remain authoritative if the channel changes.

Both output modes display the full profile response, rather than guessing field
names or flattening away constraints. This command neither activates a profile nor
connects a publisher. A valid content contract does not establish provider
connection readiness or guarantee publication success.

## Inspect publisher connections

```sh
bun scripts/postdot.ts publishers list --project <project-id> --json
```

The response preserves the existing `connections` and `oauthReadiness` fields.
Each connection identifies its channel, provider, account, scopes, and recorded
state (`active`, `reconnect_required`, or `revoked`). Credentials are referenced
by ID; access tokens and refresh tokens are not returned. An empty connection
list is valid, including for projects using manual channels.

`oauthReadiness` describes application configuration for LinkedIn, Bluesky, and X:
`ready`, `not_configured`, or `unavailable`. It is not a live provider health check,
and does not describe every provider. An active connection plus ready application
configuration does not guarantee a successful delivery. This read command neither
connects a provider nor sends a test publication.

## Share and manage channels

The commands in this section, channel cadence and publication moves require
`0.1.0-alpha.3` or later, on both the CLI and the API. See
[Share a channel](/docs/shared-channels/) for Studio and the effects of sharing.

Inspect the source project's channel and the authorized workspace view:

```sh
bun run postdot channels sharing --project "$PROJECT_ID" --channel "$CHANNEL_ID" --json
bun run postdot channels list --workspace "$WORKSPACE_ID" --include-archived --json
```

The sharing response exposes `channel.revision`, the managing project when
readable, permitted actions and eligible projects. Workspace listing filters each
channel and usage by the key owner's live access and the key's project scope.
An unreadable managing project's name stays hidden.

Copy the inspected revision before attaching another project:

```sh
bun run postdot channels attach --project "$PROJECT_ID" --channel "$CHANNEL_ID" --target-project "$TARGET_PROJECT_ID" --expected-revision "$CHANNEL_REVISION" --json
```

Use the new revision from a successful mutation response, or inspect again before
another change. Transferring management requires an attached target project:

```sh
bun run postdot channels transfer --workspace "$WORKSPACE_ID" --channel "$CHANNEL_ID" --target-project "$TARGET_PROJECT_ID" --expected-revision "$CHANNEL_REVISION" --json
bun run postdot channels withdraw --project "$PROJECT_ID" --channel "$CHANNEL_ID" --target-project "$TARGET_PROJECT_ID" --expected-revision "$CHANNEL_REVISION" --json
```

`attach`, `withdraw`, `transfer`, `cadence` and `configure-cadence` accept exactly
one context: `--project` or `--workspace`. `--target-project` identifies the project
gaining use, losing use or accepting management. Withdrawal retains history and
can make pending work unavailable. Pass `--archive-last` only when you intend to
archive the channel as its final attachment is withdrawn. A `stale_revision`
response requires another inspection; the CLI does not refresh and retry for you.

Keys need `channel:share` for attachment, withdrawal and management transfer, with
scope for each affected project and the owner's live authority. `channel:manage`
controls profile/connection/cadence configuration. Sharing does not grant dispatch,
credential access or workspace administration. Use `project:read` for inspection;
see [authentication](/docs/reference/authentication/#shared-channel-access).

For HTTP clients, the matching [channel operations](/docs/reference/channels/getProjectChannelSharing/)
use project paths under `/api/projects/{projectId}/channels/{channelId}` and
workspace paths under `/api/workspaces/{workspaceId}/channels/{channelId}`.
Both contexts expose `attachments`, `management` and `cadence`. Project withdrawal
uses `attachments/{attachedProjectId}/withdraw`; workspace withdrawal uses
`withdraw` with `projectId` in the body. Keep `expectedRevision` in mutation bodies.

## Configure cadence and inspect occupied times

Read the rules before writing:

```sh
bun run postdot channels cadence --project "$PROJECT_ID" --channel "$CHANNEL_ID" --json
```

Save the following as `cadence.json`, replacing `expectedRevision` with
`rules.revision`, or `0` when `rules` is null. Each limit accepts `null` to disable
it. API intervals use milliseconds; Studio displays minutes.

```json
{
    "expectedRevision": 0,
    "timeZone": "Europe/Paris",
    "dailyMax": 3,
    "weeklyMax": 10,
    "minimumIntervalMs": 3600000
}
```

```sh
bun run postdot channels configure-cadence --project "$PROJECT_ID" --channel "$CHANNEL_ID" --input cadence.json --json
bun run postdot channels occupancy --project "$PROJECT_ID" --from "$FROM_EPOCH_MS" --to "$TO_EPOCH_MS" --json
```

The occupancy range uses epoch milliseconds, with `to` later than `from`. The
server returns readable publication details or anonymous occupied times according
to current access. It omits unreadable drafts. It does not estimate activity
outside Postdot. For calendar periods and rule behavior, see
[optional cadence](/docs/shared-channels/#set-optional-cadence).

### Confirm a planning exception

An exceeded maximum returns exit 1 and HTTP `409`, with `error.code` set to
`cadence_conflict`. JSON stderr also includes `error.confirmation` and
`error.warnings`: channel, rule, civil period, maximum and count. The rejected
operation makes no partial changes. Review the warnings before resubmitting the
same plan with its confirmation:

```sh
bun run postdot publications schedule --project "$PROJECT_ID" --publications "$PUBLICATION_ID" --at "$EPOCH_MS" --cadence-confirmation "$CONFIRMATION" --json
```

`promote` and `retry` accept the same option. For `posts create` and
`publications move`, add `cadenceConfirmation` to the JSON input. Changed plans,
rules or competing work can produce a new challenge. Review that conflict rather
than replaying an old token until a write succeeds.

### Override one minimum interval

Read the publication's timing and copy its current `confirmation`:

```sh
bun run postdot publications cadence --project "$PROJECT_ID" --publication "$PUBLICATION_ID" --json
bun run postdot publications override-cadence --project "$PROJECT_ID" --publication "$PUBLICATION_ID" --confirmation "$CONFIRMATION" --json
```

Timing reports `scheduledAt`, `eligibleAt`, a nullable delay `reason` and a
confirmation. It can be absent for manual work or a publication outside pending
automatic states. An override requires dispatch permission and a current timing
confirmation. It does not change the requested schedule or bypass provider limits,
security checks or destination confirmation. A stale confirmation returns a conflict.

## Move pending work

Inspect the source publication with `publications show` and the destination with
`channels list` or `channels profile`. The destination must be another active
channel attached to the same project. Only drafts and future ready/scheduled work
without an execution attempt qualify.

Prepare `move.json` using these inspected values; preserve nulls exactly:

| Input field                      | Inspected value                                   |
| -------------------------------- | ------------------------------------------------- |
| `targetChannelId`                | Destination channel's `id`                        |
| `deliveryMode`                   | Explicit `manual` or supported `automatic` choice |
| `expectedPublicationUpdatedAt`   | `editor.publication.updatedAt`                    |
| `expectedDraftRevision`          | `editor.draft.revision`                           |
| `expectedSourceRevision`         | `editor.post.sourceRevision`                      |
| `expectedTargetRevisionId`       | `editor.publication.targetRevisionId`             |
| `expectedScheduledAt`            | `editor.publication.scheduledAt`                  |
| `expectedTargetProfileVersionId` | Destination channel's `profileVersionId`          |

```sh
bun run postdot publications move --project "$PROJECT_ID" --publication "$PUBLICATION_ID" --input move.json --json
```

The response contains the replacement `editor`, including its new publication ID
and `movement.fromPublicationId`. The operation preserves the post and saved
working content, revalidates media/content, and cancels/links the original
atomically. Compatible scheduled work retains its date. Incompatible content
becomes an unscheduled review draft with `movement.requestedScheduledAt` retained;
review and explicitly schedule it afterward. Approval, execution results and
cadence exceptions do not transfer.

A stale draft, source, target, schedule or destination profile fails before the
original is cancelled. Inspect before resubmitting. Moving requires an editor
role and `publication:manage`; moving scheduled work additionally requires
`publication:dispatch`. Read the complete [move request and responses](/docs/reference/publications/movePublication/)
for HTTP clients.

## Retire a project or workspace

`0.1.0-alpha.3` supports the following lifecycle commands. See [archive and delete](/docs/projects/) for the data
and external-effect contract.

Read the impact before changing a resource:

```sh
bun run postdot projects impact --project PROJECT_ID --json
bun run postdot projects list --include-archived --json
```

Copy the returned `fingerprint` into the action. Postdot refuses a stale preview
so you can review a changed impact before confirming again.

```sh
bun run postdot projects archive --project PROJECT_ID --fingerprint FINGERPRINT --cancel-pending
bun run postdot projects restore --project PROJECT_ID --fingerprint FINGERPRINT
bun run postdot projects delete --project PROJECT_ID --fingerprint FINGERPRINT --confirm-name "Project name" --cancel-pending
```

Use `--cancel-pending` to confirm cancellation of the pending work shown by the
preview. For permanent deletion with unresolved outcomes, also pass
`--acknowledge-uncertain`. The CLI sends a single action request and reports the
returned state; it does not silently retry a write or poll cleanup completion.

Workspace commands use `workspaces impact|archive|restore|delete --workspace ID`
with the same confirmation options and require a human session through
`POSTDOT_SESSION_COOKIE`. To retire the default workspace, also pass
`--replacement-workspace OTHER_WORKSPACE_ID`. The replacement must be active and
manageable by the current user.

HTTP clients use `GET /api/projects/{id}/lifecycle`,
`POST /api/projects/{id}/lifecycle/archive`,
`POST /api/projects/{id}/lifecycle/restore`, and
`DELETE /api/projects/{id}/lifecycle`. Workspace paths replace `projects` with
`workspaces`. Action bodies carry `fingerprint` and any required confirmation
fields. A `409` response means the client must resolve the stated conflict and
review the impact again. Session users can inspect their pending retirements at
`GET /api/resource-removals`.
