# Capability Availability and Verification

- Last verified: 2026-09-27
- Scope: the web dashboard, HTTP API, shipped script CLI, and checked-in end-to-end evidence

This is a snapshot of observable client coverage, not a feature-parity promise or a product roadmap. A surface marked **Present** exposes some workflow for that capability; it does not claim that every operation or state is covered. **Partial** identifies a deliberately narrow surface or a known user-journey gap. **—** means no first-party surface was found in the reviewed repository.

## Deliberate boundaries and current gaps

- The CLI is a supported, intentionally smaller operator surface, not a command-for-command copy of the dashboard. Its current commands are discoverable with `bun run herald --help`; the implementation is in [scripts/herald.ts](../scripts/herald.ts).
- MCP is **deferred, not rejected**. The owner asked to stabilize and organize the web workflows first; [ISSUE-036](../.autonomos/ISSUES.md) remains open without an implementation task. This matrix does not authorize starting an MCP client.
- The HTTP API may expose a capability before the dashboard or CLI does. That difference is recorded as partial or absent coverage, not silently treated as a finished user journey.
- Playwright evidence proves only the scenarios named by each test. Other route, API, and unit tests add evidence, but do not establish end-to-end coverage for an entire capability.

Update this matrix when a client surface or its end-to-end evidence materially changes. Keep capability status tied to observable user workflows and named tests; do not infer client completion from backend implementation alone.
